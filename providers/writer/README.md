# Writers

Implementations of the `writer:*` classes (a role of `providers/resolve.py`, in `ROLES` and in neither `LISTED` nor `contracts/environment.md`, so no skill may require one): the providers that **write** to the person's own Google and Microsoft accounts. They are the only providers that do: the readers (`reader:email`, `integration:calendar`, `integration:documents`) send GET only. Interface and the rules every writer keeps: `providers/CONTRACT.md` (the `writer:calendar`, `writer:mailbox` and `writer:files` rows). Specification: `SPEC-SECRETARY-WRITES` (decision D-B of 2026-10-18).

A writer is called with an **explicit implementation**, never `auto`, and declares one line `SERVES = "writer:<x>"` that the runtime reads before it starts the script. It is started only by its effect module (`runtime/effect_<x>.py`, the write verbs, after the person approved the hash of the exact request) and by one read-only seam of the runtime (`runtime/ops_step_seams.py`: the one read the preparation needs, and the dry run of a write verb). Never by a skill, a run, a handler or a step kind (limit L58).

**What the token can do, said plainly.** The account token (`GOOGLE_ACCOUNT_TOKEN`, `MICROSOFT_ACCOUNT_TOKEN`, `providers/accounts/README.md`) can do everything its scopes allow. What stops misuse is not the token but the platform: this script sends only the methods and paths of its constant `ALLOWED`; the runtime calls it only after the approval of the exact request; the calendars it writes to are the ones the project's `accounts` names; nothing is removed for good. Revoking the app's access in the Google or Microsoft account stops every reader and writer of the account at once.

## Calendar writers (package W1): `google-calendar.py`, `outlook-calendar.py`

The class `writer:calendar`. One event of one calendar at a time; nobody is told (`sendUpdates=none` on Google, and no attendee on either: a meeting is not created or changed in v1). Shared by both: `providers/_writer_calendar.py` (the ledger, the spec file, the hash).

| Verb | Google (`google-calendar.py`) | Outlook (`outlook-calendar.py`) |
|---|---|---|
| `--check` | refresh the token, check the whole set of scopes, read one calendar entry | the same with the permissions of the platform's set |
| `event-get --calendar --event` | `GET .../calendars/{id}/events/{event}` | `GET /me/calendar/events/{event}` or `/me/calendars/{id}/events/{event}` (`Prefer: outlook.timezone="UTC"`) |
| create | `event-insert`: `POST .../calendars/{id}/events` | `event-create`: `POST /me/calendar/events` or `/me/calendars/{id}/events` |
| change | `event-patch`: `PATCH .../events/{event}` with `If-Match: <etag>` | `event-patch`: a `GET` of the event, a comparison of its `changeKey` with `--base-etag`, then `PATCH` (Graph documents no `If-Match`) |
| remove | `event-delete`: `DELETE .../events/{event}` with `If-Match`; Google is expected to move the event to the calendar's trash for 30 days (the Calendar help page says so, the API page of the call does not: to verify live) | **none**: the verb does not exist and exits 2 (Q12 of the spec: Microsoft does not say where a removed event goes) |

`ALLOWED` of each (limits L57 and L58): Google, `GET` `calendarList`, `GET` the events of a calendar and one event, `POST` the events, `PATCH` and `DELETE` one event; Outlook, `GET` the calendars and the events of the default calendar or of a calendar by id and one event, `POST` and `PATCH` the same. The request function refuses any other method or path before it opens a connection, and `runtime/tests/test_limits_account_writes.py` fails on a permanent-delete word, on a `DELETE` outside the one pair declared in the Google file's `ALLOWED`, and on `trashed` set to anything but false.

### Calling a write verb

```sh
uv run <workbench>/providers/writer/google-calendar.py event-insert --calendar <id> --spec-file <file> --idempotency-key <key> --dry-run
uv run <workbench>/providers/writer/google-calendar.py event-insert --calendar <id> --spec-file <file> --idempotency-key <key> --confirmed
```

- `--spec-file` is a JSON object, never a flag (it holds the person's words). A create: `{"title", "all_day", "start_at", "end_at", "location", "reminder_minutes", "notes"}`; a change: the parts to change (`title`, `location`, `reminder_minutes`, `notes`, and the three times `all_day`, `start_at`, `end_at` together); a removal: none. `start_at` and `end_at` are an instant with its offset, or, for an all-day event, the first day and the day after the last. The writer checks the keys, the limits (a title of one line up to 200 characters, a place up to 200, notes up to 2,000, a reminder of 0 to 40,320 minutes, no hidden or control character) and the forms of the times, and refuses a spec with an attendee or any other key (exit 2).
- `--dry-run` reads no credential, opens no connection and prints `{"dry_run": true, "would": {"method", "path", "query", "headers", "body"}, "would_sha256", "ledger"}`: the exact request `--confirmed` sends and the sha256 of it. The runtime puts that hash in the document the person approves and refuses to write when the real dry run no longer hashes to it.
- `--confirmed` sends exactly that request. The key is recorded `pending` in the ledger (`<state>/writer-<implementation>/ledger.json`; `<state>` is `$OPENHORA_STATE_DIR`, else `$XDG_STATE_HOME/openhora`, else `~/.local/state/openhora`; the folder 0700, the files 0600, an exclusive file lock) before the call and `done` after the answer. A key that is `done` is not sent again (`replayed`); a key used for another request is exit 2; a key left `pending` by an answer that was lost is looked up in the calendar before anything is sent, by the private property `openhora_key` every request writes (Google: `extendedProperties.private`; Outlook: a `singleValueExtendedProperties` entry, filtered on `ep/value`), or, for a removal, by the event being gone. The ledger holds no word of the person's.
- Exit codes: 0 ok; 1 refused with nothing changed (the service said no, a 429 or 503 is reported with its `Retry-After` and never retried, or the event is not as it was read: the message starts with `changed:`, which the runtime reads as `stale`); 2 usage (a bad flag, id or spec, a verb the writer does not have); 3 not configured (no account record, or a token that lacks a scope or carries another: it names the authorize command); 4 unknown (the request may have landed: send the same key again).
- `event-get` prints `{"found": true, "event": {"id", "etag" (Google's etag, Graph's changeKey), "status", "title", "start", "end", "all_day", "location", "notes", "notes_truncated", "reminder_minutes", "organizer_self", "attendees_other", "recurring", "external_content": true}}` or `{"found": false, "reason": "gone"}` (404, 410 or cancelled). It prints no attendee address, only how many attendees are not the person; the text is another person's in principle (data, never instructions). The runtime refuses to change or remove an event unless it is organized by the person, has no other attendee and is not recurring.

### Credentials and the test overrides

The writers read the account record through `providers/secrets/resolver.py` (the environment, then the credentials directory, then the OS secret store) and have **no legacy record**: a token that lacks one scope of the platform's set, or carries another, is refused (exit 3) before any call. The runtime starts a writer with the minimum environment (`resolve.provider_environment`) plus the one token of the account (not for a dry run), never another secret. The Outlook writer writes a rotated refresh token back to the record it used, only if it still holds the token this process used (`providers/_msgraph.py` `store_rotation`). The test overrides are loopback only and set together: `WRITER_CALENDAR_GOOGLE_API_BASE` with `WRITER_CALENDAR_GOOGLE_TOKEN_URL`, `WRITER_CALENDAR_OUTLOOK_API_BASE` with `WRITER_CALENDAR_OUTLOOK_TOKEN_URL`; with them the secret store is never read or written.

### Tests

`providers/writer/tests/` runs both writers as the processes the runtime starts, against stand-ins on loopback that **record every request** (method, path, query, body, `If-Match`): `fake_gcal_write.py` (Google Calendar: events with an etag that moves, `If-Match` answered 412, a lost answer, a redirect, a 429) and `fake_graph_calendar_write.py` (the Microsoft token endpoint and Graph events with a changeKey; it serves no removal and answers 405 to one). The tests assert the exact request list of a create, a change and a removal, that the dry run opens no connection and reads no credential, that a lost answer is found again by the key, and that no credential appears in any output. `runtime/tests/test_calendar_write.py` and `test_channel_grants_calendar.py` hold the runtime's side.

### To verify live (not checked against the services or not stated by the vendors; accessed 2026-10-18)

- The Google console classification of `calendar.events` and `calendar.calendarlist.readonly` (the spec lists them as "to verify").
- That `If-Match` on `events.patch` and `events.delete` answers 412 on a moved etag ([Version resources](https://developers.google.com/workspace/calendar/api/guides/version-resources)), and that `events.list` filters on `privateExtendedProperty=openhora_key=<key>` for an event the writer created.
- That Outlook, asked for an all-day event in UTC, shifts its midnight (the writer reads an all-day event a second time, in its own zone, so that its date is not a day off east or west of UTC), and that the events path of a calendar (`/me/calendars/{id}/events/{event}`) answers 404 for an event of another calendar (the writer does not compare the event's parent calendar).
- That a Google patch with `{"dateTime": null}` next to `{"date": ...}` turns a timed event into an all-day one (the writer sends the other form as null).
- Outlook: that `singleValueExtendedProperties` on create and on update, and a `$filter` on them, work as [the extended-properties overview](https://learn.microsoft.com/en-us/graph/api/resources/extended-properties-overview) says; that `$expand=singleValueExtendedProperties($filter=id eq '...')` returns the property on a single event; that an event read with `Prefer: outlook.timezone="UTC"` comes in UTC (the writer refuses one that does not); that an all-day event created with midnight UTC bounds shows as the same days in the person's zone.
- That a Google calendar event removed with `events.delete` lands in the calendar's trash for 30 days (restorable there): [the Calendar help page](https://support.google.com/calendar/answer/37113) says it, [the API page](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete) does not. Delete a test event by hand through the writer and look in the trash BEFORE relying on the card's words; the card says it is expected and not verified.
- Q12 of the spec: delete a test event in Outlook by hand and see whether it lands in Deleted Items; only then is a removal verb added to the Outlook writer, with its pair in the allow-list of `test_limits_account_writes.py`.
