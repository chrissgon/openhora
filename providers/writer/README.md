# Writers

Implementations of the `writer:*` classes (a role of `providers/resolve.py`, in `ROLES` and in neither `LISTED` nor `contracts/environment.md`, so no skill may require one): the providers that **write** to the person's own Google and Microsoft accounts. They are the only providers that do: the readers (`reader:email`, `integration:calendar`, `integration:documents`) send GET only. Interface and the rules every writer keeps: `providers/CONTRACT.md` (the `writer:calendar`, `writer:mailbox` and `writer:files` rows). Specification: `SPEC-SECRETARY-WRITES` (decision D-B of 2026-10-18).

| Class | Implementation | Service | Package | Verbs |
|---|---|---|---|---|
| `writer:calendar` | `google-calendar.py`, `outlook-calendar.py` | Google Calendar, Outlook calendar | W1 | `--check`, `event-get`, `event-insert`/`event-create`, `event-patch`, `event-delete` (Google), `event-instances` and `event-cancel-occurrence` (both), `event-cancel-series` (Outlook; Google's is `event-delete --series`) |
| `writer:tasks` | `google-tasks.py`, `microsoft-todo.py` | Google Tasks, Microsoft To Do | CB-4 | `--check`, `task-get`, `task-insert`, `task-complete` |
| `writer:files` | `gdrive.py` | Google Drive | W4a | `--check`, `file-meta`, `create`, `update` |
| `writer:files` | `onedrive.py` | OneDrive | W4a | `--check`, `file-meta`, `create`, `replace` |

`_files_common.py` is the plumbing the two file writers share (exit codes, the allow-list guard, the canonical dry run, the content reader, the ledger). A name with an underscore is no implementation.

A writer is called with an **explicit implementation**, never `auto`, and declares one line `SERVES = "writer:<x>"` that the runtime reads before it starts the script. It is started only by its effect module (`runtime/effect_<x>.py`, the write verbs, after the person approved the hash of the exact request) and by one read-only seam of the runtime (`runtime/ops_step_seams.py`: the one read the preparation needs, and the dry run of a write verb). Never by a skill, a run, a handler or a step kind (limit L58).

**What the token can do, said plainly.** The account token (`GOOGLE_ACCOUNT_TOKEN`, `MICROSOFT_ACCOUNT_TOKEN`, `providers/accounts/README.md`) can do everything its scopes allow. What stops misuse is not the token but the platform: this script sends only the methods and paths of its constant `ALLOWED`; the runtime calls it only after the approval of the exact request; the calendars it writes to are the ones the project's `accounts` names; nothing is removed for good. Revoking the app's access in the Google or Microsoft account stops every reader and writer of the account at once.

## Calendar writers (package W1): `google-calendar.py`, `outlook-calendar.py`

The class `writer:calendar`. One event of one calendar at a time; nobody is told (`sendUpdates=none` on Google, and no attendee on either: a meeting is not created or changed in v1). Shared by both: `providers/_writer_calendar.py` (the ledger, the spec file, the hash).

| Verb | Google (`google-calendar.py`) | Outlook (`outlook-calendar.py`) |
|---|---|---|
| `--check` | refresh the token, check the whole set of scopes, read one calendar entry | the same with the permissions of the platform's set |
| `event-get --calendar --event` | `GET .../calendars/{id}/events/{event}` | `GET /me/calendar/events/{event}` or `/me/calendars/{id}/events/{event}` (`Prefer: outlook.timezone="UTC"`) |
| create | `event-insert`: `POST .../calendars/{id}/events` | `event-create`: `POST /me/calendar/events` or `/me/calendars/{id}/events` |
| change | `event-patch`: `PATCH .../events/{event}` with `If-Match: <etag>` | `event-patch`: a `GET` of the event, a comparison of its `changeKey` with `--base-etag`, then `PATCH` (Graph documents no `If-Match`) |
| remove | `event-delete`: `DELETE .../events/{event}` with `If-Match`; Google is expected to move the event to the calendar's trash for 30 days (the Calendar help page says so, the API page of the call does not: to verify live) | `event-delete` (slice S21): a `GET` of the event, a comparison of its `changeKey` with `--base-etag` and of its organizer, attendees and type, then one `DELETE /me/calendar/events/{event}` or `/me/calendars/{id}/events/{event}` (204). **Microsoft does not say where a removed event goes**; it may not be recoverable (see "To verify live") |

**Series (package CB-6, SPEC-CATALOG-BATCH 6.6; the runtime side is CB-7).** A create spec may also hold `recurrence` and `time_zone` together: a series made of timed events, `daily` or `weekly` on one weekday (the weekday of the start in that zone), no end, written in the zone it is expanded in. Both writers read and cancel it:

| Verb | Google | Outlook |
|---|---|---|
| create a series | `event-insert`, the spec holds `recurrence` and `time_zone`: `"recurrence": ["RRULE:FREQ=DAILY"]` or `["RRULE:FREQ=WEEKLY;BYDAY=MO"]`, `start`/`end` each with `timeZone` (Google requires it for a recurring event) | `event-create`, the same spec: `"recurrence": {"pattern": {"type": "daily" or "weekly", "interval": 1, "daysOfWeek": [<day>], "firstDayOfWeek": "sunday"}, "range": {"type": "noEnd", "startDate": <date of the start in the zone>}}` (a daily pattern has no `daysOfWeek`, no `firstDayOfWeek`), `start`/`end` in the zone (a first wall time that is ambiguous in the zone is exit 2: a series is never written in UTC) |
| report the series | `event-get` prints `series_id` (the master's id for an instance, its own for a master, else null) and `series_rule` (`daily`, `weekly:<MO..SU>`, `other`, null): one more `GET` of the master for an instance | the same, from `seriesMasterId` / `type` and the master's `recurrence` |
| the instances in a window | `event-instances --calendar --series <master> --from --to` (at most 2 days): `GET .../events/{master}/instances` with `timeMin`, `timeMax`, `showDeleted=false`, `maxResults=10`; prints `{instances: [{id, etag, start, end, status, original_start}]}`, no title, no attendee | the same verb: `GET .../events/{master}/instances` with `startDateTime`, `endDateTime` (UTC), `Prefer: outlook.timezone="UTC"`, `$top=10`; `etag` is the changeKey |
| cancel the whole series | `event-delete --series`: the existing `DELETE` on the master's id after a read of it (a series master, `series_rule` not `other`, the person's alone, base etag unmoved) | `event-cancel-series --calendar --event <master> --base-etag --idempotency-key`: `POST .../events/{master}/cancel`, body `{}`, after the same read (changeKey compared), 202 |
| cancel one occurrence | `event-cancel-occurrence --calendar --event <instance> --series <master> --expect-start <instant> --base-etag ...`: one `PATCH` of the instance with `{"status": "cancelled"}` and the private key property only, `If-Match` the instance's etag, `sendUpdates=none` | the same verb: `POST .../events/{occurrence}/cancel`, body `{}`, 202 |

Before an occurrence is cancelled both writers read it again and its series and refuse (exit 1, nothing sent) a moved base, an instance that is gone or already cancelled (`changed:`), an instance of another series than `--series`, an occurrence that does not start at `--expect-start` (a moved one, `changed:`), a series whose rule is `other`, one the person does not organise or with another attendee, and a start that has passed (`not eligible:`). Neither verb touches the master or another instance, and neither sends a DELETE (Google's occurrence cancel is a PATCH; Graph's is the `cancel` action). Graph's `cancel` moves the event to Deleted Items by its page and is for the organizer; if Graph refuses it, the writer exits 1 and sends nothing else: there is no fallback to a DELETE. A plain Google `event-delete` (no `--series`) is unchanged and checks nothing of a series (the runtime's `step_calendar_event._eligible` refuses one); only `--series` reads the master first. `--series` is a switch on Google's `event-delete` and carries the master's id on the other verbs.

`ALLOWED` of each (limits L57 and L58): Google, `GET` `calendarList`, `GET` the events of a calendar and one event, `POST` the events, `PATCH` and `DELETE` one event; Outlook, `GET` the calendars and the events of the default calendar or of a calendar by id and one event, `POST` and `PATCH` the same, and `DELETE` one event of either; since CB-6 Google also has `GET` `.../events/{id}/instances` (the one `DELETE` pair is also the series' own, on the master's id), and Outlook has `GET` `.../events/{id}/instances` and `POST` `.../events/{id}/cancel` in both forms (the default calendar's and a calendar's by id) and no further `DELETE`. The request function refuses any other method or path before it opens a connection, and `runtime/tests/test_limits_account_writes.py` fails on a permanent-delete word, on a `DELETE` outside the pair declared in the Google file's `ALLOWED` and the two declared in the Outlook file's, and on `trashed` set to anything but false.

### Calling a write verb

```sh
uv run <workbench>/providers/writer/google-calendar.py event-insert --calendar <id> --spec-file <file> --idempotency-key <key> --dry-run
uv run <workbench>/providers/writer/google-calendar.py event-insert --calendar <id> --spec-file <file> --idempotency-key <key> --confirmed
```

- `--spec-file` is a JSON object, never a flag (it holds the person's words). A create: `{"title", "all_day", "start_at", "end_at", "location", "reminder_minutes", "notes"}`; a change: the parts to change (`title`, `location`, `reminder_minutes`, `notes`, and the three times `all_day`, `start_at`, `end_at` together); a removal: none (`event-delete` takes no spec). `start_at` and `end_at` are an instant with its offset, or, for an all-day event, the first day and the day after the last. A create of a series adds `"recurrence": {"freq": "daily"}` or `{"freq": "weekly", "byday": "MO".."SU"}` and `"time_zone": "<IANA name>"`, together and nothing else (an end, an interval, a day of the month, an all-day event, a weekday that is not the start's in the zone, or a patch that carries either key is exit 2). On Outlook a `--time-zone` beside a series must be the spec's `time_zone`. The writer checks the keys, the limits (a title of one line up to 200 characters, a place up to 200, notes up to 2,000, a reminder of 0 to 40,320 minutes, no hidden or control character) and the forms of the times, and refuses a spec with an attendee or any other key (exit 2).
- `--time-zone <IANA name>` (Outlook only, `event-create` and `event-patch`, optional; a flag, not a spec key, because it is not the person's words and the shared spec validator, so Google, is untouched). With it a timed event's `start` and `end` are sent as the same instants in that zone's wall time with `"timeZone": "<name>"` (for example `America/Sao_Paulo`, instant `2026-11-05T13:00:00Z` -> `2026-11-05T10:00:00`), so the event carries its own named zone and a series made later keeps its hour across a clock change. A name that is not `Area/Place` or `Area/Region/Place`, or that the machine's zone database does not load, is exit 2 with nothing sent. A wall time that is ambiguous in the zone (the repeated hour of a clock change) or that does not read back as the same instant is sent in UTC, as without the flag; an all-day event and a run without the flag are unchanged. The runtime passes the flag only for an Outlook timed create or a change that carries times, only when the document's `zone` is an IANA name (an offset zone such as `UTC-03:00` passes nothing), and only from that field (`calendar_document.outlook_zone_args`); the flag is part of the dry run, so the hash the person approves covers it. Reads are unchanged: `event-get` and the reader still ask Graph for UTC and Graph converts. `ALLOWED` is unchanged: same methods, same paths.
- `--dry-run` reads no credential, opens no connection and prints `{"dry_run": true, "would": {"method", "path", "query", "headers", "body"}, "would_sha256", "ledger"}`: the exact request `--confirmed` sends and the sha256 of it. The runtime puts that hash in the document the person approves and refuses to write when the real dry run no longer hashes to it.
- `--confirmed` sends exactly that request. The key is recorded `pending` in the ledger (`<state>/writer-<implementation>/ledger.json`; `<state>` is `$OPENHORA_STATE_DIR`, else `$XDG_STATE_HOME/openhora`, else `~/.local/state/openhora`; the folder 0700, the files 0600, an exclusive file lock) before the call and `done` after the answer. A key that is `done` is not sent again (`replayed`); a key used for another request is exit 2; a key left `pending` by an answer that was lost is looked up in the calendar before anything is sent, by the private property `openhora_key` every request writes (Google: `extendedProperties.private`; Outlook: a `singleValueExtendedProperties` entry, filtered on `ep/value`), or, for a removal, by the event being gone. The ledger holds no word of the person's.
- Exit codes: 0 ok; 1 refused with nothing changed (the service said no, a 429 or 503 is reported with its `Retry-After` and never retried, or the event is not as it was read: the message starts with `changed:`, which the runtime reads as `stale`); 2 usage (a bad flag, id or spec, a verb the writer does not have); 3 not configured (no account record, or a token that lacks a scope or carries another: it names the authorize command); 4 unknown (the request may have landed: send the same key again).
- `event-get` prints `{"found": true, "event": {"id", "etag" (Google's etag, Graph's changeKey), "status", "title", "start", "end", "all_day", "location", "notes", "notes_truncated", "reminder_minutes", "organizer_self", "attendees_other", "recurring", "series_id", "series_rule", "external_content": true}}` or `{"found": false, "reason": "gone"}` (404, 410 or cancelled). It prints no attendee address, only how many attendees are not the person; the text is another person's in principle (data, never instructions). The runtime refuses to change or remove an event unless it is organized by the person, has no other attendee and is not recurring.

### Credentials and the test overrides

The writers read the account record through `providers/secrets/resolver.py` (the environment, then the credentials directory, then the OS secret store) and have **no legacy record**: a token that lacks one scope of the platform's set, or carries another, is refused (exit 3) before any call. The runtime starts a writer with the minimum environment (`resolve.provider_environment`) plus the one token of the account (not for a dry run), never another secret. The Outlook writer writes a rotated refresh token back to the record it used, only if it still holds the token this process used (`providers/_msgraph.py` `store_rotation`). The test overrides are loopback only and set together: `WRITER_CALENDAR_GOOGLE_API_BASE` with `WRITER_CALENDAR_GOOGLE_TOKEN_URL`, `WRITER_CALENDAR_OUTLOOK_API_BASE` with `WRITER_CALENDAR_OUTLOOK_TOKEN_URL`; with them the secret store is never read or written.

### Tests

`providers/writer/tests/` runs both writers as the processes the runtime starts, against stand-ins on loopback that **record every request** (method, path, query, body, `If-Match`): `fake_gcal_write.py` (Google Calendar: events with an etag that moves, `If-Match` answered 412, a lost answer, a redirect, a 429) and `fake_graph_calendar_write.py` (the Microsoft token endpoint and Graph events with a changeKey; its removal is one `DELETE`, and, since CB-6, the instances of a series and the `cancel` action, which answers 202 and moves the event, or a master and its occurrences, to `removed`). `test_writer_google_calendar_series.py` and `test_writer_outlook_calendar_series.py` hold the series verbs against them: the closed spec, the exact request of each dry run and confirmed run, every refusal with nothing sent, the lost answers, the allow-lists, and the oracles' vacuity cases. The tests assert the exact request list of a create, a change and a removal, that the dry run opens no connection and reads no credential, that a lost answer is found again by the key, and that no credential appears in any output. `runtime/tests/test_calendar_write.py` and `test_channel_grants_calendar.py` hold the runtime's side.

### To verify live (not checked against the services or not stated by the vendors; accessed 2026-10-18)

- **Series (CB-6; the maintainer's live steps, SPEC-CATALOG-BATCH section 8 step 4b; vendor pages read 2026-10-27).** Google: that a recurring event inserted with `start`/`end` carrying both an offset and `timeZone` is expanded in that zone ([events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events): "for recurring events this field is required and specifies the time zone in which the recurrence is expanded"; the pages do not say how an offset beside the zone is read); that `events.list` without `singleEvents` returns the master for the lost-answer lookup by `privateExtendedProperty`; that `DELETE` on a recurring event's own id removes every instance and where it goes ([events.delete](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete) says nothing of a series or of the trash); that an instance of a series accepts a `PATCH` of `{"status": "cancelled"}` with `If-Match` its etag as [the recurring-events guide](https://developers.google.com/workspace/calendar/api/guides/recurringevents) says a PUT does ("setting its status to cancelled"), that the instance then reads as cancelled, and how a person restores it; that `events.instances` filters as its page says (`timeMin` on the end, `timeMax` exclusive on the start; [the page](https://developers.google.com/workspace/calendar/api/v3/reference/events/instances) lists no instance field, the events resource does: `id`, `recurringEventId`, `originalStartTime`). Outlook: that Graph expands a series written with `start`/`end` in an IANA zone and no `recurrenceTimeZone` in that zone ([recurrenceRange](https://learn.microsoft.com/en-us/graph/api/resources/recurrencerange): "if not specified, the time zone of the event is used"; `startDate` "must be the same value as the start property"), so that the hour holds across a clock change; that `firstDayOfWeek` `sunday` is accepted beside one `daysOfWeek` and interval 1 (the [page](https://learn.microsoft.com/en-us/graph/api/resources/recurrencepattern) requires `firstDayOfWeek` for a weekly pattern); that `POST .../events/{id}/cancel` with an empty JSON object works on a series master's id, on an occurrence's id and on an event that has no attendee (its [page](https://learn.microsoft.com/en-us/graph/api/event-cancel) speaks of meetings, says the action "moves the event to the Deleted Items folder", and that an occurrence is cancelled "by providing the occurrence event ID"), that the series and its occurrences are then in Deleted Items, and how the person restores them; that an occurrence's id is gettable at `/me/calendar/events/{occurrenceId}` and carries a `changeKey` that moves when the occurrence does; that `instances` accepts `$select` and `$top` and times with a trailing `Z` ([List instances](https://learn.microsoft.com/en-us/graph/api/event-list-instances)).

- The Google console classification of `calendar.events` and `calendar.calendarlist.readonly` (the spec lists them as "to verify").
- That `If-Match` on `events.patch` and `events.delete` answers 412 on a moved etag ([Version resources](https://developers.google.com/workspace/calendar/api/guides/version-resources)), and that `events.list` filters on `privateExtendedProperty=openhora_key=<key>` for an event the writer created.
- That Outlook, asked for an all-day event in UTC, shifts its midnight (the writer reads an all-day event a second time, in its own zone, so that its date is not a day off east or west of UTC), and that the events path of a calendar (`/me/calendars/{id}/events/{event}`) answers 404 for an event of another calendar (the writer does not compare the event's parent calendar).
- That a Google patch with `{"dateTime": null}` next to `{"date": ...}` turns a timed event into an all-day one (the writer sends the other form as null).
- Outlook: that `singleValueExtendedProperties` on create and on update, and a `$filter` on them, work as [the extended-properties overview](https://learn.microsoft.com/en-us/graph/api/resources/extended-properties-overview) says; that `$expand=singleValueExtendedProperties($filter=id eq '...')` returns the property on a single event; that an event read with `Prefer: outlook.timezone="UTC"` comes in UTC (the writer refuses one that does not); that an all-day event created with midnight UTC bounds shows as the same days in the person's zone.
- Outlook: that Graph accepts the IANA name the writer sends in `timeZone` on create and update. [The dateTimeTimeZone page](https://learn.microsoft.com/en-us/graph/api/resources/datetimetimezone) (read 2026-10-27) says `timeZone` "can be set to any of the time zones currently supported by Windows, as well as the other time zones supported by the calendar API", lists IANA names such as `America/Sao_Paulo` and `America/New_York` under "Additional time zones", and says create and update "might not support all" of them. The list is shorter than the IANA database (for example `Europe/Lisbon` is not on it): for a host zone Graph does not accept, the create or patch is refused by Graph (exit 1, nothing written) until the person's zone is on the list or a follow-up adopts CLDR's `windowsZones.xml` as a pinned data file (principle 14); no hand-written table is shipped. Check with scenario 16 on a throw-away event: the event's details in Outlook web show the named zone and 10:00.
- That a Google calendar event removed with `events.delete` lands in the calendar's trash for 30 days (restorable there): [the Calendar help page](https://support.google.com/calendar/answer/37113) says it, [the API page](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete) does not. Delete a test event by hand through the writer and look in the trash BEFORE relying on the card's words; the card says it is expected and not verified.
- That Graph answers 404 for an event asked for through the path of another calendar (`/me/calendars/{id}/events/{event}` for an event of a different calendar, or `/me/calendar/events/{event}` for one that is not in the default calendar). The Outlook writer's pre-read of a change and of a removal relies on it to be sure the event is in the calendar the card names (it does not compare the event's parent calendar); the stand-in models it. If Graph answered 200, a removal asked for through a wrong calendar's path would remove the event.
- If the answer to an Outlook removal is lost and the event then disappears for another reason (the person removed it, another client did), the retry finds it gone and records the removal as done (`replayed`). That is the writer's documented reading of a lost answer (its help says so); the ledger cannot tell the two apart.
- Whether an Outlook event removed with `DELETE` lands in Deleted Items (OPEN, UNVERIFIED). Q12 of the spec asked for this check before any Outlook removal; the maintainer reversed Q12 on 2026-10-22 ("Apenas apague", `docs/decisions.md`) and the verb `event-delete` exists without it. The Graph page of the call does not say where the event goes, the runtime keeps no copy, and the Outlook card tells the person that Outlook may keep none. Delete a test event by hand through the writer and look in Deleted Items to close this.

## File writers (package W4a): what `gdrive.py` and `onedrive.py` do

The class is `writer:files`. The operations are `file-create`, `file-replace`, `file-save` (`runtime/ops_files.py`) and, since slice R2-A, `file-trash` (`runtime/ops_file_trash.py`, the move of a file to the service's trash); the card, the document and the rules are in `contracts/runtime.md` ("Files (package W4a)").

- **The account.** Every verb but `--check` takes `--account <address>`, the address of the account the document names, and compares it with the `account` of the token record before it refreshes the token: a token of another account reads and writes nothing (exit 1). The address in the project's `accounts` must be the one `google_auth.py` / `microsoft_auth.py` recorded (a Microsoft record holds the address `GET /me` named, which may not be an alias the person typed).
- **One secret.** `GOOGLE_ACCOUNT_TOKEN` or `MICROSOFT_ACCOUNT_TOKEN`, the account record made by `providers/accounts/google_auth.py` or `microsoft_auth.py`, read through `providers/secrets/resolver.py`. The runtime starts the process with the minimum environment and that one secret. A token that lacks a scope of the platform's set, or carries another, is refused (exit 3, naming the authorize command). There is no legacy record for a writer.
- **An allow-list in code (L58).** Each writer has a constant `ALLOWED`, a tuple of `(method, path regex)` pairs, and one function that sends a request and refuses any other. The one removal of either is the move to the service's trash (R2-A, below): Drive's `PATCH /drive/v3/files/{id}` with the body `{"trashed": true}` (a module constant, `TRASH_BODY`, and nothing else) and OneDrive's `DELETE /drives/{drive}/items/{item}` (Graph moves the item to the recycle bin). There is no call that deletes for good (Drive's `files.delete`, Graph's `permanentDelete`), no call on the trash or the recycle bin (no emptying, no restoring), no move or rename, no sharing or permission call (L57; the static scan of `runtime/tests/test_limits_account_writes.py` reads both files, honours the two moves above only as the constant and the pair it names for that file, and `providers/writer/tests/` shows the fake servers saw nothing else).
- **Ids are percent-encoded** with `urllib.parse.quote(value, safe='')` wherever they enter a URL, after a full-match pattern; a name is a closed set of characters (letters and digits of any script, space, `. _ - ( )`).
- **Fixed hosts.** The API and token hosts are constants; the test overrides are loopback only and set together. No redirect is followed with a credential. A request times out at 60 s. A 429 or 503 is reported with its `Retry-After` and never retried by a verb. The token is never printed (`_google.scrub`), and an error names a host, never an address that is a credential.
- **Dry run and confirmed.** `--dry-run` reads no credential, opens no connection, and prints the exact list of requests the verb would send (`{"method", "path", "query", "body"[, "if_match"]}`, the body of an upload described by its content type, byte count and sha256) and `would_sha256`, the sha256 of the canonical text of that list (sorted keys, no spaces, ASCII). `--confirmed` sends exactly that list. The runtime builds the same list from the document the person approved (`runtime/files_document.py` `requests`) and refuses `--confirmed` unless the writer's dry run hashes to the document's `dry_run_sha256`; a test starts each writer's dry run for every shape of document and compares.
- **The content is the approved bytes.** `--content-file` is an absolute path to a regular file the runtime wrote in a private folder; the writer refuses it unless its size and sha256 are the flags' (`--bytes`, `--sha256`). At most 25 MiB.
- **Idempotency.** `--idempotency-key files-<32 hex>` (derived by the runtime from the task, the operation, the account, the target, the name, the content and the base) and a ledger in `<state>/writer-<impl>/ledger.json` (the state folder is `$OPENHORA_STATE_DIR`, else `$XDG_STATE_HOME/openhora`, else `~/.local/state/openhora`; folders 0700, files 0600; an exclusive file lock): `pending` before the request that changes the account, `done` after the answer. A `done` key is answered again with no request (`replayed`); a key bound to other requests is refused; a key whose request the service refused outright is given back.
- **Exit codes.** 0 ok; 1 refused with nothing changed (including `changed:`, a moved base); 2 usage; 3 not configured; 4 unknown (the connection failed or timed out, or the service answered a server error: the request may have landed). The key stays pending after a 4, and the next attempt looks for its own mark first.

### `gdrive.py` (Drive)

Scopes: the platform's four (`drive` is what lets a writer create a file and write a revision of any file the person names; the Picker is not needed). Endpoints (accessed 2026-10-18: https://developers.google.com/workspace/drive/api/reference/rest/v3/files/create, `.../files/update`, `.../revisions/update`, https://developers.google.com/workspace/drive/api/guides/manage-uploads, https://developers.google.com/workspace/drive/api/guides/manage-revisions):

| Verb | Requests, in order |
|---|---|
| `file-meta --id` | `GET /drive/v3/files/{id}?fields=...` |
| `file-meta --folder --name` | `GET /drive/v3/files/{folder}`, `GET /drive/v3/files?q='<folder>' in parents and name = '<name>' and trashed = false` |
| `trash` (R2-A) | the file read again and compared with the base (`--base-version`, `--base-modified`, `--base-mime`, `--base-parent`; it must be a file, owned by the account and not already in the trash; a difference is exit 1 `changed:`), then ONE `PATCH /drive/v3/files/{id}` with `{"trashed": true}`. A key an earlier attempt left pending and a file that is in the trash now is that attempt's own: `replayed`. Nothing is deleted: the owner restores the file from the trash |
| `create` | the folder read (it must be a folder, not in the trash), the name read (any file of that name, whatever its content, is exit 1: it never overwrites), `POST /upload/drive/v3/files?uploadType=multipart` with the metadata (`name`, `parents`, `mimeType`, the private mark `appProperties.openhora_key`) and the media. `--gdoc` makes a Google Doc (metadata `mimeType` is the Google type, the media is `text/markdown`; Drive converts it on import) |
| `update` | the file read again and compared with the base (`--base-version`, `--base-modified`, `--base-mime`, `--base-md5`, `--base-head-revision`; a difference is exit 1 `changed:`), then, for a file with binary content, `PATCH /drive/v3/files/{id}/revisions/{head}` with `{"keepForever": true}` BEFORE the content is written (Drive purges an old revision 30 days after newer content; at most 200 revisions of a file can be kept), then `PATCH /upload/drive/v3/files/{id}?uploadType=multipart` with the media and the mark. A Google-native file keeps its own history and has no such revision |

**Where code cannot enforce it.** Drive v3 has no precondition on a media update (no etag on v3 files): between the read and the write there is the time of one request. The mark makes a retry find what an earlier attempt wrote. The name check of `create` and the create are two requests, not one atomic step: the lock of the decision keeps two approvals that go through the runtime from racing for a name, and a person who makes the same name in Drive in between ends with two files of that name (Drive allows it). Only a file the account owns and may edit is replaced (`ownedByMe`, `capabilities.canEdit`); `keepForever` is limited to 200 revisions per file, and when Drive refuses it the writer writes nothing and says so.

**Images (ATT-3).** `--media-type` also takes `image/png`, `image/jpeg`, `image/webp`, `image/gif`, `image/heic` and `image/heif` (`_files_common.IMAGE_TYPES`, the same table as `runtime/files_document.py`): the runtime sends one only for a save of a file a sender sent, with the bytes the hold read as that image; only the verb that creates a file takes one (`check_media_type(..., images=True)`); `update` and `replace` refuse an image type. The bytes are written as they are, never converted to a Google Doc.

**To verify live (the maintainer's step 10 of SPEC-SECRETARY-WRITES section 10):** that `files.create` with `mimeType` Google Doc and a `text/markdown` media is converted; that `files.update` of a Google Doc with a `text/markdown` media body replaces its content in place and keeps the revision history (if it does not, the fallback is a new Doc beside it, "<name> (edited)"); that `appProperties` set by a multipart update are returned by the list.

### `onedrive.py` (OneDrive)

Permission: `Files.ReadWrite` (of the platform's set). Endpoints (accessed 2026-10-18: https://learn.microsoft.com/en-us/graph/api/driveitem-put-content, `.../driveitem-createuploadsession`, https://learn.microsoft.com/en-us/graph/api/resources/driveitem):

| Verb | Requests, in order |
|---|---|
| `file-meta --id <drive>/<item>` | `GET /drives/{drive}/items/{item}?$select=...` |
| `file-meta --folder --name` | `GET` of the folder (`/me/drive/items/{id}` or `/me/drive/root:/path`), `GET` of `<folder>:/{name}` (404 is "not there") |
| `create` | the folder read, then `PUT <folder>:/{name}:/content?@microsoft.graph.conflictBehavior=fail` with the bytes (at most 25 MiB here; Graph takes 250 MB): a file of that name makes Graph answer 409 and the verb exit 1 `taken:` (unless it holds exactly the approved bytes and the key is pending: then it is the earlier attempt's own and is `replayed`) |
| `trash` (R2-A) | the item read again (it must be a file in the account's own drive) and compared with the base (`--base-etag`, `--base-ctag`, `--base-size`, `--base-parent`; a difference is exit 1 `changed:`), then ONE `DELETE /drives/{d}/items/{i}` with `If-Match: <eTag>` (412 is exit 1 `changed:`). Graph answers 204 and the item is in the recycle bin. A key an earlier attempt left pending and an item Graph no longer finds is that attempt's own: `replayed` |
| `replace` | the item read again and compared with the base (`--base-etag`, `--base-ctag`, `--base-size`), `POST /drives/{d}/items/{i}/createUploadSession` with `If-Match: <eTag>` and `{"item": {"@microsoft.graph.conflictBehavior": "replace"}}` (412 is exit 1 `changed:`), then one `PUT` of the bytes to the upload address Graph names, with `Content-Range: bytes 0-{n-1}/{n}` |

The upload address is a pre-authenticated bearer credential: it must be https (http to a loopback host in test mode), carry no user or password, the default port, and be on a host of the closed list (`api.onedrive.com`, `1drv.com`, `sharepoint.com`, or a subdomain), it is sent NO Authorization header, it is named to the allow-list as `/upload-session` (its own path is Graph's and secret), and it is never printed. **To verify live:** the host Graph names for a personal account's upload session (the list above is the one seen in the documentation's examples), and `If-Match` on `createUploadSession`. OneDrive keeps the earlier version in the file's history (retention is the service's own setting, not for ever). **A lost answer is told from the person's own edit by the content hash Graph reports** (`file.hashes`: `sha256Hash`, else `sha1Hash`; `quickXorHash` alone cannot be compared here): a file that holds exactly the approved bytes is ours (`replayed`); one that holds other bytes is the person's (`changed:` / `taken:`); one whose hash cannot be compared stays `unknown` (exit 4). Only a file in the account's own drive is replaced (`file-meta` prints `owned`, from `GET /me/drive`).

### The trash (slice R2-A): what the documents support, and what is not verified

Drive: `files.update` with `trashed` true is the API's way to move a file to the trash ([files resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), `trashed`: whether the file has been trashed, and only the owner may trash it; [files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update)); `files.delete` would delete for good and is not in the allow-list. Drive's help says a file in the trash is deleted for good after 30 days (https://support.google.com/drive/answer/2375102): the card says "recoverable for about 30 days" for Google Drive and says no more. **No precondition on the Drive trash.** Like `update`, the trash `PATCH` has none (Drive v3 has no etag on `files.update`): a few hundred milliseconds pass between the read that compares the base and the write, in which an edit or a move is not seen. The comparison of the base (version, modified time, type, folder) is the protection, and this gap is the limit of it; OneDrive's `DELETE` carries `If-Match` and has no such gap. The Drive `PATCH` is also bound at `send()`: its body is exactly `TRASH_BODY` and its query the fields list alone, so it cannot rename a file, change its parents or reach `/files/trash`; OneDrive's `DELETE` pattern refuses `..`, `%2E%2E`, `root:` and a query string in either id.

**Not verified live:** that the file lands in the trash of the owner for a file in a subfolder, that `version` changes when a file is moved between folders (the base also holds the parent, so the writer compares it), and the 30 days (the API pages do not state them).

OneDrive: [Delete a driveItem](https://learn.microsoft.com/en-us/graph/api/driveitem-delete) says the item is moved to the recycle bin and not deleted for good, and the call takes `If-Match` (412 on a moved eTag); `permanentDelete` is a different call and is not in the allow-list. How long the bin keeps it is the service's own setting (it differs between a personal and a work account), so the card says only "recoverable while it is in the trash". **Not verified live:** that a personal account's item lands in the recycle bin as documented, that `If-Match` is honoured on this call, and that the item's `parentReference.id` changes when it is moved (the base also holds it).

## Mailbox writers (package W3): `gmail.py`, `outlook-mail.py`

The class `writer:mailbox`. They change up to **20 messages** of one mailbox at a time (archive, move to a folder or label, mark read or unread, move to the trash), save a **draft**, and read the state of messages. **They send nothing**: there is no verb that sends, and neither `ALLOWED` holds a send (`messages.send`, `drafts.send`, `sendMail`, `/send`, `/reply`, `/forward`). **They remove nothing for good**: the trash is the provider's own (Gmail's `messages.trash`, which Gmail empties after 30 days; a Graph `move` to `deleteditems`), and neither file holds a removal call, `batchDelete`, `permanentDelete` or `emptyTrash` (limit L57: `runtime/tests/test_limits_account_writes.py` scans both). Shared by both: `providers/_writer_mailbox.py` (the ledger, the spec reader, the patterns of the ids).

| Verb | Google (`gmail.py`) | Outlook (`outlook-mail.py`) |

| `message-meta --account --ids [--key]` | one `GET .../messages/{id}?format=metadata` for each (subject, sender, date and Message-ID headers, labels, thread) | one `GET /me/messages/{id}?$select=...` for each (changeKey, folder, `isRead`, subject, sender, `internetMessageId`) |

### Calling a write verb

```sh
uv run <workbench>/providers/writer/gmail.py modify --account <address> --spec-file <file> --idempotency-key <key> --dry-run
uv run <workbench>/providers/writer/gmail.py modify --account <address> --spec-file <file> --idempotency-key <key> --confirmed
```

- `--account` is the address the document names. Every verb but `--check` compares it with the account of the token record and refuses another (exit 1, nothing read or changed). A dry run reads no credential, so it only uses the flag (a draft's `From`).
- `--spec-file` is a private JSON object, never a flag. Gmail `modify`: `{ids, base ({id: the sorted labels the message had when it was read}), add, remove}` (it removes only `INBOX` and `UNREAD`, and adds none of `TRASH`, `SPAM`, `SENT`, `DRAFT`, `CHAT` or `INBOX`, whatever the spec says); `trash`: `{ids, base}`; `draft-create`: `{to, cc, bcc, subject, body, in_reply_to, thread_id}`. Outlook `move`: `{ids, base ({id: {change_key, folder_id}}), internet_ids ({id: the internetMessageId or null}), to}` with `to` one of `archive`, `deleteditems` (the trash's), `inbox` or a folder id (every other name made of letters alone, in any case, `drafts`, `outbox`, `recoverableitemsdeletions`..., is refused); `mark`: `{ids, base ({id: {change_key, is_read}}), read}`; `draft-create` and `draft-reply`: `{to, cc, bcc, subject, body}`. The writer checks the keys, the limits (1 to 20 distinct ids; a subject of one line up to 200 characters; a body up to 100 KB; at least one and at most 20 recipients; no hidden or control character) and the forms of the ids, which never start with a hyphen (a flag would read it) and are percent-encoded wherever they enter a path.
- `--dry-run` reads no credential, opens no connection and prints `{"dry_run": true, "would": {"requests": [{"method", "path", "query", "headers", "body"}]}, "would_sha256", "ledger": {item: "absent"|"pending"|"done"}}`: the exact requests `--confirmed` sends and the sha256 of them. The runtime puts that hash in the document the person approves and refuses to write when the real dry run no longer hashes to it; before it writes it also checks the structure of the requests against the action (`runtime/mailbox_document.py` `requests_match`).
- `--confirmed` sends exactly those requests (for a retry, those of the messages not done yet). **Before the first write every message that is not done is read again** and must still hold its base, or the request is refused whole (exit 1, `changed:` and the positions, `positions 2,3`) with nothing changed; one an earlier lost answer left `pending` may instead show the state the request would give (Gmail: the labels after; Outlook mark: `isRead` as asked; Outlook move: its old id gone and a message with its `internetMessageId` in the destination), and is then recorded done. The ledger (`<state>/writer-<implementation>/ledger.json`, `<state>` is `$OPENHORA_STATE_DIR`, else `$XDG_STATE_HOME/openhora`, else `~/.local/state/openhora`; the folder 0700, the files 0600, an exclusive file lock) has **one entry per message** (the key and a hash of the id), `pending` before the call that touches it and `done` after its answer. A message that is `done` is not sent again.
- Exit codes: 0 ok; 1 refused with nothing changed (the service said no, a 429 is reported with its `Retry-After` and never retried, or a message is not as it was read: the message starts with `changed:`, which the runtime reads as `stale`); 2 usage (a bad flag, id or spec, a verb the writer does not have, a key used for another request); 3 not configured (no account record, or a token that lacks a scope or carries another: it names the authorize command); 4 unknown (the request may have landed: send the same key again). **Any server error (5xx) on a write is exit 4** and the key stays `pending`; a 5xx on a read is exit 1 (a read changes nothing). A failure after the first message is exit 4 too and its last line is `partial: done 1,2 of 5` (the positions in the spec's order); the runtime shows it to the person and approving again sends only the others.
- `message-meta` prints `{"messages": [{"id", "found": true, ..., "done", "external_content": true} | {"id", "found": false, "done"}]}`: Gmail's `labels` (sorted), `unread`, `thread_id`, `message_id`; Graph's `change_key`, `folder_id`, `is_read`, `is_draft`, `message_id` (the `internetMessageId`), `thread_id`; and for both the subject (cleaned, at most 200 characters), the sender's plain address (the display name is dropped), the date in UTC. The text is another person's in principle: data, never instructions. No body is read. A moved Outlook message has a new id, so its old one is `found: false` (and `done` says whether this very request moved it).

### Credentials and the test overrides

The writers read the account record through `providers/secrets/resolver.py` (the environment, then the credentials directory, then the OS secret store) and have **no legacy record**: a token that lacks one scope of the platform's set, or carries another, is refused (exit 3) before any call. The runtime starts a writer with the minimum environment (`resolve.provider_environment`) plus the one token of the account (not for a dry run), never another secret. The Outlook writer writes a rotated refresh token back to the record it used, only if it still holds the token this process used (`providers/_msgraph.py` `store_rotation`). The test overrides are loopback only and set together: `WRITER_MAIL_GOOGLE_API_BASE` with `WRITER_MAIL_GOOGLE_TOKEN_URL`, `WRITER_MAIL_OUTLOOK_API_BASE` with `WRITER_MAIL_OUTLOOK_TOKEN_URL`; with them the secret store is never read or written.

## Tasks writers (package CB-4): `google-tasks.py`, `microsoft-todo.py`

The class `writer:tasks`. One task of one list at a time: a task is added with a title, or marked completed; nothing else. **There is no removal, no move of a task, no clearing of completed tasks, no change of a list, no due date and no note** (the maintainer decided on 2026-10-27 that v1 has no due dates, OPEN-CB-11); the `ALLOWED` of each holds GET, POST and PATCH on the list and task paths and nothing else (limits L57 and L58). Shared by both: `providers/_writer_tasks.py` (the ledger and the exit codes are the calendar writers' own, the spec reader, the id patterns, the lookup after a lost answer). Every verb but `--check` takes `--account <address>` and compares it with the account of the token record.

| Verb | Google (`google-tasks.py`) | Microsoft (`microsoft-todo.py`) |
|---|---|---|
| `--check` | refresh the token, check the five scopes, read one list entry | the same with the six permissions |
| `task-get --list --task` | `GET /tasks/v1/lists/{list}/tasks/{task}` (`deleted` counts as gone) | `GET /me/todo/lists/{id}/tasks/{task}` |
| `task-insert` | `POST /tasks/v1/lists/{list}/tasks` with `{"title"}` (no `parent`, no `previous`) | `POST /me/todo/lists/{id}/tasks` with `{"title"}` |
| `task-complete` | a fresh `GET`, the etag compared with `--base-etag`, then `PATCH` `{"status": "completed"}` | the same, with `@odata.etag` |
| `--list` | an id, or `default` (the literal `@default`, which Google's Ads Scripts example uses and no reference page documents) | an id the reader printed; `default` is refused (it needs a read, and a dry run reads no credential) |

**No conditional write.** The pages read (tasks.patch; Update todoTask) mention no `If-Match`, so none is sent. `task-complete` reads the task again right before the PATCH and compares its etag with the one the person approved; the dry run prints that precondition as `requires: {"etag"}` inside what its hash covers. The window is one network round trip, roughly 100 to 500 ms, between that read and the PATCH: a change made in it is not caught. The worst case is completing a task whose title was edited in that window (the person approved the old title and the completed task has the new one); a task deleted in the window answers 404, reported as `changed:`. (To verify live whether either service takes `If-Match`; if one does, the writer should send it and the fake should answer 412).

**A lost answer (OPEN-CB-12).** There is no hidden property on a task to find a request by, so a key left `pending` by an answer that was lost is settled before anything is sent: for an insert, by the open tasks of the list with exactly the spec's title updated since the key went pending (the ledger's time, less 5 seconds for the clocks): one means it landed (`replayed`), none means it is sent again, more than one (or a Microsoft list with more than 10 pages to look through) is exit 1 `ambiguous:` and nothing is sent, the key stays pending and the person is asked; for a completion, by reading the task. A task the person completed in the meantime is not an open task: an insert whose task was completed before the lookup is sent again (a known gap, one more task, never a loss).

**Calling a write verb**, **credentials and the test overrides** as the calendar writers: `--dry-run` reads no credential and prints the exact request and its hash; `--confirmed` sends exactly that request; the overrides are `WRITER_TASKS_GOOGLE_API_BASE` / `_TOKEN_URL` and `WRITER_TASKS_MICROSOFT_API_BASE` / `_TOKEN_URL` (loopback only, both set together). The token must be the five Google scopes or the six Microsoft permissions: the previous sets are refused (exit 3) with the authorize command named. No title is written to stderr.

**Tests.** Against stand-ins on 127.0.0.1 (`providers/tasks/tests/fake_gtasks.py`, `fake_graph_tasks.py`), no vendor host: `providers/writer/tests/test_writer_google_tasks.py`, `test_writer_microsoft_todo.py`, and the scope rule in `providers/accounts/tests/test_account_tasks_scope.py`.
