# Providers: the native layer for environment requirement classes

A provider is a self-contained script that satisfies one requirement class from `contracts/environment.md` when the harness has no connector for it. Providers are core: they name third-party services (a scheduler API, a mail API), never AI tools.

```
providers/
├── CONTRACT.md                 # this file
├── resolve.py                  # the one function that turns a class into a provider script
└── <folder>/<impl>.py          # e.g. publisher/buffer.py, mailer/smtp.py, generator/openai.py
```

## From a class to a folder

A class is `<role>:<target>` (`contracts/environment.md`, "Classes"). `providers/resolve.py` holds the one map from a class to its folder and to the variables that select its implementation:

| Class | Folder | Variables, most specific first |
|-------|--------|--------------------------------|
| `publisher:<platform>` | `providers/publisher/` | `PUBLISHER_<PLATFORM>_PROVIDER`, then `PUBLISHER_PROVIDER` |
| `messenger:<platform>` | `providers/messenger/` | `MESSENGER_<PLATFORM>_PROVIDER`, then `MESSENGER_PROVIDER` |
| `converter:document` | `providers/converter/` | `CONVERTER_DOCUMENT_PROVIDER`, then `CONVERTER_PROVIDER` |
| `exporter:document` | `providers/exporter/` | `EXPORTER_DOCUMENT_PROVIDER`, then `EXPORTER_PROVIDER` |
| `script:project` | `providers/script/` | `SCRIPT_PROJECT_PROVIDER`, then `SCRIPT_PROVIDER` |
| `model:text` | `providers/model/` | `MODEL_TEXT_PROVIDER`, then `MODEL_PROVIDER` |
| `writer:calendar`, `writer:mailbox`, `writer:files` | `providers/writer/` | `WRITER_CALENDAR_PROVIDER` (or `WRITER_MAILBOX_PROVIDER`, `WRITER_FILES_PROVIDER`), then `WRITER_PROVIDER` |
| `generator:image`, `generator:video` | `providers/generator/` | `GENERATOR_IMAGE_PROVIDER` (or `GENERATOR_VIDEO_PROVIDER`), then `GENERATOR_PROVIDER` |
| `search:web` | `providers/search/` | `SEARCH_WEB_PROVIDER`, then `SEARCH_PROVIDER` |
| `integration:<service>` | `providers/<service>/` (`integration:vcs` is `providers/vcs/`) | `INTEGRATION_<SERVICE>_PROVIDER` only: each integration is a different kind of service, and one never serves another |
| `reader:email` | `providers/mailbox/` | `MAILBOX_PROVIDER` |
| `sender:email` | `providers/mailer/` | `MAILER_PROVIDER` |
| `scheduler:job` | `providers/scheduler/` | `SCHEDULER_PROVIDER` |
| `store:runtime` | `providers/store/` | `STORE_PROVIDER` |

The first six rows are derived from the text of the class: the folder is the role (the service, for an integration), and a hyphen in a name becomes `_` in a variable. The last four are an explicit table in `resolve.py`: those classes were the bare names `mailbox`, `mailer`, `scheduler` and `store` until 2026-10-02, and their folders and variables keep those names, because the provider tests, the Python 3.9 set, the pre-commit hook, every provider's path to the secret resolver and the jobs already scheduled on users' machines all name the folders. `resolve.py` still reads the four old class names as aliases of the new ones. `providers/secrets/` is not a class.

**A class with a parameter.** In `publisher:<platform>` and `messenger:<platform>` the part after the colon is handed to the implementation as `--platform`, because one implementation may serve several platforms. Each implementation of such a class declares the platforms it serves in one line at the top level of its file:

```python
PLATFORMS = ("<platform>", "<another platform>")
```

`resolve.py` reads that line as text, without importing the file (a provider's dependencies are not installed where the resolver runs). An implementation that declares nothing serves nothing. Every other class has a fixed target, which is part of the class and is passed to nobody.

## Selection

One function chooses the implementation of a class: `providers/resolve.py` (`resolve(cls)` when imported; `python3 providers/resolve.py --class <class>` prints the script's path, `--list` every class with its implementations and the one that resolves now). Skills, the agent runtime (`scripts/runtime.py`) and `scripts/doctor.py` all go through it. Nothing outside `providers/` names an implementation or builds a provider's path: a skill names the class and runs the path the function prints.

The order, first match wins:

The candidates are the implementations shipped in the class's folder; for `publisher:<p>` and `messenger:<p>`, those among them that serve `<p>`. So a second publisher added for another platform changes nothing for the first, and a platform nobody serves does not resolve.

1. The environment, most specific first: the variables of the table above (`PUBLISHER_<PLATFORM>_PROVIDER=buffer`, then `PUBLISHER_PROVIDER=buffer`; `SCHEDULER_PROVIDER=systemd`; `INTEGRATION_VCS_PROVIDER=github`). For `publisher:<p>` the general variable is a preference: when the implementation it names does not serve `<p>`, it is passed over.
2. The platform default, where the class has one: `scheduler:job` is `launchd` on macOS and `systemd` on Linux (`providers/scheduler/README.md`).
3. The only candidate, when exactly one is left.

Otherwise nothing resolves (exit 3, naming the variable to set): "no native provider", and the skill degrades as described in its body. A name from the environment is accepted only when it is a candidate; it is never used as a path. A caller with its own configuration (the runtime's `runtime.json`) may pass an implementation name explicitly, which wins over the environment and must be a candidate too.

The workbench root, where `providers/` is, comes from the environment variable `WORKBENCH_ROOT` (the absolute path of the checkout a project uses); unset, it is the checkout `resolve.py` itself is in. A skill runs `python3 <workbench root>/providers/resolve.py --class <class>` and asks the user for the path when the variable is not set.

A new class is added to `contracts/environment.md` and to the list in `resolve.py` in the same change (a test compares them); a platform default is added to `PLATFORM_DEFAULTS` there. A new platform of `publisher:<platform>` adds no class: it adds a name to the `PLATFORMS` line of the implementation that serves it, or a new implementation.

## Interface every provider implements

- `--help`: usage, verbs, required environment variables, examples.
- `--check`: verify configuration and credentials without performing any action or printing any secret, with a one-line reason on stderr when it fails. An implementation of a class with a parameter also takes `--check --platform <p>`, which answers for that platform. The exit codes have one reading, and a caller may depend on it:
  - `0`: ready. The next call of a verb is expected to work.
  - `3`: not configured. There is no credential, or it expired, or the service rejects it; or a local service the provider needs is not available to this user. The person has something to do (authorize, set a variable), and the reason says what. A skill reads 3 as "degrade, and tell the user what is missing".
  - `1`: any other failure: the service cannot be reached, it answered something unexpected, a local file is damaged. Whether the provider is ready is not known; a caller may try again later.
  - `2`: a usage error, which includes `--platform <p>` for a platform the implementation does not serve.

  A caller that only needs "ready or not" treats every non-zero exit as not ready; `scripts/doctor.py` does.
- `--dry-run` on every verb with side effects: print the exact payload that would be sent, do nothing: no credential is read and no network call is made. A value only the service knows is shown as a placeholder. One verb is an exception, and its row says so: the dry run of `commit-files` reads the remote, because the payload it shows is a diff against the branch. It clones the branch over SSH with the user's own key, reads no token, and writes nothing, neither to the remote nor to the ledger.
- Data to stdout as JSON; diagnostics to stderr. Never print tokens, keys or full credentials, not even partially.
- Credentials only through the secret resolver, `providers/secrets/resolver.py` (the environment variable, then the OS secret store; `contracts/secrets.md`), never from files inside a project or from flags. A new credential is registered there first.
- Idempotent: a verb that publishes, sends or creates a record at a remote service takes a required idempotency key (the scheduler's job id plays that role locally). The key is recorded as pending in a local ledger, under a file lock, before the request, and as done after it. A pending key whose outcome is unknown (a timeout, a crash, an answer that does not say the request was refused: a 5xx, a 408, a 429) blocks every new attempt until a `resolve` verb records what the user found. A key is released only when nothing was sent or the service refused the request. `resolve` is a verb with a side effect on the ledger: its `--dry-run` changes nothing, also next to `--confirmed`.
- A ledger is state, not cache: it lives in the data folder the scheduler uses (`~/Library/Application Support/ai-workbench/` on macOS, `$XDG_DATA_HOME/ai-workbench/` or `~/.local/share/ai-workbench/` elsewhere), never in a cache folder, where clearing the cache would lose the record of what was already published. The publisher and vcs ledgers moved there on 2026-10-02: on first use, when the new file does not exist and the old one (under `$XDG_CACHE_HOME/ai-workbench/` or `~/.cache/ai-workbench/`) does, the provider copies the old ledger to the new place, says so on stderr, and never deletes the old one. Jobs scheduled before this change run a copy of the old provider and keep writing to the old location, so they must be scheduled again after upgrading. A provider that moves a state file later does the same.
- Every network call and subprocess has a timeout. A request that carries a credential never follows a redirect.
- Files and folders a provider writes outside the repository (ledgers, job folders, logs) are 0600 and 0700.
- An override that replaces a real service or binary for tests is honoured only in test mode: a loopback URL, or an explicit test flag such as `SCHEDULER_TEST=1`.
- Exit codes of every verb: 0 success, 1 provider or service error, 2 usage error, 3 not configured: the same reading as `--check` above.
- PEP 723 inline dependencies pinned to exact versions (`==`); run with `uv run providers/<folder>/<impl>.py ...`. A provider whose dependency is worth a hash check (a library that handles a credential over a long-lived connection) also commits a lockfile written by `uv lock --script providers/<folder>/<impl>.py`, as `<impl>.py.lock` next to it; `interpreter_for` then starts it with `uv run --locked`, so uv installs only the locked, hash-checked files and refuses to start when the header and the lock disagree. `providers/messenger/discord.py` is the first, and its test fails when the lock is missing or names another version than the header. The header's `requires-python` is the oldest version the script really runs on (see "Python version").
- Offline tests in `providers/<folder>/tests/` (no network, no real credentials, never the real secret store: a fake service on 127.0.0.1 and fake tokens from the environment; the root `conftest.py` forces the null keyring backend, `contracts/secrets.md`). The pre-commit hook runs them whenever the class changes, and refuses a commit that leaves an existing class without tests.

## Calling a provider from code

One function runs a provider's verb for every caller of the task runtime: `providers/resolve.py`, `call(cls, verb, args, *, root=None, implementation=None, platform=None, config=None, timeout=600, env=None, run=None, stdin=None)`. It resolves the class (as "Selection" says; `implementation` is the configuration's choice), starts the script, and returns the one JSON object it printed; nothing else of a caller builds a provider's command or chooses its interpreter.

- **The interpreter** (`interpreter_for(path)`): a header with `# dependencies = []` runs on the caller's interpreter, any other header with `uv run` (`uv run --locked` when `<script>.lock` sits next to it).
- **The configuration**, when `config` is given, is written to a temporary file of mode 0600, passed after the verb as `--config-file`, and removed afterwards. `env`, when given, is the whole environment of the child; else the caller's is inherited. The function reads and passes no credential: a provider reads its own.
- **The exit codes** are mapped to `ProviderCallError.kind`: 2 is `usage`, 3 is `not-configured` (a class that does not resolve is too, with no exit code), any other exit, a start that failed or output that is not one JSON object is `failed`, and a start over `timeout` is `timeout`. The error carries `reason`, `exit_code` and the last 300 characters of stderr (`stderr_tail`).
- **The standard input**, when `stdin` (a `str`) is given, is what the child reads: a prompt or a request body, never on the command line and never in a file (`model:text` is the first class that uses it). No temporary file is written for it. It is refused with `config` (kind `usage`) and when it is not a `str`. A `run` stand-in is called as `run(argv)` when there is no `stdin` and as `run(argv, stdin)` when there is, so a stand-in written before keeps working.
- `invoke(path, verb, args, ...)` is the same call for a script already resolved (the effects, whose provider path the operations layer chose); `verb` may be `None` when `args` start with it.

A scheduler starts its jobs with the system interpreter (`/usr/bin/python3`, Python 3.9 on macOS), because that path and its hash survive package upgrades and cache cleaning. So one set of scripts must run on Python 3.9, standard library only:

- the scheduler providers themselves (`providers/scheduler/*.py`), whose runner copy the scheduler calls;
- the agent runtime the scheduler runs (`scripts/runtime.py`, `scripts/runtime_vote.py`, `scripts/vote_job.py`) and `providers/resolve.py`, which it imports;
- every script the runtime starts with its own interpreter: the store provider (`providers/store/*.py`) and the skill scripts it calls (the gate, the parsers, the builders).

Rules for a script in that set:

- Its header says `requires-python = ">=3.9"` and `dependencies = []`. A header never claims a newer version than the script needs: the header is what `uv run` obeys, and what a reader trusts.
- It starts with `from __future__ import annotations` when it annotates with `X | None`, and uses no syntax or standard-library call newer than 3.9.
- It is listed in `ON_SYSTEM_PYTHON` in `scripts/tests/test_runtime_python39.py`, which checks the syntax, the header and that the file imports. CI runs that file and the tests of those scripts on Python 3.9 (`.github/workflows/checks.yml`, job `python39`; the list is `scripts/python39_tests.txt`): on a pull request into an integration branch the job runs the selected tests inside that list, and the file above always among them, so every script still parses and imports on 3.9; at the nightly run (`nightly-python39`), on a pull request into `main` and on a push to `main` it runs the whole list. A 3.9-only break that shows only when unselected code runs is found by the nightly within 24 hours, before any release (`docs/decisions.md`, T4).

Every other provider (one that reaches the network or needs a dependency) declares the version it needs and is started through its declared runner, `uv run <script>`, never with the caller's interpreter. A provider that needs newer syntax stays out of the set above and is started that way.

A provider started that way runs on the interpreter uv finds at each start, and the OS secret store trusts a binary, not a version. So a scheduled job pins it: `schedule` records the interpreter that `UV_PYTHON` names (an absolute path, resolved to the real binary; unset or a version such as `3.11` records nothing and the dry run warns), the approved digest covers it, every firing checks it (a changed interpreter refuses the job) and the command starts with `UV_PYTHON` set to it. `provider_environment` passes `UV_PYTHON`, so a provider started through the resolver keeps the pin (`providers/scheduler/README.md`).

## Verbs per class

Every verb prints one JSON object on stdout. The "Prints" column names the keys of that object a caller may depend on: an implementation prints them under these names, whatever else it adds. A second implementation of a class is written against this column, never against the output of the first.

| Class | Verb and flags | Prints |

**Functions of the store.** The tables the task runtime added to `store:runtime` (`tasks`, `task_runs`, `pending_decisions`; `providers/store/README.md`) have no verb: `runtime/ops.py` imports the implementation the class resolves to and calls its functions, one transaction each. Add a verb when a skill needs it, together with the skill. A row that starts "No implementation ships" is a reserved shape, not a promise: no provider answers it, a skill that uses the class degrades as its body says, and the first implementation may change the row in the change that adds it.

### The account tokens

`providers/accounts/` is not a class folder (like `providers/secrets/`): `providers/resolve.py` never lists it and no skill requires anything in it. It holds one authorization command per provider of an account, `providers/accounts/<provider>_auth.py authorize|check|forget [--account <slot>]`, for the person's own account: one OAuth client per provider, one consent per account with the platform's whole scope set, one record (decision of 2026-10-18; it reverses the one-registration-per-purpose design of the single-permission records, and `contracts/secrets.md` says so). The restriction is the platform's (policies, a card of the exact content for each write, the verbs each script sends, no token in a run), not the token's.

- `authorize` asks the whole set in one consent (PKCE S256, a state, a loopback redirect), checks that the granted set is exactly the platform's (a missing or an extra permission: exit 3, naming the command, nothing stored), reads the account's address once and stores one record. `check` reads the record back through the resolver, makes no network call and prints no token. `forget` deletes the local record of that account and nothing else. `--account` defaults to `main`, the only slot in this version; the record carries it.
- `providers/accounts/microsoft_auth.py`: secret `MICROSOFT_ACCOUNT_TOKEN`, store username `microsoft-account`, the set `Mail.ReadWrite`, `Mail.Send`, `Calendars.ReadWrite`, `Files.ReadWrite`, `User.Read` (and `offline_access`), code constant `PLATFORM_SCOPES` of `providers/_msgraph.py`; the client id is `MICROSOFT_CLIENT_ID` in the environment of the command, never a flag. Details, the rotation race and the live checks: `providers/accounts/README.md`.
- A provider process is started with the minimum environment plus the one account secret it is named for (`provider_environment`); the token is never in a run, a prompt, a manifest, a card or a log (limit L59). Exit codes as everywhere: 0 ok, 1 failed (including an address that could not be read), 2 usage (a slot other than `main`), 3 not configured (no authorization, a consent that needs an admin, a missing or an extra permission).

### Identifiers of a class with a parameter

The publisher's verbs name a post and a comment by flags that belong to no platform: `--post-id`, `--comment-id` and `--parent-comment-id`. Their value is opaque to the caller: a skill, the runtime or a script passes the identifier exactly as it received it (from a parser's output, from a provider's output, from the user) and never builds, cuts or rewrites one. What an identifier looks like on a platform is a fact of that platform, written in its reference (`shared/references/platforms/<platform>.md`, section "Identifiers") and in its data file; the implementation that serves the platform checks the shape before it uses the value, and answers a value of another shape with exit 2.

An implementation written before 2026-10-02 took these values under names of its platform's vocabulary. It keeps those names as aliases of the generic ones (the first publisher takes `--post-urn`, `--comment-urn` and `--parent-comment`), so a command written with them, in a project's notes or in a scheduled job, keeps working; new callers use the generic names, and a new implementation defines only those.

## Shared provider code

A file whose name starts with an underscore, or is not an implementation of a class, is shared code and never a provider (the resolver lists only `<name>.py` files of a class folder). `providers/_container.py` is the one home of a sandboxed container job, for a provider that runs a program inside a container on this machine: it owns the `docker run` command with every limit written once (no network, read-only root, all capabilities dropped, no new privileges, limits on processes, memory with swap, CPUs, memory-backed `/tmp` and `/scratch`, an image that is never pulled, a run label and a deadline label), the rule for a bind-mount path, the docker client and its environment, `require_local_daemon` (a remote daemon is refused, because a job's files would cross a network), the run (a timeout, a stop signal or an error removes the container by name; the container's stderr is capped), `stop` and `remove` by name, and `reap`, which removes the containers of a run label whose deadline has passed, and `old_definition_images` / `remove_old_definition_images`, which list and remove by tag the images of a provider's earlier definitions through a container tool passed in (`tool(*args) -> (returncode, stdout)`): a candidate carries the label `org.openhora.definition`, has exactly the provider's repository and differs from the current definition by label and tag; an unlabelled, untagged, `wb-eval` or current image is never one; no `--force`, no `prune`. Only `python3 scripts/doctor.py --remove-old-images` calls them. `provider_environment(cls)` gives a provider's process a fixed minimum plus exactly the variables `resolve.variables(cls)` returns for its class, never a list of provider names. It owns neither the image, nor the folders a job uses, nor what a provider prints. The eval container's runner, `evals/executor.py`, does not use it, so it is outside the measurement fingerprint. Tests: `scripts/tests/test_provider_container.py`, `scripts/tests/test_container_images.py`. `providers/_email.py` is the shared code of the providers that speak e-mail (the outbox, `providers/mailer/smtp.py`, and the e-mail channel that will follow): the form of an address and of a header value, the `<oh.<hex>@domain>` Message-ID, the rules of the connection (SMTP 465 or 587 with a required STARTTLS, IMAP 993, the certificate verified, no password before TLS, plain only for a test on a loopback host with `OPENHORA_MAIL_TEST_PLAIN=1`) and the MIME message. Tests: `providers/mailer/tests/test_email_helpers.py`.

## OAuth services

Services that need user consent ship an `auth.py` next to the provider: `uv run providers/<folder>/auth.py --provider <impl>` runs the authorization once in the browser and stores the refresh token in the OS secret store under a documented key. It never writes tokens to disk in plain text.

**Account tokens (decision of 2026-10-18, package ACCT-G for Google).** The Google readers (`mailbox/gmail.py`, `calendar/google.py`, `documents/gdrive.py`) sign in with one token per Google account, made by `providers/accounts/google_auth.py authorize|check|forget [--account main]`: one OAuth client, one consent, the platform's whole scope set (`gmail.modify`, `calendar.events`, `calendar.calendarlist.readonly`, `drive`), one JSON record in the secret `GOOGLE_ACCOUNT_TOKEN` (store username `google-account`). The record carries a `slot` (`main`, the only one in this version) so that a second account needs no new shape. `providers/accounts/` is a home for authorization helpers, not a class folder: `resolve.py` never lists it and a name with an underscore is never an implementation. The shared code is `providers/_google.py` (the scope check, the record, the order in which a provider looks, the token endpoint, the scrub of every credential from printed text); each reader loads it by path. A token that lacks a scope of the set or carries another is refused (exit 3, naming the authorize command). The token can do everything its scopes allow and that is accepted: the restriction is the platform's (policies, an effect card of the exact content for every write, the verbs a provider script exposes, no token in a run), so **each provider script exposes only the verbs its job needs: the readers send GET only (and the token POST), and a test fails on any other method**. Each reader reads the account record first and, when it is absent, its old record with its old exact scope rule, printing on stderr once per process "using the legacy record <username>; run <authorize command> to move to the account token"; the fallback and the old `*_auth.py authorize` commands are removed in the cycle after the integration branch reaches `main` (backlog ACCT-LEGACY). `providers/accounts/README.md` states the scopes, the consent, the revocation and the sources.

## Side effects

Providers execute; they do not decide. The confirmation gate lives in the skill that calls the provider. A provider must refuse to run a side-effect verb without `--confirmed` unless `--dry-run` is present, so an accidental call from a skill that skipped its gate fails loudly.

A verb whose effect happens later (the scheduler) fixes what was approved. Every file the deferred command reads through its arguments, the program and the runner are hashed; the dry run prints a digest of them, the confirmed call must pass that digest back, and the run refuses when any hash changed. A file argument that is not snapshotted makes the job refused. A file argument is a path of its own or `--flag=<path>`; a file named in any other spelling (glued to a short flag, `key=<path>`, a list of paths) is refused too, since the scheduler cannot swap it for a verified copy.
