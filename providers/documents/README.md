# Documents provider (`integration:documents`)

The documents of the task runtime (`runtime/`), mirrored where the project keeps them: on the machine or on a platform. The runtime calls a provider of this class with the project configuration's `documents` object (`docs/workbench/runtime.json`); the verbs and what each prints are in `providers/CONTRACT.md`, "Verbs per class". A write replaces the whole document; it never merges.

| File | What it is |
|------|------------|
| `local.py` | The documents as Markdown files in a folder of the machine, outside the project (`dir`); comments are the `- ` lines of a side file `<path>.comments.md`, which does not move the version (the sha256 of the document's bytes). Standard library only, Python 3.9 |
| `notion.py` | The documents as pages of a Notion workspace under one parent page: `{"provider": "notion", "parent": "<page id>", "expires": "YYYY-MM-DD"}`. Python 3.10 or newer, with `keyring`: run with `uv run` |
| `gdrive.py` | The files a person picked in Google Drive, read as sources of a project (`SOURCES_ONLY`: it writes nothing). Scope `drive.file`. Python 3.10 or newer, with `keyring`: run with `uv run` |
| `gdrive_auth.py`, `gdrive_picker.py` | Helpers, not implementations: the one-time authorization and the later picks, and the one-shot loopback page that runs Google's Picker (see "Google Drive" below) |
| `onedrive.py` | The files a person chose in their own OneDrive, read as sources of a project (`SOURCES_ONLY`: it writes nothing). Delegated Microsoft Graph permission `Files.Read`. Python 3.10 or newer, with `keyring`: run with `uv run` |
| `onedrive_auth.py` | A helper, not an implementation: the one-time authorization (and `forget`) of `onedrive.py` (see "OneDrive" below) |
| `notion_blocks.py` | A pure helper, not an implementation: Markdown to the blocks of a page and back (`round_trip`), the platform's side of the trip for an implementation that stores blocks |

The class is found by its folder; its row in `contracts/environment.md` (and `LISTED` of `providers/resolve.py`) comes with the router's first change of its routing table.

## Which documents a person may edit on a platform

A skill's runtime manifest (`skills/<name>/evals/runtime-manifest.json`) marks each document it writes `editable` or `read_only`. A type is `editable` only when it survives the trip: `tests/test_document_types.py` runs, for each `editable` entry, the skill's own checker on its fixture before and after `notion_blocks.round_trip` (or, with no checker, checks that no word is lost). A fixture is a case of `tests/fixtures/round-trip.json` or of `tests/fixtures/types/<skill>.json`, a document a lab run of the skill wrote on its own fictional fixture. A type that fails is set to `read_only` in its manifest; the converter is not changed to make it pass.

Two types are decided by that test and by what their checker can be given: `design-system`'s document is `editable` (fixture `fixtures/types/design-system.json`, checked with its flows file), and `product-feature-spec`'s is `read_only`, because each acceptance criterion continues on indented lines under its item (Given, When, Then, Covers), which the converter returns as a separate paragraph, so the spec's checker fails on the document after the trip (measured on six specs that pass it before). Three more are `editable`, each on a fixture in `fixtures/types/<skill>.json` built from a fictional person's file (the source line of each says which): `mkt-content-plan`'s calendar (no checker applies, `slots.py` computes slots and checks no document, so the test is that no word is lost), `mkt-social-copy`'s post file (checked with `check_post.py`, against the voice guide and the profile it reads) and `mkt-messaging`'s messaging document (checked with `lint_messaging.py`). The post file's path has a placeholder (`docs/marketing/content/<post>.md`), which the test reads as one path segment. The fixtures are not documents a lab run wrote: the repository keeps no run's output, so each is a document in the shape of the skill's own template, and the type is to be run again on a lab run's document when one is kept.

A document whose checker needs an argument that varies per document (`design-brief`: `--type` and `--values`; `design-handoff`: `--screen`; `design-execute`: `--brief`; `design-ux-flows`: `--phase`, without which the lint demands a flow for every must or should feature of every phase) has no checker in its manifest and is `read_only`.

A `read_only` page carries one notice, written by the runtime (`runtime/documents.py`, `NOTICE`): it says that edits made on the page are not imported and that the page is not overwritten while it differs from what the runtime last wrote. The class carries it with `write --notice <text>` (the notice is the page's first block, kept when present with the same text, added when absent) and the verb `notice --id <id> --text <text>` (adds it to a page that has none, touching nothing else); `read` leaves it out of `markdown` and prints it as `notice`, so it is never counted as a change of the page and never imported. On the local disk it is the file's first line, `> [notice] <text>`, and one empty line.

## Notion (`notion.py`)

The token is `NOTION_TOKEN`, read only through `providers/secrets/resolver.py` (stored with `uv run --with keyring==25.7.0 keyring set openhora notion`): an internal integration with read content, update content, insert content and read comments, given only the parent page. Neither the parent's identifier nor the token is ever written in this repository: they live in the project's `docs/workbench/runtime.json` and in the secret store.

- A document is a page under `parent`, created by the first `write` without `--id` and titled by its project-relative path; its id is the page's identifier. An id that is not a page identifier names no document (exit 1).
- `write` converts with `notion_blocks.to_blocks` and replaces every child block of the page: the new blocks are appended first, at most 100 per call, each sent without its own children (a table keeps its rows), whose children are appended under it in later calls, so no request nests more than one level; then the old blocks are deleted. A failure never leaves the page empty.
- The notice is a callout block with the provider's own icon (`NOTICE_ICON`) and the notice's text. `write --notice` keeps a first block that is that notice and otherwise puts the notice at the start before the new body is appended; `notice` lists the first child (one call, `page_size` 1) and, when it is not a notice, appends the callout at the start (`position` `{"type": "start"}`). `read` leaves a first block that is a notice out of the Markdown.
- `read` lists the children at every depth and converts them with `notion_blocks.to_markdown`: it returns the round trip of what was written, not the same bytes (`expected` of the harness). `stat` retrieves the page object only.
- `version` is the page's `last_edited_time`; `archived` is true when the page reports `in_trash`, `is_archived` or `archived`. Comments are those the service lists for the page and for each of its blocks, each once: a comment on a block is listed under that block only (measured, N4). The reference: unresolved comments only. The version is rounded to the minute and a comment does not move it (measured, N1 and N3), so the version covers the content and `comments` lists the page's own comments in one listing whatever the version; the runtime calls it for every mirrored page at every pull, and the comments on blocks come with `read` (WP-3.15).
- At most one page per idempotency key: the key is pending in the ledger (`documents-notion.json` in the data folder, 0600; `INTEGRATION_DOCUMENTS_NOTION_LEDGER` names another file) before the creation and done after it, scoped by the parent. A 4xx other than 408 and 429 releases it; anything else keeps it pending until `resolve`. No verb retries: a 429 or a 5xx is exit 1 with the status (and `Retry-After`) on stderr.
- No redirect is followed. `INTEGRATION_DOCUMENTS_NOTION_API_BASE` replaces the service's address for tests only, and only with a loopback URL (exit 2 otherwise); the secret store is then never read.

Choices made where the plan left one (the smallest call table the verbs need): no request nests children (the reference allows two levels; one call per parent block costs calls, not endpoints); the new body before the old one is deleted; a creation carries the title only, and the body follows by appends.

### The outputs of a task: `page-create`, `table-read`, `table-create`, `rows-append`

Package NOTION-OUT (`docs/architecture/platform/outputs.md`). Five verbs of this provider, called by `runtime/effect_write.py` (the three that write, after the person approved the exact content) and by a step kind's read-only service (`table-read`, `rows-state`). A provider that has no such verb (the local one, the Drive one) answers exit 2 "unknown argument", and the effect fails with nothing written. All four take `--config-file` (the `documents` object), use the token `NOTION_TOKEN` and never `NOTION_SOURCES_TOKEN`, and print one JSON object.

| Verb | Flags | Prints |
|---|---|---|
| `page-create` | `--parent <page id>` `--title <text>` `--markdown-file <f>` `--idempotency-key <k>` `--dry-run \| --confirmed` | `id`, `version`, `created`, `replayed`, `url`, `expected_sha256`; the dry run: `would` with `state` (`new`, `pending`, `created`, `done`), `id`, `blocks`, `bytes`, `expected_sha256` |
| `table-read` | `--id <data source id>` | `id`, `name` (the table's title, or null), `schema` (`[{name, type}]` sorted by name), `schema_sha256`, `select_options` (`{column: [option names]}`), `title` (the title property's name), `row_count`, `last_edited` (the newest `last_edited_time` of a row, or null); exit 1 for a table of more than 2,000 rows |
| `table-create` | `--parent <page id>` `--title <text>` `--table-file <json>` `--idempotency-key <k>` `--dry-run \| --confirmed` | `id` (the database), `data_source_id`, `url`, `created`, `rows`, `rows_created`, `rows_replayed`, `schema_sha256`; the dry run: `would` with `state`, `id`, `rows`, `rows_done`, `rows_pending`, `rows_new` |
| `rows-append` | `--id <data source id>` `--table-file <json>` `--schema-sha256 <hash>` `[--scope <word>]` `--idempotency-key <k>` `--dry-run \| --confirmed` | `id`, `rows`, `rows_created`, `rows_replayed`, `schema_sha256`; the dry run: `would` with `verified` (false: it makes no call, so it counts the ledger alone), `rows`, `rows_done` (under this key, or under another key of the same scope), `rows_pending`, `rows_new` |
| `rows-state` | `--id <data source id>` `--table-file <json>` `--scope <word>` `[--idempotency-key <k>]` | `id`, `scope`, `verified` (true), `rows`, `rows_done`, `rows_pending`, `rows_new`: how many rows of the file the ledger holds under the scope (and under the key, when one is given) as written or of unknown outcome. **A row counts as done only if the table lists the page that was made for it now** (a page a person trashed is a row to write); so it lists the table (up to 2,000 rows; a longer table is exit 1 "will not guess") and reads a credential. It writes nothing |

`resolve` takes `--parent <page id>` for a page or a database made under another parent than the configured one. `stat` also prints `title` (the page's). The table file is `{"columns": [{"name", "type"}], "rows": [[...]]}` with the types `title`, `rich_text`, `number`, `date`, `select`, `checkbox`, `url`, checked by `notion_tables.py` (a pure helper, not an implementation): at most 500 rows and 30 columns, a text of at most 2,000 UTF-16 code units (the reference says "characters" and not in which unit; code units are the larger count), exactly one title column, a value of each row's column in its type; a date is `YYYY-MM-DD` or a date-time **with Z or an offset** (one with no zone is exit 2). A table file out of its form is exit 2 before any call. A dry run reads the ledger and prints what a run would do, and makes no call and reads no credential. `rows-append` and `table-create` refuse rows that do not fit the table: a column the table lacks, a column of another type, or no title column (`rows-append`: exit 1, nothing written); a `--schema-sha256` that is not the hash of the table's columns now is exit 1, nothing written.

**Idempotency, per operation and per row.** The ledger (`documents-notion.json`, mode 0600) holds the operation's key under its parent (`<parent>/<key>`: `pending`, `created` for a page whose body is not finished, `done`) and each row's under the data source (`<data source>/<key>/row-<nnnn>`: `pending`, `done`, with the hash of the row's values and the `--scope`), recorded before the call and marked after it. A row done is skipped. A row of the file whose values hash like a row of an entry with the same `--scope` under another key (an earlier attempt of the same task, started over after the table changed) is that row: its entry moves under this key and it is not written again. A row pending is looked for in the table (the rows made since the attempt began, `created_time` on or after it less 120 s, compared cell by cell with the row, dates as dates and date-times as moments, excluding every id ANY entry of the ledger holds) and adopted if found, written if not; a page or a database pending is looked for among the parent's children (exactly one `child_page` or `child_database` of that title, made since the attempt began, claimed by no entry) and adopted if found, else the key stays pending until `resolve`. A page or a database the person put in the trash since is made again. A 4xx other than 408 and 429 releases the entry. The key is the document's own (`runtime/output_document.py`). A done entry made by these verbs (`kind` `output`) older than 90 days is dropped when the ledger is next saved, unless its key still has an entry of unknown outcome (pending): then none of that key's entries is dropped. The runtime refuses to approve an output decision older than 90 days (`ops_step_effects.OUTPUT_RETENTION_DAYS`), because the ledger could have forgotten its key. A **row is trusted only as far as the table bears it out**: an entry counts as done only if the page it made is among the rows the table lists now. **The scope (or the key) is locked** for the life of a write (an exclusive lock on a file next to the ledger, `<ledger>.<hash>.key.lock`, removed with the lock; the hash is of `scope/<--scope>` when the call has a scope, else of `key/<target>/<key>`): a provider that outlives a killed runtime cannot run beside the next run of the same task, even under a new key; the second is refused after 2 s with "another run of this provider is writing this key now". A key's entries are `<parent>/<key>` (a page or a database) and `<data source>/<key>/row-<n>` (its rows); the pruning groups them by the key, so a pending database keeps its rows. The row key is in the ledger and not in a property of the table, because a column added to a person's table would be an unapproved change; the cost is that a listing that lags behind the write can make an unknown-outcome row be written twice (said in `outputs.md`).

**Rate and retry.** These verbs, and only these, keep to 2.8 calls a second (0.35 s between two calls) and retry a 429 or a 529 up to four times after the first attempt, waiting the `Retry-After` the service names, at least 1 s and at most 60 s; in the tests, which reach the loopback stand-in only, they wait a few hundredths of a second. The verbs above them never retry.

**Choices.** A table of one data source (`initial_data_source`); the properties of the seven types only; a select's options are the values that occur; rows are written one page each (`POST /v1/pages` with the data source as parent), never in a batch, so that a row is the unit of the ledger. The row count of `table-read` is made by listing the rows (`POST /v1/data_sources/{id}/query`, 100 a call); `last_edited` is the newest `last_edited_time` among them.

## Measured on the live service

The ten measurements of the platform plan (stage 3, WP-3.10, step 4) were made on a scratch page and a scratch base of the maintainer's workspace with the provider's own verbs and, where no verb exists, the smallest direct call, the token read from the secret store. The person's actions (an edit, a comment, archiving) were made through the API where the API allows it; each row says so, and what is still to be done by hand. Each row is written as observed: the command, what it printed with identifiers removed, the date; times are UTC. Where a row is not measured, the code follows the public reference and the stand-in service of the tests decides what the reference leaves open (`tests/fake_notion.py` of the documents class says what). ### A page read as a source (`read --as-source`)

`read --id <id> --as-source` reads a page the person chose as a source of a project (`runtime/sources.py`, decision D13), not a document of it. It needs no `--config-file`: a page chosen as a source has no parent in the project's `documents` object. It uses a separate secret, `NOTION_SOURCES_TOKEN` (stored with `uv run --with keyring==25.7.0 keyring set openhora notion-sources`): an internal integration with read content only, given only the pages chosen as sources. It never uses `NOTION_TOKEN`, which writes, even when that one is set and the other is not (exit 3, no request made). It prints the same object as `read` with `comments: []` and `as_source: true`, and asks the service for no comments. No other verb takes `--as-source`. The tests are `providers/documents/tests/test_documents_notion_as_source.py`, against the stand-in service.

## Google Drive (`gdrive.py`)

`gdrive.py` serves the files a person picked as **sources** of a project (`runtime/sources.py`, decision D13). It is an implementation of this class by its folder and its verbs, and it is read only: `stat` and `read` take `--as-source` (as the Notion provider's `read` does, so that a later write-back keeps its own flags); `comments`, `write`, `notice` and `resolve` answer "not supported" (exit 2). It declares `SOURCES_ONLY = True`, which the contract tests of the class read to skip the write-and-read cases for it (`gdrive.py`, `gdrive_auth.py` and `gdrive_picker.py` have their own suites, `tests/test_documents_gdrive*.py`, against the stand-in service `tests/fake_drive.py`).

**Files only, one scope.** The scope is `https://www.googleapis.com/auth/drive.file`, and nothing wider is requested (a test reads the consent URL; `gdrive.py` refuses a token that carries any other scope). Under it a file the person picks in the Picker is given to the app. A picked **folder** is not: the spike on a one-shot loopback page (2026-10-15) found `files.get` on the folder answered, and `files.list` with `'<folderId>' in parents` listed 0 children of a folder that held files. So the Picker is configured to open folders for navigation and not to select them, and several files can be picked at once; a Drive folder as a source is deferred, and `drive.readonly` is not requested. **`drive.file` is not read-only**: it lets the app read and write every file the person picked. The provider sends GET requests only (a test records the method of every request), and the sources code calls only the read verbs; the token itself could write, so it is kept like the files it opens (below).

**What `read` does with each type.** It writes the bytes to `<out-dir>/content` and prints their description; it never parses a file (the runtime hands the bytes to the converter, a container with no network, limit L27). The export is Drive's own (`files.export`):

| Drive type | Read as | Then |
|---|---|---|
| Google Doc | `text/markdown`; if the service answers 400 for that format, `.docx` | Markdown text goes in as a version with the converter `markdown` (it is text already, scanned for credentials like a Notion page); `.docx` goes to the converter |
| Google Sheet | `.xlsx` (every sheet) | the converter |
| Google Slides | `application/pdf` | the converter |
| any other file | downloaded as it is (`alt=media`), its md5 checked against the one Drive recorded | its type read from its bytes (PDF, Word, Excel, HTML, CSV, text; any other type is refused by the intake) |
| a folder, a drawing, a form, a script, a shortcut, a file in the trash | refused (exit 1) with the reason | |

Limits: `--max-bytes` (the runtime passes 25 MiB, the intake's cap) bounds a download, checked against the size Drive reports before the bytes are asked for, and an export; Google limits exported content to 10 MB, and a 403 for it is reported as that. These two numbers and the Markdown export of a Doc are from the API reference as recalled, and the live service has not been called for them (item 2 of the plan's "To verify" stays open): the fallback to `.docx` is there because of that.

**Pictures in a Doc.** Google's Markdown export may embed a pasted picture as a base64 `data:` URI, inline or as a reference definition at the end, which can push an ordinary Doc past the 1 MiB converted cap. The runtime replaces each with a short placeholder that keeps the picture's name (`strip_embedded_images`, `images_removed` in the answer and in the manifest) before the cap applies; nothing else in the text changes, and a picture written inside a fenced block is replaced too. So `original.md` of a Drive Doc exported as Markdown is the text with the pictures already removed, not the bytes Google sent (the manifest's `images_removed` says how many); the scan is linear, since the text is another person's and may be hostile, and an alt text over 200 characters is not recognised. Whether the live service embeds pictures this way is the risk noted under item 2 of the plan's "To verify".

**Change detection.** `stat` returns `version`: Drive's `version` counter and `modifiedTime` together, which moves when the file changes. A refresh asks `stat` first and reads the file only when `version` differs from the one recorded with the newest version of the source (`origin_version`); when the bytes read turn out to be the ones already held, no version is made.

**Authorization and the secret.** `GDRIVE_SOURCES_TOKEN` is the one secret entry: a JSON record `{refresh_token, client_id, client_secret, api_key, project_number, scope, obtained_at}`, written to the OS secret store (service `openhora`, username `gdrive-sources`) by `gdrive_auth.py authorize` after the person's consent, or exported as the same JSON text in an environment. The client and the Picker's API key travel in it so that one entry covers a refresh and a later pick. The access token is made in memory for each call and never stored. A token whose response reports no scope, or any scope but `drive.file`, is refused.

**The Picker page.** Google's Picker is a script and frames from Google's hosts, so it never runs inside the runtime's page (`default-src 'self'`; `interface/` loads nothing from another host). `gdrive_auth.py authorize` (once) and `gdrive_auth.py pick` (later, no new consent) serve it from a one-shot server (`gdrive_picker.py`); `gdrive.py pick` is the same command as a verb of the provider, which is how the runtime starts it: bound to 127.0.0.1 on a random port; every request must carry that exact `Host`; the way in is the start URL the command prints, `/start?k=<key>` (a random key, compared in constant time, served once: a request without it, or a second one, gets a bare 404 and learns neither the consent URL nor the nonce, so a local process that only knows the port reaches nothing); the OAuth callback is served once, only when it is shaped like one (`state` and `code` or `error`), and its state is compared in constant time; the page, the token and the picks need a nonce that /start gives only to the key's holder; a post must carry this server's own `Origin` (none is refused); it stops after the picks (or a cancel, a failure or 10 minutes). It sets no `script-src` policy, because the hosts the Picker needs cannot be checked offline; it sets `frame-ancestors 'none'`, no referrer and no caching.

**Setup, once.** The steps are in `uv run providers/documents/gdrive_auth.py --help`: a Google Cloud project with the Drive API and the Picker API enabled, the consent screen "In production" (in "Testing" the refresh token dies after seven days), the scope `drive.file` added, a Desktop app client, an API key with an API restriction to the Picker API only (no referrer restriction: the page sends none); then `uv run providers/documents/gdrive_auth.py authorize`, which asks for the client id, the client secret and the key at a hidden prompt (or reads `GDRIVE_CLIENT_ID`, `GDRIVE_CLIENT_SECRET` and `GDRIVE_PICKER_API_KEY` from the environment of that one command), and verify with `uv run providers/documents/gdrive.py --check`. In the project, `python3 runtime/cli.py source-drive --project <dir>` opens the Picker and registers each file as a source. On a shared machine run `uv run providers/documents/gdrive.py pick --no-browser` (or authorize with `--no-browser`) and paste the printed address into your own browser: `xdg-open` or `open` puts the address, with its one-use key, in the argument list of a process other users can see for a moment.

## OneDrive (`onedrive.py`)

`onedrive.py` serves the files a person chose in their own OneDrive as **sources** of a project (`runtime/sources.py`). Like the Drive provider it is an implementation of this class by its folder and its verbs, it is read only, and it declares `SOURCES_ONLY = True` (the contract tests of the class skip the write-and-read cases for it; its suites are `tests/test_documents_onedrive.py` and `tests/test_documents_onedrive_auth.py`, against the stand-in service `tests/fake_graph.py`). `stat` and `read` take `--as-source`; `comments`, `write`, `notice` and `resolve` answer "not supported" (exit 2). There is no picker: Microsoft's File Picker is a page on Microsoft's hosts that needs SharePoint-resource tokens, and under `Files.Read` it would narrow nothing; the runtime's page loads nothing from another host. The person chooses in the terminal with two read-only verbs, `search --query <text>` and `children --path <folder>`, which print up to 25 candidates (name, folder path, size, modified date, the `<drive id>/<item id>`) and register nothing; the runtime registers the ones the person names.

**One permission, and what it can do.** The authorization asks for the delegated Microsoft Graph permission `Files.Read` and `offline_access` (the refresh token), and nothing else; the refresh request names the same scope so that the access token is no wider than asked. Microsoft has no permission that is granted per chosen file on both account kinds, so **`Files.Read` lets the token read every file of the person's own OneDrive, not only the chosen ones, and it writes nothing.** The narrowing to the chosen files is the runtime's: only registered item ids are read, and no verb lists a folder for a run. Compared with the Drive provider's `drive.file`: wider in reach, narrower in power (read only). The provider refuses a token whose reported scope is anything but `Files.Read` (the `offline_access`, `openid`, `profile` and `email` it may report next to it grant no file access are ignored): a registration that still carries `User.Read`, or any `.All` or `ReadWrite` permission, is a setup error (exit 3, naming the extra scope), and so is a response that reports no scope. Rejected, with the reason: `Files.Read.All` (also SharePoint and shared files; excluded from user consent by Microsoft's default policy, so a work user needs an admin) is package O3 and waits for a real case; `Files.Read.Selected` is in preview, work and school only, and its access lasts hours; `Files.SelectedOperations.Selected` needs admin consent and a grant per file by someone with site rights; `Files.ReadWrite.AppFolder` reaches only the app's own folder (it is the scope of a later write-back, package O4, in a separate secret).

**What `read` does with each item.** It reads items of the person's own OneDrive that are files, and writes the bytes to `<out-dir>/content` (it never parses a file; the runtime hands the bytes to the converter, a container with no network, limit L27). OneDrive holds a file as it is, so `content` is always `file`, and the runtime reads its type from its bytes (PDF, Word, Excel, PowerPoint, HTML, CSV, text; any other type is refused by the intake).

| Item | Result |
|---|---|
| a file (DOCX, XLSX, PPTX, PDF, CSV, HTML, text, ...) | downloaded as it is |
| a folder | refused: "a folder is not a source: choose the files in it" |
| a package (a OneNote notebook) | refused |
| an item shared from another drive (`remoteItem`) | refused: outside `Files.Read` |
| an item with a `malware` facet, or a `deleted` facet | refused |
| a legacy Office file (`.doc`, `.xls`, `.ppt`) | refused: "save it as .docx, .xlsx or .pptx" (a remote conversion is not requested) |

`stat` describes any of them and says `supported: false` with the reason.

**Change detection.** `stat` returns `version`, the item's `cTag`, which Microsoft documents as changing when the **content** changes and not when only metadata does (a share, a rename); the `eTag` is printed as `etag` and is kept for a later write-back. A refresh asks `stat` first and reads the file only when `version` differs from the one recorded with the newest version of the source. After a download the item is read again: a changed cTag, or bytes whose length differs from the size Graph reported, refuse with "the file changed while it was read". The hash Graph offers (`quickXorHash`) is the only one on both account kinds and is not checked.

**The download.** Graph answers `GET /drives/{drive}/items/{item}/content` with a `302` to a preauthenticated URL that needs no Authorization header and may expire within minutes. A redirect is never followed automatically (no request with a credential follows one): the provider reads the `Location`, requires `https`, no user or password in it, the default port, and a host on a closed list (`files.1drv.com`, `sharepoint.com`, and subdomains of either), then fetches it with **no Authorization header and no cookie**, follows no further redirect and reads at most `--max-bytes + 1`. The address is a bearer credential: it is never printed, logged or stored, and an error names its host only. `size` is checked against the cap before the download. `--max-bytes` defaults to 25 MiB (the intake's cap) and is at most 256 MiB. A `429` or `503` is reported with its `Retry-After`; a verb never retries.

**Authorization and the secret.** `ONEDRIVE_SOURCES_TOKEN` is the one secret entry: a JSON record `{refresh_token, client_id, tenant, scope, account_kind, obtained_at}`, written to the OS secret store (service `openhora`, username `onedrive-sources`) by `onedrive_auth.py authorize`, or exported as the same JSON text in an environment or copied into the credentials directory. There is no client secret: the app is a public client. The flow is the authorization code flow with PKCE (S256) and a state, in the system browser, with a loopback redirect: the script listens on `127.0.0.1` (and `::1` on the same port when it can) on a random port, sends `redirect_uri=http://localhost:<port>`, accepts only a request whose `Host` is exactly `localhost:<port>` and that is shaped like a callback, compares the state in constant time, serves the callback once, logs no request line (it carries the code) and stops after the callback or after 10 minutes. The client id is read from `ONEDRIVE_CLIENT_ID` in the environment of the one command, or typed at a hidden prompt, never a flag; an office with its own single-tenant registration also sets `ONEDRIVE_TENANT`. `onedrive_auth.py forget` deletes the stored record (our own local record; it revokes nothing at Microsoft). A work or school tenant whose admin has blocked user consent answers with a consent error: the provider says "your Microsoft 365 admin must approve the app" and stops (exit 3).

**Rotation of the refresh token.** Microsoft replaces the refresh token on every use; the old one is not revoked and lives out its lifetime (90 days for this kind of client). When the record was found in the OS secret store, `onedrive.py` writes the new token back into that one record after a refresh (the one exception to "a provider never writes the store", `contracts/secrets.md` rule 1, decided 2026-10-17); when the write fails (a locked store, a headless machine) it carries on with the old token and says so on stderr. A record found in the environment or in the credentials directory is never rewritten, so it ages 90 days from the consent; `--check` prints `rotation` to say what happened. The refusal of an expired or revoked token (`invalid_grant`) is exit 3 with "run `onedrive_auth.py authorize` again".

**Test overrides.** `INTEGRATION_DOCUMENTS_ONEDRIVE_API_BASE`, `..._TOKEN_URL` and `..._DOWNLOAD_HOSTS` replace Graph, the token endpoint and the download-host list; they must name loopback addresses only, must all be set together, and in that mode the secret store is neither read nor written.

**Microsoft setup, once** (the project's maintainer, not each person; the steps are in `uv run providers/documents/onedrive_auth.py --help`). In the Microsoft Entra admin center: App registrations, New registration, supported account types "Accounts in any organizational directory and personal Microsoft accounts"; Authentication, Add a platform, "Mobile and desktop applications", custom redirect URI `http://localhost` (the port is ignored for localhost matching), no client secret, no certificate; API permissions: remove `User.Read`, add Microsoft Graph, Delegated, `Files.Read` (and `offline_access`), no admin consent for a personal test. Then `ONEDRIVE_CLIENT_ID=<the Application (client) ID> uv run providers/documents/onedrive_auth.py authorize`, sign in, and verify with `uv run providers/documents/onedrive.py --check`.

### To verify (the live step of the package; nothing here was run against Microsoft)

The tests use a stand-in service that serves what the plan's reading of the reference says, so each item below is a fact the stand-in encodes and the live service has not confirmed.

1. The download host suffixes. The list is `files.1drv.com` and `sharepoint.com`; a personal account's address may be on another host (the refusal names the host it saw, and the host seen is to be recorded here).
2. The `scope` string the token endpoint returns (with or without the `https://graph.microsoft.com/` prefix, and which of `offline_access`, `openid`, `profile`, `email` it adds); `scopes_of` strips the prefix, compares without case and ignores those four.
3. That `localhost` in the browser reaches the `127.0.0.1` listener (the listener also binds `::1` on the same port, when the machine has it, since a browser may resolve `localhost` to either).
4. That a work tenant that allows user consent lets the person consent to `Files.Read`, and the error codes of one that does not: the provider recognises the error `consent_required` or `interaction_required`, or the codes `AADSTS65001`, `AADSTS90094` and `AADSTS65004` in the description, only to say "your admin must approve the app"; the codes are from memory of the identity platform and were not read for this package.
5. Whether the refresh token really rotates on every use for both account kinds, and how long the unrotated token of a headless machine lives (the plan says 90 days from issue).
6. That `GET /me/drive?$select=id,driveType` answers under `Files.Read` for both account kinds, with `driveType` `personal` or `business` (a failure there stores the account kind as `unknown` and nothing else changes); that `$select` accepts the names the provider asks for on both kinds; and that the percent-encoded search text and the doubled quote in `search(q='...')` are understood.
7. That a `cTag` is present on every file of both account kinds (an item without one is refused: "a change of it cannot be told") and that it does not move when only metadata does.
8. The answer for an item shared from another drive (`remoteItem`) and for a legacy `.xls`/`.doc`/`.ppt` file under `Files.Read`, and whether `children` of a OneNote notebook or a Teams-linked folder lists what the provider expects.
