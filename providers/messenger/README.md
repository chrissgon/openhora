# Messenger providers

An implementation of the class `messenger:<platform>` (`contracts/environment.md`) connects a messaging app to the messaging bridge (`runtime/messaging.py`). The bridge has no model in it: it turns what a person sends into an operation of the operations layer and turns a pending decision into a card. A provider only moves messages. The platform is a parameter, handed to the script as `--platform`; the script declares the platforms it serves on one top-level line, `PLATFORMS = ("<platform>",)`, which `providers/resolve.py` reads as text.

The bridge reaches a provider through `providers/resolve.py` (`call("messenger:<platform>", verb, args)`): the variables `MESSENGER_<PLATFORM>_PROVIDER` then `MESSENGER_PROVIDER` choose among several, and one candidate is chosen on its own. Nothing in the bridge names an implementation. `messenger:<platform>` is a class the runtime uses, not one a skill may require, so it is on purpose not in the class table of `contracts/environment.md` (which skills copy).

## The four subcommands

JSON on stdout, diagnostics on stderr, input by flags or files, never a prompt, `--help`. Exit codes: 0 ok, 1 the service failed, 2 usage (also a message beyond the capabilities), 3 not configured (no credential, a credential the service rejects, a webhook set where polling is needed, another program reading the same bot's updates). The credential is read only through `providers/secrets/resolver.py` and never appears in an argument, a log, an output or a traceback.

| Subcommand | Prints |
|------------|--------|
| `capabilities --platform <p>` | `{"max_text": int, "buttons": bool, "max_buttons": int, "max_button_label": int, "lists": bool, "max_list_rows": int, "url_buttons": bool, "reply_context": bool, "documents": bool}` |
| `receive --platform <p> --offset <n> --timeout <s>` | `{"updates": [{"update_id", "sender", "chat", "private": bool, "text": str or null, "action": str or null, "action_ref": str or null, "reply_to": str or null, "forwarded": true (only when the platform marks the message as forwarded)}], "next_offset": n}` |
| `send --platform <p> --chat <id> --message-file <f>` | `{"message_id": str}` |
| `ack --platform <p> --action-ref <ref>` | `{"acked": true}` |

- `capabilities` has four optional keys, false (0 for a number) when left out: `listen` (below), `actions_need_reply` (the bridge acts on a typed approve, reject, release or answer only when the update's `reply_to` is the card of that decision in that chat; only the e-mail provider sets it), `attachments` (the provider maps a file a sender sends into the update's `attachments` and serves `fetch-attachment`; without it the bridge answers "This app's connection does not take files yet." and fetches nothing) and `max_attachment_bytes` (the most the platform serves for one file; 0 says none).
- `receive` waits up to `--timeout` seconds for an update (long polling where the platform has it). `action` is the id of a tapped button, `action_ref` what `ack` needs to acknowledge it, `reply_to` the platform's id of the message the person replied to, `sender` and `chat` strings, `private` true for a chat between the bot and one person. An update that is neither a text nor a tapped button is not returned, and `next_offset` still moves past it.
- An update may carry `"attachments": [{"ref", "name", "size", "type"}]` (at most 10; ATT-1): `ref` is a string of 1 to 512 characters, opaque to the bridge and enough for the provider to fetch the file by (never an address taken from the platform, never a credential); `name` the file's name or null; `size` the declared bytes (a whole number) or null; `type` a media type, or `photo`, `voice`, `video`, `audio`, `sticker`, or null. `text` is then the caption, or null. An invalid element drops the update (logged by class). The bridge refuses a medium, a declared size over the cap and every file the project's policy does not take before it asks for a byte.
- `send` reads the neutral message from the file: `{"text": str, "actions": [{"id": str, "label": str}], "link": {"label", "url"} | null, "document": {"name", "text"} | null}`. The provider renders it with the means of its platform and prints the id of the message that carries the text (a document is sent after it, as a reply to it). The text is Markdown, as the agents write it. A provider renders the subset its platform can show, with everything escaped first so that text from a project can never become markup, or sends it plain. The provider refuses (exit 2) a message beyond its capabilities; the bridge never sends one, because it reads `capabilities` first and folds what does not fit into typed-command lines (`Send /approve 12`).
- `fetch-attachment --platform <p> --ref <ref> --out <dir> --max-bytes <n>` (only a provider that declares `attachments`; ATT-1) writes the file as `<dir>/content` (created with `O_EXCL|O_NOFOLLOW`, mode 0600, in the folder the bridge made) and prints `{"bytes": int, "sha256": str}`. It never fetches an address taken from an update: it builds the address from ids it validated with a closed pattern and a fixed base, over HTTPS, to the platform's own hosts, follows no redirect but the ones its README names, sends no credential to a content host that does not need one, counts the bytes while it streams and stops over `--max-bytes`, and checks a hash the platform declared. Exit 2: usage or over the cap; 1: failed; 3: not configured. A reference the platform no longer serves is **exit 1 and the last non-empty line of stderr exactly `gone`** (the resolver gives the bridge a failed verb's stderr and not its stdout, and `ProviderCallError.stderr_last` is that last line; nothing else is read as `gone`: a message that merely contains the word, or has it on an earlier line, is an ordinary failure). Write a detail on an earlier line if you like. The bridge checks the file against the answer.
- A message also carries `"footer": [str]` when the platform declares `actions_need_reply`: the lines `text` ends with (the typed commands, the hash line), named by the bridge so that a provider (e-mail) can move them up without guessing where they start.
- `ack` acknowledges a tapped button where the platform needs it.

`send` has no `--confirmed` and no idempotency key, which `providers/CONTRACT.md` asks of other verbs that send: the bridge is the only caller, sends only to a chat of the project's accepted `messaging.senders` list, and keeps its own record (the ledger of `runtime/messaging_ledger.py`) of what it sent.

## The listen mode

Some platforms cannot be served one process per verb: a gateway that must stay connected (it delivers button taps only on its open connection, and limits how often a client may connect), or a client that holds one live session that both receives and sends. A provider of such a platform declares `"listen": true` in `capabilities` (absent means false; Telegram leaves it out) and implements a fifth subcommand, `listen --platform <p>`. The bridge starts it once (`providers/resolve.py` `start`) and keeps it; it still reads `capabilities` first, through the ordinary one-shot verb. `receive`, `send` and `ack` are never called on it: `receive`'s offsets do not apply (the provider resumes on its own after a restart), and there is no `ack`.

The process runs until its standard input ends or it receives SIGTERM, and it must exit **within 5 seconds of the end of its standard input**: it runs in a session of its own, so the kill of the bridge never reaches it, and the end of its stdin is what stops it. Protocol: JSON lines on binary standard input and output, one object per line, UTF-8, written with `json.dumps(..., ensure_ascii=True)` and a newline, flushed after every line, at most 1 MiB per line (a longer line is dropped by the reader).

| The bridge writes (stdin) | |
|---|---|
| `{"id": <int>, "op": "send", "chat": <str>, "message": <the neutral message>}` | ids count up across restarts; the provider answers each |

| The provider writes (stdout) | |
|---|---|
| `{"event": "ready"}` | once connected; the bridge sends nothing before it, and accepts it again after a reconnect the provider made itself. Not within 180 s of the start counts as a crash |
| `{"event": "update", "update": {...}}` | the shape of one element of `receive`'s `updates`; `private` is true, `sender` and `chat` are non-empty strings and **`chat` equals `sender`** (the bridge requires it for a private chat and sends each card to the chat of every listed sender: a platform whose direct-message channel has an id of its own, Discord, reports the person's id as `chat` and opens the channel itself when it sends), `text`, `action` and `reply_to` are a string or null, and `forwarded` is there only for a forward (see "Forwarded messages"). A tapped button is acknowledged **by the provider, at once, before it emits the update**, which carries `action_ref: null` (the bridge writes nothing back for a tap). An update that is not valid is dropped and logged by class |
| `{"id": <int>, "ok": true, "message_id": <str>}` | the answer to a send |
| `{"id": <int>, "ok": false, "kind": "usage" \| "not-configured" \| "failed" \| "deferred", "reason": <str>}` | a send that failed; the reason is redacted. `deferred` is not an error: the platform cannot take the message now (the official WhatsApp API outside its 24-hour window), the bridge records no card for it, offers it again at the next notice period and at once when the person writes, and logs one line for a card at most every 24 hours |
| `{"event": "error", "kind": "usage" \| "not-configured" \| "failed" \| "paused" \| "skipped", "reason": <str>}` | a connection problem it is retrying itself, or, before exit 2 or 3, the reason the bridge shows. `paused` is for a session that only the person can mend (a logged-out device): the provider exits 3 after it and the bridge waits and asks again instead of stopping (below). `skipped` is a message the provider gave up and nothing was done with (the e-mail provider, after the server refused it for an hour): it is not the state of the connection, the reason is never stored, logged or forwarded, and the bridge tells the listed senders its "N more waiting" line goes to one sentence of its own, at most once an hour to a chat. Write it for a message that was refused or pushed out, never for an exception on one message (that is a log line, never an event). It can be written before the sender of the message is known, so whoever can make the server refuse a FETCH can cause at most one fixed line an hour per chat, which carries nothing of theirs |

A provider that declares `attachments` also answers one more request, `{"id": <int>, "op": "fetch", "ref": <str>, "out": <dir>, "max_bytes": <int>}`, with `{"id": <int>, "ok": true, "bytes": <int>, "sha256": <str>}` after it wrote `<out>/content` as `fetch-attachment` does, or the failure line of a send, whose `kind` may also be `gone` (a reference the platform no longer serves). The bridge waits up to 150 seconds for the answer; a fetch runs beside the sends.

Nothing else is ever written to stdout. Diagnostics go to stderr, never a token, a message text or a sender id; the bridge keeps only the last 300 characters of stderr and uses them only when no error event gave a reason; that tail, like an error event's reason, may be shown to the person after the repository's credential redaction (`scripts/redact.py`), so write nothing there you would not want shown. Exit codes as for every verb: 3 not configured (no token or session, a credential refused), 2 usage, 1 anything else. Exit 2 or 3 stops the bridge with the reason of the last error event, **except exit 3 right after an error event of kind `paused`**: then the bridge logs the reason, waits 5 minutes (a close interrupts the wait) and starts the provider again, without counting that start against the ceiling below and without changing the backoff; while the provider stays paused the line is written again every 24 hours (never an id), and again once it has been connected in between. Cards wait as they do for any provider that is not ready. Any other exit is started again after a backoff (1, 2, 4 ... up to 300 s, and at most 200 starts per 24 hours for each bridge process, after which the bridge stops: a platform may reset a credential that connects too often).

Rules for an implementation:

- At the start, duplicate fd 1 for the protocol and point fd 1 at stderr (`os.dup2(2, 1)`), so that a library's `print` cannot corrupt a line. Flush after every line. Never call `setsid`: the bridge already started the process in its own session and stops it by that group.
- Interactive pairing (a QR code, a pairing code) is a separate verb the person runs in a terminal, never inside `listen`. `listen` without a session, or after a logout, writes the error event, of kind `paused`, with a sentence that names the pairing command and exits 3.
- **Delivery is at least once.** A send in flight when the provider dies fails; the card is sent again after the next `ready`, and the first copy, if it was delivered, has buttons the ledger has no record of, which answer the stale-button sentence.
- Stdout carries the protocol and nothing else, in either direction; a provider treats a line from the bridge that it cannot parse as a usage error of that request.

The stand-in used by the tests is `runtime/tests/fixtures/messenger_listen_standin.py`. The listen providers are `discord.py`, `email-imap.py`, `whatsapp.py`, `whatsapp-cloud.py` and `whatsapp-twilio.py` (below); a provider whose dependencies matter commits a hash lock (`providers/CONTRACT.md`).

## Who a sender is, and how far to trust it

The bridge compares `sender`, the id the provider printed in an update, with the project's `messaging.senders.<platform>`, and a listed sender may have a profile of their own (`policies`, `docs/architecture/platform/messaging.md`): the owner's phone may approve and an employee's may only read and answer. What an id proves is whoever controls that account at that moment, and nothing more.

| Platform | The id the bridge compares | Set by | Another user can forge it? | Weak points |
|----------|----------------------------|--------|----------------------------|-------------|
| Telegram | the numeric user id (`from.id`) | Telegram's servers | no | the account itself (a SIM swap, an open session) |
| Discord | the user's id (a snowflake), in a direct message | Discord's gateway | no | the account itself, an open client |
| WhatsApp, linked device | the phone digits of the sender as the linked device sees them (`whoami` prints them); a hidden address (LID) is resolved to the digits, and a message whose sender cannot be resolved is dropped (`providers/messenger/whatsapp/inbound.go`, `senderDigits`) | WhatsApp, read by the person's own device | no | the phone |
| WhatsApp Cloud API | phone digits; a business-scoped id mapped to digits (`identities.json`) and dropped when it is not mapped | Meta, signed by HMAC | no | the phone |
| WhatsApp through Twilio | the `From` digits; a business-scoped id (a username) is mapped to digits through the pairs the provider learned, and dropped when it is not | Twilio, signed (`X-Twilio-Signature`) | no | the phone |
| E-mail | the From address of a message the receiving server's own authentication accepted for that From domain (`email-imap.py`, "Who is admitted"; an address is the sender id, up to 254 characters) | the sender's mail domain and the receiving server (SPF, DKIM or DMARC, read from the topmost `Authentication-Results` of the configured id) | no, unless the sender's domain or the receiving server is compromised | the mailbox of the sender (a stolen password, a forwarding rule), a domain without authentication |

A shared or unlocked phone, a stolen session file, a SIM swap or a phone number a carrier gave to someone else all inherit the profile, and code cannot see any of them. Give a profile with effect grants only to an account on a phone with a lock and an app lock, and remove a person's entry the day they leave. The id stays on the rows of the store that were written while the entry was there, and in no file of the project.

## Forwarded messages

A message the person **forwarded** is never a request (package FWD): the update carries `"forwarded": true`, and the bridge answers it with one sentence and acts on nothing in it (`runtime/messaging_inbound.py`, `runtime/messaging_bridge.py`; the key is absent for any other message). A provider sets the key only for the marks below, from the platform's own field, never from the words of the text. The bridge reads the key with the rule `absent` or `false` is no and any other value is yes (`messaging_provider.forwarded_of`: an unreadable mark fails closed). A **file** that is forwarded stays an update with `attachments` and `forwarded`: its card opens as any file's does (a standing grant that adds files without a card never applies to it), and the words sent with it never name a source or preselect a save. A reply or a quote is the person's own text and is never marked.

| Provider | What marks a forward | What does not |
|---|---|---|
| Telegram | `forward_origin` (Bot API 7.0 and later), the older `forward_from`, `forward_from_chat`, `forward_sender_name` and `forward_date`, or `is_automatic_forward: true`; a field present with any value but null counts | `quote`, `external_reply` and `reply_to_message` alone |
| Discord | `message_reference.type` 1 (FORWARD), a non-empty `message_snapshots`, or the `HAS_SNAPSHOT` flag (`1 << 14`). A forward holds its words in the snapshot, which is never read: the update has `text` null | `message_reference.type` 0 (a reply) |
| WhatsApp (unofficial client) | `ContextInfo.IsForwarded`, or a `ForwardingScore` above 0, on the extended text, document, image, video, round video, audio or sticker message | a plain conversation message; a context that holds only a quoted id |
| WhatsApp Cloud API | `context.forwarded` (forwarded five times or fewer) or `context.frequently_forwarded` (more than five), documented at developers.facebook.com, "Incoming message webhooks" | a `context` that holds only `id` (a reply) |
| WhatsApp through Twilio | the inbound webhook's `Forwarded` (`true` if forwarded once) or `FrequentlyForwarded`, documented at twilio.com/docs/messaging/guides/webhook-request; absent, empty, `false` and `0` are not a forward, any other value is. **Twilio is not forward-blind** | `OriginalRepliedMessageSid` (a reply) |
| E-mail | a Subject that starts with a forward prefix, case-insensitively and after any number of reply prefixes (`Re`, `Aw`, `Res`, `Sv`, `R`, `Rif`): `Fwd`, `Fw`, `Enc`, `Rv`, `Tr`, `Wg`, `I`, `Vs`, with an optional `[n]`, then a colon (`Info:` and `Invoice:` are not); a line of the body that is a forward marker of a mail client in English, Portuguese, Spanish, French, German or Italian; or an attached message (`message/rfc822`). A forward by subject is not read further: the update has `text` null | a marker inside a quoted line (`>`) or an HTML `blockquote`, and an ordinary `Re:` |

A platform with no field for it would be declared forward-blind in its section here and in `capabilities` (`"forward_blind": true`); none is today. What no provider can see (an e-mail forwarded by a client that writes no prefix and no marker, with the text pasted) is the residue the card guards: it is read as the person's own words, and only a card of its exact content can follow.

## Adding a platform

Add one file, `providers/messenger/<impl>.py`, that declares `PLATFORMS` and implements the four subcommands as above, and register its credential in `providers/secrets/resolver.py` and `contracts/secrets.md`. Nothing in the bridge changes: the platform's name goes in `runtime.json` (`messaging.senders.<platform>`) and on the bridge's `--platform` flag. Tests are offline, in `providers/messenger/tests/`, with the network patched out.

## Running several platforms

One local service starts several bridges: `uv run --with keyring==25.7.0 python3 runtime/service.py --project <dir> --messaging telegram,whatsapp-twilio` (a comma list, or the option repeated; at most 6 platforms, none twice). Each platform gets its own bridge child with its own lock and ledger ("The messaging bridge" of `contracts/runtime.md`).

- **Cards go to every app.** Each bridge sends its own card for what waits for the person, so each app gets one. A decision resolved in one app is refused in the others, with the operation's own refusal; nothing runs twice. Conversations are per app.
- **One router, two bridges.** The bridges are separate processes and share the project's file locks, so writing in two apps at the same moment may answer "busy" in one of them; send the line again.
- **Ports.** `whatsapp-cloud` and `whatsapp-twilio` both listen on port 8787 unless `setup` is given another. The service cannot see the providers' settings, so when you run both, give each its own port: `setup ... --port 8787` for one and `setup ... --port 8788` for the other (then expose each port at your public address). A bridge whose provider cannot bind its port exits with a reason on the service's standard error, named with its platform; the other bridges keep running.
- **One exit does not stop the rest.** Each child's exit is reported with its platform; the others keep running until the service stops, which stops all of them together.

## Telegram

`telegram.py` serves `telegram` with the Bot API over HTTPS and the standard library: `getUpdates` long polling (never a webhook; a `409` of `getUpdates` is told in two: one whose description says another `getUpdates` request terminated this one gets the sentence that another program is reading this bot's updates (a second bridge, or another tool with the same token); any other, the one that tells the person to remove the webhook; both exit 3, since the provider has no exit 4), `sendMessage` with an inline keyboard (the action ids are the buttons' `callback_data`, at most 64 bytes), a URL button for the link, `sendDocument` for a document, `answerCallbackQuery` for `ack`. **Rendering.** `send` converts the Markdown of the text to Telegram's HTML parse mode (`render_html`): the text is split into fenced blocks, table lines and `> ` quote runs on the raw text (a fence that never closes is ordinary text), everything else is escaped with `html.escape` before any mark is applied, and then `# ` headings become bold, `- ` and `* ` bullets a dot (the indent stays), `**x**` bold, `~~x~~` strike, `` `x` `` code, fences and tables `<pre>`, quote runs `<blockquote>`. Single-mark italics (`*x*`, `_x_`) are not rendered, because paths, globs and `snake_case` are common in the agents' text. A link `[text](url)` is shown as `text (url)`, never as an anchor, so the person sees where it points. Marks never cross a line, a code span or each other; a mark with no closer stays literal; the only tags are `b`, `s`, `code`, `pre` and `blockquote`. The visible text is never longer than the raw text, which `check_message` caps at 4096. Link previews are off on every message. When Telegram answers 400 "can't parse entities", the same message is sent once more as plain text with the same keyboard, and one line (never the text) goes to stderr; a text with nothing to show once rendered is sent plain from the start. Button labels and documents are not rendered. Telegram counts the offsets of formatting in UTF-16 units and Python counts code points; the provider does not build for that, since it writes tags and no offsets. The token is the secret `MESSENGER_TELEGRAM_BOT_TOKEN` (store username `messenger-telegram`): a bot created for the person, used only by this bridge. Telegram carries the token in the request path, so every error is built from the class of the exception, the HTTP status and the service's own description, with anything shaped like a token removed. A chat with a bot is not end-to-end encrypted: what the person writes and every notice that carries text passes Telegram's servers.

**Files (ATT-2).** The provider declares `attachments` and `max_attachment_bytes` 20971520 (20 MiB: the Bot API serves a download of at most 20 MB, and `getFile` answers "file is too big" above it, which the provider turns into a usage refusal, exit 2). A message with a `document`, `photo`, `voice`, `video`, `video_note`, `audio` or `sticker` becomes an update with `attachments: [{ref, name, size, type}]`: `ref` is the `file_id` (a closed pattern, `[A-Za-z0-9_-]{1,200}`: anything else is not mapped), `name` the document's, video's or audio's `file_name`, `size` the declared `file_size`, `type` the document's media type, else `photo` (the largest size Telegram made), `voice`, `video` (also a video note), `audio` or `sticker`. `text` is the `caption`, read only beside a file: a caption of a message the provider does not map stays unread. `fetch-attachment --platform telegram --ref <file_id> --out <dir> --max-bytes <n>` calls `getFile`, checks the answered `file_size` against the cap, checks the answered `file_path` against a closed pattern (relative segments of letters, digits, `_`, `-` and inner dots, none starting with a dot, at most 200 characters), builds `https://api.telegram.org/file/bot<token>/<file_path>` from the fixed base (a second check that the address is https on that host, with no credentials and the default port; the one in the path is the same token every call carries), and downloads it with the same opener that follows **no redirect** (a redirect, off the host or not, is an error that names no address). The whole fetch has a deadline of 120 s, checked before each read (10 s to connect and for each wait, so one read can add at most that; reads are `read1`, which returns what one socket read gave, so a host that drips a byte at a time cannot outlive the deadline); the bytes are counted while they stream, in reads of at most 64 KiB, and a file over `--max-bytes` (or a `Content-Length` over it, checked before the first read) is exit 2 with nothing left; a body shorter than its `Content-Length` is exit 1. The file is written as `<out>/content`, created by descriptor inside the folder opened without following a link, with `O_EXCL` and `O_NOFOLLOW`, mode 0600; a file that fails is removed. No name from Telegram is ever a path. The answer is `{"bytes", "sha256"}` (Telegram declares no hash). A `file_id` Telegram no longer knows (a 400 whose description names `file_id`) or a file path that answers 404 is exit 1 with stderr `Telegram no longer serves this file` and then the line `gone` alone as the last line (the bridge matches the last non-empty line of stderr exactly, as the contract above says). Every error is built from a class, a status and Telegram's own description with the token removed, and `http.client.HTTPException` and `ValueError` are caught where the body is read, so a cut stream or a bad status line names only its class; nothing prints a traceback. Facts about `getFile`, the 20 MB limit and the file path are written from the documented behaviour of the Bot API and **were not re-read when ATT-2 was built** (no network): **to be confirmed in the live test**. Tests, all offline with a fake opener and two loopback servers for a real redirect and a real download (`providers/messenger/tests/test_telegram_attachments.py`): the mapping of each type and of the caption, the cap before and during the download, a gone file, a file path that is not a plain relative path, an address off the host, a redirect refused, the output folder and file, and the token absent from every failure.

**Live test (the maintainer's; this package ran no network).** With the bridge running on a project whose profile has `add-sources`: send a PDF and a Word document from the personal account (each becomes a card; add one by tap and one by `/add`), send a photo, a voice note and a sticker (each is refused with the media sentence before a byte is fetched), send a file over 20 MB (refused at the platform or by the cap), send the same PDF twice (already waiting), and forward an old file after deleting it from the chat (the "can no longer be fetched" sentence). Check that `<data>/attachments/incoming` is empty afterwards and that no sender id is in the source's manifest.

## Discord

`discord.py` serves `discord` with buttons, through Discord's Gateway, and only in the listen mode (`receive`, `send` and `ack` exit 2 with "discord works only in listen mode"). It uses the standard library for HTTP and the `websockets` library (pinned in the script's header, imported only where the Gateway opens, and **hash-locked** in `discord.py.lock`, which `providers/resolve.py` honours by starting the script with `uv run --locked`). No port is opened on the machine. Sources, all read on 2026-10-12: docs.discord.com/developers/events/gateway, .../interactions/receiving-and-responding, .../resources/message, .../resources/user, .../components/reference, .../reference, .../topics/rate-limits and .../topics/opcodes-and-status-codes.

**Setup**, once per person (nothing here is done by the bridge):

1. In the Discord developer portal create an application and, in its Bot page, a bot. Turn **off "Public Bot"** and use a **guild install** only (so nobody else can add the bot anywhere). No privileged intent is needed: the provider asks for direct messages only.
2. Copy the bot's token and store it: `uv run --with keyring==25.7.0 keyring set openhora messenger-discord` (or export `MESSENGER_DISCORD_BOT_TOKEN`). Check it with `uv run providers/messenger/discord.py --check --platform discord` (exit 0 ready, 3 not configured).
3. Create a private server (only you in it) and invite the bot with no permissions at all (the invite link's `permissions=0`). Open a direct message with the bot from the server's member list.
4. Find your user id: turn on Developer Mode (User Settings, Advanced), then right-click your name and choose "Copy User ID". Put it in `messaging.senders.discord` of the project's `docs/workbench/runtime.json` and run `accept-config` in the terminal. Start the bridge with `--platform discord`.

A bot can message a person only when they share a server with it (or the application is installed to the person's account), and the person allows direct messages from that server's members. When it cannot, Discord answers HTTP 403 (error 50007) and the send fails with a sentence that says so; the bridge keeps running. Whether the bot can open a DM with a person it shares only a private server with, and whether the "installed to the person" route is needed, is **to be confirmed in the live test**.

**What it does.** One process holds the Gateway connection: Hello, Identify with the intent `DIRECT_MESSAGES` (`1 << 12`) only, heartbeats at the interval times a random jitter and then every interval (a heartbeat with no acknowledgement before the next is due means a zombied connection), op 1 answered with a heartbeat at once, Resume through `resume_gateway_url` after a dropped connection, op 7 or a missing acknowledgement (the connection is closed with code 4000, never 1000 or 1001, which invalidate the session), op 9 (not resumable: wait 1 to 5 seconds and Identify again). Identify is limited by Discord to 1000 per 24 hours, and passing it resets the bot's token: the provider sends at most one Identify in 5 seconds, reads `session_start_limit.remaining` from `GET /gateway/bot` before each Identify, and below 50 writes an error event and exits 3. Close codes 4004 (authentication failed) and 4014 (disallowed intents) exit 3; 4010 to 4013 exit 2; 4007 and 4009 start a new Identify; the others in 4000 to 4009 resume. A Gateway it cannot reach is retried by the provider itself (1, 2, 4 ... 60 seconds) with an error event of kind `failed`. The Gateway and resume URLs must be `wss://` on a `discord.gg` host; the `websockets` logger stays at WARNING (DEBUG logs the Identify frame). No HTTP redirect is followed (urllib would forward the `Authorization` header).

A message in a direct message with the bot, from a person, of type 0 (default) or 19 (reply), becomes an update with `chat` and `sender` both the person's **user id**, never the DM channel id; `reply_to` comes only from a reply (`message_reference.type` 0), never from a forward, and a forward is an update with `forwarded` true (see "Forwarded messages"). A message in a server, from a bot, from a webhook or with neither text nor a file is ignored (a message with files is an update whose `attachments` list them and whose `text` is the content, or null; see "Files" below). A tap on a button (an `INTERACTION_CREATE` of type 3, `context` 1, the person in `user`, not `member`) is answered at once with callback type 6 (`DEFERRED_UPDATE_MESSAGE`, which changes nothing the person sees; Discord wants a first response within 3 seconds), and then becomes an update with `action` the button's `custom_id`, `text` null and `reply_to` the message that carried the button. A failed callback is logged by class and the update is still written. Threads: one for the Gateway (heartbeats and the callback run inline there), one worker for sends (a send never blocks the Gateway), one worker for fetches of files (so a download never holds a send), one reader of standard input; one lock on the protocol descriptor. A 429 waits Discord's `retry_after` (at most 30 seconds, once per request), then the request fails.

**Sending.** The DM channel of a person is opened with `POST /users/@me/channels` and cached. Each message carries `allowed_mentions: {"parse": []}` (nothing can ping anyone) and the no-embeds flag (4), so links show no preview. The actions are one action row of up to 5 buttons (the first primary, the others secondary, the action id as `custom_id`, labels cut to 80 characters); the link is a link button in a row of its own; a reply is a `message_reference` with `fail_if_not_exists` false; a document is sent in the same message as a `.txt` file (multipart with `payload_json` and `files[0]`, named from the document's name). The provider declares `max_text` 1900, below Discord's 2000, so that rendering has room. A 403 answers the request (`ok` false, kind `failed`, a sentence about sharing a server and allowing direct messages) and nothing stops; a 401 writes an error event of kind `not-configured` and exits 3.

**Files (ATT-2).** The provider declares `attachments` and `max_attachment_bytes` 26214400 (25 MiB: Discord states no download limit for a bot, so this is the most the bridge takes for a source). A direct message with `attachments[]` becomes an update with `attachments: [{ref, name, size, type}]`: `ref` is `<channel id>:<message id>:<attachment id>` made of ASCII digits only (a Unicode digit is not one; the signed address is never put in an update), `name` the `filename` cut to 255 characters, `size` the declared `size`, `type` the `content_type`; at most 10; `text` is the message's content, or null when it is blank. The listen request `{"id", "op": "fetch", "ref", "out", "max_bytes"}` is answered `{"id", "ok": true, "bytes", "sha256"}` or a failure line (kinds `usage`, `failed`, `not-configured`, `gone`). A fetch reads the message again (`GET /channels/<channel>/messages/<message>`, with the bot token, to `discord.com/api` only, with the 429 wait the sends have) for a **fresh signed address**, picks the attachment by its id, refuses it when its declared `size` is over `max_bytes`, and checks that the address is **https on `cdn.discordapp.com` or `media.discordapp.net`**, with no credentials in it and the default port; any other host is a `failed` answer and nothing is requested. The download goes through `CDN_OPENER`, a separate opener that follows **no redirect**, with **no `Authorization` header** (only a `User-Agent`): the bot token never reaches a content host, and a 401 or 403 from one is the file's, never the bot's (a 401 on the message read is the token refused and stops the process with exit 3, like a send's). The whole fetch has a deadline of 120 s, checked before each read (a read is `read1`, so a host that drips a byte at a time cannot outlive it by more than the 10 s socket wait); the bytes are counted while they stream (reads of at most 64 KiB; a file over `max_bytes`, or a `Content-Length` over it, is a `usage` answer with nothing left; a body shorter than its `Content-Length` fails). The file is `<out>/content`, created by descriptor inside the folder opened without following a link, with `O_EXCL` and `O_NOFOLLOW`, mode 0600; a file that fails is removed; a name is never a path. A message or channel Discord no longer has (404), an attachment the message no longer lists, or a file the content host answers 404 or 410 for, is kind `gone`. `http.client.HTTPException` and `ValueError` are caught where a body is read, and every reason goes through `redact`. The facts about the message read, the signed address and the hosts are written from the documented behaviour and **were not re-read when ATT-2 was built** (no network): **to be confirmed in the live test**.

**Live test (the maintainer's; this package ran no network).** With the bridge running on a project whose profile has `add-sources`: send a PDF and a Word document in a direct message with the bot (one added by tap, one by `/add`), a photo and a voice message (refused as media), a file over 25 MiB with Nitro (refused by the cap), a message with three files (each a card), a file whose message is deleted before the card is answered (the "can no longer be fetched" sentence), and check the address in a debug capture of the content host's request: no `Authorization` header.

**Rendering.** Discord renders Markdown itself, so `render_discord` keeps the text and makes it safe, **outside code spans and fenced blocks only** (the effect command card's code span stays byte for byte): a masked link in any form (`[text](url)`, `[text](<url>)`, `[text](url "title")`) becomes `text (url)` so the person sees where it points, and a stray `](` is escaped; the openers `<@`, `<#`, `<t:`, `<:`, `<a:`, `</` and `<id:` (a mention, a channel, a timestamp, an emoji, a command, a guild link) get a backslash, unless already escaped; `||` (a spoiler can hide part of a decision) is escaped; a run of table lines is put in a fenced block; headers and `-#` subtext stay. `@everyone` and `@here` stay as text, because no ping is possible. A fence that never closes is shown as text. If the rendered text is over 2000 characters, the raw text goes out unrendered (the bridge has cut it to 1900).

**Privacy.** Discord direct messages are not end-to-end encrypted: what the bridge sends (every notice in `text` mode, every reply) passes Discord's servers. The token is the secret `MESSENGER_DISCORD_BOT_TOKEN` (store username `messenger-discord`): a bot of an application created for the person, used only by this bridge, with no server permissions. It appears only in the `Authorization` header and in the Identify payload, never in an argument, a log, an output or an exception; every error path masks the exact token, anything shaped like a Discord token and an interaction's token.

**Tests** (`providers/messenger/tests/test_discord.py`, `test_discord_attachments.py` (the mapping and the `fetch` op: the types, the caption, the ids, the host allow-list, a redirect refused, no `Authorization` header to the content host, the cap mid-stream, a gone message, the token absent from every answer), `test_discord_lock.py`) run offline with the Gateway as a state machine over a fake clock, a fake transport and a fake opener; the library is never imported. **To change the dependency**, edit the header and run `uv lock --script providers/messenger/discord.py` (it asks PyPI) and commit the new lock; `uv lock --check --script providers/messenger/discord.py` says whether it is current.

## E-mail

`email-imap.py` serves `email` through **a dedicated mailbox**: the address of the assistant (`assistant@office.example`), made for the bridge and never a person's own inbox (a person's inbox is a source for `reader:email`, not a channel). The listed senders write to it from their own addresses, and the bridge writes back to them. Standard library only (`imaplib`, `smtplib`, `email`); any mailbox with IMAP, SMTP and a password works, an app password where the host requires one. It works only in the listen mode (`receive`, `send` and `ack` exit 2). The Gmail API (OAuth) would be a second implementation of the same platform later.

**Setup**, once, by the person (nothing here is done by the bridge):

1. Make the mailbox and an app password for it. Check that its server writes an `Authentication-Results` header on the messages it receives (every large host does; a small server needs `opendkim` and `opendmarc`, or equal). Without that header the channel cannot tell a forged sender, and it drops every message.
2. Store the password: `uv run --with keyring==25.7.0 keyring set openhora messenger-email` (or export `MESSENGER_EMAIL_PASSWORD`).
3. `python3 providers/messenger/email-imap.py setup --platform email --address assistant@office.example --imap-host imap.office.example --smtp-host smtp.office.example` (ports 993 and 587 by default; `--username` when it is not the address; `--poll-seconds`, at least 15, default 30). This writes `settings.json` (no secret). Without `--authserv-id` it prints the ids on the newest messages' headers (log in once, read only) and picks none: run it again with `--authserv-id <the id your server writes first in Authentication-Results>`.
4. `python3 providers/messenger/email-imap.py --check --platform email` logs in to both servers and exits 3 unless the topmost Authentication-Results header of each of the newest messages has that id (a header lower down may be one a sender wrote).
5. Put the sender addresses in `messaging.senders.email` of the project's `docs/workbench/runtime.json` (lower case) and run `accept-config` in the terminal. Start the bridge with `--platform email`.

**Who is admitted.** The provider emits an update only when ALL hold: the **topmost** `Authentication-Results` header with the configured id (the receiving server's own; a header of another id, or lower down, is ignored, since anyone can add one) holds **exactly one** DMARC result and it is `dmarc=pass` with a `header.from` that **equals** the From domain (no organisational-domain guess; neither DKIM alone nor SPF admits; no header, no admission; a header with a double quote inside a comment is not read); there is one plain From address, a `Sender` equal to it, no `Resent-*`, and it is not the mailbox's own; the mailbox is the only recipient in To and Cc; the message is not automatic (`Auto-Submitted` other than `no`, `Precedence` bulk, list or junk, `List-Id`, `List-Unsubscribe`, a delivery report); it is under 1 MiB; and the sender has sent fewer than 30 in the last hour, and, when the provider has never written to that address, its From domain fewer than 120 (a person it writes to is not locked out by strangers at a shared webmail domain; a listed sender the bridge has never written to counts under the domain's budget until the first card reaches them, which the bridge sends at its next notice for any open decision); both are counted before the text is made. A message that is a bounce (`MAILER-DAEMON` or `postmaster` as the sender, `Return-Path: <>`) or carries `X-Autoreply`, `X-Autorespond` or `List-Post` is automatic. A message the server will not give (a FETCH it refuses while the connection is alive) is tried again at every poll and the messages after it are read; at most 200 such messages are kept (the oldest is given up, with a log line); after three failures spread over an hour it is skipped. The provider then writes an error event of kind `skipped` (also when the oldest of the 200 is given up); **the bridge counts it and messages the listed senders** its "N more waiting" line goes to (those whose profile reads what waits and is not `notices: actionable`) one fixed sentence: a message sent to the channel could not be read and was set aside, nothing was done with it, send it again if it was theirs. That is at most one line an hour to a chat, with the count of what happened in between, and only to a sender who still hears the count when the line goes out (the policy is read again then: a sender removed, narrowed to `notices: actionable` or no longer allowed to read is not told); a line that failed to send is tried again an hour later; it names no uid, Message-ID, address or subject, and the provider's reason is not forwarded. The count of what a chat has not yet been told is kept in memory: a restart of the bridge loses it (the bridge's log line stays). An unexpected exception on one message (a message a stranger who passes DMARC for their own domain could craft) writes no event, only a log line, so nobody is messaged about it: look at the bridge's log, and at the mailbox for a message the channel never answered. A lost connection is never counted against a message. The cheap checks come first (sizes of the address headers, the From, the authentication) and the text last, because anyone whose own domain passes authentication reaches this far, whoever they are. A header over 16 KiB, a header block over 64 KiB, or an address header over 2,000 characters is dropped as `size` before any header is read (a References header of several hundred ids would be one). The body is parsed only in the budgeted child, together with the HTML: a part with tens of thousands of parameters in its Content-Type costs one 3-second budget, and the message is dropped as `slow`. A message that fails is dropped with one log line by class (`size`, `sender`, `self`, `not-private`, `automatic`, `unauthenticated`, `unparsable`, `empty`, `slow`, `rate`, `unreadable`) and **no reply**, so the channel creates no backscatter and the log holds no address, subject or text. The bridge then drops a sender that is not in the list.

**What an update is.** The `text/plain` part, else the text of the HTML part with its hidden text, scripts, styles and quoted blocks left out (HTML is never rendered, a link never followed, an attachment never opened; the text of an HTML part is made by a short-lived child process with a 3-second budget, because the standard library's HTML parser can take time that grows with the square of the input, and a part over 200,000 characters is not tried: the message is dropped as `slow`). Hidden text is removed when the `hidden` attribute or an inline style hides it (`display:none`, `visibility:hidden`, `mso-hide:all`, `opacity:0`, a zero `width`, `height`, `max-width` or `max-height` with `overflow:hidden`, or a zero `font-size` for the text written in that element: see `providers/_email_text.py` and `providers/mailbox/README.md`, "Outlook", for the rule and for what a browser does that it does not model: a colour, a class, a style sheet, position off the page and comments are not read, and where it differs from a browser it hides); tag characters, variation selectors and the other invisible marks are removed from every text. Quoted history is cut at the first line that starts with `>`, a `-- ` signature line, or an attribution or forward marker of a closed list in English, Portuguese and Spanish ("On ... wrote:", "Em ... escreveu:", "El ... escribio:", "-----Original Message-----", an Outlook `From:` / `Sent:` block, and their forms), so an old quoted `/approve 12` is never read. A reply that is bottom-posted or written between the quoted lines has nothing before the first quoted line, and is dropped as `empty` with no answer: write the reply above the quote. When the first line is one of the bridge's commands (`/approve`, `/reject`, `/release`, `/pending`, `/project`, `/help`; not `/answer`, which takes the rest, and not a line that merely starts with `/`), that line alone is the text, so a signature a phone adds ("Sent from my phone") cannot turn `/approve 12` into a typed hash; write the command on the first line of the reply. At most 8,000 characters. `reply_to` is the `In-Reply-To` only when it is a Message-ID this provider sent to that chat (`sent.json`, the last 1,000 for each chat).

**The card.** One `text/plain` message, no HTML part, no attachment (`documents` is false: the whole text of a decision is in the body, and a card that does not fit in 8,000 characters is cut; for a decision whose approval needs its whole text (an effect, a plan that reaches the network) a cut card is never approvable by e-mail and says where to approve, and a plain plan or an acceptance follows the rule it always had). `Auto-Submitted: auto-generated`, a random Message-ID, a Subject that is the card's first line cut to 78 characters, and the lines that say how to act ("Reply to this e-mail with: /approve 12", and the hash the approval is of) are moved right under the first line, where a preview or a clipped message still shows them. There is no threading of the bridge's own messages in v1.

**Approving by e-mail.** The capability `actions_need_reply` makes the bridge act on a typed approve, reject, release or answer only when the e-mail is a **reply to the card of that decision**, and it binds the action to that card. That is also how delivery is confirmed: an accepted SMTP message is not a delivered one, but a reply that names the card's random Message-ID proves the card reached the person's mailbox, and no approval is taken without it. A forged message that somehow passed the checks above still could not act: the Message-ID went only to the listed mailbox.

**Never.** It never changes the mailbox (IMAP `EXAMINE`, `UID SEARCH`, `UID FETCH` with `BODY.PEEK` and `RFC822.SIZE`, `NOOP`, `LOGOUT`: no flag, move, copy or delete), renders HTML or follows a link, reads an attachment, answers an unlisted, unauthenticated, automatic or group message, sends to any address but the chat of a listed sender, logs an address, a subject or a body, or sends a password before TLS (IMAP 993 from the first byte; SMTP 465, or 587 with a required STARTTLS; the certificate verified; plain only to a loopback host with `OPENHORA_MAIL_TEST_PLAIN=1`, for tests).

**What an address proves.** An address is trivial to forge, so the list of senders never admits a message alone. What admits one is the receiving server's own check, and what that proves is that the receiving server saw the sender's domain vouch for the message, not which mailbox of the domain sent it. Weak points: another account on the same domain (on a small company server, any user can often set the From of what they send, and the server's check vouches for the domain, not for the mailbox), who can impersonate a listed address for what is not reply-bound (a plain line for the planning agent, `/pending`, `/project`); a domain whose mail does not pass DMARC (its mail is dropped, which is safe: a DKIM signature alone does not admit); a shared sending service that signs for the domain; a server that writes the header for some messages only (a forger could copy a header of the right id onto a message the server did not annotate, which `--check` looks for in the newest messages; it cannot see a message the server did not annotate and the sender did); the account itself (a stolen app password). A signed message that someone captured and sends again can at most repeat what its sender approved, for a decision that is still open and unchanged. **The card's Message-ID is a bearer secret.** Whoever holds it, and can send mail as the sender's domain, can act on that card: it leaks through a reply-all that keeps a Cc (the message is then dropped as not private, silently, and the Message-ID has still left), a forward of the card as an attachment, or a mailbox other people can read. Keep the mailbox and the sender's mail to yourselves. **Residual risk, named:** a server that writes an echoed address without its quotes (a MAIL FROM such as `"x) ; dkim=pass header.d=..."@evil.example` in a comment or in `header.i`) puts a sender's `dkim=pass` into the header as a result of its own, and nothing in the header tells it from a real one; the provider does not read a header in which a comment holds a double quote (the form a quoted MAIL FROM takes when a server echoes it into a comment; a reader that counts quotes and one that follows RFC 5322 end that comment in different places), admits only one DMARC result, refuses a message with two headers of its id, and `--check` looks at the newest messages, but how the host writes a quoted MAIL FROM is checked by hand (below). **Two cases are not detected when the server wrote no DMARC result of its own for that message** (with one, an injected `dmarc=pass` is a second result and the header is refused): an unquoted parenthesis echoed into a comment (a HELO such as `a) ; dmarc=pass header.from=... ; (b`), and a server that escapes `\"` but not `)` in the echoed address. `--check` exits 3 when none of the newest messages carries a DMARC result, which is the host this case needs; a host that writes one for most messages and none for some is the weak point. Alias addresses that forward to the mailbox make the message not private (the To is not the mailbox's address) and are dropped; so is a reply-all that keeps a Cc, with no answer. A From with an international (non-ASCII) domain is refused as `sender`: the provider compares ASCII addresses only, so a person writes from the xn-- form. A banner a server or a gateway adds above the text ("[EXTERNAL]") is the first line, and then `/approve 12` is no longer the first line: switch the banner off for the mailbox.

**State**: `<state folder>/messenger-email/` (0700; files 0600): `settings.json`, `cursor.json` (`uidvalidity` and `last_uid`; a new UIDVALIDITY or no cursor starts from "now on", never the whole mailbox), `sent.json` (Message-IDs, no text), `listen.lock` (one program reads the mailbox at a time). Exclude it from backups. A refused login, a missing authserv-id and another program reading the mailbox are exit 3; any other loss of the connection (a busy or limited server, a failed fetch) is a `failed` error event and exit 1 with the cursor not moved, and the bridge starts the provider again with its backoff.

**To verify on first use** (offline tests use a fake IMAP and SMTP server on loopback; none of this has been run against a real mail host):

- the host writes a DMARC result (`dmarc=pass ... header.from=`) on the mail of your own domain: `setup` and `--check` say when the newest messages carry none (the channel refuses them, and `--check` exits 3 when none of them does);
- the host really writes `Authentication-Results` with a stable authserv-id on every message (`setup` without `--authserv-id`, then `--check`), and whether the From of a message sent from the person's own address passes (`dmarc=pass` or an aligned `dkim=pass`);
- a card arrives as one plain text message, the reply `/approve <id>` on its first line acts, and the same words typed in a new e-mail do not;
- a message sent from another domain with the owner's address in From, through a server that does not sign for that domain, is dropped (the log line says `unauthenticated`);
- the quote cut on the person's real mail client and phone (the attribution of its language), and that a phone signature does not break the command;
- the host's limits: a message size limit near 25 MB (the channel reads under 1 MiB), and that password IMAP and SMTP are allowed (Microsoft 365 may refuse them: the login is then exit 3);
- the card in a real client: clipping (a long message cut with "view entire message"), a partial download on a phone, and how the client threads the card and the reply (the reply must carry `In-Reply-To`);
- whether the host strips an `Authentication-Results` header a sender planted, whether it annotates internal mail (a message from another account of the same server), how it writes a quoted MAIL FROM in its comments, and that exactly one header of its id is on each message (a message with two is dropped);
- `imaplib` has no IDLE before Python 3.14, so the mailbox is polled every `--poll-seconds`; the delay of a reply is that interval plus the host's.

## WhatsApp

`whatsapp.py` serves `whatsapp` through an unofficial WhatsApp Web client, **only in the listen mode** (`receive`, `send`, `ack` and `fetch-attachment` exit 2 with "whatsapp works only in listen mode"), with **no buttons**: every action is a typed line (`Send /approve 12`), the way the bridge folds actions for any platform without them. The client is [whatsmeow](https://github.com/tulir/whatsmeow) (MPL-2.0), in a small Go program in `whatsapp/` that is built from source on the machine that runs the bridge. No native library is downloaded when it runs.

**The risk, stated plainly.** WhatsApp's terms of service bar automation and unofficial clients (whatsapp.com/legal/terms-of-service, read 2026-10-13), so **the number the bridge uses may be restricted or banned**, with no recourse. The protocol is not published and may change under the client: a version WhatsApp stops accepting is refused and the bridge stops with a sentence that says to update and build again. Therefore:

- Use **a separate number of your own**, never the number you cannot lose. The bridge is a linked device of that number only. You write to it from your personal WhatsApp as to any contact.
- Keep the volume low: one contact (you), the notices and replies the bridge sends, nothing in bulk. Messages from anyone else are ignored.
- Do not install WhatsApp for this number on a phone you do not control, and do not share the session (below).

**What is pinned.** `go.mod` names the exact versions (the pins and their dates are in the pull request that last changed them); `go.sum` holds the hash of every module, including the pure-Go SQLite driver (`modernc.org/sqlite`, BSD-3-Clause; no cgo, so no C compiler is needed). The Go program is also pinned to the toolchain `go.mod` names (`toolchain` line). The build verifies every module against `go.sum` (`go mod verify`, `-mod=readonly`); the checksum database is asked only about an entry `go.sum` lacks. A toolchain newer than the one installed is downloaded by Go itself and verified by the checksum database, and the download fails if that database is switched off (go.dev/doc/toolchain). The provider runs Go with `GOENV=off` (a `go env -w` setting is ignored), `GOFLAGS=-mod=readonly`, `GOWORK=off`, `CGO_ENABLED=0` and without `GOSUMDB`, `GONOSUMDB`, `GOPRIVATE`, `GONOPROXY` and `GOINSECURE`.

**Licenses.** The program links whatsmeow (MPL-2.0) and, through it, `go.mau.fi/libsignal` (GPL-3.0). The repository carries source only, and the binary is built on your own machine for your own use. Do not hand a binary built from it to anyone without meeting those licenses (the GPL-3.0 asks for the source of the whole program, which is in this folder).

**Prerequisites.** A Go installation (`go version`). The machine's Go may be older than `go.mod` asks (the module needs Go 1.26 or later): Go then downloads the toolchain `go.mod` names, which needs network access to Go's module proxy and checksum database the first time. Nothing else is installed.

**Setup**, once:

1. `python3 providers/messenger/whatsapp.py build` builds the program into the per-user state folder (below), checks the modules, and records what it built. Run it again after every update of the repository: `listen` refuses to start when the program or its sources differ from the record (a stale build), with a sentence that names this command. The record (`build.json`) is a check for a stale or damaged build, **not for tampering**: whoever can rewrite it, in a folder only you can open, can already read the session.
2. In a terminal, `python3 providers/messenger/whatsapp.py pair --phone <digits of the bridge's number>`. It prints a pairing code and the steps: on the phone that holds that number, open WhatsApp, Linked devices, Link a device, choose to link with a phone number instead, and type the code. It refuses when the session is already paired (unlink the device on the phone, delete `whatsapp/session.db`, and pair again). No QR code is drawn (it would cost a dependency; the code does the same).
3. Find the digits WhatsApp itself uses for you: stop any bridge, run `python3 providers/messenger/whatsapp.py whoami`, and, within the 120 seconds it listens, send any message from **your personal WhatsApp** to the bridge's number. It prints the phone digits of every one-to-one sender that writes meanwhile, and nothing else. It never sends and never goes through the bridge, and it refuses (exit 2) while a bridge holds `<state folder>/messaging-whatsapp.lock`. (`whoami` prints phone numbers, so it writes only to a terminal and exits 2 when its output is a pipe or a file. `--seconds` changes the time, 1 to 600. While it runs it receives your message like any linked device, so WhatsApp marks it delivered; the bridge, started later, does not see that message again.)
4. Put those digits in `messaging.senders.whatsapp` of the project's `docs/workbench/runtime.json`, type `accept-config` in the terminal, and start the bridge with `--messaging whatsapp` on the service (or `--platform whatsapp` on `runtime/messaging.py`).

**The Go environment.** `build` clears the settings that would weaken the checks (see "What is pinned"). Other settings come from your environment: `GOPROXY`, `GOMODCACHE`, `GOTOOLCHAIN` and `GOVCS`. That is safe because `go.sum` and the checksum database verify every module and toolchain whatever the proxy or cache says.

**Senders are digits only**, with the country code and no `+`, no spaces, no leading zero (for example `5511900000000`). Some numbers have an address that differs from the number as written (a number registered before its country added a digit may have an address without it): the digits `whoami` prints are the ones to use, and an update from a sender that is not in the list is dropped with no reply.

**The state folder** is `$OPENHORA_STATE_DIR`, else `$XDG_STATE_HOME/openhora` (when absolute), else `~/.local/state/openhora`: a real directory of your user with no access for the group or others, checked before every use. The bridge's `--state-dir` flag does not reach providers: **for WhatsApp use `OPENHORA_STATE_DIR`**, and give the bridge and the provider commands the same value. In it, `whatsapp/` (mode 0700) holds `session.db` (0600, with SQLite's `-wal`, `-shm` and `-journal` files made under umask 077), `bin/whatsapp-bridge` and `build.json`. The provider repeats the state-folder rule of `runtime/messaging_ledger.py` because a provider may not import `runtime/`; a test holds the two equal.

**The session file is the account.** `session.db` holds the keys of a linked device: whoever holds the file can read and send as that number. Never copy it, never put it in a project or a repository, never send it to anyone. **Exclude it from backups**: on macOS `tmutil addexclusion <state folder>/whatsapp` keeps Time Machine from copying it, and the same holds for any other backup tool (an encrypted, private backup of it is still a copy of the account). The same goes for cloud-synced folders.

**Unlinking.** On the phone: WhatsApp, Linked devices, choose the device, Log out. That ends the session at once (the next check of the bridge finds it logged out). After it, delete `whatsapp/session.db` and pair again to link a new one. Unlinking every device ends every session of the number.

**When the session is lost.** A logged-out device (you unlinked it, or WhatsApp did) makes the provider write an error event of kind `paused`, with a sentence that names the `pair` command, and exit 3. The bridge does not stop: it waits 5 minutes and asks again, forever, and logs the reason once and then again every 24 hours while it stays paused (the page does not show a paused bridge yet). It recovers by itself within 5 minutes of a new `pair`. **Messages you send to the number while it is paused are processed when the provider reconnects** (WhatsApp delivers them to the linked device then; delivery is at least once, as on Telegram), and each approval stays bound to the card you saw, so an old `/approve 12` for a decision that has changed is refused. A second program using the same session (a copied session file, or a second bridge) is not a pause: the provider says another program is using this session and the bridge stops (exit 3). A refused version of the client stops it the same way.

**What it does.** One process holds the connection, with the library reconnecting by itself (`ready` may be written again after a reconnect; a lost connection is an error event of kind `failed`). An update is made only for a **text message or a file in a one-to-one chat from another person**: not from the linked device itself, not a group, broadcast list, status or newsletter, not an edit, a reaction or a protocol message (a file is described under "Files" below). The sender is the **phone number in digits**, both as `sender` and as `chat` (the bridge requires them equal); an address WhatsApp gives as a hidden identifier (LID) is resolved to the number with the message's own alternative address, then the library's store, and a message whose sender cannot be resolved is dropped with one log line that carries no id. `reply_to` is the id of the message the person quoted, which is how a reply to a question card reaches `answer`. `action` and `action_ref` are always null.

**Files** (ATT-4). The capabilities declare `attachments` and `max_attachment_bytes` 104857600 (100 MiB: the most the program holds for one file, since the library decrypts a medium in memory; it is the program's ceiling, not a limit WhatsApp states, and the bridge's own cap of 25 MiB is lower). A message that carries a medium with a download path becomes an update whose `attachments` holds one element: a **document** (`DocumentMessage`, also when it arrives inside the wrapper WhatsApp uses for a document with a caption) keeps its file name (or title), its declared media type and its declared length, `null` for what the message did not say; a **photo**, **video** (a video note too), **audio file**, **voice note** (an audio message marked push-to-talk) and **sticker** is named by its kind in `type` (`photo`, `video`, `audio`, `voice`, `sticker`), which is all the bridge needs to refuse it before a byte is fetched. `text` is the caption (a document's, a photo's or a video's) or `null`, and `reply_to` the message the file quotes. The name is cleaned (no path separator, no control character, at most 100 characters) and a declared type is cut at 100; nothing else of the message's metadata leaves the program. The **reference** is 32 random hex characters, made by the program: it carries no media key, no address and no part of the message, and it means something only inside the process that made it. The table behind it is in memory, holds for one hour each at most 10 references of one sender (that sender's oldest goes first, so a stranger who sends many stickers cannot push a listed sender's reference out; the list of senders is applied by the bridge, so any one-to-one chat reaches the table) and at most 200 in all, and gives the same message delivered again within the hour the same reference (delivery is at least once), so the bridge sees one file. A restart of the program, an expired or a dropped reference is `gone`: the bridge answers "send it again".

The **fetch** (the listen op `fetch`, answered by the program itself) downloads the medium with the library inside the process (the media key never leaves it), in a worker of its own so that a card is not held up behind a download (the bridge asks for one fetch at a time; a few more may wait, and the rest are answered `failed` at once). It refuses before any download when the folder is not a real directory (no link) owned by the user with no access for the group or others, when the reference is not one it made (`usage`) or is unknown (`gone`), when the length the sender declared is over the cap (`usage`), and when the message carries no hash to check the file by (`failed`). The cap is the smaller of `max_bytes` and the ceiling above, and it is counted **while the bytes arrive**: the client the library downloads media with is replaced by one that speaks HTTPS only, connects within 10 seconds, follows no redirect, ends the response and cancels the download the moment it passes the cap (the encryption overhead, 64 bytes, is allowed on top), and so a sender who declared a small file and sent a large one is stopped, with memory held to about the cap. The whole fetch is bounded to 120 seconds. The library decrypts and verifies the file against the hashes of the message; the program then checks the plaintext's sha256 against the declared one again before it writes. The file is written only as `<out>/content` through a root opened on the folder the bridge made (created with `O_EXCL|O_NOFOLLOW`, mode 0600; an existing `content`, a planted link or another name is never written through, and a file not written whole is removed), and the answer is `{"bytes", "sha256"}` of what was written. WhatsApp keeps a medium for a limited time: a 403, 404 or 410 from its media host is `gone`. A failure is a sentence of the program's (WhatsApp did not answer in time, is not connected, could not deliver the file), never the library's error text, which carries an address. Nothing the program logs holds a file name, a caption, a reference, a media key or an address: the library's own warnings are redacted of web addresses as well as of numbers and ids. The program reaches no host but WhatsApp's media hosts, which the library takes from the connection WhatsApp itself opened (the program builds no address from an update).

**Sending.** The text goes out as one text message to the number's chat, with no link preview and no mention (the message has no context at all, so `@` text cannot ping anyone). A document is uploaded and sent after the text with its name and the type `text/plain` or `text/markdown` (by its extension). The answer carries the id of the text message. A number WhatsApp has no conversation for yet (nobody has ever written between them) cannot be sent to; the send answers `failed` with a sentence, never the library's error text, and nothing stops.

**Rendering** is done in the Go program (`render.go`), because after `listen` replaces the Python process none is on the send path. WhatsApp has no escape for its marks and no hidden links, so the conversion keeps what WhatsApp shows and shows every link target: `**x**` becomes `*x*`, `~~x~~` becomes `~x~`, a heading becomes `*text*`, bullets, quotes and fenced blocks stay, a masked link `[text](url)` becomes `text (url)`, a run of table lines is put in a fenced block, and single `*x*` and `_x_` of the source are left as they are (WhatsApp may italicise or bold them). A code span (the effect command of a card) and a fenced block stay byte for byte. Text over 4096 characters after rendering is cut, ending with "(continues on the page)".

**Privacy.** Messages are end-to-end encrypted between WhatsApp's clients; this program is one of them, so it decrypts them on the machine that runs the bridge, and WhatsApp sees the metadata (who, when, how much), as for any linked device. The program writes no message text, sender, id, file name or media address to its log or standard error; the library's warnings and errors go to standard error. A file the bridge asks for is downloaded and decrypted on the machine that runs the bridge, held in memory while it is checked, and written once, to the folder the bridge made. Nothing is sent anywhere but WhatsApp. The bridge keeps its ledger as for any platform (no text of a project in it).

**Tests.** `providers/messenger/tests/test_whatsapp.py` (offline, the Go commands replaced, a stand-in program for the exec path) and, in the Go folder, `go vet ./...` and `go test ./...` (the framing, the inbound filter, the send validation, the rendering, the logout and replaced-stream events, the descriptor reservation, and for files the mapping of each kind of medium, the reference table with its bound and expiry, the fetch with a fake downloader (the cap, the hash, a gone reference, the folder checks, a planted link, the log), the bounded media client over a fake transport, and the fetch worker beside the sends, all with the library's types built in memory and no network). `whatsapp/testdata/` holds the update line and the two answers the Go tests compare their output with; `test_whatsapp.py` hands the same files to the bridge's own checks (`runtime/messaging_provider.py`). The live test (a real number) is the maintainer's: build, pair, a message from the personal number, a card with typed commands, a reply to a card, a document, and a logout from the phone; and for files: a PDF and a docx sent from the personal number arrive as a card and are added by the typed `/add <n>` (this provider has no buttons; the file lands as `content` in the folder the bridge made, with the size the phone shows); a photo and a voice note are refused by the bridge before a download; a file over the bridge's cap is refused by its declared size; a document sent with a caption arrives with the caption (an exact `@<id>` names a source); and, because only the library's own default client has downloaded media before, **a download that fails where it should work** (the program refuses redirects, accepts HTTPS only and reads the response through a counting body) is the first thing to look at.

## A public HTTPS address for the official WhatsApp providers

`whatsapp-cloud` and `whatsapp-twilio` receive their messages as webhook calls, so the platform (Meta or Twilio) must reach the bridge's small local server (`127.0.0.1:<port>`) over **HTTPS from the internet**. The workbench does not choose how: any public HTTPS address that forwards `https://<host>[:<port>][/<prefix>]/<path>` to `http://127.0.0.1:<port>/<path>` works (`<path>` is the random 32-character path `setup` makes; the proxy keeps it, and removes the address prefix if you use one). Give that address to `setup` with `--public-url https://<host>[:<port>][/<prefix>]` (`--public-host <host>` is the shorthand for `https://<host>`): https only, a host of letters, digits, dots and hyphens, an optional port, an optional prefix; no query, fragment, credentials or spaces. `setup` prints the callback URL to paste in Meta or Twilio and one line, `Expose: https://<host>/<path> must reach http://127.0.0.1:<port>/<path> (the path kept)`. Twilio signs the exact URL it calls, so `setup` stores it whole and the provider checks the signature against that text.

Tailscale is only a helper: when neither flag is given, no earlier `setup` stored an address (a stored tunnel address is never silently replaced) and the `tailscale` command is found (in the PATH, or at `/Applications/Tailscale.app/Contents/MacOS/Tailscale`), `setup` uses the machine's Tailscale hostname and also prints the Funnel command as one example. Without a flag and without Tailscale, `setup` exits 2 and says what to give. No account with any service is required by the workbench itself.

| Option | Cost | Who can read the messages in transit | Address | Account |
|---|---|---|---|---|
| Tailscale Funnel | free plan | nobody in between: TLS ends on your machine; Tailscale's relays carry the encrypted traffic | stable (`<machine>.<tailnet>.ts.net`) | a Tailscale account, and its macOS app (App Store or Standalone) |
| Cloudflare Tunnel | free | Cloudflare: TLS ends at Cloudflare, which can read the traffic | stable, a name on a domain you own | a Cloudflare account and a domain on it |
| ngrok | free plan to try | ngrok: TLS ends at ngrok | on the free plan it changes at each start (a reserved domain is a paid or account feature) | an ngrok account |
| A reverse proxy on a server you run (Caddy, nginx) | the server | nobody in between: TLS ends on your server (a valid certificate, for example from Let's Encrypt), which forwards to this machine over a network you control | stable | none beyond the server; the forward from the server to this machine is yours to secure |

In every case the platform sees the messages (Meta, and Twilio with Meta), the provider checks a signature on every call (the signature is the only authentication; the secret path is defence in depth), and its server binds `127.0.0.1` only. **If the address changes** (a tunnel restarted on a free plan, a new domain), run `setup` again with the new `--public-url` and update the webhook in Meta's app settings or the Twilio Console; the stored path is kept unless you add `--new-path`.

**Secrets and the Python that runs.** Every command below that reads a secret is written `uv run --with keyring==25.7.0 python3 ...`, because the OS secret store is read through the `keyring` library, which a plain `python3` lacks. Without it the provider says "the OS secret store is not available in this Python (the keyring library is missing)" instead of "missing or malformed", and then only exported environment variables are read.

## WhatsApp Cloud API

`whatsapp-cloud.py` serves the platform `whatsapp-cloud`: the **official** WhatsApp Business Cloud API, with buttons, **only in the listen mode** (`receive`, `send` and `ack` exit 2). It is the second WhatsApp platform beside `whatsapp` (the unofficial client, above); a bridge serves one platform, so the person picks one for each bridge (`--messaging whatsapp-cloud`, or `runtime/messaging.py --platform whatsapp-cloud`). Standard library only. Sources, read 2026-10-13: Meta's documentation for the WhatsApp Business Platform (developers.facebook.com/documentation/business-messaging/whatsapp/: get-started, webhooks/create-webhook-endpoint, webhooks/overview, webhooks/components, business-scoped-user-ids, support/error-codes, pricing, templates/template-categorization, business-phone-numbers/phone-numbers) and Tailscale's (tailscale.com/kb/1223 Funnel, kb/1153 HTTPS certificates, kb/1311 Serve and Funnel commands, and the Serve reference).

**The two options.**

| | `whatsapp` (unofficial client) | `whatsapp-cloud` (official API) |
|---|---|---|
| Rules | breaks WhatsApp's terms: the number may be restricted or banned | the platform's intended use: no restriction risk for the number |
| Number | a separate personal-style number, linked as a device | a number **not** on the WhatsApp app, registered to a business account |
| Buttons | none: typed commands (`Send /approve 12`) | up to 3 reply buttons per message |
| Needs | a Go toolchain to build the program; no port | a Meta business portfolio, an app, a system user token, a template (optional); a public HTTPS address (any tunnel or proxy, see above) and a local port |
| Outside the 24-hour window | nothing special: the linked device writes freely | a free-form message only after the person wrote in the last 24 hours; with an approved template (optional), a reminder, and utility templates outside the window are paid |
| Messages | end-to-end encrypted to the machine that runs the bridge | processed by Meta as the Cloud API host; the webhook is TLS-encrypted to the machine |

**Setup**, once (nothing here is done by the bridge). Each step names where the value goes; the three secrets go in the store or the environment, never in an argument.

1. In Meta's business tools, have a **business portfolio**. Create an **app** with the WhatsApp use case, and add a phone number that is not registered on the WhatsApp app (a number that is already on the app has to be removed from it first). Meta's test number works for a first try; it can message only the recipients you list in the app.
2. Create a **system user** in the portfolio, give it the app and the number, and generate a **permanent token** with the permissions `whatsapp_business_messaging`, `whatsapp_business_management` and `business_management`. Store it: `uv run --with keyring==25.7.0 keyring set openhora messenger-whatsapp-cloud` (or export `MESSENGER_WHATSAPP_CLOUD_TOKEN`).
3. Copy the app's **secret** (App settings, Basic) and store it: `keyring set openhora messenger-whatsapp-cloud-app-secret` (or `MESSENGER_WHATSAPP_CLOUD_APP_SECRET`). It is used only to check the signature of each call Meta makes.
4. Make up a **verify token**: a random string of letters and digits (for example the output of `python3 -c "import secrets; print(secrets.token_urlsafe(24))"`). Store it: `keyring set openhora messenger-whatsapp-cloud-verify-token` (or `MESSENGER_WHATSAPP_CLOUD_VERIFY_TOKEN`). You type the same string in the app's webhook settings in step 8. It grants nothing but Meta's handshake.
5. **Optional:** create the **template** (skip this step to run without one: after 24 hours of silence the person must write to the number first, and the cards wait until then; you can add the template later by running `setup` again). In WhatsApp Manager, Message templates: name `decisions_waiting` (lowercase letters, digits, underscore), the language you want (for example `pt_BR`), **no variable**, one **quick-reply** button, and a fixed text with no project data. Suggested texts, written as an account alert (the Portuguese form is on the next line): English, "openhora: decisions are waiting for you." with the button "See decisions". Choose the category **Utility** and submit it for approval. **Meta may classify it as Marketing** instead (it decides on the text, not on your choice): a marketing template costs more, has per-user limits and can fail with error 131049; the maintainer accepted that risk, and a plain text with nothing promotional is the best defence. Wait for the approval before the live test.
   - `pt_BR`: "openhora: há decisões esperando por você." with the button "Ver decisões". (validate: allow english-only -- the template text in the language it is approved in)
6. On the machine that runs the bridge, run `uv run --with keyring==25.7.0 python3 providers/messenger/whatsapp-cloud.py setup --phone-number-id <the number's id> --public-url https://<your public host> --template decisions_waiting --template-language pt_BR` (`--port 8787` is the default; `--public-url` is the address from "A public HTTPS address" above, and may be left out when an earlier `setup` stored an address or the `tailscale` command is found). Without a template, leave out both `--template` and `--template-language` (giving one without the other is a usage error, exit 2); running `setup` again with both adds the template, and `--no-template` removes it. It writes `<state folder>/whatsapp-cloud/settings.json` (mode 0600) with a random 32-character path for the webhook, and prints the **callback URL** (`<your public address>/<path>`) and the line `Expose: ... must reach http://127.0.0.1:<port>/<path>`, plus the Funnel command only when Tailscale was used. `--new-path` makes a new random path.
7. Expose the path at your public address, by the means you chose in "A public HTTPS address" above, so that `Expose:` line holds. With Tailscale Funnel: in the Tailscale admin console turn on **MagicDNS** and **HTTPS certificates**, and make sure the node has the **funnel** attribute (kb/1223); on macOS install the App Store or Standalone app (the open-source `tailscaled` variant has no Funnel); then run the command `setup` printed, which has this shape: `tailscale funnel --bg --https=443 --set-path=/<path> http://127.0.0.1:8787/<path>`. `--bg` keeps it after a reboot (kb/1311); `--set-path` makes Funnel serve only that path (the provider answers 404 to any other, and the path does not appear in Certificate Transparency logs, which list only the hostname).
8. In the app's WhatsApp configuration, set the webhook: the callback URL from step 6 and the verify token from step 4. Meta checks the callback when you save it, so the provider must be running at that moment: start `whoami` (step 9) in another terminal, or the bridge (step 10), and then save. Subscribe the app to the field **`messages`**.
9. Find your own identifiers: stop any bridge, run `uv run --with keyring==25.7.0 python3 providers/messenger/whatsapp-cloud.py whoami` in a terminal, and send any message to the business number from your own WhatsApp within the 120 seconds it listens. It prints the **phone digits** and the **business-scoped user id** (BSUID) of each signed message and nothing else. It never sends, and refuses (exit 2) while a bridge holds `<state folder>/messaging-whatsapp-cloud.lock` or when its output is not a terminal (`--seconds` changes the time, 1 to 600).
10. Put the digits (country code, no `+`, no spaces, for example `5511900000000`) in `messaging.senders.whatsapp-cloud` of the project's `docs/workbench/runtime.json`; if you use a WhatsApp username and your digits are hidden, put the BSUID `whoami` printed as well (see "Identity"). Type `accept-config` in the terminal, and start the bridge with `--messaging whatsapp-cloud` on the service (or `--platform whatsapp-cloud` on `runtime/messaging.py`). Keep `OPENHORA_STATE_DIR` the same for `setup`, `whoami` and the bridge.

**Tailscale Funnel facts** (only if you chose Funnel; Tailscale's documentation, 2026-10-13). TLS ends **on your machine**: the Funnel relay servers do not decrypt the traffic (kb/1223). The certificate is from Let's Encrypt and its key is stored on the machine; the hostname is published in Certificate Transparency logs (kb/1153), so anyone can learn the hostname, but not the secret path. Funnel listens on ports 443, 8443 and 10000. No Funnel or identity header reaches the service (Serve reference): the **signature is the only authentication**, the path is defence in depth. The provider's server binds `127.0.0.1` only, so nothing else on the network can reach it. Whether `--set-path` forwards the path as the provider expects (the command repeats the path in the target so that the service sees `/<path>` either way) is **to be confirmed in the live test**: if Meta's handshake answers 404, the provider writes "a request for another path (404)" to its diagnostics once a minute.

**What it does.**

- **Server.** `http.server.ThreadingHTTPServer` on `127.0.0.1:<port>`; `GET` and `POST` on `/<webhook_path>` only (another path 404, another method 405); HTTP/1.0 (one request per connection); `Content-Length` required (411), over 3 MiB refused before it is read (413), a total deadline of 10 seconds for a request, at most 8 requests at once (503 beyond). Request logging is replaced: nothing from a request (the path, the query, the verify token) reaches any log; the diagnostics are by class and at most one a minute per class.
- **Handshake.** `GET` with `hub.mode=subscribe` and `hub.verify_token` equal (compared as bytes, in constant time) to the verify token: 200 with `hub.challenge` as text, else 403.
- **Signature.** `POST` is accepted only with `X-Hub-Signature-256: sha256=<HMAC-SHA256 of the raw body, keyed with the app secret>`, checked on the **raw bytes** in constant time (a re-serialised body fails): 401 otherwise, logged by class. Until `ready` (the token check) every `POST` gets 503 and nothing is marked seen, so Meta's retry is handled after a startup that failed would have exited. A valid call is processed **before** the 200: parse, write the update line to the bridge and flush it, persist `seen.json`, answer 200 (milliseconds; Meta documents no response timeout). A crash before the 200, or a failure to write `seen.json` (then a 500), makes Meta retry, and the retry is deduplicated. The path is matched on the raw request target, before any decoding.
- **Filter.** Only values whose `metadata.phone_number_id` is the configured one. A message is a `text` (an update with `text`), an `interactive` `button_reply` (`action` the button's id, `reply_to` the message the button was on) a `button` (a tap on the template's quick reply, which becomes the text `/pending`, so the person gets the cards) or a medium (a `document`, `image`, `audio`, `video` or `sticker`: next bullet). Anything else is ignored. `statuses[]` are ignored except a `failed` status with error 131047 for a message this process sent. A message id (wamid) is remembered for **8 days** (`seen.json`), so Meta's retries (up to 7 days) and duplicates are dropped, also after a restart.
- **Files a sender sends** (ATT-3; the bridge takes them only where the project's policy allows, `docs/architecture/platform/messaging.md`). The provider declares `attachments: true` and `max_attachment_bytes` 104857600 (100 MiB, the most Meta serves for a document; images, audio and video are smaller; the bridge applies its own lower cap). A medium with a valid media id (`[A-Za-z0-9_-]{1,64}`: it goes into the path of an address) becomes an update with one attachment: `ref` the media id, `name` the document's `filename` cleaned of control characters and cut to 255 (null for the other kinds), `size` null (the webhook does not carry it), `type` the document's media type, or `photo` (image), `audio`, `voice` (an audio with `voice: true`), `video`, `sticker`, which the bridge refuses before it asks for a byte; `text` is the caption of a document, image or video, else null. A medium with no usable id is ignored and opens no window. The signature check, the dedupe and the window are the ones of a text. **The fetch** is the listen op `fetch` (`{"id", "op": "fetch", "ref", "out", "max_bytes"}`, answered with `bytes` and `sha256`), run on a thread of its own so that a download never holds up a send. The media address is short-lived, so it is asked for at that moment: `GET /<media id>` on the Graph API (the token goes there as for a send) answers `url`, `file_size`, `sha256`. The provider requests `url` only if it is https on **exactly** `lookaside.fbsbx.com` (a constant, `MEDIA_HOSTS`; no suffix match, no user information, no other port; the request is made to the address rebuilt from its parsed parts), with the token, which the media host requires, and never anywhere else; **no redirect is followed** (the opener raises on one, so the token cannot be forwarded). A `file_size` over `max_bytes` is refused before the download; the bytes are counted while they stream and the read stops at the first byte over the cap (a usage answer); the whole fetch has a 120-second deadline, looked at after every receive (the body is read with `read1`, so a host that sends a byte at a time cannot hold it longer), and each read a 10-second one; a `file_size` given as an integer or as a string of up to 18 digits is read, anything else is no check; the `sha256` Graph declares (hex or base64) is checked after the download, and a value of neither shape is a failure. The file is `<out>/content` only, created with `O_EXCL` and `O_NOFOLLOW`, mode 0600, in the folder the bridge made (opened by descriptor, absolute, not a link, owned by this user); a name from the platform never reaches a path; a failed fetch removes the partial file. Answers: Graph's 404, or 400 with error 100 (the object does not exist), and the media host's 404 or 410, are `gone` (the bridge says the file can no longer be fetched); a refused token at Graph is `not-configured` (and stops the provider, as for a send); anything else is `failed` with the status or the class of the error, **never the body, an address or the token** (`http.client` errors and the like are caught by class). The one-shot verb `fetch-attachment` exits 2 here, as `receive` does. **Not tested live, to confirm with a real account.** The media host, the 100 MiB figure and the form of the hash have **no source with an access date yet**: they were written from memory and Meta's documentation was not re-read for this change. To confirm: that the media host is `lookaside.fbsbx.com` (a host not on the list fails closed with "did not give the address of the file on its media host"), that it needs the token, that it does not redirect, that the hash is hex or base64 as handled, and the size limit; then record the source and the date here.
- **Identity.** `sender` and `chat` are the phone digits in `from` when present. Meta may send only `from_user_id` (a business-scoped user id) for a person who uses a WhatsApp username: then the digits remembered for that id are used, else the id itself. The pairs are learned whenever both arrive together, kept **30 days** (`identities.json`, pruned at start). So list your digits and, if you use a username, the BSUID `whoami` prints in `messaging.senders.whatsapp-cloud`; using the BSUID alone is a later choice, after the live test.
- **The window.** WhatsApp lets a business send free-form messages only within 24 hours of the person's last message. The provider records, for each chat, the time of the last message **as the message's own timestamp** (a late retry cannot reopen it) in `window.json`, and sends a card only while that is **less than 23 hours 30 minutes** old.
- **Outside the window** a send is not made. The provider sends the **template** (no variable, no project text) **once for each closed window**, and again at most **every 7 days** while the window stays closed and the bridge still asks for cards (`template_sent_at` in `window.json` decides; a restart never resends it), and answers `deferred`. **Without a template** (`setup` was given none) it sends nothing at all, still answers `deferred`, and logs one line per chat every 24 hours at most ("outside the 24-hour window and no reminder template is configured; the card waits until you write"); the card goes out when the person next writes. The bridge keeps the card (it is not in its ledger) and sends it after the person's next message: tapping "See decisions" sends `/pending`, which opens the window and brings the cards.
- **A late 131047.** Meta usually accepts a send and reports error 131047 ("more than 24 hours since the person wrote") later, as a `failed` entry in `statuses[]`. The provider reads that only for a message it sent: it marks that chat's window closed and sends the template (still once; without a template, only the log line). A card lost that way is already in the bridge's ledger, so it is not sent again; the person reaches it through `/pending`, which lists the open decisions as text.
- **Sending.** `POST https://graph.facebook.com/v25.0/<phone_number_id>/messages` with `Authorization: Bearer <token>`, no link preview (`preview_url: false`), `context.message_id` for a reply. A card whose rendered text is at most 1024 characters is **one** interactive message with the text as body and the buttons (title cut to 20 characters after collapsing spaces, never empty, made different from the others with " 2", " 3"; id up to 256, at most 3); a longer one is a **text message** (up to 4096) followed by a message of the fixed line "Choose an action for the card above." with the buttons, as a reply to the text. The answered id is always the **text** message's. A document is uploaded (`POST /<phone_number_id>/media`) and sent after the text as a reply to it (`filename` the bridge's name, type `text/plain`). A part after the text that fails is logged by class and the send still answers ok, so the bridge does not send the text twice. A tap arrives with the button's id and binds by action id and chat, not by message id; a reply to the buttons message of a long card is given the text message's id as `reply_to` (this process remembers the pairing), so it binds to the card, and a late 131047 on the buttons message also closes the window.
- **Errors.** 190 and 0 (a token expired or refused) and HTTP 401: an error event `not-configured` and exit 3. 130429 and 131056 (rate limits): `failed`, and the sender waits a few seconds before the next request. Anything else: `failed` with the status and Meta's code, **never the body**. A network error while checking the token before `ready` exits 1 (the bridge starts it again with its backoff). `ready` is written when the server listens and `GET /<phone_number_id>` with the token works. An exit on the end of stdin or SIGTERM takes no Graph call to wait for.
- **Rendering** (`render_whatsapp_cloud`) follows the rules of the other WhatsApp provider's Go renderer (`**x**` becomes `*x*`, `~~x~~` becomes `~x~`, a heading becomes `*text*`, a masked link becomes `text (url)`, a table is put in a fenced block, code spans and fences stay byte for byte, a long text is cut at a line boundary, never inside a fence or a code span), and a test holds the two to the same outputs on a shared corpus (`providers/messenger/tests/whatsapp_render_corpus.json`, read by `render_test.go` and by `test_whatsapp_cloud_render.py`). Meta does not document the syntax the Cloud API renders; the app's own marks (`*bold*`, `_italic_`, `~strike~`, triple backticks) are assumed, **to be confirmed in the live test**.

**State and backups.** `<state folder>/whatsapp-cloud/` (mode 0700; every file 0600) holds `settings.json`, `seen.json`, `window.json` and `identities.json`, which contain phone numbers and ids. **Exclude the whole folder from backups**: on macOS `tmutil addexclusion <state folder>/whatsapp-cloud` and check it with `tmutil isexcluded`; the same for any other backup tool or synced folder. `seen.json` keeps 8 days and `identities.json` 30 days, and both are pruned at every start and once a day while the provider runs (the window entries too: 30 days after their last use). Secrets are never in these files; they are read through the resolver and appear only in the `Authorization` header of the Graph calls and in the signature check.

**Privacy.** Meta processes every message as the Cloud API host (the messages are not end-to-end encrypted to your machine as with the unofficial client), and Meta sees who writes to whom and when. Who else can read the webhook calls in transit depends on the tunnel you chose (the table in "A public HTTPS address": with Tailscale Funnel or your own proxy nobody in between, with Cloudflare Tunnel or ngrok that service). The provider writes no message text, number or id to its diagnostics. The template carries no project data, so what a closed window costs the person's privacy is one fixed sentence.

**Costs.** Messages inside the open window are free of the per-message charge for a business that answers a person. A utility template sent outside the window is a paid message at Meta's rate for the recipient's country (Meta's pricing page); the bridge sends **at most one for each closed window and one every 7 days at most** while it stays closed. A template Meta classifies as marketing costs more. A tunnel may have its own cost or plan limits (the table in "A public HTTPS address"); check the current terms of the one you choose.

**Tests.** `providers/messenger/tests/test_whatsapp_cloud.py` (verbs, secrets, `setup`, `whoami`, the state folder, a real process over the protocol), `test_whatsapp_cloud_webhook.py` (a local HTTP client against the server on port 0), `test_whatsapp_cloud_send.py` (the window, the template, the messages, the errors, the listener over a pipe), `test_whatsapp_cloud_optional_template.py` (setup with and without the template, the send side without it) and `test_whatsapp_cloud_render.py` (the shared corpus), `test_whatsapp_cloud_attachments.py` (each kind of medium mapped, the signature unchanged, the fetch: the host list, the token, the cap mid-stream, the hash, a gone medium, the token absent from every error, a redirect refused, the fetch beside a send) and `test_whatsapp_meta_media.py` (the stream, the folder and the host check shared with the Twilio provider) and `test_whatsapp_official_attachments_bridge.py` (what both providers write for a file, run through the bridge's own `valid_update` and capability checks), all offline with the Graph API and the media host replaced by fakes; the bridge's `deferred` rule in `runtime/tests/test_messaging_listen.py`. The live test is the maintainer's: the handshake from Meta's dashboard, a message from the personal number, a card with buttons, a tap, a reply, a document, the template after 24 hours of silence, and, for files: a PDF and a Word document sent from the personal number reach the bridge as attachments and are fetched (the media host, the token on it, no redirect, the hash), a photo and an oversized file are refused by the bridge, and a medium deleted in WhatsApp's retention window answers `gone`.

## WhatsApp through Twilio

`whatsapp-twilio.py` serves the platform `whatsapp-twilio`: WhatsApp reached through **Twilio**, **only in the listen mode** (`receive`, `send` and `ack` exit 2). It is the third WhatsApp platform, beside `whatsapp` (the unofficial client) and `whatsapp-cloud` (Meta directly); a bridge serves one platform (`--messaging whatsapp-twilio`, or `runtime/messaging.py --platform whatsapp-twilio`). Standard library only. It shares its server, window rules, state store, identity map and rendering with `whatsapp-cloud.py` through `whatsapp_meta.py` in the same folder (a module the two providers load by path; its underscore keeps the resolver from listing it as an implementation). Sources, read 2026-10-13: Twilio's documentation (twilio.com/docs/messaging/guides/webhook-request, usage/webhooks/webhooks-security, usage/webhooks/webhooks-connection-overrides, messaging/guides/outbound-message-status-in-status-callbacks, messaging/api/message-resource, iam/api-keys and iam/api-keys/restricted-api-keys, content/twilio-quick-reply, content/using-variables-with-content-api, content/content-types-overview, api/errors/63016, messaging/guides/whatsapp/tutorial/message-template-approvals-statuses, twilio.com/en-us/whatsapp/pricing, and the changelog entry on WhatsApp usernames and the business-scoped user id) and Tailscale's (kb/1223 Funnel, kb/1311 Serve and Funnel commands).

**The three WhatsApp options.**

| | `whatsapp` (unofficial client) | `whatsapp-cloud` (Meta directly) | `whatsapp-twilio` (through Twilio) |
|---|---|---|---|
| Rules | breaks WhatsApp's terms: the number may be restricted or banned | the platform's intended use | the platform's intended use, through a Business Solution Provider |
| Account | none beyond the number | a Meta business portfolio, an app, a system user token | a Twilio account and a WhatsApp sender registered through it |
| Number | a separate personal-style number, linked as a device | a number **not** on the WhatsApp app | the Twilio WhatsApp sender |
| Card buttons | none: typed commands | up to 3 reply buttons per message, no template | typed commands; up to 3 quick-reply buttons once you create three Content templates (below) |
| Documents | yes | yes | no: the text is cut and the full text is on the page |
| Text per message | 4096 | 4096 | 1600 |
| Needs | a Go toolchain; no port | a public HTTPS address (any tunnel or proxy, see above) and a local port | the same |
| Outside the 24-hour window | writes freely | an approved template, paid | an approved Content template (optional), paid |
| Costs | none to the provider | Meta's template fees only | Twilio's fee per message, in or out (US$0.005 at the time of writing), **plus** Meta's fees, plus US$0.001 for a failed message |
| Missed while the laptop sleeps | caught up on reconnect | Meta retries for up to 7 days | **lost for good** (Twilio retries once, on a connection failure only) |
| Main risk | the number is banned | an expired token, Meta's template classification | the same classification; being tied to Twilio (leaving is a migration, below) |

**Setup**, once. The three secrets go in the store or the environment, never in an argument.

1. In Twilio, have an account with a **WhatsApp sender** (a number registered for WhatsApp through Twilio). Note the account's **Account SID** (`AC...`) and the sender's number.
2. Create a **Restricted API key** (Console, Account, API keys & tokens). A restricted key is chosen permission by permission: **copy the permission names from the console** when you create it (the ones for sending messages; Twilio's restricted-key page lists Messaging, and whether a Content permission is listed is for the console to say). Grant nothing else. The provider only creates messages, with the Messages API. Store the key's **SID** (`SK...`) and its **secret** (shown once): `uv run --with keyring==25.7.0 keyring set openhora messenger-whatsapp-twilio-api-key-sid` and `... messenger-whatsapp-twilio-api-key-secret` (or export `MESSENGER_WHATSAPP_TWILIO_API_KEY_SID` and `MESSENGER_WHATSAPP_TWILIO_API_KEY_SECRET`).
3. Store the account's **Auth Token** the same way: `keyring set openhora messenger-whatsapp-twilio-auth-token` (or `MESSENGER_WHATSAPP_TWILIO_AUTH_TOKEN`). It is used **only** to check `X-Twilio-Signature` (only the Auth Token is documented as the signing key); it never sends anything. Rotating the Auth Token means storing the new one here.
4. **Optional:** in the Content Template Builder, create the **template for outside the window** (skip it to run without one): type **quick reply**, a fixed text with **no variable** and no project data, one button "See decisions" whose **id** is `see-decisions` (the id is what a tap sends back; `--template-button-id` changes it if you use another). Suggested text, written as an account alert: English "openhora: decisions are waiting for you." with the button "See decisions"; `pt_BR` "openhora: há decisões esperando por você." with the button "Ver decisões". (validate: allow english-only -- the template text in the language it is approved in) Submit it for WhatsApp approval as **Utility**. Meta may classify it as Marketing instead (it decides on the text): marketing costs more and has per-user limits; a rejected template name is blocked for 30 days. Note its **Content SID** (`HX...`).
5. On the machine that runs the bridge: `uv run --with keyring==25.7.0 python3 providers/messenger/whatsapp-twilio.py setup --account-sid AC... --sender +<the sender's digits> --public-url https://<your public host> --template-sid HX...` (the template is optional: leave out `--template-sid` to run without one, add it later by running `setup` again, remove it with `--no-template`; without it the person must write first after 24 hours of silence and the cards wait until then; `--port 8787` is the default; `--public-url` is the address from "A public HTTPS address" above (`--public-host <name>` for a host alone; both may be left out when an earlier `setup` stored an address, or the `tailscale` command is found); `--new-path` makes a new random path). It checks every flag first (a missing or malformed argument, the three `--button-sid-*` not given together, a malformed or missing public address: exit 2, nothing written, no folder made), then refuses unless the three secrets are in the store or the environment (exit 3, the error names each missing secret by its store username). It writes `<state folder>/whatsapp-twilio/settings.json` (mode 0600) and prints these: the **webhook URL**, the **status callback URL** and the line `Expose: ... must reach http://127.0.0.1:<port>/<path>` (and the Funnel command only when Tailscale was used). The webhook URL is stored whole (`public_url`, `https://<host>[:<port>][/<prefix>]/<random 32-hex path>`) because Twilio signs the URL it called, and the provider checks the signature against that stored text, not against anything rebuilt from the request.
6. Expose the path at your public address, as for the other official platform (step 7 of its setup and "A public HTTPS address" above). With Tailscale Funnel, run the command `setup` printed: `tailscale funnel --bg --https=443 --set-path=/<path> http://127.0.0.1:<port>/<path>`. Whether `--set-path` forwards the path as the provider expects is **to be confirmed in the live test** (the target repeats the path so the service sees `/<path>` either way).
7. In the Twilio Console, on the WhatsApp sender's **Endpoint configuration**, set "When a message comes in" to the webhook URL (method POST). **Do not set a status callback URL on the sender**: the provider passes `StatusCallback` (the printed URL, which is the webhook path with `?status=1`) in every message it sends, and both together would deliver each report twice.
8. Find your own identifiers: stop any bridge, run `uv run --with keyring==25.7.0 python3 providers/messenger/whatsapp-twilio.py whoami` in a terminal, and send a message to the sender's number from your own WhatsApp within the 120 seconds it listens. It prints the **phone digits** and the **business-scoped user id** of each signed message, and nothing else (it needs only the Auth Token; it never sends; it refuses while a bridge holds `<state folder>/messaging-whatsapp-twilio.lock` or when its output is not a terminal).
9. Put the digits (country code, no `+`, for example `5511900000000`) in `messaging.senders.whatsapp-twilio` of the project's `docs/workbench/runtime.json`; if you use a WhatsApp username and your digits are hidden, add the id `whoami` printed. Type `accept-config` in the terminal, and start the bridge with `--messaging whatsapp-twilio`. Keep `OPENHORA_STATE_DIR` the same for `setup`, `whoami` and the bridge.

**Card buttons (off until you turn them on; not yet tested live).** Without buttons the bridge sends a card's actions as typed commands ("Send /approve 12"), exactly as for the unofficial platform. To turn buttons on, create **three quick-reply templates** in the Content Template Builder, for one, two and three buttons: the body is the variable `{{1}}`, and each button's **title** and **id** are variables, in this order: the first button `{{2}}` (title) and `{{3}}` (id), the second `{{4}}` and `{{5}}`, the third `{{6}}` and `{{7}}`. Give each variable a sample value in the builder. A quick-reply template used inside the 24-hour window needs no WhatsApp approval (Twilio's quick-reply page); the limits that satisfy both of Twilio's pages are at most 3 buttons, a body of at most 1024 characters, titles of at most 20 and ids of at most 128. Then run `setup --button-sid-1 HX... --button-sid-2 HX... --button-sid-3 HX...` (all three or none; `--clear-buttons` turns them off). Only then does `capabilities` report `buttons: true`, `max_buttons: 3`, `max_button_label: 20`, and the bridge draws buttons. A card with actions is sent as one Content message (the template chosen by the number of actions, `ContentVariables` with the rendered body and each button's title and id) when its text is at most 1024 characters; a longer one is the text followed by a Content message whose body is the fixed line "Choose an action for the card above.". Whether Twilio accepts a newline inside a session variable is not documented: if it refuses the variables (error 21656) the provider logs it **once** and sends the text and then the buttons message with that short fixed body, and goes that way for the multi-line cards that follow. The refusal may come in the send's answer or, after Twilio accepted the message, in a status callback (`ErrorCode` 21656) for a card this process sent; on the callback the card is resent once the same way (text, then the fixed-body buttons message), so it is not lost (the card is remembered in memory only: a restart in between loses that resend). A tap returns the button's id in `ButtonPayload`, which the provider maps to the action; the title Twilio also puts in `Body` is never read.

**What it does.**

- **Server.** The same server and limits as `whatsapp-cloud` (`127.0.0.1` only, a random path, HTTP/1.0, `Content-Length` required, a total deadline per request, at most 8 requests at once, no request in any log), with `POST` only on `/<webhook_path>` (any other method 405, any other path 404) and a body cap of 256 KiB. Twilio's connect timeout is 5 seconds and its total timeout 15 seconds; the provider processes a call before it answers (milliseconds).
- **Signature.** `X-Twilio-Signature` is `base64(HMAC-SHA1(Auth Token, URL + the form parameters))`, computed as Twilio's own validator does: the body is read as a UTF-8 form with blank values kept, the names are sorted and each name's values sorted with a repeated value counted once, each name followed by its value, over UTF-8 bytes; the URL is the stored `public_url` plus the **query string exactly as received** (never re-encoded), accepted with and without `:443`; the comparison is on bytes in constant time. A missing or wrong signature, a body that is not UTF-8 or has over 1000 fields, is a 403 and nothing is processed. SHA-1 is Twilio's choice, not the provider's. Tests include Twilio's published example (token `12345`, `https://mycompany.com/myapp.php?foo=1&bar=2`, the parameters CallSid, Caller, Digits, From and To, signature `RSOYDt4T1cUTdK1PDd93/VVr8B8=`).
- **The answer** to every valid call is an empty TwiML `<Response/>` (`Content-Type: text/xml`), so Twilio sends no reply of its own. A processing failure is a 500; Twilio does not retry it.
- **Filter.** Only calls whose `AccountSid` is the configured account and whose `To` is the configured sender (for a status callback, `From`). A parameter that arrives twice with different values is never read. A message is deduplicated on its `MessageSid` for **8 days** (`seen.json`), also after a restart. A message is a `Body` with text, or a message with media (next bullet).
- **Files a sender sends** (ATT-3; the bridge takes them only where the project's policy allows, `docs/architecture/platform/messaging.md`). The provider declares `attachments: true` and `max_attachment_bytes` 16777216 (16 MiB, what Twilio's WhatsApp media allows; the bridge applies its own lower cap). `NumMedia` (a plain number from 1 to 10; anything else that is not a number reads the message as it always was, by its `Body`) says how many media the form carries; each `MediaUrlN` must be **exactly** `https://api.twilio.com/2010-04-01/Accounts/<AC...>/Messages/<MM...>/Media/<ME...>` with the ids 32 lower-case hex digits after their two letters, the account the configured one and the `MM` id equal to the webhook's own `MessageSid` (a full-match pattern; a query, a suffix, another host, port, scheme, account or message fails it). The update has one attachment for each: `ref` `<MM...>:<ME...>`, `name` null and `size` null (Twilio sends neither; the bridge shows `file.<extension from the bytes>`), `type` the `MediaContentTypeN` without parameters, or `photo` (any `image/*`), `audio`, `video`, which the bridge refuses before it asks for a byte; `text` is the `Body` (the caption), null when blank. If any medium of a message cannot be read, or `NumMedia` is over 10, the whole message is dropped with one log line by class (an update that showed only some of the files would hide the rest). A tap (`ButtonPayload`) or a title (`ButtonText`) is read as before, whatever media fields come with it. The signature, the account and `To` filters and the dedupe are unchanged. **The fetch** is the listen op `fetch` (`{"id", "op": "fetch", "ref", "out", "max_bytes"}`, answered with `bytes` and `sha256`), on a thread of its own. The ref must be exactly `<MM...>:<ME...>` (a full match); the address is **rebuilt** from the two ids, the configured account and the fixed base `https://api.twilio.com/2010-04-01`, never taken from the update. It is requested with HTTP Basic of the Restricted API key at `api.twilio.com` only, and no redirect is followed by the HTTP library: Twilio answers with a redirect (301, 302, 303, 307 or 308) to its media host, and **one** is followed by the provider, only if the `Location` is https on **exactly** `media.twiliocdn.com` or `mms.twiliocdn.com` (`MEDIA_HOSTS`, an exact list; the request is made to the address rebuilt from its parsed parts), **without the key** and with no further redirect; a redirect anywhere else is a failure and the second request is never made. A `Content-Length` over `max_bytes` is refused before a byte is read; the bytes are counted while they stream and the read stops at the first byte over the cap (a usage answer); the whole fetch has a 120-second deadline, looked at after every receive (the body is read with `read1`, so a host that sends a byte at a time cannot hold it longer), and each read a 10-second one. Twilio declares no hash, so none is checked. The file is `<out>/content` only, created with `O_EXCL` and `O_NOFOLLOW`, mode 0600, in the folder the bridge made (opened by descriptor, absolute, not a link, owned by this user); a failed fetch removes the partial file. Answers: 404 or 410 from either host is `gone`; a 401, a 403, error 20003 or error 20403 on the media path is `failed` with a sentence that the key may lack the permission to read media (`contracts/secrets.md`) and **does not stop the provider** (a key that was really revoked is caught by the next send); anything else is `failed` with the status and Twilio's code or the class of the error, **never the body, an address, the key or its SID** (`http.client` errors and the like are caught by class). The one-shot verb `fetch-attachment` exits 2 here, as `receive` does. **Not tested live, to confirm with a real account.** The media hosts, the 16 MiB figure and the address shape have **no source with an access date yet**: they were written from memory and Twilio's documentation was not re-read for this change. To confirm: that the Restricted API key can read media (with the account's media authentication on and off), the exact status of the redirect and the host it points to (`media.twiliocdn.com` and `mms.twiliocdn.com`; any other host fails closed), that the CDN needs no credential, the size limit, and that **Twilio WhatsApp media addresses use `MM...` ids (if they use `SM...`, every media message is dropped, with a log line of the class `media`)**; then record the sources and the dates here.
- **A tap.** When `ButtonPayload` is present the provider emits **only the action**, never `Body`: a payload equal to the template's button id (`see-decisions`) becomes the text `/pending` (the person gets the cards), a payload of the form `<seq>:<operation>` becomes the action of a card button, and any other payload is ignored. `OriginalRepliedMessageSid` (Twilio sets it only for replies to messages of the last 7 days) becomes `reply_to`; a reply to the buttons message of a long card is given the text message's SID, so it binds to the card.
- **Identity.** `From` is `whatsapp:+<digits>`. Since the usernames rollout it can instead be `whatsapp:<CC>.<BSUID>` with no number: the provider tells the two apart, never assumes `WaId` holds digits (it reads `WaId` and `ExternalUserId` only when they have the shape of a number and of an id), learns the pair whenever both arrive together (`identities.json`, 30 days, pruned at start and once a day) and uses the remembered digits for an id seen alone, else the id. List your digits, and the id if you use a username, in `messaging.senders.whatsapp-twilio`.
- **The window.** WhatsApp lets a business send free-form messages only within 24 hours of the person's last message. Twilio sends **no message timestamp** in the webhook, so the clock is the **time of receipt** (Twilio retries once, only on a connection failure, so the delay is small). A card is sent only while the last message is less than **23 hours 30 minutes** old (`window.json`).
- **Outside the window** nothing free-form is sent. The provider sends the **template** (`ContentSid`, no variable) **once for each closed window**, and again at most **every 7 days** while the window stays closed and the bridge still asks for cards (`template_sent_at` decides; a restart never resends it), and answers `deferred`; the bridge keeps the card and sends it after the person's next message (tapping "See decisions" sends `/pending`). Without a template nothing is sent: the answer is still `deferred`, one log line per chat is written every 24 hours at most, and the card goes out when the person writes.
- **Error 63016.** Twilio usually accepts a free-form message and reports error 63016 later, in a status callback (`MessageStatus` failed or undelivered, `ErrorCode` 63016); it may also answer 63016 to the send itself. Either closes that chat's window and sends the template (still once; without a template, only the log line). The callbacks are asked for **per message** (`StatusCallback`), and only for a `MessageSid` this process sent: those SIDs are kept in `sent.json` for 2 days, so a report that arrives after a restart still matches. A card lost that way is already in the bridge's ledger and reaches the person through `/pending`.
- **Sending.** `POST https://api.twilio.com/2010-04-01/Accounts/<AccountSid>/Messages.json`, a form, HTTP Basic with the Restricted API key; `From` and `To` as `whatsapp:+<digits>`, `Body` up to 1600, `StatusCallback`. Twilio has no reply-to parameter, so `reply_to` is not sent. The provider declares `max_text: 1600` and `documents: false`: the bridge cuts a card's text to 1600 with "(continues on the page)", splits replies itself and never offers a document, so each text is one message and the answered SID is that message's. The provider renders the Markdown for WhatsApp (as `whatsapp-cloud` does, same shared corpus) and cuts again at 1600 only because rendering can lengthen a text.
- **Errors.** 20003 (authentication) and HTTP 401: an error event `not-configured` and exit 3. 63018 (rate, 80 per second per sender): `failed` with a short wait. Anything else: `failed` with the status and Twilio's code, **never the body**. There is **no remote ready check** (the key may be restricted so that it can read nothing): `ready` is written when the server listens, and a key Twilio refuses is found on the first send.
- **Rendering** (`render_whatsapp_twilio`) is the shared renderer with the 1600 limit; the tests hold it to the same outputs as the Go renderer on the shared corpus where the text fits.

**State and backups.** `<state folder>/whatsapp-twilio/` (mode 0700; every file 0600) holds `settings.json` (the account SID, the sender, the port, the path, the public URL, the template SID, the button template SIDs), `seen.json`, `window.json`, `identities.json` and `sent.json`, which contain phone numbers and ids. **Exclude the whole folder from backups**: on macOS `tmutil addexclusion <state folder>/whatsapp-twilio` and check it with `tmutil isexcluded`. Secrets are never in these files; they appear only in the `Authorization` header of the sends and in the signature check.

**Messages lost while the laptop sleeps.** Twilio retries a webhook once, and only when the connection or the TLS handshake fails (a timeout or an error answer is not retried). A message the person sends while the machine is asleep or offline is therefore **lost for good**, unlike Meta's up to 7 days of retries on `whatsapp-cloud`. There is no catch-up: the person writes again. A card sent while the person's window is open is unaffected.

**Privacy.** Twilio and Meta both process every message (the messages are not end-to-end encrypted to your machine as with the unofficial client). Who else can read the webhook calls in transit depends on the tunnel you chose (the table in "A public HTTPS address"). The provider writes no message text, number or id to its diagnostics.

**Costs.** Twilio charges US$0.005 for each message, inbound or outbound, plus Meta's fees for a template sent outside the window, plus US$0.001 for a message that fails (Twilio's WhatsApp pricing page; check it for the current figures). A card is usually **one** message (two when its text is over 1024 characters and buttons are on); the template is sent at most once for each closed window and once every 7 days. A tunnel may have its own cost or plan limits (see "A public HTTPS address").

**Leaving Twilio later.** Do not delete the sender: that gives up the WhatsApp number's registration. Move the number with **Meta's migration between WhatsApp Business Accounts** (a verified business, an approved display name, two-step verification off; the display name, quality rating and messaging limits are kept, and only approved templates in the green state are copied). Afterwards use `whatsapp-cloud` and the new account's credentials.

**Tests.** `providers/messenger/tests/test_whatsapp_twilio.py` (verbs, secrets, `setup`, `whoami`, the state folder, a real process over the protocol), `test_whatsapp_twilio_webhook.py` (the signature with Twilio's published vector, the filters, the mapping, the status callbacks, a local HTTP client against the server on port 0), `test_whatsapp_twilio_send.py` (the window, the template, text and Content messages, the errors, the listener over a pipe), `test_whatsapp_twilio_optional_template.py` (setup with and without the template, the send side without it) and `test_whatsapp_twilio_render.py` (the shared corpus), `test_whatsapp_twilio_attachments.py` (the media fields mapped, the strict address and ref patterns, the signature unchanged, the fetch: the key only at `api.twilio.com`, the one redirect to the media host without the key, the cap mid-stream, a gone medium, the key absent from every error) and `test_whatsapp_meta_media.py` (the stream, the folder and the host check shared with the Cloud provider), all offline with Twilio's API and media hosts replaced by fakes. The live test is the maintainer's: the sender's webhook set in Twilio's console, a message from the personal number, a reply, a card as typed commands, the template after 24 hours of silence, and, later and separately, the buttons; for files: a PDF and a Word document sent from the personal number reach the bridge as attachments and are fetched (the key's permission to read media with the account's media authentication on, the redirect and its host, no credential on the CDN), a photo and an oversized file are refused by the bridge, and a deleted medium answers `gone`.
