# The local interface

The folder `runtime/service.py` serves: the static files of the page a person uses to work with the task runtime on
their own machine. It holds no rule of the work. Which words a pending decision takes, what a state leads to and what a
hash must equal are decided by the operations layer (`runtime/ops.py`) and the store; the page shows what an operation
returned and sends what the person typed or clicked.

## Where a rule goes

The page's rules used to be one file, `style.css`. They are one stylesheet for the shared parts and one for each screen, so that the package of a screen edits its own files and no other package's. `index.html` links them in this order, and the order is the cascade: of two rules of the same weight that apply to one element, the one in the later file wins, as the later one in the single file did.

| File | What is in it |
|---|---|
| `css/base.css` | The fonts, the page's tokens (`:root`), the library's overrides, the reset, the icons, and the parts more than one screen draws: dots, tiles, chips, meters, form fields, the checkbox, the command block, the segmented tabs and the accordion row, the viewer, the sheet, rendered Markdown, the reduced-motion rule |
| `css/frame.css` | The frame every screen stands in: the scene host, the top row, the switcher, the KPI column, the camera buttons, the dock (Back, the crumbs, the tracking bar), "Waiting for you", the panel shell and its widths, the command panel, the phone's bottom bar and sheet (up to 899 px), and the layouts of the tablet and in-between bands |
| `css/token.css` | The token prompt and the owl |
| `css/city.css` | The City: the label of a building, the list of projects (the scene's keyboard twin), the line shown without WebGL, the City's sheet on a phone |
| `css/building.css` | The Building: the plate and the phone's floor card, the corner card, the work-order tag, the Building's panel, the floor steps |
| `css/floor.css` | The Floor and the modules the Lobby shows inside its own panel: the Floor's panel and tabs, the Agent tab, the decision cards, the Inbox, the Desk, the Tasks tab, the plan card |
| `css/lobby.css` | The Lobby: its panel and its segmented tabs, the conversation, the request blocks, the "New request" form, the composer with the list of commands, the Desk's rows, the plan card's blocks, the dialog that cancels a request |
| `css/control.css` | The Control room (round 4): the wide panel and its segmented tabs, the filters, the list of skills as accordions and the phone's cards, the caps rows with meters, the chart and its table, the tables, the soft notices, the Connections cards; the parts of the page that `base.css` lacks are built here, scoped to the screen |

- **A rule goes to the screen its selectors serve.** A rule two screens need goes to `base.css` (a component) or `frame.css` (the frame). A screen's own width rules (`@media`) are in its file, after its base rules; the frame's layouts of the tablet and in-between bands are in `frame.css` and carry the tokens of those bands (`--wb-panel-narrow`, `--wb-wait-w`, `--wb-plate-w`, `--wb-card-w`, `--wb-panel-lobby`).
- **A rule that overrides another of the same weight is in the same file or a later one.** A new rule that must beat a rule of another screen's file is written with a selector of more weight, never by moving it. The order of the links is checked by `test_interface_files.py`, and the whole text, read in link order, by `runtime/tests/interface_css.py` (`interface_css()`: every test that looks at "the stylesheet" reads that).
- **A screen's package edits its own stylesheet and its own test file** (`runtime/tests/test_interface_r4_<screen>.py`, beside the older files of that screen), and of the shared files (`base.css`, `frame.css`, `index.html`, this README outside its own section, `runtime/tests/test_interface_files.py` and the other tests that look at more than one screen) only the smallest change it must make, which it lists in its report. `js/floor/*` and `js/cards/*` are the Floor's, and the Lobby only reuses them: a change the Lobby needs in them goes to the Floor package or waits for it.

## The brand

The page's primary colour is the library's one token `--pui-theme`, set once at `:root` in `css/base.css` to the brand pair `light-dark(#6B4429, #C99A6E)` (a brown on a light ground, a lighter brown on a dark one); the one other token of the library the page sets is `--pui-radius`, 0.625 rem (R-12: the cards, plates and sheets are 1.5 and 2 times it). Everything that is "the theme" reads that token and nothing else: the tints derived from it (`--wb-ink-theme`, `--wb-tint-selected`, `--wb-tint-reserved`), the meters, the focus rings, the running dot, the outline buttons, and the scene, which reads the token through a probe element when it is built and when the colour scheme changes (`js/scene/palette.js`; the outline of a hovered or selected object copies `palette.T.theme`, so no scene file holds a colour of its own). To change the primary, change that one line. It is the only colour literal in the stylesheet, and `runtime/tests/test_interface_files.py` keeps it so.

The "working" light of a floor's windows is the library's amber (`--pui-warn`), not the brand brown. On a dark ground the two were looked at side by side in the served page (a working floor beside the selected floor's outline, and the amber dot of a waiting floor beside the brown dot of a running one): the brown `#C99A6E` and the amber `#F59E0B` are about 14 apart in CIEDE2000 and read as two colours at the size of a window, so the amber stays; the identity's alternative, a warm white `#FFE8C2` for the working light, is not used.

The favicon (`favicon.svg`) and the mark (`brand/openhora-mark.svg`) are the identity's drawings with their provenance metadata block and the namespace declaration that only that block used removed, and nothing else changed; a test records the hash of each file and the first path of each drawing, so a new drawing changes those two lines on purpose.

## How to open it

```
python3 runtime/service.py --project <dir>
```

`--project` repeats: the service holds every project it is started with, one building each, and the set is fixed until it is started again. The page does not add or remove one and never opens a folder: the City's "Add a project" takes the folder's path and shows the line that starts the service again with it, with Copy (the head of the line is the service's own start line, `connections.service.start`; the folders of the other projects are the `folder` of each entry of `GET /projects`, which the service knows for every project, accepted or not (A-34)), and, when the person says the folder has no configuration, three numbered steps: the `core-project-init` line (with the autonomy they choose; it makes `state.md` only), then writing `docs/workbench/runtime.json` by hand (the service does not start without it), then the restart line; a path must be absolute (`~/` is refused, quoted it would name a folder called `~`), and a project's name never goes into a line except with every character outside letters, digits, space, `.`, `_` and `-` replaced; "Leave a project" shows the line without that project. Both are the switcher's foot (A-35, round 4: "Add a project..." and "Leave this project...", the same panel from every screen, drawn by the frame in a card with its Close); the City has no box of its own for them (R-22).

It prints one JSON line with the page's `url` and the path of the `token_file`. Open the url in a browser. With the service's opt-in `--lan` it also prints `lan_url`, the address to open on a phone, and a warning first; the page is the same, the token is pasted by hand (it is never in the address), and `GET /token-file` answers the loopback only, so on the phone the prompt keeps its sentence about the first line and shows no command. The bar of the prompt names the address the page was opened on (`location.host`, as text; the `host` option of `showTokenPrompt` is a test's), so the phone shows the LAN address. The prompt is a technical sheet (R-13): a frame 1040 px wide with a line at each side on a ground of faint dots (the text colour at 28 percent
in light and 20 percent in dark), small crosses at the corners of its body, a bar with the mark, the wordmark, `local service · ` and the address the page was opened on (`127.0.0.1:<port>` by default) and the colour-mode button, the eyebrow
`01 · service token`, the title at 52 px, the form, the owl at the right (168 px; 64 px, centred above the title, on a phone) and numbered steps along the foot. The owl keeps watch
(R-15): it blinks and its eyes travel to one side and back in an 8 s cycle, and stands still under reduced motion. The prompt reads
`GET /token-file` (the one request the page sends without a token: no bearer header, and it never carries the token) and shows

## The rules of these files

- **Nothing from another host.** No CDN, no font host, no analytics, no remote import. Every `src`, `href`, `import`,
  `url(` and `fetch` is a relative path inside this folder, a `/api/` path of the service or its one open path, `/token-file`. The typefaces are files of `vendor/fonts/`, named by `@font-face` in `css/base.css`.
- **No build step, no package.** There is no manifest and no tool to run: a file here is the file the browser gets.
- **The token lives in memory and in `sessionStorage`, nowhere else.** Never in a URL, a cookie or `localStorage`; the
  client sends it only as the `Authorization: Bearer` header and logs nothing. There is no exception: the colour mode (`js/mode.js`) is
  not stored either, so nothing is stored but the token (R4D-3, R-4); no module of the page touches `localStorage`, and
  `runtime/tests/test_interface_files.py` and `test_interface_adj_b1.py` keep that.
- **Text is text.** What came from the service goes into the page with `textContent` or a text node; the page never builds
  markup from a string. The one place that reads Markdown is `js/markdown.js`: it builds elements with `createElement` and
  text nodes only, so a tag, a comment or a script inside a document or a reply is shown as typed.
- **No import map.** The service's policy (`default-src 'self'`) forbids an inline script, and an import map is one, so a
  module imports another by a relative path (the 3D library by `js/three.js`).
- **The styling library's images are blocked by the policy.** Perfect UI draws the mark of a checkbox, a radio and a
  select as an inline `data:` image, which `default-src 'self'` does not allow. A panel that needs one of these controls
  draws its mark in a stylesheet of `css/` or uses another element, until the service's policy is widened in a package of its own.

`runtime/tests/test_interface_files.py` keeps these rules: the routes the client calls are routes of the service, nothing
is loaded from another host, no inline script or forbidden call is in a page file, and every vendored file has the hash its
README records.

## The vendored libraries, and how to update one

Three.js (the 3D renderer) and Perfect UI (the panels' styling) are copied from their npm packages without an edit. To
update one: in a folder outside the repository run `npm pack <package>@<version>`, unpack the tarball, replace the
folder under `vendor/` with the package's files exactly as its README lists them, rewrite the version and the hashes in
that README (`shasum -a 256 <file>`), and run `pytest -q runtime/tests/test_interface_files.py`. A vendored file is never
edited by hand: a change to one fails that test.

## How the page stays current

The page is always current with the runtime (WP-9.13). While the tab is visible it asks the service for the change signal once a second
(`GET /api/v1/versions`: for each project a number that grows on every write to its store, whoever wrote it: this page, the dispatcher's
thread, the terminal). When a number moved it reloads everything it shows, so a change made anywhere is on the screen within about two
seconds (one second of waiting for the next read and the time the reads take). A reload is: `projects`, `status` and `agents` of each
accepted project and the followed project's running tasks (`js/data.js`, never from a cache), then each screen's own reads, which it
makes when the stamp it is given moves: the Floor the bodies of the agent's tasks and the documents, the Building the documents, the
Lobby the conversation (above its newest message), the bodies of the requests it shows, the documents and the planning agent's tasks,
the Control room `costs` and, when older than 30 s, the open tab; the Floor and the Lobby also the document that is open; the City, the frame and the scene are drawn from the snapshot. The scene's state (the
figure's pose, the lit windows, the beacon, the badges, the tracking bar) follows the same reload, because it is drawn from the same
data. After any write the page sends it reloads at once, when the answer returns (`api.onWrite`), and a job it started keeps its fast
poll; a button press is one reload: the screen's own call to read again after its write joins the reload the client already asked for
(`coalesce.join`), and the page's own write is not reloaded again by the next read of the signal, because a reload reads the signal before
its data and the watcher takes that as its baseline. A body whose read began before a later change is read again when it ends. A reload
that one project refused (not "not accepted") is read again after 10 seconds, not left to the safety net. With nothing changing, the page makes one small request a second, plus one full reload after 30 quiet seconds as a safety net;
while the tab is hidden it asks nothing, and when it is visible again it reloads once. A server push would save the second a poll waits;
the service sends one response per request and holds no connection (`contracts/runtime.md`, "The change signal"), so it is not built.

A ready task the dispatcher holds for one of the five turn words is queued, with its sentence (`agent at max_parallel` names the agent's `holders`: "Every slot of this floor is held, by #12, #15; it starts when one ends."). The limit of this release: tasks whose skills declare the same output (every task writing `docs/engineering/plans/<task>.md`, a design artifact, a brief) count as one file, so inside one floor they run one after another; different floors run together (backlog R17 makes the files per task).

When the router and tasks both run, the composer's note names the router's run (it is the state that makes a plain line wait); the tracking bar lists the running tasks first and the router's card after them. A floor's `running` chip counts the agent's running tasks over every request, as its state does; `done`, `left` and the board's notes stay the followed request's.

### Waits, queued lines, and what a card hands over (A-23, A-25, A-26, A-29 to A-33)

- **What waits.** A task that waits for another keeps the state `planned`; `waiting_for` ([{task_id, request_id, reason}], `task_id` null for the person's own `after`) is what the page words: "waiting for #10, request #3" on the tracking bar's step and as one chip on the plate ("waiting for #10", or "2 waiting", its tooltip the reasons), under `left`, and one line with the reason on the Tasks tab's row and in the Agent tab. "Go ahead" (`POST /tasks/{id}/go-ahead`) drops a derived wait, "Drop the after" (`drop_after: true`) the person's own. A plan card lists `waits`, `missing` and `cycles` before approval, each task that waits for a task with a "Go ahead" box; the boxes ticked travel as `go_ahead: [task keys]` with the hash shown. The request form and `/new --after n` take "After request #".
- **The conversation during a run.** Tasks run beside the router (PAR-5): a task run never holds the composer. It says, in place and before Send, what runs: the running task of `status` linked ("Task #12 Build the page"), or "N tasks running" linked to the Building, and that a plain line is routed at once; while the router works on a request it names that request ("Planning agent · routing request #2 · for 3 min", A-51) and says a plain line waits for it. Send stays on in both, and a line typed while the router answers is stored by the service with `queued` and shown with the word "queued" until its reply exists; the page reads the conversation again from the oldest queued line while one waits. `Route it` is queued, and says so, only behind the router's run on another request (`routerBusy`); a request made from the form then is shown as recorded, to be routed when that run ends. A question about the state is answered by the service in prose.
- **The unrecognised route.** The question whose payload `actions` are `choose-flow` and `cancel` has its sentence as body, "Show the agent's reply" (`payload.raw` as plain text), "Choose a flow" (the flow list, read once, then `route` with the flow) and "Cancel the request".
- **A request line (C-2, E-20).** Each request block of the Lobby's Conversation has an id (`wb-request-<n>`). The route `#/p/<id>/lobby/conversation/request/<n>` opens the Conversation, scrolls to that block and focuses its title, once per visit; the "Waiting for you" row of a plan decision opens that route (the plan card is under the request's message), so a plan is two clicks from the Building. A request that waits for its route has "Route it"; after a reload, which forgets the flow chosen in the form, the line carries a flow select beside it (the flows read once, "Let the planning agent route it" first): "Route it" sends `route` with the chosen flow, or with none (a model run). The page never changes a request's text. While the router works on a request (`routing` of the request in `status`, A-51, which a reloaded page or another client sees as well as the page that clicked), the line shows a disabled `Routing...` with the run on its tooltip, with no `Route it`, no flow select and no `Cancel request` (the store refuses it); the tracking bar, the Building's "Running now" and the composer's run line say "Planning agent · routing request #2 · for 3 min", and the planning agent's window and owl work (the City's label says "routing request #2" from `routing_request`; the run's words also stand as text under the disabled button; another request's `Route it` stays on and says on its tooltip that the service queues it while a run holds the project), until the run ends and the plan card or the "Not routed yet" notice shows.
- **A card that is done** puts its result on its own line under the chip and the title (the card wraps); an id (commit, pull request) is mono, a sentence is prose, and `kept: n files` with the run folder to copy comes from the payload.
- **A review hands a file over, in two steps (C-17).** "Hand a file over" on the review card sends to the review's task; for a task with the web the runtime's line (`task.drop.line`) stands above the control before the file is chosen; the Agent tab's "Hand a file over" does the same (the current task's body is used as it is, another target is read once). Choosing a file sends nothing: the chosen name and a button "Hand over to task #n" appear (`handOverStep` of `floor/hand-file.js`), and the button sends `handOver`; the button names the task the file goes to now, a refusal the page can know (over 25 MiB, a name the service would refuse) is said at the choice, and a failure leaves the file chosen so that the button can be pressed again.
- **The viewer's image.** The raw route is under `/api/`, so it needs the bearer header: the client returns a Blob (`artifactRaw`), the viewer shows it from a `blob:` URL it revokes when the file changes or the viewer closes, and "Open in a new tab" opens that URL for a png, jpeg or webp (never a svg: a svg is shown in the page as an image only, and a document of the service's origin made of it is a sandbox question nobody verified); bytes of any other type are "cannot show", whatever the list said. The service's policy allows `img-src 'self' blob:` and never `data:`; the library's checked box draws its mark with a `data:` image, so the page's own `.wb-checkbox` draws the checked state in `css/base.css` with tokens.

## What the scene does and does not do

The scene is drawn only when something changed (data, camera, hover, size) or while a state animates: a running project's
beacon, the agent's shadow at the windows of a lit floor (R-19, a 48 s cycle), a decision mark's notification (R-20, 3.4 s) and the owl of a room (R-41: the raised wing waves while it waits, its two wings tap while it works, it breathes and three z rise while it is idle), all at most 30 frames a second, and the camera moving in (the prototype's curve, about 1 s). It draws nothing
while the document is hidden, caps the pixel ratio at 2, stops its ambient animation under `prefers-reduced-motion`, and
without WebGL shows one line of text and leaves every panel and action working. Its colours are read from the page's CSS
custom properties when it is built and when the colour scheme changes. Nothing in it is decorative: no vehicles, people,
birds or weather. `canvas.wbStats()` (a function on the canvas element) returns the frames drawn so far, for a check.

The Building (the floors separate once when it opens, the work-order tag moves
to the next floor once) and the Floor (the camera moves into the room once) follow
the same rules; the camera's and the opening's motions are the prototype's (WP-9.8). A reload that finds the same state, or only other words, does not build the scene
again (`canvas.wbStats()` has `builds` and `relabels`). The City (round 4, R-16 to R-21) is drawn in flat faces from the recipes of the design's `scene.css`, each colour a token or a mix of two (`cityTones` in `palette.js`, mixed in the encoded space as the stylesheet mixes them): a building has a ledge at every floor, windows set back in the wall and nearly the floor's height (the ground floor, the Lobby's, has the same windows as the others, M-27, with the entrance door in place of the second one in front, under its canopy), a roof in the brand colour with a parapet and two units. A window is a warm white while the floor's agent is active (working or waiting for an answer: R-21) and dark otherwise; a lit floor shows the agent as a shadow in the owl's outline coming to its windows in turn (one still figure under reduced motion); a mark (a bar over a cube, the same amber in light and in dark, drawn at 70 percent of its first size: `MARK_SCALE` of `marks.js`, A-60) stands beside a floor that is lit and waits, never beside one that works. The building the person follows or points at wears eight corner brackets in the brand colour, four on the ground and four at the roof, not an outline. A closed building is the drawing's height (0.64 of the rooms': `CLOSED_SQUASH` in `tower.js`) and rises to the rooms' as the walls fade; a project that stops being accepted while its Building is open keeps the open building at its size (the squash is for a closed tower only). **The trees** (A-44, M-5, M-14) are the page's, with variety: a crown that is an icosahedron (20 facets) in four tones decided in the world from the sun at the upper left of the picture (`treeLight`, `crownFacets` in `city.js`), in one of four variants (`VARIANTS`: variant 0 as it was, the others turned about the vertical axis and with their vertices moved by a seeded jitter, their tones decided after the turn so the light stays at the upper left on every tree; no instance is turned, because a turn after the lighting showed a crown from another side), picked for each tree by where it stands (`treeLook`, seeded: the same city every time) with a width and a height of its own (0.9 to 1.1 and 0.9 to 1.15 of its size); a thin six-sided trunk a little narrower at the top (the three sides the camera sees, the one the sun reaches in the bark brown of `cityTones().trunk`, the others a step darker: a mix of the warn, error and ink tokens in light, of the page colour in dark, brown and never yellow); and a flat ground shadow (the shadow ink at 9 percent in light and 42 in dark) 9.5 px to the left of the trunk. Six instanced meshes (a crown for each variant, the trunks, the shadows), none casting a real-time shadow. The City round the lots is drawn beyond every edge the camera can show, in a handful of draw calls (batches and instances). The wheel and a pinch zoom (up to 3 times), a drag pans, a double click on the
ground, the Fit button or the key 0 fit the whole scene, + and - and the arrow keys work with the focus on the scene. The pointer picks meshes only (`pick.js`): the tooltip, the click and the mark name one object. A building of the City has the silhouette of its body as the outline `outline.js` draws a room and what is in it are marked by brackets (below). **The rooms (round 4: R-21, R-23, R-23b, R-28, R-31, R-41, R-42, R-49).** A floor's room is the page's room (`building.html`, `floor.html`, `lobby.html`) in the City's flat style, the same meshes in the City's building while it is closed (hidden behind the walls), in the Building's cutaway, on the Floor and in the Lobby. ## What the Floor sends

Only `js/floor/`, the Lobby's `views/lobby*.js` and `cards/` send a write, through `actions.js`: `answer`, `release`, `approve`, `reject`, `verdict`, `cancel`, `setMode`,
`retry` and `handOver` (with `pollJob` for a job). A card draws one button per word of its decision's `actions` and none for a
word it does not know; an effect or a plan is approved with the hash the card shows, read back from the page's own text at the
click, and a hash that is not the decision's is refused before any request; a blocked change set cannot send a release from

the cards and the Agent tab under a fake document and a fake client and checks what each button sends.

A part reads `env.can(op, kind)`, a getter over the current snapshot's entry, at every draw (it is optional and defaults to allow): a card or action that the policy withholds is left out, a line under the remaining controls says "Turned off for the page: <operations>. Use the terminal." (the operations' own names, never a button's label), the keyboard paths (Ctrl+Enter in an answer, Enter in the composer) ask too, and cards, tabs and the Lobby's thread draw again when the list changes; the "/" list is read again on the reload an accept-config causes. ## How the service serves it

`python3 runtime/service.py --project <dir>` binds `127.0.0.1` only and serves this folder at `/`; the opt-in `--lan` (never the default, with a warning that the page and the token then cross the network unencrypted) also serves it on one private LAN address, to open it on a phone on the same wifi. A file is served when
all of these hold, and is a 404 otherwise:

- its real path (links resolved) is inside this folder, and no part of the path is empty, `.` or `..`, or starts with a dot;
- its extension is one the service knows (html, css, js, json, svg, images, fonts, glTF models, txt): an unknown extension
  is never served;
- it is a regular file of at most 16 MiB. There is no directory listing;
- it is not under `demo/` (the demo mode's files, "The demo mode" below): the service never serves them, by any spelling of the path or case.

Every response carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`; an HTML or SVG document also
carries `Content-Security-Policy: default-src 'self'; img-src 'self' blob:; frame-ancestors 'none'` and `Referrer-Policy: no-referrer`. So a page
here loads nothing from another host (no CDN, no font service, no analytics), runs no inline script or style that the
policy does not allow, and cannot be put in a frame; its images are its own files or `blob:` URLs it built from bytes it
fetched itself (never `data:`).

The static files need no token and hold no data. Everything a page shows comes from `/api/v1/...`, which needs the
token: the person pastes it once per browser session from the token file the service prints the path of (never the token
itself), the page keeps it in memory only, and sends it as `Authorization: Bearer <token>`. It is never in a URL, a
cookie, a log line or the page's source. The service has no cross-origin header, so no other origin can read an answer.

## What a page must do with what it receives

- **Text is text.** A reply, a title, a comment and every field a model or another person wrote leaves the service as a
  JSON string; a page puts it in the document as text (`textContent`), never as markup.
- **A path is data.** Results carry host paths (a run folder, an effect's file). They are shown as text, never as a link
  to open.
- **A job is asked for again.** A route whose operation calls a model or a platform answers `202` with a job; the page asks
  `GET /api/v1/jobs/<n>` until its `state` is `done` or `failed`. The records are in the store; a job lives only in the
  service's memory.
- **A button for each word of `actions`, and for no other.** Whether a decision can be approved, rejected, answered or
  released is the operation's answer.

## What the approval of an effect is worth

An effect (a pull request prepared up to its confirmation gate) is approved from the page with the hash of the content the
page showed: the card draws the exact content and `payload_sha256`, and the click sends that hash, which the operations
layer compares with the effect's file before it executes anything. The guarantee is that the person's browser sent the hash
of the content it displayed. The token and the checks of `Host` and `Origin` keep a stranger and another page from sending
it; they cannot tell a click from a script that holds the token, which is the person's own machine and account. A chat
channel and the MCP channel never approve an effect: the service passes the channel `page` itself, and a request cannot name
one.

## Not here

`accept-config` is not a route: a configuration hash is accepted in the terminal only, so a page can never accept the
change that widens what an agent may do. The same holds for `set-mode --accept`, the one terminal command that sets a wider mode and accepts it: the mode route takes the mode and nothing else, and the Agent tab only shows that command to copy. `run-next` is not a route either: the dispatcher decides what runs.
