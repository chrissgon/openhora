# The task runtime

Code that turns a request into tasks and runs each task as one skill, once, in the container the skill was
proven in (`evals/executor.py`), on a fresh copy that holds only what may enter it (`workcopy.py`). What a run leaves
comes back to the project by one rule of paths, and the task then waits for the person. The design is the
platform plan, `docs/architecture/platform-plan-2026-10-05.md` (removed on 2026-10-15; `git show bc830832:docs/architecture/platform-plan-2026-10-05.md`); this folder began as its stage 1, an end-to-end
skeleton, and holds the stages built since: the limits that live in code, each with its test, are listed in
`contracts/runtime.md` ("The limits").

It is a second runtime only in its code. The first one, `scripts/runtime.py`, runs one agent on social
comments and stays as it is until that agent moves to the container (stage 7). Both keep their state in the
same store (`providers/store/sqlite.py`): the tables of this one are migrations 2 to 9 of that file.

## Modules

| File | What it owns |
|------|--------------|
| `lab.py` | The lab facade: the one file here that talks to the lab, through the execution kit `evals/execution.py` (the names of its `__all__`, and of its `STATUS_NAMES` in the status script). Runs one skill once in the container; the attempts of a run (the pause on the account limit, the refusals, the early end, the retries) are made by the lab's one function, `evals/run_attempts.py`, reached through the kit, and the stopping is the lab's own: the runtime has no loop of its own |
| `ops.py` | The operations layer: every operation a shell can perform, once. | `ops_core.py` | The names every module of the operations layer shares, once: `ROOT` (the checkout), `OpsError`, `context`, `store_module`, the store call (`_stored`), the locks (`_config_lock`; and, under `<data_dir>/locks/`, the task lock `_task_lock`, the router's `_route_lock`, the short `_claim_lock`, the re-entrant `_write_lock`, the `_dispatch_lock` and the `_effect_lock` of an executing effect (`_effects_running`), with `_try_lock` that probes a lock and writes nothing), the runtime's own key for each model (`_own_key`, `_model_key`, `Keys`), the billing of a model (`_model_billing`), the evidence recorder's name (`EVIDENCE`) and the data-folder names. | `ops_say.py` | The conversation with the planning agent: `say` (one turn: a command of the table, a question about the state answered by code, an answer to the router's question, or a new request routed with the conversation's memory; a line typed on the page while the router answers another request is queued; the terminal and the MCP mode refuse it), `route_queued` (answers the oldest queued line, or routes the oldest queued request, when the router's lock is free), `chat_memory` and their helpers. | `ops_runs.py` | The runs of tasks and the dispatcher's round: `run_task` (one named task in its own lock `task-<id>.lock`: recovery of what dead processes left, admission by `parallel.admit`, the claim and the run row under the claim lock, the run, the push of the documents it returned), `run_next` (the person's verb: picks the oldest ready task the rules let in and runs it in this process), `dispatch` (a round: decides a list of starts and starts each as a child process, `cli.py run-task`, with its output in `<data_dir>/task-runs/children/`; with `wait` it keeps reaping and deciding until no child of its own is alive, because a scheduler's job kills what it leaves; the local service passes `wait=False` and reaps on every tick), `spawn` (the one seam a test replaces), `reap`, the report of the runs that ended (`dispatch:reported`), the stop of the children (`stop`, `stop_children`) and `_recover`. | `ops_cancel.py` | Cancel a request and stop a task at any moment (R18, limit L41): `cancel` and `stop_task`. In this order: the request's effect lock (an executing effect is never interrupted: the call is refused, nothing written, nothing signalled), the stop request written first under the project's write lock (`request_stop`, `task_stop` of the store: the tasks that are not running are cancelled at once), the running runs ended through `run_stop`, what a dead holder left finished by the store's rule. A second call answers `already`. The write of an output (NOTION-OUT) takes minutes under the request's effect lock and the lock of its decision (`lock_name`, `release`): a way to cancel a request nothing runs for (`request_cancel`: the direct reply, a routine closing its stops) and `cancel_request` when it has nothing to signal leave that decision open, with its task, and cancel the rest (`writing`, `said`, `kept` in the answer); one that would signal a running task is refused, nothing stopped. | `run_stop.py` | The process mechanics of a stop: `stop_tasks` (the holder of each task lock gets TERM, then KILL after 30 s, never this process and never a lock nobody holds; the lab's containers, key proxy and network that the process tree named are removed through the container tool by `orphans.remove_runs`), `snapshot` (`ps`, the lab run ids a `docker run` line names) and `watch` (a thread beside the router's lab call that ends the lab's runs of the process when the request's stop request is set; the router's run is inside the calling process and is never signalled) |

names an AI tool, although the validator does not check this folder: the model and its adapter come from the

`<project>/docs/workbench/runtime.json` holds no secret and is accepted by its hash (`accept-config`). The file is closed: `runtime/project_config.py` refuses a key it does not know and, when one is close to it (`difflib`), names that one. The defaults below are the code's (`TASK_RUNTIME_KEYS` and the checks beside it); `python3 runtime/project_config.py --project <dir>` prints the checked configuration and its hash.

## The MCP mode

`python3 runtime/mcp.py --project <dir> [--project <dir>]...` is started by an MCP client, not by hand: it speaks JSON-RPC 2.0 on standard input and output, one message per line, and writes nothing else to standard output. In a client's configuration it is a server whose command is `python3` and whose arguments are `<this checkout>/runtime/mcp.py --project <dir>`; it needs no key, no token and no network.

What the client gets, `tools/list`, is one tool for each row of `runtime/operations.py` that lists the `mcp` channel: the reads (`status`, `pending`, `task`, `flows`, `progress`, `agents`, `conversation`, `skills`, `costs`, `connections`, `artifacts`, `artifact`, `version`) and `request`, `route`, `answer`, `release` (a draft) and `say`, then `projects` and `job`: a model client may request, route, answer, release a draft and say, and nothing else. A tool takes the operation's arguments by name, and `project` when more than one project is served. A tool that calls a model or a platform (`route`, `release`, `say`) starts a job and returns it at once (`state` `running` and a `poll`); the tool `job` with `{"job": <n>}` asks for it again.

What is refused: `approve`, `reject`, `cancel`, `stop-task`, `retry`, `accept-config`, `run-next`, the standing approvals and every other row without `mcp` have no tool; approvals, rejections, cancellations and retries are made in the terminal or on the page, where the person is. The same holds for a command typed into `say`: `/approve`, `/reject`, `/retry`, `/cancel` and `/stop-task` answer `/<command> is done in the terminal or on the page` and do nothing. An effect (a publication, a pull request, a message sent) is approved only with its hash, in the terminal or on the page, or on a messaging app the project grants that effect's word; never from here. A project may grant this mode plans (with their hash), acceptances, reject-cancel and retry (off by default; `channels.mcp`, accepted with `--widen`), and `tools/list` then shows `approve`, `reject`, `cancel` or `retry`. An unaccepted configuration is refused on every tool with the sentence of `412` until `accept-config` is typed in the terminal. A refusal is a tool result with `isError: true`; a bad argument or an unknown tool is a protocol error. The log on standard error holds no argument and no result, and the traceback of an internal failure. A project may narrow this list further with `"channels": {"mcp": ["read", "talk", ...]}` in its `runtime.json` (it must list `read`; a change takes effect after `accept-config`): `tools/list` still shows the ceiling's tools, and the check that enforces the policy is made at each call, per project, so a call the policy withholds is a tool result with the sentence. `say` is the group `talk`, which also creates and routes requests; `request` and `route` are the group `request`. The full rules, the errors and the shutdown are in [contracts/runtime.md](../contracts/runtime.md), "The MCP mode".

## The messaging bridge

`uv run --with keyring==25.7.0 python3 runtime/messaging.py --project <dir> --platform telegram` is started by the person and runs until SIGINT or SIGTERM. The project's `runtime.json` names who may write to the bot (`"messaging": {"senders": {"telegram": ["<your Telegram user id>"]}}`) and, optionally, `"notices": "count"` (a count and a link instead of the text), a `page_url` and a `"channels": {"messaging": [...]}` policy; the default policy is read, talk and answer, so approving, releasing, rejecting, cancelling and retrying from the app are turned on by listing their groups. Like every change of the file, they take effect only after `accept-config` in the terminal. The bot's token is stored once with `uv run --with keyring==25.7.0 keyring set openhora messenger-telegram`; an effect is never approved from the app. `service.py --messaging telegram` starts the bridge for you as a child of the service, with the same projects, and stops it with the service (so an upgrade note says: the bridge child stops when the service stops). `--messaging telegram,whatsapp-twilio` (or the option repeated; at most 6, no name twice) starts one bridge per platform from the one service: every app gets its own card, a decision resolved in one app is refused in the others, conversations are per app, and writing in two apps at once may answer "busy" in one; give two official WhatsApp providers different ports in `setup`. A project that is not accepted yet, or lists no sender, is skipped and looked at again every minute; a second bridge for the same bot exits 4 with the lock's path. The contract is "The messaging bridge" of `contracts/runtime.md`.

## The channel policy

The `channels` column of the table of operations is the ceiling of a channel; a project narrows it in `runtime.json` with named groups, for the channels `page`, `mcp` and `messaging` (never the terminal, never `chat`): `"channels": {"page": ["read", "talk", "approve-plans"]}`. The groups are `read`, `talk` (also creates and routes requests, and answers the planning agent's open question), `answer`, `release`, `request`, `approve-plans`, `approve-acceptances`, `approve-effects` (the page only), `approve-effect-create`, `approve-effect-write`, `approve-effect-send`, `approve-effect-publish`, `approve-networked-plans`, `go-ahead`, `reject-cancel`, `brakes` (`cancel` and `stop-task`: R18, turned on for messaging by listing it; `cancel` is in both groups), `retry`, `set-mode` (also `set-model`), `consent` (the page's `give-consent`, which `set-mode` does not imply), `dispatch`, `documents` and `verdict`. A channel with no entry keeps its ceiling (messaging keeps its closed default: `read`, `talk`, `answer`, `routine-brakes`); a `page` or `mcp` list must include `read`. On the page, `cancel`, `stop-task` and a move down of an agent's mode are never withheld (a move up needs `set-mode`). The local service answers a route the policy withholds with `409` and the sentence before anything runs, `GET /projects` lists per project what the page may do (`permissions`), and a typed line is checked under the channel that carries it and never approves an effect. A project widens a channel only by a grant (`operations.GRANTS`: `approve-effect-<word>` and `approve-networked-plans` for messaging, `approve-plans`, `approve-acceptances`, `reject-cancel` and `retry` for the MCP mode), accepted only with `accept-config --widen <the sha256 of the widening list that config shows>`. The service's own dispatch loop is not governed by the page's policy. The contract is "The channel policy" of `contracts/runtime.md`.

## Trying it

A project is configured with four absolute paths in `<project>/docs/workbench/runtime.json` (the optional keys are in "The keys of `runtime.json`" above):

```json
{"workbench": "<this checkout>", "data_dir": "<a folder outside every repository>", "store_db": "<data folder>/tasks.sqlite", "sources_dir": "<a dedicated folder, apart from the data folder>"}
```

Every command refuses a configuration whose hash is not the one the person accepted last. Read the file, then
accept it with the hash the refusal shows (and again after every change of the file):

```sh
python3 runtime/cli.py accept-config --project <dir> --sha256 <hash>
python3 runtime/cli.py request  --project <dir> --flow market-positioning --text "<what you want>"
#   or, without --flow, the router plans it: a model call, like run-next; then approve the plan it opens
python3 runtime/cli.py request  --project <dir> --text "<what you want>"
uv run --with keyring==25.7.0 python3 runtime/cli.py route --project <dir> --request <id>   # or --flow <name>: no run
python3 runtime/cli.py approve  --project <dir> --id <n> --sha256 <the plan's hash>
#   go-ahead on a task that is already waiting: python3 runtime/cli.py go-ahead --project <dir> --task <id>
#   a plan lists the waits the runtime derived (docs/brand/identity.md, written by task #10) and the required inputs nothing writes;
#   add --go-ahead <task key> (repeated) to drop the waits of a task, and request --after <id> to run a request after another
uv run --with keyring==25.7.0 python3 runtime/cli.py run-next --project <dir>   # needs docker and the credential
python3 runtime/cli.py pending  --project <dir>
python3 runtime/cli.py answer   --project <dir> --id <n> --text "<your answer>"
python3 runtime/cli.py release  --project <dir> --id <n>
python3 runtime/cli.py status   --project <dir>
#   sources: give the project something to read (a file, or --url <Notion page address>; source-drive opens Google's Picker; source-onedrive --search lists your OneDrive files to choose from; source-mail and source-calendar read a window of your mailbox or one calendar as a dated snapshot), then see the catalog
python3 runtime/cli.py source-import --project <dir> --source <id> --file <path>
python3 runtime/cli.py sources  --project <dir>
#   flows of the workbench and of the project, with the flow check; a model per request: run-next --model <id>|auto
python3 runtime/cli.py flows    --project <dir>
```

The local service reads and writes the same project through a page (`interface/`): start it with the `uv run` form, which is also what lets it find the credential, and it dispatches the ready tasks by itself every 30 seconds, as far as the modes and the daily caps of the area agents allow (`--no-dispatch` turns that off; `status` then says `dispatch off` for every ready task of this service, and `run-next` above runs one by hand). A project that already has the scheduler's two jobs (`contracts/runtime.md`, "The dispatcher's two jobs") should be served with `--no-dispatch`, so that two dispatchers do not run:

```sh
uv run --with keyring==25.7.0 python3 runtime/service.py --project <dir> [--no-dispatch]
```

At its start it logs, on standard error, what it found (the secret store, the credential, docker, the eval image, dispatch) and, when the secret store cannot be read, the command above. The commands that the service and the operations name in their sentences (the `accept-config` that a refused route asks for, the `next` of `set-mode`) are absolute and carry the same `uv run` prefix when the service was started that way, so they can be copied and typed from any folder. From the page the mode of an agent can only be narrowed (stop, supervise): code accepts that change at once, because it widens nothing. A wider mode is yours, in the terminal: the Agent tab shows `set-mode --project <dir> --agent <name> --mode <mode> --accept`, one command that sets the mode and accepts the hash it makes (`by: "person"`), provided the file was the accepted one before, so the only difference you accept is that mode; with any other unaccepted change in the file it refuses and writes nothing, and you read the file and type `accept-config`. A page never passes `--accept`.

Every run records a use of its skill with the existing recorder (`scripts/evidence.py record --start`, with the
model and adapter of the gate file), in the project's `.workbench-local/evidence/`; a use that cannot be recorded
never stops a run. The verdict on what a run delivered is yours, once per run:
`python3 runtime/cli.py verdict --project <dir> --run <run id> --word worked|corrected|failed`.

A run goes to a model only with a key for it. The runtime's own key for a model is the secret `WB_RUNTIME_KEY_<variable>`, one for each
variable a model's credential travels under (registry `runtime/secrets.json`; the one for `OPENROUTER_API_KEY` is kept under the
store username `runtime-floor`, as the single key of earlier releases was): store it when you want the runtime's runs on a key of
their own, with a spend cap set at the provider. It wins when it is stored. Without it, a run uses the lab's key for the model: the
variables `pass_env` of its entry in the gate file, set or found in the secret store the way the lab's runner finds them. A model
with neither is no candidate of `auto`, and a model you name does not start. The routing a run returns names the key by its source,
never by its value: `"key": "runtime"` or `"key": "lab"`.
`proof --project <dir>` shows, without a model call, where each skill in use would run and why.

`run-next` calls a model: it runs the skill on the model chosen for it (`--model <id>|auto` names one; `proof --project <dir>` shows what would run and each model's band, price and
expected cost without calling a model), in the eval container. It
writes no lab evidence and edits no file of the measurement.

After a run the task waits on one pending decision, unless the skill stopped on a missing input that another
skill writes (ending `blocked`): then the task is `blocked`, and `retry` makes it ready once the input exists.
A run that wrote nothing (or changed only the state file) and asks (ending `question`) opens a `question`, which is answered. Every other ending opens a `review`, whose body is the whole reply: a
run that wrote a declared output and still asks (ending `draft_with_questions`) included. A review is released
as it stands (the task is done; the document keeps its open questions and stays a draft) or answered (the task
runs again with the answer). A skill whose runtime manifest sets `mandatory_milestone` is a milestone whatever the
flow file says (the plan shows `yes, mandatory`); the review of its delivery says that the next task accepts it only
with your approval written in the document, and carries `"mandatory_milestone": true`.

## Tests

`uv run --with pytest==9.1.1 pytest runtime/tests`: offline. A stand-in adapter (a shell script) and two
invented skills replace the container and the model (`runtime/tests/standin_tree.py`); the parity test gives
the same adapter output to the lab's runner and to `lab.py`, expects the same classification, and checks that
both reach one function and that `runtime/` keeps no loop of its own.

No test reads the real secret store: the root `conftest.py` forces the null keyring backend (`PYTHON_KEYRING_BACKEND=keyring.backends.null.Keyring`) for the test process and for every child a test starts with an env of its own, also where `uv run --with keyring` installs the library (`contracts/secrets.md`, "Rules").
