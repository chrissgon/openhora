# Secrets contract

The workbench is automation that runs anywhere: a laptop, a cloud session, CI and the agent runtime. Every script and provider asks for a secret by name through one resolver, `providers/secrets/resolver.py`, and never knows where the value lives. Only where the value is stored changes between environments; the code path is the same.

## Rules

- A secret is read only through the resolver. A provider, script or eval never reads a credential from its own environment variable or the OS secret store directly. The direct uses of the store are the writes of an authorization's own file: an `auth.py` (or `*_auth.py`) stores the record of an authorization it has just run, and its `forget` command, where it has one (`providers/calendar/google_auth.py`, and the one of `providers/documents/onedrive_auth.py`), deletes that same record and no other; its `--check` or `check` reads the record back through the resolver, like the provider does. One further write is allowed (decision of 2026-10-17): the provider `providers/documents/onedrive.py` (Microsoft replaces the refresh token on every use) writes the new token back into that one record, only when the record was found in the store and still holds the token the provider used.
- Lookup order, the same everywhere: the environment variable named like the secret, then its aliases, then the credentials directory (a file named like the secret, for a machine with no desktop session), then the OS secret store (keyring, service `openhora`, the username in the registry), then, only for a name the person mapped in the password-manager mapping file, the password manager ("The password manager" below). The order is fixed: the person cannot change it, so the environment lets CI and a cloud session override, and a stale entry in the OS secret store shadows the manager (`--list` and the doctor mark a name that is also mapped). The first non-empty value wins. A store that raises instead of answering (locked, or no backend) is told apart from a secret that is not stored: `resolve_state` says `locked`, `--check` exits 4, and every message says "the secret store is locked or unavailable: unlock it" and not "missing". The credentials directory is `OPENHORA_CREDENTIALS_DIR`, else `CREDENTIALS_DIRECTORY` (what a systemd unit sets for `LoadCredential=`), else `~/.config/openhora/credentials`; the folder must be this user's with mode 0700 and each file 0600 or 0400, and a link is refused (`docs/architecture/platform/unattended.md`).
- Compatibility stage: a name not found under the service `openhora` is looked up under the service the workbench used before it was renamed, `ai-workbench` (`LEGACY_SERVICE` in the resolver), so a credential stored earlier keeps working. The resolver's `--check` and `--list` say which service answered (`service: "ai-workbench (legacy)"`), so the person knows what to store again; every write (the command the runtime shows, the records an `auth.py` stores) names `openhora` only. The fallback is removed with the next change of the lab models (backlog T23). A job scheduled before the rename runs a snapshot of the provider with the resolver of that day, which reads `ai-workbench` only, so the old entries are kept until those jobs have run or are scheduled again; delete them only then.
- Never in the repository, a project file, a flag, a prompt or the conversation. The resolver, `scripts/doctor.py` and every provider print where a secret was found (`environment (NAME)` or `secret store`), never its value, not even partially.
- Tests never touch the real secret store. The `conftest.py` at the repository root (with the `pytest.ini` that makes the root pytest's rootdir, so that it is loaded for any test folder run alone) forces `PYTHON_KEYRING_BACKEND=keyring.backends.null.Keyring` for the test process, for the keyring library when it is already loaded, and for every child process a test starts with an env of its own (a minimal one carries nothing of the parent's). It matters wherever the keyring library is installed (`uv run --with keyring`), where the machine's store would otherwise answer, and on a Mac ask for the key `openhora`. `scripts/tests/test_test_isolation.py` fails when a test folder would run without it.
- One secret per purpose, with the minimum permission listed below. A permission that writes (dismissing alerts, publishing) lives in a separate secret from the one that reads, when the service allows it.
- A secret a provider reads is added to `REGISTRY` in the resolver and to the table below in the same change; the resolver's tests compare the two cell by cell and fail when they disagree.
- A secret only an adapter's runs need (a model provider's key, a login token of the tool the adapter drives) is registered by that adapter, in the `secrets` list of `adapters/<harness>/adapter.json`, with the same fields as a registry entry (`name`, `purpose`, `permission`, `readers`, and optionally `store_username`, `aliases`, `note`, `set_local`) and one more, required in a manifest: `billing`, how the credential is billed ("How a credential is billed" below). The core lists none of them and the resolver never opens an adapter by itself: a caller outside the core hands it the file (`--registry <file>` on the command line, `register_file(path)` in code) and the list is merged for that call. A name two adapters register must agree on its store username and aliases.
- A new place to keep secrets is a new lookup function in the resolver, after the last one; callers do not change. The password manager is the fourth place ("The password manager" below); a second manager is one more class in `providers/secrets/password_managers.py` and a word of the mapping file's `backend`.

## Where to put a secret, per environment

| Environment | Where | How |
|-------------|-------|-----|
| Cloud session | the environment's settings, as an environment variable | name it exactly like the secret (`VCS_GITHUB_TOKEN`) |
| CI | a repository secret, mapped to an environment variable of the same name in the workflow | `env: VCS_GITHUB_TOKEN: ${{ secrets.VCS_GITHUB_TOKEN }}` |
| Local machine | the OS secret store (preferred), or an export in the shell | `uv run --with keyring==25.7.0 keyring set openhora <username>`: the value is typed at a hidden prompt, never on the command line |
| Headless machine (a server with no desktop session) | the credentials directory | a file named like the secret, mode 0600, in a folder of mode 0700; the value is what the environment variable would hold (for a token, the bare token) |
| Company machine with a password manager | the password manager (1Password first), through its command-line tool | a reference such as `op://Example Vault/github-read/credential` in the mapping file, never the value; the person signs in (the desktop app's unlock on a laptop, a service account's token in the credentials directory on a headless machine) |
| Agent runtime | wherever the machine it runs on keeps secrets (one of the rows above), through the same resolver | the runtime's configuration holds paths and limits only (`contracts/runtime.md`) |

Check what is set, without printing any value: `python3 providers/secrets/resolver.py --list` for the table below, or `python3 scripts/doctor.py`, which adds the secrets every adapter registers and names the requirement classes that read each one.

**The password manager.** The fourth place, asked only for a name written in the mapping file `$XDG_CONFIG_HOME/openhora/password-manager.json`, else `~/.config/openhora/password-manager.json`. It holds references and never values: `{"backend": "1password", "account": "<optional sign-in address>", "timeout_seconds": 15, "references": {"VCS_GITHUB_TOKEN": "op://Example Vault/github-read/credential"}}`. Without the file nothing changes. The file is checked like the credentials directory (not a link, a regular file, this user's or root's, mode 0600, at most 64 KiB, JSON with only those four keys, a known backend, and references of the form `op://<vault>/<item>[/<section>]/<field>`), and a file that fails is `unsafe`: the manager is not called. Each lookup calls the vendor's tool once (`op read <reference>`, no shell, no terminal, a deadline, a minimum environment) and keeps nothing; the tool is never called inside an eval container (limit L39 of `contracts/runtime.md`). Sign-in is the person's: the resolver never signs in or unlocks. A manager that is locked, not signed in or not installed is `locked`, never "missing"; only the tool's answer that the item or field does not exist is `missing`. The manager's own sign-in, `OP_SERVICE_ACCOUNT_TOKEN`, is found in the environment, the credentials directory or the OS secret store and cannot be mapped. A token that is only exported never reaches a provider the runtime starts (`provider_environment` strips `OP_*`), so for a provider only the credentials directory or the OS secret store works.

**Variables passed into an eval run.** The names have one home: the `pass_env` of each model's entry in `models` of `evals/eval-gate.json` (and the runner's `--pass-env` flag for a run by hand). The eval runner checks each of those names against the secrets the adapters register and takes no name from that registry: a name that is registered for eval runs and missing from the environment is filled from the OS secret store, so a key kept there reaches the runs without an export; any other name is passed as it is. A variable named for one model's runs never reaches another model's runs.

**Where the eval models' credentials live during an eval run.** Not in the run. Since 2026-10-03 a model's provider key is held by the key proxy of the eval network (`evals/container/keyproxy/`, whose `keyproxy.json` names the variable): a container of its own, beside the egress proxy, that the eval executor starts with the key in its environment. The run container gets a placeholder in the key's variable and the proxy's base URL; the proxy forwards the provider's API path only, to the provider's one host, over HTTPS and through the egress proxy, and adds the key to each call. It also pins a model's provider where its entry names one (`provider_pin`): on every POST to a path ending in `/chat/completions` it sets `"provider": {"only": [<the route's provider_only>], "allow_fallbacks": false}` in the body, whatever the run asked for, and it refuses a body that is not a JSON object. Another model's credential, such as the maintainer's account token, is held the same way by a key proxy of its own, on networks of its own: a run gets a placeholder and its own model's proxy address, can spend its own model's credential through that proxy and cannot reach another model's proxy. A model under test can still spend a credential through its proxy, within that credential's limit, but cannot read it, print it or carry it to another host. The runner still replaces every passed value in what a run leaves, by exact value, before anything is stored or graded.

## How a credential is billed

Every entry of the `secrets` list of an adapter's manifest states `billing`, one of three words, and `scripts/validate.py` fails (an error, not a warning) on an entry without one or with another word. The runtime reads the words, and nothing else about money, from the manifests (`runtime/billing.py`), to decide which daily cap a run counts against (`contracts/runtime.md`, "The daily caps"):

| Word | A run on this credential | Counted against |
|------|--------------------------|-----------------|
| `subscription` | is covered by a fixed fee (an account's login or long-lived token); what a run costs is not billed | `max_runs_per_day` |
| `metered` | is paid by use (an API key of a model provider); the cost of the run is recorded | `max_usd_per_day` |
| `free` | costs nothing and needs no key: a model on the person's own machine | `max_runs_per_day` |

`free` is for a credential-less local model. No adapter has one today, so no entry of this checkout carries it; the word exists so that an adapter for such a model declares itself `free` (through `login_billing` below, there being no variable) without a change to the caps.

A harness that holds the credential itself (the login of its own command-line tool, no variable passed) declares it once in the manifest, outside the `secrets` list, as `"login_billing"`: one of the same three words, read when a run passes no variable. A manifest without it and a run without a variable have no billing the runtime can know, and the dispatcher does not start the run (it never guesses a cap).

`login_billing` is reachable only in a configuration whose model passes no variable; inside the eval container the CLI's login does not exist, so a runtime run there always passes a variable.

A credential two adapters list has the same word in both (the validator checks it), and a run that passes several variables is billed by the strictest: `metered`, then `subscription`, then `free`. Today the long-lived token of the first lab model's harness and that harness's own login are `subscription`, and every model provider's key an adapter registers (a model's alternative key, the provider keys of the other models, the key for the open-network eval cases) is `metered`; the manifest of each adapter is the list.

## The runtime's own keys

The task runtime may keep a key of its own for a model, apart from the lab's. They are not rows of the registry above: `runtime/secrets.json` lists them, and the runtime hands that file to the resolver (`register_file`), as an adapter's manifest is handed. Each is optional and is named `WB_RUNTIME_KEY_<the variable a model's credential travels under>`; the runtime uses it only for a model that passes exactly one variable (`ops_core._model_key`), and a variable the file does not list is still registered from the same pattern, with the store username `runtime-<the variable in lower case, hyphens>` (`ops_core._own_key`). When it is stored, every run the runtime routes to such a model uses it, and otherwise the run uses the lab's key for the model (`contracts/runtime.md`, "The choice of the model").

| Secret | Store username | For the models whose credential is |
|---|---|---|
| `WB_RUNTIME_KEY_OPENROUTER_API_KEY` | `runtime-floor` | `OPENROUTER_API_KEY` |
| the second entry of `runtime/secrets.json` (the same pattern, for the account token of a lab model's harness) | the entry's `store_username` | that account token's variable |

## Credential files that are not resolver secrets

The WhatsApp provider (`providers/messenger/whatsapp.py`) has no token in the registry: its credential is a file, the session of a linked device, `session.db`, in the `whatsapp/` folder of the per-user state folder (`$OPENHORA_STATE_DIR`, else `$XDG_STATE_HOME/openhora`, else `~/.local/state/openhora`). The file is 0600 and the folder 0700, checked before every use; SQLite's `-wal`, `-shm` and `-journal` files beside it are made under umask 077. It is made by the program's `pair` command and read only by that program. Whoever holds the file holds a linked device of the account (it can read and send as that number), so it is never copied, never put in a project, a repository, a backup or a log (the README of the messenger providers says how to exclude it from backups), and it is revoked from the phone (Linked devices). It is not read through `providers/secrets/resolver.py` and appears in no table above.

## Why

Decided on 2026-09-28 (backlog S13): the first calls to real services showed each provider resolving its credential its own way, a cloud session's own `GITHUB_TOKEN` shadowing the maintainer's token (fixed with `VCS_GITHUB_TOKEN`), and a model provider's key living only in one shell and lost to later sessions. The lookup order (environment, then the OS secret store) is the one the providers already used; a password manager was added as a fourth place on 2026-10-15 (backlog S16, built in pull request #421; `git show 156a08cb:docs/backlog.md`).

Decided on 2026-10-02: the registry named one AI tool's credential variable, its store name and three adapter paths, against the rule that the core names no AI tool and never reads an adapter. Each adapter now registers its own secrets, and the names passed into eval runs stay in the gate file alone.
