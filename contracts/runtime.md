# Runtime contract

## What the runtime is

The runtime runs work without a person at the keyboard and keeps the person in charge of what matters. A person writes a request; code plans it as tasks from a flow file; each task runs as one skill, once, in the same container and through the same entry in which the skill was proven in the lab; what the run leaves comes back to the project by one rule of paths; and the task then waits for the person on a pending decision: a question to answer, or a delivery to release or send back. Releasing is not approving: a released delivery stays a draft in the project's state file. The runtime names no AI tool: the model and its adapter come from the gate file, `evals/eval-gate.json`, and adapters do the rest.

Two runtimes exist today. The first runtime (`scripts/runtime.py`) runs one agent on social comments and stays as it is until that agent moves to the container (stage 7 of the platform plan, `docs/architecture/platform-plan-2026-10-05.md`). The task runtime (`runtime/`) began as stage 1 of that plan, an end-to-end skeleton accepted on 2026-10-05 (`docs/architecture/skeleton-findings-2026-10-05.md`), and holds the stages built since ("Pieces" below). Both keep their records in one store, `providers/store/sqlite.py`.

## The first runtime (until stage 7)

The runtime starts agents without a person at the keyboard: a scheduler fires, the runtime finds new work, runs an agent on it through an adapter, and executes the agent's proposal only when a deterministic gate allows it. It names no AI tool; adapters do. Decided on 2026-09-28 (`docs/decisions.md`, "An agent runtime as a new, tool-free layer"); first built for one agent, `social-manager` (backlog PB7), on a Mac with the launchd scheduler.

### Pieces

| Piece | Where | What it does |
|-------|-------|--------------|
| Trigger | `scheduler:job` class, a recurring job | runs `scripts/runtime.py tick` every N minutes |
| Runtime | `scripts/runtime.py` | finds new work, records it, runs the agent, applies the gate, executes, logs |
| Store | `store:runtime` class (`providers/store/`) | events, cursors, runs, inbox, actions; many writers at once |
| Agent run | `runtime/cli.py contained-run` (the first runtime, `scripts/runtime.py`, until WP-7.5: `adapters/<harness>/run-agent.sh`) | runs one skill on one task in the eval container, on a copy of the artifacts it declares, and returns its answer |
| Gate | the skill's own script (`mkt-engage/scripts/policy_gate.py`) | decides whether a proposal is inside the person's approval |
| Actuator | a provider (`publisher:<platform>`) | executes, with an idempotency key |
| Configuration | `docs/workbench/runtime.json` in the project | paths, model, budgets, and optionally the implementation of a class; no secret. Its keys `mailbox`, `store`, `scheduler` and `publisher` are configuration keys, not class names, and the file's keys are closed (an unknown key is refused, and the error names the nearest known one): the runtime maps them to `reader:email`, `store:runtime`, `scheduler:job` and `publisher:<platform>` |
| Provider resolution | `providers/resolve.py` | turns a requirement class into the provider script; the runtime builds no provider path itself |

### An agent run

- **Input:** the agent definition (`agents/<name>.md`), a task file the runtime writes (what to do, and the trigger's data marked as external content), the skills the agent lists, and the project folder, which the runtime passes to the adapter as `--project`. The runtime itself confines nothing: what the model can read, inside the project and outside it, is what the adapter and its harness allow (each adapter's README says how far that goes; containing a runtime agent beyond its tool list is backlog N15, which "The contained run" below closes). The social handler (`runtime/handlers/social.py`, `social_vote.py`) runs its agent as that operation: `contained-run` with the skill `mkt-engage` or `mkt-vote-round` and the task text of the measured cases, so what this section says about the adapter holds only for the first runtime (`scripts/runtime.py`), which stays as the rollback until WP-7.5. A contained run takes no agent file and no model from the configuration: the skill must be in the pack of an enabled agent of the `area_agents` section of `runtime.json`, and the model comes from the skill's proof.
- **Tools:** in the first runtime's adapter run, read only: the model reads files and answers, and cannot write files, run commands or call a network service. In a contained run the model can read, answer and run commands inside the container, on the copy, with no credential and not the open network; nothing but its reply comes back (the four restrictions of "The contained run"). Either way everything it proposes comes back as a fenced JSON block in its answer, whose shape the task names.
- **Budget:** a spend limit per run (`max_cost_usd`; a contained run has none: its bound is one attempt within `timeout_seconds`, and a run on a subscription or free credential has no billed cost) and a time limit (`timeout_seconds`); a daily spend cap across runs (`daily_cost_cap_usd`), checked before each run from the store. A run whose cost is unknown (the adapter has no price for the model, the run timed out, or it never ended) counts as `max_cost_usd_per_run`, and the tick's output says how many such runs the day has (`runs_without_cost_today`).
- **Output:** `<out>/response.md`, `<out>/timing.json` (`total_tokens`, `duration_ms`, `cost_usd`, `exit_code`), `<out>/raw.json` and `<out>/stderr.log`. The runtime keeps `<out>` under the run's folder and records the run in the store.

Adapter entry point (the first runtime's; the handler's agent run is `contained-run`, below):

```text
run-agent.sh --agent-file <agents/name.md> --task-file <f> --project <dir> --model <id> --out <dir>
             [--skill-dir <dir>]... [--max-cost-usd <amount>] [--timeout-seconds <n>]
```

It copies the skills (never links them) into a fresh working folder for the run, names `--project` to the harness as a folder to read, allows only reading tools (how far they reach outside `--project` is the harness's doing, and the adapter's README says it), loads no connectors and no user-level settings, and writes the files above. It exits 0 when the model answered, 1 otherwise.

### Why the model never acts

The trigger's data is written by strangers (comments, e-mails). A model that could run the publisher could be talked into publishing. So the model proposes; code decides and executes:

1. The model returns a proposal (a category, a language, a reply text).
2. The runtime writes the proposal's text to a file and runs the gate script with the approved policy. The policy file is bound by hash to what the person approved (its `policy:<sha256>` in the state file's standing approval); the gate script is bound only for a scheduled tick that carries `--pin` (below).
3. Only a gate result of `auto` makes the runtime call the actuator, with the file the gate checked and an idempotency key. Anything else goes to the inbox with the gate's reasons.

### What the approval of a recurring tick covers

The person approves the tick once, when it is scheduled (`scheduler:job`, `--every`), and it then runs unattended with the publishing credential. That approval covers:

- what the scheduler hashes: the command's arguments, the program, the scheduler's runner, and the files in the command file's snapshot (`runtime.py`, `runtime_vote.py`, `redact.py`, `providers/resolve.py`, the pin file). The job runs its own copies of them, and a firing whose hashes differ is refused;
- with `--pin <file>`: `docs/workbench/runtime.json` and the gate script (`mkt-engage/scripts/policy_gate.py` of the workbench `runtime.json` names), by the sha256 that `runtime.py pin` recorded in the pin file. Before anything else, every firing hashes both again and refuses (exit 3, nothing runs) when either differs. A tick without `--pin`, run by hand, checks nothing.

It does not cover the rest of what a firing loads from the workbench checkout that `runtime.json` names: the notification parser, the platform's data file (`shared/references/platforms/<publisher>.json`, from which the tick reads the platform's limits and which it passes to the skills' scripts), the adapter's `run-agent.sh` (the first runtime's agent run), for the handler's contained run `runtime/cli.py` with the modules it loads, the skill that runs and the platform references staged with it, and the eval image, and the agent file and its skills, the providers (the publisher included), the vote step's scripts, and the folders of `path`. A vote job, once approved, runs its own verified copy of the data file. A change to them (a pull in that checkout) takes effect at the next firing, without a new approval. So does a change of the model of a contained run: it comes from the skill's proof, not from the configuration, which the pin covers. Keep that checkout on a reviewed revision; to bind one of those files, add it to the pin first.

A change to `runtime.json` or to the gate script stops the tick until the person reviews it, runs `runtime.py pin` again and schedules the tick again with the new pin file: that is the new approval.

### Records

- Every trigger item is an event (deduplicated by source and external id), claimed atomically, and ends `done`, `failed` or `to_inbox`.
- Every run: agent, event, start and end, status, exit code, cost, tokens, output folder.
- Every outward action: kind, idempotency key, target, payload hash, provider result.
- Every item for the person: the inbox, with the payload and its hash; the person approves or rejects it, and an approved item runs only if its hash still matches.

### The weekly vote step

When `runtime.json` has a `vote` section (`repo`, `branch`, `pillars`, optional `pillar_aliases`, `image`, `card_html`), each tick also runs the weekly vote step (`scripts/runtime_vote.py`; design in `docs/architecture/weekly-vote.md`):

1. Code reads the vote files from the repository (the `integration:vcs` provider's `read-file`, read only) and runs `mkt-vote-round`'s `vote_state.py`. Nothing pending, or a round already handled (cursor `vote:<round>`), ends the step. The cursor is written only once the round has an inbox item, so a failure before that leaves the round for the next tick; `reject` on a vote item clears it (the store's `cursor-clear`), and the next tick redoes the round.
2. The agent runs read-only with `mkt-vote-round` and returns one `vote-proposal` block. The runtime checks it against the state (the winner's text or one of the three options with a reason, the slot's language, the next pillar, three non-empty options) and never repairs it.
3. Code builds everything the approval covers: the content file, `check_post.py`, the post image (`render.py`; without a browser the post goes text-only and the item says so), the next round's queue file (`vote_update.py --queue-round`, which refuses used topics), the publish job (which carries the publisher's idempotency ledger, as the publisher's dry run names it, so that the job at its slot uses the ledger it was approved with), and one bundle file. The bundle's sha256 is the inbox item's hash. A failed check leaves the item not ready: it cannot be approved.
4. `approve --id <n> --confirmed --sha256 <hash>` on a `vote` item re-hashes every file, refuses when the queue file in the repository moved, schedules the job at the slot (the scheduler's dry run, then the confirmed call with its digest) and commits the queue file (`commit-files`, only `data/pick-queue.json`).
5. At the slot, `scripts/vote_job.py`, scheduled with the system interpreter's fixed path and carrying the folders of `runtime.json`'s `path` (the scheduler's own `PATH` is short), publishes the post (first comment, image), reads the vote files again and commits only `post_url` on the round, the post in `posts.json` and its image. The post counts as published as soon as the publisher prints its address: when only the first comment failed, the job still records the post, then exits 1 and reports the comment's error. A failure after publishing prints what to record by hand.

### Safety rules

- The runtime never publishes without a gate result of `auto` under an active approval, or an inbox item the person approved with a matching hash.
- The runtime never publishes a text in which the shared credential formats (`scripts/redact.py`) match: the model that drafted it can read files, and a comment can ask it to quote one. A reply with such a match is not sent, by the tick or by `approve`; it goes to the inbox with the value masked and no reply file, and the person answers by hand. A vote proposal with one is masked in everything built from it, and its item cannot be approved.
- A proposal block that is missing, malformed or has fields outside the task's shape sends the event to the inbox; the runtime never repairs a proposal.
- A mailbox that cannot be read (an expired authorization, the network) does not stop the tick: pasted comments and the vote step still run, the mailbox cursor stays where it was, the tick's output carries `mailbox: {status: failed, note}`, and the person is notified at most once a day.
- The mailbox cursor never moves past a message that was not read. The mailbox answers newest first and says when older messages were left out; the tick reads on until none is, and when it cannot (a later search fails, or more wait than a tick reads) it keeps what it read as events, leaves the cursor where it was and says `mailbox: {status: incomplete, note}`.
- An error the runtime did not expect, in one event or in the vote step, does not end the tick: the event ends `failed` with the error's type, a run that was open ends `failed`, the traceback goes to stderr, and the next event is handled.
- The daily cost cap stops new runs; pending events wait for the next day or for the person.
- Configuration holds paths and limits only; credentials come through `providers/secrets/resolver.py`.
- One tick at a time per project (a lock); the scheduler also refuses overlapping firings.

The configuration of a project names three absolute paths: `workbench` (the checkout the runtime runs from, a reviewed revision), `data_dir` (a folder outside every repository, for run folders and the run lock) and `store_db`. Every operation refuses a project whose configuration names another checkout than the one it runs from, and a configuration whose hash is not the one the person accepted last (`accept-config --sha256 <hash>`, kept in the store).

**The configuration, and who may accept a change of it.** A change of `runtime.json` takes effect only when its hash is the accepted one, and the person accepts a hash in the terminal (`accept-config`, recorded as `by: "person"` in the store's cursor `config:accepted-by`). One exception, for a change that can only take power away: `set-mode`, from any channel (the terminal, the page), to a mode lower in the order `stopped < supervised < milestones < autonomous < autonomous-with-policy` (`runtime/autonomy.py`, `MODES`; `narrows(old, new)`) is a narrowing, and code accepts the new hash at once, as `accept-config` would (the same cursor, the state file's `Checkpoints` line rewritten), recorded as `by: "code:narrowing"`; nothing refuses afterwards. It does so only when the configuration was the accepted one before the call (every operation checks it first) and the file read back is the one the call wrote. A move up the order, or any other change (a cap, an agent, a pack, a handler, a price, a credential), is never accepted by code: the hash stays unaccepted, every operation answers `412`, and `set-mode` returns `accepted: false` and `next`, the command that accepts it. Two changes never overlap: `set-mode` and `accept-config` take a lock (`<data_dir>/config.lock`, from the service's threads and from the terminal alike), and under it `set-mode` reads the file and the accepted hash again; when either moved since the call began (another request finished first) it writes nothing and is refused, so a stale copy of the file can never bring a widening that code then accepts. A dispatcher round likewise ends when the file or the accepted hash moved during it, so a narrowing stops the next start. The single writer of the accepted hash is one function (`ops._record_acceptance`), called by `accept_config` and by the narrowing branch of `set_mode` and by nothing else; a test over every pair of modes and a test of the call graph keep it so (`runtime/tests/test_mode_narrowing.py`). The same mode changes nothing and writes nothing.

**The commands the runtime names.** Every sentence the operations layer or the service returns that names a terminal command (the `412` refusal, `set-mode`'s `next`, the commands of the held reasons) is built by `operations.command_line`, the one place that spells the syntax. It is absolute (`python3 <this checkout>/runtime/cli.py ...`), so it runs from any folder, and it carries the prefix `uv run --with keyring==25.7.0` when the process was started through uv (uv sets `UV_RUN_RECURSION_DEPTH` for what `uv run` starts, whatever environment it made; failing that the interpreter lives in uv's cache or under `UV_CACHE_DIR`; `WORKBENCH_STARTED_WITH_UV` set to `1` or `0` says it outright) or when the operation needs the secret store (`run-next`). A text stored before it is shown, such as the body of an effect, names no checkout and keeps the relative form.

**The social agent's auto reply.** The reply to a comment is an effect under a policy, so it is executed by `ops.execute_under_policy` like the published-posts commit, and by nothing else. The handler (`runtime/handlers/social.py`) runs the agent as a contained run, takes its decision, and writes into the run's folder the reply text, the comment, the sources the agent cited and its category and language; it builds one effect document (policy `engagement-policy`, kind `publish`, the post as the target, the four files, one item, the key the gate derives from the comment's identifier, the hash of the reply, and the publisher's own flags) and hands it to `cli.py execute-under-policy`. It passes no `--confirmed`, runs no gate and records no action. On `executed` it appends the engagement log entry and the event is `done`; otherwise the reply goes to the inbox with the operation's reason among its reasons, as an item the person can approve by hand (the exact-content path, unchanged). Two conditions hold at once, and neither alone sends anything:

1. *The bound, in code.* The standing approval of `docs/marketing/engagement-policy.md` carries bounds that `approve-policy` derives from the file's ```engagement-policy block, not from a bounds file: effect `publish`, target class `comment-on-published-post`, no files, one item per run, and the block's `max_replies_per_day` as the daily cap (a block without it is refused at approval; a Markdown policy without the block keeps the three keys it had and covers no effect). The file's hash binds the block, so a changed block covers nothing until it is approved again, and the bounds are derived again then. A class word is no literal target: `autonomy.covers` accepts the document's target only when it is in the set the operation resolved before the call, from the publisher's ledger through its read-only verb `posts` (it reads the ledger and nothing else, with no token and no request). So "a post this project published" is a fact code recorded and not a reading of the notification, whose text anyone can write; a ledger that cannot be read, lists no such post or answers nothing makes the reply not covered, and nothing runs. The post id the action records is the one the ledger matched.
2. *The judgement, by the skill.* After `covers` and before any provider call the operation runs the kind's judgement: the parent comment is a comment on the post of the request (the platform's data file gives the form of a comment id, which embeds its post, because the publisher addresses the request to the parent), the run folder is `runs/<n>` of the project's data folder, the text file is read once and its bytes are the ones the document hashed, they pass the credential scan (R4, `scripts/redact.py`'s formats), and are written to a private file (a folder the operation makes, mode 0700, the file created exclusively, 0600) which the gate reads and which the operation gives the publisher in place of `--text-file`, so the text sent is the text judged whatever happens to the run folder's file afterwards; the private folder is removed when the call ends. Then `mkt-engage`'s `policy_gate.py decide` (category, language, the daily and per-person limits, sensitive topics, the reply rules, the sources), started through `runtime/isolated.py`, answers `auto` with the document's idempotency key, run at the operation's clock (`--now`, the operation's local time with its offset; the zone the gate computes a day in is still the machine's, since the gate runs with a bare environment); otherwise the gate's reasons are the `why`. The gate's `auto` is never the approval: the standing approval is.

The operation then makes the publisher's dry run and its confirmed call and records the action (kind `engagement-policy`, target the post). Cut-over on a project that already runs the agent, in this order and by the person: `approve-policy --file docs/marketing/engagement-policy.md --agent <the area agent in autonomous-with-policy> --expires <date>` (an approval given before the derivation carries three keys and covers nothing), `standing --policy engagement-policy` must answer `covered: true`, then `python3 runtime/handlers/social.py replay --project <dir> --runs <data_dir>/runs` judges the stored runs again through the operation with `--replay-log` (every check, no execution, no record; the log it reads is a copy cut before the run, so that a run the old path sent is not refused for having been sent): every run the old gate sent must be `auto` and every run it held `inbox`, and a difference is read before the switch, never after. Only then does the scheduler's tick run this code. A tick whose reply is not covered writes an inbox item, never only a log line. The operation takes the project's run lock: a reply that arrives while a task of the project runs is refused ("another run of this project is in progress"), and goes to the inbox with a `failed` log entry and a `to_inbox` one. The replay does not apply the run-folder rule (it judges a scratch copy of the stored files and executes nothing); if the replay says a run the old path sent is not covered because "the target is not one of the comment-on-published-post the operation resolved", the ledger records another URN type than the notification carries, and a mapping the provider supplies is needed before the switch, never one invented here.

## A task run

`run-next` takes the oldest `ready` task of the project, one task at a time per project (a lock in `data_dir`), and runs its skill once:

- **What enters the copy** (`runtime/workcopy.py`, limits L1 to L6): for a skill that requires the web, only the artifacts it declares (its `inputs`, `outputs` and `updates`) found under `docs/` and `.workbench-local/`, and the files the person handed to that task (`drop.WEB_TASK_TAKES_DROP`, the maintainer's decision of 2026-10-09: the hand-over answers `web: true` with the line "this file will be visible to a run with the open network", and `task` carries `drop: {web, takes, line}` so that a page shows the line before the send); for any other skill, the files the project's git tracks, the documents and the state file under `docs/`, and the machine files the skill declares. Never the runtime's configuration, the store or the runtime's data folder, a link or a file whose real path leaves the project, a path with a part that carries a tool's settings, work data the skill does not declare, a credential file by its name, a file too large to scan, or a file whose text looks like it holds a credential. The project's `AGENTS.md` enters only when the skill declares it, without the two lines of the workbench section the container cannot serve (recording a use and the skill check); when a glob of `protected_paths` covers it and the skill is not of a code area, only its workbench section enters. Every file left out is listed in `left_out` with its reason.
- **The text:** the request in the person's words, then "For this task:" and the task's text from the flow file; on a run made after an answer, every earlier reply of the task with the person's answer, oldest first, each answer stated as the person's decision. Right before the answers, one line per document the documents mirror imported from the platform since the task's last run, when the skill lists it among its inputs and the project's file is still what was imported: "The person edited <path> on the platform since the last run; its content is theirs." Only code writes that line, from the record of imports, never from a run's text, and a run is given it once. The text names no skill: the one skill staged for the run loads by its description, as in a lab run.
- **How the skill is staged:** as in a lab run (`scripts/stage_skills.py`): the skill's folder, without its `evals/` and `scripts/tests/`, with the shared references it cites, where the adapter's tool discovers skills. Only that skill is staged. A skill that cites the platforms' folder (`shared/references/platforms/`) is also given the reference of every platform, with its data file, as a lab case is given the platforms it names: the runtime does not know in advance which platform a run will be told. They are read-only inputs: like the skill, they never come back (the path rule's `staged`).
- **Where it runs:** in the eval container of `evals/executor.py`, on the image the lab evidence is bound to, through the adapter's `run-prompt.sh`, on the model the skill's proof gives (`runtime/proof.py`): the floor model of the gate file only where the skill is `reliable` there, the proof holds on this checkout and machine and a key for it is found; the reference model otherwise, or when the person asks for it (`run-next --tier strong`). A copy that carries a tool's settings is refused before any model call.
- **The network:** a skill that requires `search:web` runs on the open network and may search and fetch pages; any other run reaches only the model provider, through the egress proxy.
- **The credential:** never enters the container. The model's credential is read from the secret store on the machine and held by a key proxy outside the run container, which adds it to each call. Every value passed to a run is replaced by its marker in everything the run leaves, before anything is read or stored.
- **Limits of time:** the gate file's `timeout_seconds` (1,800) per attempt, and its retries for a timeout, a failure of the adapter, a refusal or an early end. A refused credential is never retried. On the account limit the run pauses and starts again afterwards, without counting as a failure.
- **What comes back:** each file the run created or changed is given one class by the path rule. `document` (Markdown under `docs/`), `machine` (any other file under `docs/`, and `.workbench-local/`) and `state` come back; `state` through the merge of `runtime/state_merge.py`, line by line on top of what the project has now (L10), so a state file that changed at the origin during the run is merged, not kept whole. A document bound to an approval, and a machine file a skill's runtime manifest names, come back as `machine` (`runtime/workcopy.py`, `returning`). Only a regular file with its real path inside the copy comes back, a file that changed in the project while the run was in progress is never overwritten, and a file whose text looks like it holds a credential, or that is too large to scan, stays in the run folder. The reply the person reads in a pending decision has every line that looks like it holds a credential replaced by a marker (`body_masked` in the payload counts them); the run folder's `response.md` is left as it is. What does not come back is listed in `kept` with its class and reason. Nothing in the project is deleted. A versioned file comes back only from a code task (a skill of a code area), as a change set made against a commit, and such a run is refused while the project's tracked files other than the state file carry uncommitted changes; any other task is not held to that, and a versioned file outside `docs/` it changed is listed in `kept`.
- **Where it is kept:** the run folder `<data_dir>/task-runs/<run id>/`: `prompt.md`, `cwd/` (the copy as the run left it) and `outputs/` (`response.md`, `timing.json`, `raw.json`, `stderr.log`, `stream.jsonl`); an attempt made again is set aside beside them. The run's row in the store records the rest.

## The contained run

`contained-run` (`ops.contained_run`) runs one skill of an area agent's pack once, in the eval container, for a caller that is not a task: the agent run of a handler (the social agent's comment and vote runs). It is the one mode of execution of an agent: the run is the one the battery measured, so the proof of the skill stands for it, **provided the task text is the measured one**. A comment, a vote file or a page a stranger wrote reaches only a copy.

```text
python3 runtime/cli.py contained-run --project <dir> --skill <name> --prompt-file <f> --out <dir>
                                     [--platform <name>]... [--timeout-seconds <n>]
```

It checks, before anything is copied, that the configuration's hash is the accepted one, that the skill is a folder of the checkout's `skills/` with a whole runtime manifest, and that it is in the pack of an enabled area agent of the configuration (a check of scope, not of mode): a project that names no area agent puts no skill in scope, and nothing is allowed that no pack names (exit 2; a configuration that was not accepted is exit 3). The tier, the model and the adapter come from the skill's proof (`runtime/proof.py`, with the runtime's own key for the floor model as `run-next` passes it), never from the configuration's `model` or `harness`; a skill that is not proven runs on the reference model. The copy holds the artifacts the skill declares and nothing else (the form of limit L3), and never the runtime's configuration, although a skill may declare it as an input. The run is one attempt, in a new folder `<data_dir>/contained-runs/<n>/`, and the platform references the skill cites are staged as in a task run, with each `--platform` added. `<out>/response.md` holds the reply, past the credential scan of limit L14 (a line that looks like a credential is replaced by a marker that names the labels, never the value); `<out>/timing.json` holds `total_tokens`, `duration_ms`, `exit_code` and `cost_usd`, which is null unless the credential of the run is metered (a run on a subscription or a free credential has no billed cost). They are the two files and the keys `run-agent.sh` writes, so a handler reads them as it did. The command prints `{"status", "failure", "tier", "model", "adapter", "ignored_changes", "run_dir"}` and exits 0 when the model answered, 1 when it did not, and 3 when no run could be made: no eval image on this machine, a configuration the lab refuses, a platform with no reference. It never builds the image.

Four restrictions, each held by code:

| # | Restriction | How code holds it | Test (`runtime/tests/test_contained_run.py`) |
|---|---|---|---|
| R1 | A malicious comment reaches only the copy with that agent's documents | The copy holds only the artifacts the skill declares (limit L3's list), never `runtime.json`, never a versioned file the skill does not declare, no `AGENTS.md` it does not declare | `test_a_contained_social_run_sees_only_the_artifacts_its_skill_declares` |
| R2 | The model can read, answer and run commands in the container, with no credential | The lab facade passes only what `lab.reference(tier)` names; the publishing credential never leaves the handler's process | `test_no_credential_but_the_model_s_own_enters_a_contained_social_run` |
| R3 | What it can spend is bounded | One attempt (no retry), the caller's `--timeout-seconds`, never the open network (`web` is false whatever the skill requires), the model from the proof, and on the floor model the runtime's own capped key | `test_a_contained_social_run_is_one_attempt_within_its_time_limit_and_never_on_the_open_network`; `test_the_model_of_a_contained_social_run_comes_from_the_proof_never_from_the_configuration` |
| R4 | Something can leave only through the reply | Nothing comes back from the copy: no file is brought back (their number is `ignored_changes`), and the reply passes the credential scan before it is written out | `test_nothing_but_the_reply_leaves_a_contained_social_run`; `test_the_reply_passes_the_credential_scan_before_it_is_written_out` |

The proof is the battery's, with the same task text as the measured cases: the social handler's text is compared with the cases' prompts byte for byte (`runtime/tests/test_social_task_text.py`: `test_the_engage_task_text_is_the_prompt_of_the_measured_runtime_cases` and `test_the_vote_task_text_is_the_prompt_of_the_measured_runtime_cases`), and `test_a_contained_run_is_given_the_platform_the_cases_name` that the run is given the platform the cases name. `test_a_missing_image_is_a_refusal_and_never_a_build` holds that a missing image is a refusal; `test_the_platform_s_reference_is_staged_as_the_lab_stages_it_for_a_case` that the references are those of a lab case; `test_the_cost_of_a_run_on_the_reference_model_is_written_as_unknown` that the cost is never guessed.

## Records

**Three tables** of migration 2 of the store: `tasks` (a request, with no parent and no skill, and the tasks of its plan), `task_runs` (one row per run: skill, version and content hash, model and adapter, web, status, failure kind, ending, attempts, cost, tokens, duration, whether the skill was reported loaded, image digest, run folder, error, and `billing`, how the credential the run used is billed, "The daily caps") and `pending_decisions` (what a task waits for the person to decide: kind, title, the reply as the body, a payload, status, resolution and answer).

**Nine task states:** `requested`, `planned`, `ready`, `running`, `waiting`, `blocked`, `done`, `failed`, `cancelled`. A `waiting` task always has exactly one open pending decision; one task is `running` at a time per database.

**Six endings** of a run that did not fail: `done`, `question`, `draft_with_questions`, `gate`, `blocked`, `unclassified`. Every ending is recognised by a rule that reads only the run's facts, what the skill declares (its frontmatter and runtime manifest) and sentences of the skills' own text; what no rule recognises is `unclassified` and reaches the person whole. The rules are tested against a corpus of archived lab runs, with labels a person read (`runtime/tests/corpus/`). `blocked` (the reply names a missing input and the skill that writes it) opens nothing: the task is `blocked` until the person retries it, and its `note`, in `status` and in `task`, is the first line of the reply that names the missing input and the skill that writes it (`endings.missing_input_line`; the start of the reply when no line does), so that the person sees what unblocks it beside Retry. `gate` (the run wrote the file the manifest names for its confirmation gate and asks) opens an `effect` when its payload was recovered and parsed, agrees with the configuration and its change set is not blocked; otherwise a `review` whose body starts with the reason (`runtime/ops.py`, `_effect_or_review`). A run that changed no file, asks nothing and finds the task's declared output already in the project is `done`. A run that failed has a failure kind instead: `timeout`, `refused`, `auth`, `adapter`, `early_end`, `settings`, `stopped` or `internal`.

**Six kinds of pending decision:** `plan` (stage 3), `question`, `review`, `effect` (stage 4), `acceptance` (stages 3 and 6) and `your_document` (stage 10). The store accepts all six; the runtime opens five today, and `your_document` is not opened yet:

| Kind | Opened when | Resolutions |
|---|---|---|
| `plan` | The router's run on a request gave a route, or the person named a flow (`route --flow`): code built the plan, with its hash | `approve --sha256 <hash>`: the plan's tasks are created and those with no dependency and no wait are `ready` ("Derived waits"; `--go-ahead <task key>` drops the waits of a task); `reject`: the request is cancelled |
| `question` | A run ended `question`: it wrote nothing (a change limited to the state file counts as nothing) and asks | `answered`: the task is `ready`, and its next run gets the answer |
| `review` | A run ended `done`, `draft_with_questions` or `unclassified`, or ended `gate` without a payload that makes an `effect`: the body is the whole reply, so a draft's open questions are in it | `released`: the task is `done`, the tasks that depended on it become `ready`, and the document stays a draft with its open questions; `answered`: the task is `ready` again, and its next run gets the person's text |
| `effect` | A run ended `gate` and its payload was recovered, parsed, agrees with the configuration and its change set is not blocked; its hash is that of the effect document | `approve --sha256 <hash>`: the approval is recorded (L17), code checks that nothing moved and executes the effect (L15), and the task is `done`; `answered`: the task runs again with the answer; `rejected`: the task is cancelled and nothing is sent. Answering or rejecting revokes the approval in the same transaction |
| `acceptance` | An item a person wrote on the task board became a request; a backlog proposed sub-tasks outside the approved plan's limits (`subtasks`); a delivery was routed again after its brief, or a request an autonomy mode completed waits for the person's acceptance of its deliveries (`deliveries`) | `accepted` or `rejected`: a board request accepted is routed next, rejected is cancelled; accepted sub-tasks are added to the request; for deliveries the resolution and its note are recorded |

## Derived waits

A person adds requests in any order: on the page, in the terminal or on a task board. The runtime orders the tasks by itself, from the artifact contract (`contracts/project-layout.md`): what a task needs is the `inputs` its skill declares, and what an open task will write is the `outputs` of its skill. A task that is not started waits for another task, and the wait is stored with its reason.

**The rule** (`runtime/plan.py`, `derive`, a pure function; `runtime/ops_waits.py` reads the store and the project's files and applies it). For each task that is `planned` or `ready`, and each path of its skill's declared inputs that does not exist in the project (a path with placeholders is a pattern; a path that ends in `/` is a folder with a file in it): the owner skill of the path is the skill whose declared outputs hold it; if a task of another open request has that skill, the task waits for the oldest such task, with the reason `<path>, written by task #<id>`. Then:

- An input the project has creates no wait. An input that a task of the task's own request writes is the flow file's business (`depends_on`), not a wait. An input nothing writes creates no wait. A skill that reads its own output (a plan it keeps up) waits for no task of its own skill and reports nothing missing for that path: it starts it.
- A task that waits stays `planned` and the word is *waiting for task #n*; the dispatcher never starts it (`dispatcher.decide` holds a ready task with an open wait as `waiting`; the store's `task_claim_next` and `task_claim` refuse it, so the rule does not rest on the caller). The wait ends when the awaited task is `done` or `cancelled` (the store clears it in the transaction that moved the task), when the file appears (the next derivation), or when the runtime no longer derives it (a request cancelled, another writer found). A task whose waits all ended becomes `ready`. An awaited task that failed or is blocked keeps the wait: the task waits for it until it is retried or cancelled.
- A wait that would close a circle with the dependencies and the waits already made is not made and is reported (the plan's `cycles`); the older task keeps its wait. A derivation never waits in a circle.
- A skill's **required** input is a row of its `## Inputs` table whose Required cell, lowercased, is exactly `yes` (one reader, `flow_files.required_inputs`, the one `scripts/validate.py` uses for the flow files and `plan.skill_facts` calls; `**yes**`, `yes.` and "yes for a person" are not the word, and a table whose header has no Artifact and Required columns is not read). A required input that the project does not have and no open task writes is said before the person approves a plan: `<skill> needs <path>; nothing writes it: run <owner> first or go ahead and it will stop` (`add the file` when no skill owns the path). It is a sentence, not a refusal: the plan can be approved, and the task will stop on the missing input.

**The override.** `request --after <id>` (the terminal, the page's request form, `/new --after <id> <text>` in the conversation, an `after #<n>` in the title or text of an item on the task board) keeps the request `<id>` on the new request (`tasks.after_request`; a task's id means its request). Every task of the request waits until that request is `done` or `cancelled`, with the reason `after request #<id>`. It is a wait the contract cannot see; a circle of `after`s is reported like any other. **Go ahead:** `approve --id <plan> --go-ahead <task key>` (repeated, or a list in the page's JSON) removes the derived waits of those tasks of the plan, in the transaction that creates them, and keeps the decision: the dropped wait stays in `task_waits` as `dropped`, and a later derivation does not bring back that wait, the same path for the same awaited task. The person agreed to the waits they were shown, not to every wait for ever: a writer that replaces the one they went ahead of (a cancelled request made again) or another path is a new wait. Code writes one line to `## Decisions` of the state file as the person's decision (`state_merge.with_go_ahead`). Go ahead leaves the `after` override alone. A key the plan does not have, or that waits for no task to derive, is refused and the plan stays open, naming the key. **Go ahead on a task already created:** `go-ahead --task <id>` (the terminal and the page, `POST /tasks/{id}/go-ahead`; not the conversation, not the MCP mode) ends the derived waits of that one task the same way (`dropped`, one line in `## Decisions`) and returns `{task_id, state, dropped, waiting_for, decision}`. It is refused for a request, for a task that is not `planned` or `ready`, and for a task with no derived wait, which includes one that waits only for the request it was told to follow: an `after` is the person's own, and only they drop it, for one task, with `--drop-after` (the page sends `drop_after: true`), recorded the same way; the override of the whole request is changed by `request_after_set`, which a board item does when the words `after #<n>` are added to, or taken out of, its text.

**When it is derived.** When a request is planned (`request` with a flow, `approve` of a plan: the waits of the new tasks are written with the tasks, in the same transaction, so that no task is ever `ready` before its wait exists); when a task ends or a request is cancelled (`release`, `reject` of an effect, `cancel`, `retry`, and the store itself clears a wait whose awaited row is `done` or `cancelled`); when a board item is accepted; at the start of every `poll` and every round of `dispatch`, and before a task is claimed, which is how a file that appears on its own is noticed. A derivation is cheap when there is nothing to derive: with one open request and no `after`, the skills are not read. Everything a derivation changes is one `waits_sync` of the store: it opens the waits that are derived and not open, clears those that are not derived any more, and sends a `ready` task that gained a wait back to `planned`.

**What the reads carry.** `status`: each task of `requests[].tasks[]` has `waiting_for: [{task_id, request_id, reason}]` (empty when none; `task_id` is the awaited task, `null` for an `after` wait, whose `request_id` is the awaited request), and each request has `after` (the request it runs after, or `null`). `task`: the same `waiting_for` in the task row, and `after` for a request. A pending decision of kind `plan` carries, before approval, `waits: [{task_key, task_id, reason}]`, `missing: [{task_key, skill, path, owner, sentence}]` and `cycles: [{task_key, sentence}]` in its payload, and the same lines in its body above the plan hash; the plan hash covers the tasks only and does not move. `approve` accepts `go_ahead` (the table's `list` kind: repeated `--go-ahead` in the terminal, a JSON list on the page; the conversation cannot carry it) and returns `waits` and, for a go-ahead, `state` (`{"written": true}`). `request` returns `waits` and `missing` for a flow. A mirrored item's note on the task board says `waiting for #10, #12 (+1)` (at most two awaited tasks named, the rest counted, a request as `request #n`) before the task's own note. On the board an `after #<n>` is an instruction only at the start of a text or on a line of its own; inside a sentence it is prose. `run-next` with nothing ready names the tasks that wait and why (`no task is ready; waiting: task 12 for ...`).

**The store.** Migration 8 adds `tasks.after_request` and the table `task_waits` (`task_id`, `awaited_id`, `kind` = `input` | `after`, `path`, `reason`, `status` = `open` | `cleared` | `dropped`, `created_at`, `ended_at`, `ended_by`); a wait is never deleted (L13, a trigger), it ends. `waits_list`, `waits_sync`, `waits_go_ahead` and `request_after_set` are its functions. `request_add`, `plan_approve`, `tasks_add`, `acceptance_resolve` (accepted sub-tasks) and `task_retry` take the waits their tasks begin with, in their own transaction, so that no task is ready before its wait exists; the one exception is a retry the task board asks for during `sync`, which `sync` derives right after the pull.

**Known limits.** A plan that is approved before the request it depends on is planned gets no wait (that task is not there yet): the plan says the input is not written, and the next derivation orders them, but the task may have started in the meantime. The owner of a path is the owner skill only; a skill that merely updates a file (`updates`) is not a writer. A `yes` of a Required cell that carries a condition is not read as required.

## The daily caps

Package ADJ-R3 (row A-38 of the interface adjustments, decided 2026-10-10). An area agent has two caps, `max_runs_per_day` and `max_usd_per_day` (an absent cap is 0, never unlimited). Which one a run counts against follows the **billing of the credential the run uses**, not the model's tier:

| Billing of the credential | A run on it | Counted against | Reason when held |
|---------------------------|-------------|-----------------|------------------|
| `subscription` | is covered by a fixed fee | `max_runs_per_day`, one per run | `cap: runs per day` |
| `free` | costs nothing (a local model, no key) | `max_runs_per_day`, one per run | `cap: runs per day` |
| `metered` | is paid by use (an API key) | `max_usd_per_day`, in dollars | `cap: usd per day` |
| `unknown` | started on a route no manifest could bill; written by the runtime, never declared | `max_usd_per_day`, as a metered run (a reservation, its dollars are never left uncounted) | `cap: usd per day` |

**Where the billing comes from.** Each adapter's manifest states it for every credential it registers, and `login_billing` for a harness that holds a login of its own (`contracts/secrets.md`, "How a credential is billed"); `runtime/billing.py` reads them and nothing else. A run's credential is what `lab.run_skill` passes: the variables the gate file names for the tier (`strong_pass_env`, `floor_pass_env`), the runtime's own key for the floor model travelling under the first of the floor's; a tier with no variable uses the adapter's `login_billing`. Several variables are billed by the strictest word (`metered`, then `subscription`, then `free`). A credential no manifest lists, or an adapter that declares no login for a run that passes no variable, has **no billing the runtime can know**: the dispatcher starts no task on that route (`may_start` refuses with `unknown billing None`, which a page reads as the reason `other`; a start by hand, `run-next`, is not capped, as it never was) and a run that is made all the same (a start by hand) records the word `unknown`, which counts as `metered`. A row with no billing at all (NULL) is only a row older than migration 9.

**An API key as the reference credential** (`ANTHROPIC_API_KEY` under the reference harness) is today an edit of `strong_pass_env` in the gate file that nothing else supports: the caps count those runs in dollars, but the key enters the container with `-e` and is not held by a key proxy, so limit L6 does not hold for it. A route for it is a later package (A-40). `login_billing` is reachable only in a configuration that passes no variable; in the container the CLI's login does not exist.

**The cap is checked at the start, and a metered run carries its own limit.** `may_start` holds a metered task when what is left of `max_usd_per_day` is under `MIN_RUN_BUDGET_USD` (0.05, `runtime/autonomy.py`) with `cap: usd per day`, so no run starts with a budget of a few cents. A run that does start is given a spend limit, `autonomy.run_budget`: the per-run limit (`max_cost_usd_per_run`, else 0.5) or what is left of the day's cap rounded down to the cent, whichever is less, computed before the run's own row exists and passed through `lab.run_skill(max_cost=)` to the adapter's `--max-cost-usd` (the reference model's adapter stops the run at it; the floor model's adapter does not enforce it, and the provider key's own credit limit is its bound). A subscription or free run is given none. A run that fails or times out keeps its reservation counted: its recorded cost, else `max_cost_usd_per_run`. A start by hand (`run-next`) is not held by the cap but carries the same limit, or the per-run limit when less than the floor is left. The router's run and a contained run on a metered credential carry one too.

**The run records it.** `_route` (`runtime/ops.py`) adds `billing` to the routing of a task run, of the router's run and of a contained run; the row of `task_runs` gets it when the run starts (migration 9: `ALTER TABLE task_runs ADD COLUMN billing TEXT`, a CHECK of the three words or null), and the `task` read carries it on each run row. A run row older than the column has none: for history only, `autonomy.history_billing` gives it the tier rule the caps had before (a run on the floor model is `metered`, any other `subscription`), so a day that began before the update counts as it always did.

**The cost follows the billing.** The run's `cost_usd` is the adapter's number (`timing.json`) when the run is `metered`, whatever its model or tier, and null otherwise: a subscription or free run has no billed cost, and `runtime/costs.py` still recomputes one from the tokens and the project's `model_prices` for the report. A metered run whose cost is not recorded yet counts at `max_cost_usd_per_run` (else the default), and an unknown price never blocks a run: the reservation stays counted.

**The rule** (`runtime/autonomy.py`, pure). `spend_split(runs, agent, per_run_usd)` counts, from the day's rows with their billing: `runs_counted` (subscription and free runs), `usd_recorded` and `usd_reserved` (metered runs, the second for a run of unknown cost), `runs_without_cost` and `runs_total`; `spend` folds it into `runs_counted` and `usd_metered`. `may_start(name, agents, facts, spent, billing)` takes the billing of the run about to start: `subscription` and `free` against `max_runs_per_day`, `metered` against `max_usd_per_day` (the sum rounded to 6 places), any other word refuses. The dispatcher's snapshot carries `billing` for each ready task beside its `tier` (the tier still decides the credential check and the model), and `decide` passes it.

**What the reads carry.** `agents` keeps its keys: `runs_today` is the runs counted against `max_runs_per_day` (subscription and free), `usd_today` the dollars counted against `max_usd_per_day` (metered), with `usd_recorded`, `usd_reserved`, `runs_without_cost` and `runs_total_today` as before; it adds `billing` (`{"runs": ["subscription", "free"], "spend": ["metered"]}`, the words each counter counts) and `caps_in_use` (`{"runs": bool, "spend": bool}`: true when a run of the day, or a tier the runtime can run on (the reference model's always, the floor model's when a key for it was found), has a credential billed that way). A page draws a meter only for a cap in use, and both when it gets none of the two keys (an older service). The caps of `costs` carry the day's use in the same words as before.

## The dispatcher's two jobs

From stage 6 the task runtime runs unattended through two recurring jobs of the scheduler (`scheduler:job`, `--every 5`), both started with the system interpreter, `/usr/bin/python3`, on a copy of `runtime/dispatcher.py` kept in the job folder:

- **The poller** (`dispatcher.py poll`, `timeout_minutes` 5) calls `ops.poll`: it mirrors the task board and the documents when the project has them, expires the standing approvals past their expiry, rewrites the state file's generated lines (the `Checkpoints` line, the standing rows) when they changed, and releases the reviews each area agent's mode releases. It calls no model and starts no task.
- **The worker** (`dispatcher.py work`, `timeout_minutes` 240, the provider's maximum) calls `ops.dispatch`: the ticks of the handlers whose `dispatch` is true, the releases a mode makes, then the ready tasks one at a time, while the task's agent may start (its mode, and the daily cap of the billing of the credential the task's route uses: runs per day, or dollars per day, "The daily caps"). No new run starts once the round's budget (2700 seconds) is spent, or after a failure the next run would repeat. A firing that finds the last one still running is skipped by the scheduler (`skipped-overlap`).

`python3 runtime/cli.py pin --project <dir>` writes the pin, `<data_dir>/dispatch-pin.json` (mode 0600): the path and the sha256 of the accepted `docs/workbench/runtime.json`. `dispatcher.py command-file --job poll|work --project <dir> --pin <pin>` prints each job's command file: `argv` starts with the literal `/usr/bin/python3`, and the snapshot is the entry and the pin.

**What the approval of the two jobs covers.** The scheduler's digest covers the entry's copy, the pin and the arguments. The pin covers `runtime.json`: before it loads anything from the checkout, every firing hashes `runtime.json` and refuses (exit 3, nothing runs) when it is not the pinned file. Neither covers the rest of the checkout (the operations layer, the lab facade, the skills, the providers, the handlers): it stays on a revision the person reviewed. A change to `runtime.json` (a mode, a cap, a handler) stops both jobs until the person accepts it (`accept-config`), runs `pin` and schedules both jobs again with the new command files: that is the new approval. Whether the checkout's revision should also be in the pin is a question for the maintainer (open point O11 of the platform plan).

**The interpreter and the credentials** (open point O1 of the platform plan). The system interpreter has no secret-store library, so from a scheduled job the lab's lookup finds a credential only when it is set in the job's environment, which a command file cannot carry. Three answers:

1. Install the library for the system interpreter, in the user's own site folder (`/usr/bin/python3 -m pip install --user keyring==<the version the lab pins>`); a user agent runs in the login session and reads the login keychain. The job's command and its approval do not change. **Recommended**, if that version supports Python 3.9.
2. Start the jobs through `uv run --with keyring==<version>` instead of `/usr/bin/python3`: the scheduler then hashes a managed interpreter, and an upgrade of it refuses the jobs. It changes the entry's command file.
3. Put the credential in the job's environment: refused, a credential is never written into a file.

`dispatcher.py check --project <dir>` reports `"secret_store"` (whether this interpreter can import the library) and `"credential"` (whether the reference model's credential is set or found in the store), and exits 0 only when both, every module of `runtime/` and `runtime/handlers/`, the lab, docker and uv are found. The report is `dispatcher.inspect(ops)`, which the local service reads too at its start ("The local service", **The start**). Run it as the rehearsal's one-shot job, so the answer comes from the scheduler rather than a terminal. At every firing of the worker whose interpreter cannot read the store, the entry says so on standard error, and a round whose next run would go to the reference model without its credential starts nothing and says why in `"stopped"`, so no task fails for it.

## The local service

`uv run --with keyring==25.7.0 python3 runtime/service.py --project <dir> [--project <dir>]... [--port 8765] [--poll-every 60] [--dispatch-every 30 | --no-dispatch] [--token-file <path>]` serves the operations layer to a page in the person's browser, on the person's machine. The `uv run --with keyring==25.7.0` form is the way to start it: the secret store is read through that library, and a service started with another interpreter finds no credential and starts no task (it says so at its start). It is a shell like `cli.py`: it parses a request, calls one operation of the table and returns what it returned. It prints one JSON line (`url`, `token_file`, `projects`), never the token.

**The token.** `secrets.token_hex(32)`, new at every start, written to a file for its owner only (mode 0600, created with `O_EXCL` after the older file is removed; default `<data_dir>/service.token` of the first project) and removed when the service stops. The person pastes it once per browser session; it is sent as `Authorization: Bearer <token>`, compared with `hmac.compare_digest`, and is never in a URL, a log line, a response or a page.

**The rules of a request, in order; each is a refusal unless the request satisfies it** (each has a test in `runtime/tests/test_service.py`):

1. The socket is bound to `127.0.0.1`; there is no option for another address. It listens with a backlog of 128 (`Server.request_queue_size`), because every response closes its connection and a page of dozens of modules and icons opens that many at once; the default of 5 overflowed and some systems reset the overflow (`runtime/tests/test_service_static.py`).
2. `Host` is `127.0.0.1:<port>` or `localhost:<port>`, else `403` (`host`). A name that resolves to the machine is refused.
3. `Origin`, when present, is `http://127.0.0.1:<port>` or `http://localhost:<port>`, else `403` (`origin`); a `POST` without one is refused the same way.
4. A path under `/api/` needs the token, else `401` (`token`). The static files need none and hold no data. One more path needs none, `GET /token-file` ("Before the token" below).
5. Only `GET` and `POST` (any other method, `OPTIONS` included, is `405`; no `Access-Control-*` header is ever sent). A `POST` needs `Content-Type: application/json`, a `Content-Length` and no `Transfer-Encoding` (`415`, `411`, `400`), a body of at most 1 MiB (the file route: 34 MiB, the base64 of the 25 MiB a hand-over takes; `413`) that is one JSON object whose keys are the arguments of the operation's row, by name: an unknown, repeated, mistyped or missing key is `400` (`usage`). A `GET` reads only the query its route names; a token in a query string is not read.
6. An unknown path is `404`, a known path with another method `405`, an unknown project id `404`.
7. One route calls one operation and returns what it returned, unchanged, with `200`. `OpsError` code 1 is `409` (`refused`), 2 is `400` (`usage`), 3 is `412` (`not_configured`); anything else is `500` (`internal`, the traceback on standard error only). An error body is `{"error": "<word>", "message": "<text>"}`; the `412` adds `next`, the exact `accept-config` command (the one the message ends with), so that a page reads a field and not the sentence (a failed job's `error` carries it too).
8. A route whose operation's row has `job` returns `202` and a job (`job`, `op`, `project`, `state`, `result`, `error`, `started_at`, `ended_at`); `GET /api/v1/jobs/<n>` returns it again, `state` `done` or `failed` at the end. Jobs live in the service's memory; the records are in the store. A job whose operation calls a model is refused (`409`, `busy`) while another such job of the project, or the `dispatch` loop or the queue loop, runs, with one exception: the rows of `say` and `route` have `queues`, so the service starts them without waiting for the slot, and the operation itself finds the run lock held and queues the call ("The conversation").
9. Every response has `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`; an HTML or SVG document also `Content-Security-Policy: default-src 'self'; img-src 'self' blob:; frame-ancestors 'none'` and `Referrer-Policy: no-referrer`. The policy has three directives: `default-src 'self'` (nothing loads from another origin), `frame-ancestors 'none'` (the page cannot be put in a frame) and `img-src 'self' blob:`. `blob:` is there for one reason: the bytes of an image ("The raw artifact") are behind the bearer header, so the page fetches them itself and shows them from a `blob:` URL it built, which can only name bytes the page made; `data:` is never allowed and no other directive is widened. The one route that answers bytes (`artifact/raw`, "The raw artifact") sends both on every answer, with `Content-Disposition: inline`.
10. A static path is served only when its real path is inside `interface/`, with a known extension and no dotfile; there is no listing. `/favicon.ico`, which browsers ask for by default, is answered with the bytes of `/favicon.svg` (`image/svg+xml`), under the same rules.
11. The log line is the method, the path (never the query), the status and the duration; never a header, a body or the token.

**Before the token** (ADJ-B3). The page cannot tell the person where the token file is until it holds the token, and the path is known to the service alone, so the service answers one unauthenticated read, `GET /token-file`, outside `/api/`, under rules 2, 3, 5 and 9 (the host and origin check, `GET` only, no query, `Cache-Control: no-store`, no `Access-Control-*` header). The answer is `{"token_file": <absolute path>, "commands": {"macos", "linux", "powershell"}}` and nothing else. The commands are built on the server, by `operations.token_commands`, the one place that spells them: `pbcopy < <path>` (macOS: the token goes to the clipboard), `cat <path>` (Linux: it is printed in the terminal) with the path quoted by `shlex.quote`, and `Get-Content -LiteralPath '<path>' | Set-Clipboard` (PowerShell: single quotes, and the typographic ones, doubled). The page chooses one by the browser's system and joins nothing into it. A path with a control, format, line-separator or paragraph-separator character, or one that is not absolute, has no safe command: the answer is `{"token_file": null, "commands": null}` and the page keeps its sentence about the first line. A service with no token file to name answers `404`, which is also what an older service answers, and the page keeps the same sentence. The token is never in this answer, in any other unauthenticated answer, or on standard output; the one JSON line still names the path and never the token.

*Decision: who can read the path.* The path names the account and the project's folder, and `GET /token-file` gives it to any local process that can open `127.0.0.1:<port>` with a loopback `Host` and no foreign `Origin`. That is accepted: a process of the same account can read the file itself and its own environment; a process of another account on the machine learns a path but cannot read the file (mode 0600), and a path opens nothing without the token; a page from another origin is refused by the host and origin check, gets no CORS header and so cannot read the answer; and the person could already see the path in the terminal's first line. What it buys is that the person is told where the file is, and given the command that reads it, on the page that asks for the token. The command is the person's own act: a command copied to the clipboard is kept by a clipboard manager that keeps a history, and what the command copies is the token, so the page says it copies the token and never shows it. This is the maintainer's reading in A-39; a change to it (an authenticated route, a path hidden from the answer) is his decision.

**The routes** (prefix `/api/v1`, `{p}` a project id: the first 12 hexadecimal characters of the sha256 of the project's real path; a path is never in a URL). A route exists only for an operation whose row lists the `page` channel.

| Route | Operation |
|---|---|

The reads carry the agent where a page needs it, all read-only and from data the store or the configuration already holds: a task row of `status` has `title` and `agent` (the store's columns; `agent` is null when the task was planned in a project with no area agents); a pending decision (`status`, `pending`, one `pending` item and the `pending` of `task`) has `agent`, the area agent of its task, null for a decision on a request (a plan, a router question) and without area agents; a resolved one has `answer`, the text the person saved with it (an answer to a question, a comment on a review or an effect, the note of a rejection; null for a release, an approval and a rejection without a note), which the page shows under the date of the decision's resolved line (A-41). Only two reads carry it: `task`'s `pending[]` (every status) and `pending` with an id (one decision whole); `status`'s `pending` and the `pending` list name open decisions only, with their own fixed keys, and carry no `answer`; an `artifacts` row has `agent`, the one enabled area agent whose pack holds the row's `owner` skill (`plan.agent_of`), null when the row has no owner, the project has no area agents, or no single agent owns the skill.

Each `agents` entry carries the day's spend in the words a meter shows, from the rows the caps already count by their billing ("The daily caps"): `usd_recorded` (the recorded costs of today's metered runs), `usd_reserved` (`max_cost_usd_per_run`, else the default, for each such run with no cost yet), `usd_today` (their sum, what the dollar cap compares), `runs_without_cost`, `runs_today` (the runs on a subscription or free credential, what the runs cap compares) and `runs_total_today` (every run of the agent today, any billing), then `billing` and `caps_in_use`; the caps of `costs` (`caps`) carry the same words, with `max_runs_per_day` and `max_usd_per_day`; `usd_recorded + usd_reserved` equals `usd_today` exactly (one rule, `autonomy.spend_split`, rounded once per part; the cap compares the sum rounded to 6 places, as before). `costs` reads only the store for its rows, and the gate file (for the models) only for the day's use in `caps`: when the gate file cannot be read the caps carry the three cap keys alone. `wider` is built from the agent's configured mode, not its acting mode (a disabled agent still lists the modes above its configured one). `wider: [{mode, command}]` lists, for every mode above the agent's own in the order of "The configuration", the absolute `set-mode` command (with the uv prefix rule of "The commands the runtime names"), so a page shows it with Copy and builds no command; an agent at the top has `[]`.

A ready task that a round did not start has a reason: `status` carries `held: [{task_id, agent, reason, at, next, commands}]`, the ready tasks the last round of the dispatcher held, with the time of the round, and `agents` carries per agent `held`, how many. A reason is one of `stopped`, `cap: runs per day`, `cap: usd per day`, `credential`, `secret store`, `image`, `dispatch off`, `job running`, `no enabled agent owns the task`, `waiting` (a task with an open wait, "Derived waits"; in practice it is `planned`, not ready), `other` (`runtime/dispatcher.py`, `REASONS`; `other` stands for any reason a rule function gives that is not in the list, since free text never reaches a page): the agent's mode or caps (`runtime/autonomy.py`, `may_start`), a check the round makes before it starts a run (the reference model's credential, whether this interpreter can read the secret store, whether the eval image is on the machine; a task held for these is not failed), a task of the project that runs (one at a time), or a service that dispatches nothing (`--no-dispatch`: every ready task, for as long as the service lives; the word is `dispatch off` and means *dispatch off in this service*: the service does not know of a scheduler job that dispatches the same project, and the terminal's `status` never says it). `next` is what gets past the reason, or null: `run-next` for `dispatch off`, the start command of the service for `secret store`, and for `credential` (the store is readable, the key is not in it) the sentence "The credential is in neither the environment nor the secret store." and nothing more when every missing variable has a command in `commands`, the command being the one place that spells how to store it (`uv run --with keyring==25.7.0 keyring set openhora <username>`, the username being the one the adapter that reads the key registers in its manifest); for a variable with no registered username (`command` null) the sentence goes on with the way to store it once or export it in the shell that starts the service, with no value, and a line for that variable that points to the table of `contracts/secrets.md`, so that no command is written both in `next` and in `commands`. `commands: [{name, command}]` gives the same as fields, for the two reasons a command gets past: `credential` (one entry for each missing variable, `name` the variable, `command` the line `operations.keyring_line` builds with the registered username shell-quoted, null when no username is registered) and `secret store` (one entry, `name` `service`, `command` the line that starts the service with the secret store's library); every other reason has `[]`. The sentence `next` stays for the terminal; a page draws `commands` with Copy and parses no sentence. (`agents` carries the count `held`, not the rows.) The record of the last round is the store's cursor `dispatch:held` (at most 20 tasks, a cursor holds 4 KiB), replaced at every round and read only for tasks still `ready`; `dispatch` returns the round's `held` as it always did. A request's `title` in `status` is the one given, else its first sentence when it is at most 120 characters, else its first line cut at the last word that fits with `…` (`plan.title_of`); the plan's first line, `Plan for request <n>: <title>`, uses the same.

`connections` carries `service`, what the local service found at its start (null in any other process): `{secret_store, credential, docker, image, dispatch, problems, start, at}`, each verdict `ok` or one sentence saying what is missing, `dispatch` `every <n> s` or `off`, `start` the command that starts the service with the secret store's library. It carries paths and error text, for the token-gated page only: the interpreter's path and version, the text of the exception a failed import raised (each verdict cut at 300 characters, control characters replaced), and the paths of the checkout and of the project in `start`; it never carries a secret's value (`credential` names the variables that are missing, not what they hold).

A route takes the query keys it names and no other (`400`). `conversation` returns the messages of the project's conversation (named `project`) above an id; `costs` recomputes a run's cost from the token counts in its run folder and the configuration's `model_prices`, and a run without counts is `unknown`, counted, never priced; `connections` and `skills` start no provider and make no network call and return no secret's value; the `platform` of `connections` holds `machine` (the architecture as the system names it), `evidence` (the platform the lab evidence was made on, such as `linux/arm64`), `here` (the platform the eval image runs as on this machine without emulation, in the evidence's form: always `linux/` and the machine's architecture normalised to `amd64` or `arm64`, null when it is neither) and `same` (true when `here` equals `evidence`, false when both are known and differ, null when either is unknown), so that a page shows the answer and computes none; `artifact` reads only a regular UTF-8 file under `docs/` of the project, no link, no hidden file or folder (a path part that starts with `.`), never `docs/workbench/runtime.json`, at most 1 MiB.

**The raw artifact** (A-33). `artifacts` rows carry `kind`: `text`, `markdown`, `image` or `other`, decided by the file's bytes and never by its extension alone (an image by its magic number: PNG, JPEG, WebP; an SVG when it passes the check below; text is UTF-8 with no NUL, at most 1 MiB, and the extension only tells Markdown from other text; a hidden file or folder is not listed), so that the Desk knows before it opens a file. `GET /projects/{p}/artifact/raw?path=` answers the bytes of one image with `Content-Type` from the magic number (`image/png`, `image/jpeg`, `image/webp`, `image/svg+xml`), `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, the page's `Content-Security-Policy` and `Referrer-Policy`, and `Content-Disposition: inline`, at most 25 MiB (the size a hand-over takes). An SVG is served only when it parses as XML whose root element is `svg` (the SVG namespace or none) and nothing in it runs, loads or points outside the file: no `script`, `foreignObject`, `iframe`, `object`, `embed`, `animate*` or `set` element; no event-handler attribute (`on...`); every `href` and `xlink:href` a fragment (`#id`); no `javascript:` and no `@import` in an attribute value or a style; every `url(...)` a fragment of the file; no document type with an external identifier or an internal subset, no entity declaration and no processing instruction (`xml-stylesheet` included). That makes the file inert both as an image and as a document opened on its own from the page (a `blob:` URL on the service's origin, where the policy alone would not stop a link or a stylesheet); an SVG that fails the check is `text` in the list, and the raw route refuses it. A file of another type is refused (`400`) with the sentence the page shows, `<path> is <what>, <size> bytes: the Desk shows text, Markdown and images` (`what`: a PDF document, a woff2 font, a zip archive, a binary file...). The route is under `/api/`, so it needs the token header: a page reads it with its client and shows the bytes as an image, never as markup, and never puts the token in an address.

**The commands as data** (R4-C1, R-45). The conversation's commands are the rows `/help` prints. `commands` answers `{"commands": [{"command", "arguments", "help"}]}`: `command` is the word with its slash (`/approve`), `arguments` the placeholders after it as `/help` prints them (`<id> [sha256]`, empty when the command takes none), `help` its one line; the rows are in the order `/help` prints them (`/help` first, `/new` last) and are built by `operations.chat_command_rows` from the one source `chat_help` uses, so the read and the text cannot differ. The page lists them when the person types `/`; it draws what the operation returned and holds no list of its own. The route is a read like the others of this table (the token, the configuration check, no query); the MCP mode and the terminal have no such operation (the terminal prints the text with `/help`). `/help`'s own help line reads `list the commands`.

**The conversation** (A-23, A-25). `say` is one turn with the planning agent (`runtime/ops_say.py`); a project allows one run at a time (the run lock), and the router's run is one of them.
- *Only a shell that drains the queue may queue.* The local service runs the loop that answers the queue, so only a call from the page (`channel` `page`, which the service passes itself) queues; the terminal (`cli.py say`, `chat.py`) and the MCP mode drain nothing, so for them `say` and `route` refuse while a run holds the project, with the refusal they always had (`another run of this project is in progress`, code 1, before anything is stored), and the MCP tool's job fails with it.
- *A line typed during a run, on the page, is queued, not refused, and the queue is first in, first out.* A plain line, or `/new`, that would route while another run of the project holds the lock, or while older entries still wait for the drain, is stored, and `say` answers `{"queued": true, "reply": null, "request_id": null, "pending_id": null, "ran": false, "message_id"}`: nothing is routed, no request or decision exists, and the person never retypes. `conversation` marks the message `queued: true` until its reply exists. The queue is one cursor of the store (`conversation:queue`, at most 20 entries, changed under a file lock of the data folder); a full queue refuses the line before it is stored. A request to route from the page waits behind older entries the same way. One entry is taken at a time, the oldest first, by the service's loop or by `route-queued`, whichever comes first; while one is taken no other is. A command of the table (`/status`, `/progress`, `/pending`...) and a question about the state are not queued.
- *A request to route made during a run, on the page, is queued too.* `route` without a flow, while the lock is held, records the request once and answers `{"routed": false, "queued": true, "request", "pending_id": null}` instead of the refusal. `route` with a named flow takes no run lock (it only opens a plan; the interrupted-run recovery stays with the operations that hold the lock).
- *The service routes the queue when the lock frees.* The operation `route-queued` (terminal and the service's loop, every 5 seconds, whatever the dispatch flags say) takes the oldest entry no process has taken, only when no run is in progress, and answers the line as `say` would have (the router's memory is the messages before it) or routes the request as `route` would; one per call. An entry taken by a process that died (taken more than the run timeout of the gate file, plus 60 seconds, ago: the one bound a router run cannot exceed; one entry is in flight, so a dead one blocks the others until then) is dropped, with a word to the person: in the conversation, and for a request linked to it, so that a request left on "Route it" says why. The same for an entry that can no longer be routed (a request cancelled meanwhile). The result is `{"routed": "line" | "route" | null, "queued": n, ...}`.
- *A question about the state is answered by code.* A short plain line that is one of a closed list of forms in English and Portuguese (`ops_say.STATE_QUESTIONS`: "status", "how are we", "como estamos", "o que falta", "what is running", "what waits"...) is answered at once from `status` and `progress`, in prose (what finished, what runs, what waits for the person, what is ready or held, what is stuck), stored as the assistant's reply: no model, no request, and not queued during a run. A form with a tail ("como estamos com o brand") takes at most six words after it, no sentence mark inside the line (only a final `?`, `.` or `!`) and no verb of work in the tail, so a line that starts like a question and goes on to ask for something ("how are we going to launch the site", "how are we on the roadmap, delete the old plan") goes to the planning agent. While the router has a question open on the conversation's last request a plain line answers it, so a one-word answer such as "progress" is never taken for a status question.
- *The direct turn.* A reply of the router whose route line carries the shape `direct` (`Route: none (direct)`) is classified `{"kind": "direct", "next": <its Next line>}` (`router.read_route`). `say` answers it as the previous point does, with "The planning agent proposes: <next>" appended, cancels by code the request the line recorded (`code:direct`), opens no decision and returns `request_id` null. `route` alone leaves the request waiting and returns `kind: "direct"` with `next`.
- *The unrecognised route.* A reply that is neither a route, a question nor a direct turn opens a `question` whose body is one sentence, "The planning agent did not name a flow or a skill for request <n>", and whose payload carries `raw` (the reply whole, at most 32 KiB) and `actions: ["choose-flow", "cancel"]`; the page draws the two actions and "Show the agent's reply". The terminal's `say` reply is that sentence and how to cancel or name a flow.

**The change signal** (WP-9.13). `version` answers `{"version": <whole number>, "changed_at": <UTC time>}`. The number is kept in the store's file (the database header's user-version field, `change_counter` of `providers/store/sqlite.py`) and grows by one in the same transaction as every write that changed a row, whoever wrote it (this service's jobs and loops, the terminal, another process); a transaction that changed nothing, a rolled-back one and every read leave it alone, and after the largest value the header holds (2,147,483,647) it starts again at 1, so a reader compares two numbers for difference only. `changed_at` is when the store's file was last written. It takes no write lock and so never queues behind a writer (and works on a store that is read-only): after the configuration file is read it runs four statements on the store, the connection's two pragmas, one plain `SELECT` of the cursor that holds the accepted configuration's hash (`cursor_peek`) and the read of the header; no migration is run, no table is read. A configuration nobody accepted, or one that names another workbench checkout, is refused as for every route (`412`); the aggregate route shows it as `error` with the word of the refusal and not its sentence. The page asks `GET /versions` once a second while it is visible and reloads everything it shows when a number moved, after any write it sent, and after 30 quiet seconds as a safety net (`interface/README.md`); a server push (the protocol's event stream) would save the second a poll waits, at the price of a connection held open per tab, which this service's rules (one response, `Connection: close`, no streaming) do not allow, so it is not built. `version` has no terminal verb: a person in the terminal reads the data itself.

**Not exposed, on purpose.** `accept-config` (a configuration hash is accepted in the terminal only, so a page can never accept the change that widens what an agent may do), `run-next` (the dispatcher decides what runs), `deps`, `proof`, the standing approvals, `contained-run`, `poll`, `route-queued` (the service's queue loop calls it), `handler`, `pin` and `service-check` (the service calls it itself, at its start). No cookie, no host option, no cross-origin header, no streaming. `set-mode` is exposed with the rule of "The configuration": from the page a move down the order of the modes (stop, supervise) is accepted by code at once and no route refuses afterwards; a move up answers `accepted: false` with `next`, and every route answers `412` until the person types that command in the terminal.

**The loops.** `poll` runs for each project every `--poll-every` seconds (default 60; 0 turns it off). `dispatch` runs every `--dispatch-every` seconds, **by default every 30**; `--dispatch-every 0` or `--no-dispatch` turns it off (the two flags exclude each other). The daily caps and the modes of the area agents are what limit it, and a task is started only when its agent may start and the credential and the image are there. A handler's tick is not under the run lock, so a project that already has the scheduler's two jobs should start the service with `--no-dispatch`. A project that has a job running is skipped; an error is logged once while it repeats, and the loop goes on. A third loop, `route_queued`, runs every 5 seconds (`QUEUE_EVERY`) and is not task dispatch, so `--no-dispatch` does not turn it off: it answers or routes what waited for the end of a run ("The conversation"), one entry per project and round, the oldest first, holding the project's model slot while it does.

**The start.** After the JSON line, for each project, the service calls the operation `service-check` and logs the answer on standard error: whether this interpreter can read the secret store, whether the reference model's credential is set or in it, docker on the `PATH`, the eval image on the machine, whether it dispatches. When the secret store cannot be read, the first lines say so and give the `uv run --with keyring==25.7.0 python3 <checkout>/runtime/service.py --project <dir>` command. The answer is kept while the process lives, for `connections` (`service`) and for `status` (`dispatch off`). A check that fails is logged and the start goes on.

**The shutdown.** On SIGINT or SIGTERM the service stops accepting requests, calls `ops.stop_runs()` (it ends the container and the process group of every run a job started, which has no signal handler of its own in a thread) and does not exit before that returns; a second signal while it stops is ignored. The token file is removed.

**What it does not do.** It imports `ops.py`, `shell_kit.py` (the pieces it shares with the MCP mode) and nothing else of the runtime: no store, no lab facade, no provider, and it reads no file of a project; it writes the token file and an upload. It knows a project's data folder only through the `config` operation. Results pass through unchanged, host paths included (it is local); a page shows them as text.

## The MCP mode

`python3 runtime/mcp.py --project <dir> [--project <dir>]...` serves the operations layer to an MCP client (a model, an assistant, a messaging bridge) that starts it as a child process and speaks JSON-RPC 2.0 to it on standard input and output, one message per line (the protocol's stdio transport). It is a shell like `cli.py` and `service.py`: it parses a message, calls one operation of the table and returns what it returned. It has no token and no port: the client that started the process is the only reader of its pipes. It runs no background loop; the local service runs `poll` and `dispatch` when the person starts it.

**What a client gets.** The methods `initialize`, `ping`, `tools/list` and `tools/call`; the client's notifications are accepted and never answered. The tools are one per row of the table of operations that lists the `mcp` channel, in the table's order, and two of the shell's own: `projects` (each project with its folder, its configuration's hash, whether it was accepted and what waits) and `job`. The table lists `mcp` for the reads (`status`, `pending`, `task`, `flows`, `progress`, `agents`, `conversation`, `skills`, `costs`, `connections`, `artifacts`, `artifact`, `version`) and for `request`, `route`, `answer`, `release` (a draft) and `say`: a model client may request, route, answer, release a draft and say, and nothing else. A tool takes the row's arguments by name, and `project` (the id the local service uses, the first 12 hexadecimal characters of the sha256 of the real path; optional when one project is served). Its result is the operation's result, as JSON, in one text content; text from the project (a document, a reply, a comment) is a string inside that JSON, never interpreted, and no message but JSON-RPC is ever written to standard output (the log goes to standard error and holds no argument and no result; an internal failure also logs its traceback there, which may name a path or quote the failing value).

**Jobs.** An operation whose row has `job` is started in a thread and the tool answers with a job (`job`, `op`, `project`, `state`, `result`, `error`, `started_at`, `ended_at`, and `poll`, the call that asks for it again) instead of holding the client's turn for minutes; the tool `job` returns it again, `state` `done` or `failed` at the end. A job that ends within one second is returned ended, so a refusal is seen at once. Jobs live in the process's memory; the records are in the store. A job whose operation calls a model is refused (`busy`) while another such job of the project runs.

**What is refused, and why.**

1. An operation whose row does not list `mcp` has no tool: `approve`, `reject`, `cancel`, `retry` (approvals, rejections, cancellations and retries are made in the terminal or on the page, where the person is), `accept-config` (a configuration hash is accepted in the terminal only), `run-next`, `deps`, `proof`, the standing approvals, `contained-run`, `poll`, `handler`, `pin`, `config`, `verdict`, `set-mode`, `hand-over`, `sync` and `dispatch`. A model client must not authorise runs on its own request chain.
2. The same holds for a command typed into the tool `say`. The row of `say` takes the channel (`channel_arg`), the shell passes `mcp` itself (a client cannot name a channel), and `ops.say` does a command of a line only when that command's row lists the channel that carries the line: `/approve`, `/reject`, `/retry` and `/cancel` sent through `say` (with a leading space or control character as well, which `ops` strips) answer `error: /<command> is done in the terminal or on the page` and do nothing. The terminal and the page carry the same commands as before; the conversation's own shell passes none and is `chat`. A command that runs is still run as `chat`, so an effect is refused there by `ops.approve` (decision D8, extended on 2026-10-07): its hash is typed in the terminal or clicked on the page, never sent through an assistant or a messaging app.
3. The configuration is taken as the local service takes it: a folder that is not a configured project ends the start (exit 3); a configuration the person did not accept yet does not, and every tool of that project is refused with the sentence of `412` (`not_configured`) until `accept-config` is typed in the terminal.

**Errors.** A refusal of the operations layer (`refused` 409, `not_configured` 412, `busy` 409) is a tool result with `isError: true` and the sentence as its text content (the protocol's tool-execution error), so the model reads it. The protocol's error object is for the rest: `message` is the text and `data` is `{"error": <word>, "status": <n>}`, with the local service's words and statuses (`usage` 400, `not_found` 404, `internal` 500, the traceback on standard error only). An argument that does not fit its tool, or an unknown tool, is `-32602`, a line that is not JSON `-32700`, a message that is not a request `-32600` (a batch is accepted, although the 2025-06-18 version dropped batches), an unknown method `-32601`, a request before `initialize` `-32002`, an internal error `-32603`.

**The shutdown.** When standard input closes, or on SIGINT or SIGTERM, it calls `ops.stop_runs()` and does not exit before that returns; a second signal while it stops is ignored.

**What it does not do.** It imports `ops.py`, `shell_kit.py` (the pieces it shares with the local service) and nothing else of the runtime (the layer map says so), reads no file of a project, opens no socket and holds no secret. Its tests are `runtime/tests/test_mcp.py`.

## What the proof covers

The battery measured one skill, in one run, with an input in the form of its cases. That holds for the runtime because the container and the entry are the same. What the runtime adds was not measured: resuming a task with the person's answers in the request, and running a skill on a document another model wrote. For those the only check is field evidence, recorded from the first task. The runtime uses a band only after checking that the measurement files of its checkout are the recorded ones and that the image is the evidence's; when either fails, the skill runs on the reference model and without autonomy. A skill runs in the condition it was measured in.
