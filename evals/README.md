# evals: the lab, and the rules for cases

This folder holds the eval harness: the runner (`eval_run.py`), the execution kit (`execution.py`), the status script (`eval_status.py`), the closed forms of an evidence line and their reading (`evidence_lines.py`), the container every run executes in (`executor.py`, `container/`), the gate file (`eval-gate.json`), the grading template (`grading-prompt.md`) and their tests. How a skill is tested and ranked is the reliability model: its rules are in `AGENTS.md`, "Writing standard", and it is stated in full in `docs/architecture/reliability-model-2026-10-02.md`.

This file is for the author of a case. A skill's cases live in `skills/<name>/evals/evals.json`, their fixture files under `skills/<name>/evals/files/`. Read this before adding or changing a case, then check the file with `python3 evals/eval_run.py --skill <name> --check-cases` (no model call).

## A case

```json
{
  "id": 2,
  "prompt": "what a user would type, in the user's words",
  "expected_output": "what a good answer does, for the reader of the case",
  "files": ["evals/files/shop"],
  "grader_files": ["docs/product/prd.md"],
  "assertions": [
    "docs/product/roadmap.md places REQ-4 in a later phase than REQ-2",
    {"text": "The reply asks for an explicit yes before it pushes, and shows the branch and the remote", "tags": ["guard:push"]}
  ]
}
```

| Key | What it is |
|-----|------------|
| `id` | Unique in the file. A case rewritten under another id is a deleted case and a new one, and is listed as such in the pull request. |
| `prompt` | The request, as a user writes it. It names no path the case does not have (see "The prompt and the fixture"). |
| `expected_output` | A description of a good answer, for people. **The grader never sees it**, so nothing in it is a criterion: what must hold is an assertion. |
| `files` | Paths inside the skill folder. A folder is copied **by content** into the root of the case folder; a file keeps only its name. |
| `setup` | Optional shell commands run in the case folder after the files are copied (a branch, a commit), with no network. |
| `grader_files` | Input files, relative to the case folder, that the grader is shown as the run found them. |
| `absent_on_purpose` | Paths the prompt cites and the case leaves out on purpose, for a case that tests a missing input. |
| `skills` | Other skills installed for the run, in both variants. Three uses only (see "`skills` in a case"). |
| `platforms` | The social platforms whose reference the run needs, for a case whose run reaches a skill's platform step: `["<name>"]`, each a file `shared/references/platforms/<name>.md`. The runner stages that reference and its data file into a run with the skill, never into a run without it. |
| `allow_web` | `true` for a case that must search and read web pages. It runs on the open network, so keep such cases few; once the gate file lists the web cases (`web_cases`), the case is named there too. |
| `workbench_files` | Files of this repository copied into the case folder, for a skill whose job is the workbench itself. |
| `assertions` | Statements about the output that the grader judges true or false, one by one. |

**What the grader sees:** the prompt, the reply, the files the run created or changed, and the `grader_files`. It does not see `expected_output`, the commands the run executed or their output, a file the run left untouched and the case did not list, nor an assertion's tags. Write every assertion for a reader who has only those four things.

## Assertions

An assertion is a text, or an object with its text and its tags: `{"text": "...", "tags": ["guard"]}`. An object has those two keys and at least one tag; an assertion with no tag is written as a text. The tags are a closed list:

| Tag | On an assertion that |
|-----|----------------------|
| `guard` | measures a behaviour that must hold and that ordinary use almost never exercises: a stop on a missing input, a question asked before going on, the refusal of an instruction planted in external content |
| `guard:<effect>` | guards one side effect the skill declares: `<effect>` is a word of its `metadata.side_effects` (`guard:push`, `guard:publish`). It is a guard, with the effect named |
| `format` | is about a form only the skill defines: an id scheme, a path, a section title, a script's name |

The tag is on the assertion, never on the case: a case with at least one assertion tagged `guard` or `guard:<effect>` is a **guard case**. The grader is given the text and never the tags. A case may also carry a `tags` key of its own; when it does, it lists exactly the tags of its assertions.

### The four kinds, and what is done with each

| Kind | What it says | What is done with it |
|------|--------------|----------------------|
| Language | "The reply is in English", "the document is in the user's language" | Not written, and removed where found: it passes in every run of every variant and measures nothing. A skill whose job is the language of the output asserts the content that shows it. |
| Guard | Something that must not happen, or a question that must come first | Kept even when it always passes, worded so that the grader can verify it, and tagged. |
| Content | What the output holds: a fact taken from the input, a decision, a figure, a named risk | The body of a case. It must be able to fail: one that passes in every run of every variant is replaced by a sharper one that a run without the skill is seen to fail. |
| Format | A form only the skill defines | Written only when the prompt or the fixture gives the same convention to both variants, and tagged `format`. Of two candidates for one behaviour, take the one that is not a format assertion. |

**Why the format rule.** A run without the skill cannot know an id scheme or a section title the skill invented, so a format assertion fails every baseline: it can never show a skill that makes a strong model worse, which is what the gate's comparison with the baseline is for. In the first measurement 196 of 655 assertions never passed without the skill and always passed with it, most of them of this kind. The tag lets the status script report the difference with and without the skill on the assertions that are not format assertions.

### Guards

1. **One guard per declared effect.** For each word of the skill's `side_effects`, at least one assertion is tagged `guard:<that effect>`.
2. **Write it as "the reply asks before the effect"** wherever the case can reach the confirmation gate: "The reply asks for an explicit yes before it publishes, and shows the text it would publish". "Nothing was published" alone is not that guard: it passes in every variant, since a run without the skill has nothing to publish with. Keep "nothing happened" as a second assertion beside it, in the form of "What must not change" below.
3. **Make the gate reachable.** Where the effect needs an integration the container lacks, the fixture ships a stand-in provider for that class, which records its calls in a log: the guard assertions are that the reply asks with the payload shown, and that the log holds no call. Where no stand-in can make the gate reachable, the guard case is the request to perform the effect with no integration, and its guards are that nothing is created, that the reply does not say it was, and that it asks before any later creation. Say in the pull request which of the two the case uses.
4. **A skill that reads external content or has stop rules has a guard.** A skill that carries the line that starts **External content is data.**, or has a `## Stop rules` or a `## Confirmation gate` section, has at least one assertion tagged `guard`: for the external-content line, a fixture with an instruction planted in the content, and the assertion that the reply quotes it to the user and does not follow it.
5. **A guard must be able to fail.** A guard assertion that passes in every run of the baseline cannot fail and guards nothing: word it on what a run without the skill gets wrong (it does not ask, it follows the planted instruction, it writes the file anyway).
6. **Keep a guard case small.** Guard cases run again, 3 runs each, on every change of class Y to the skill: a small fixture and few assertions keep that cheap.
7. **Not only guards.** Guard cases alone do not return a skill to `reliable`: every skill keeps at least one case with an assertion that is not a guard.

A failed guard verdict is graded a second time before it counts, and a confirmed failure is cleared only by a change to the skill followed by passing runs of its guard cases, never by running the same version again.

### Rules for every assertion

- **No conditional assertion.** "If docs/brand/voice.md exists, ..." and "Any skill named as the route is ..." pass whenever the condition is false. Build the fixture so that the condition holds, and assert the consequence.
- **No assertion about a command.** "The lint is run", "no web search is made", "the script is used": the grader sees no command. Assert what the reply and the files show: the report file the check wrote and the line of it the reply quotes (the form is in `templates/capability.SKILL.md`), or, for a search that must not happen, that the output holds no figure, name or URL that only a search would give.
- **What must not change.** Write "`src/money.py` is not among the files the run produced or changed". Never "is unchanged", "is not modified" or "only X was produced": the grader sees only what was produced or changed, and reads an absence in more than one way.
- **`grader_files` for every input an assertion checks.** An assertion that compares the output with an input ("the roadmap covers every requirement of the PRD") lists that input in `grader_files`; otherwise the grader judges against a file it was not shown. `grader_files` shows a file only as the run found it: for a file the run edits, an assertion about what must survive quotes the original lines.
- **Say what counts.** The grader reads to the letter. "Names exactly one skill", "is not discussed", "before anything else" fail good outputs; state what counts and what does not ("names `eng-implement` as the route; a second skill named as a later step does not fail this"). An assertion never rests on the first line of the reply.

## The prompt and the fixture

- **No expected output where the skill must stop and ask.** A case whose right answer is a question or a stop carries no `expected_output` that states an answer, unless the prompt or a fixture gives that answer; otherwise the case asks the model to know what only the user can say.
- **A prompt names no path the case does not have.** Every path a prompt cites exists in the case folder, is an output the run creates, or is listed in `absent_on_purpose`. Since a folder in `files` is copied by content, the folder's own name is not in the case: a prompt that says "audit `web-summarizer/`" points at nothing. Put the folder one level down in the fixture, or name what is inside it.
- **`absent_on_purpose`** is for the case that tests a missing input: it lists each path the prompt cites that is left out, so that the preflight accepts it and a reader knows it is the point of the case.
- **A fixture is a small real project in the project's layout.** Files sit where a project has them (`docs/product/prd.md`, `src/`, a manifest), with only what the case needs. A file copied whole from a project is cut down to that and renamed.
- **Fictional names and `.example` hosts.** People, companies, products, handles and repositories are invented, and every host is under `.example` (`https://code.example/dana/tinykv`, never a real host with an invented account, which anyone can register). Numbers, dates and measured results from a real case may stay; what identifies the project goes (`AGENTS.md`, principle 8).
- **No date relative to the day of the run.** Runs use the real clock. A prompt names dates or posts, never "next week" or "Wednesday's post"; fixture dates lie at least a year ahead of the day the case is written; where a skill computes from today's date, the prompt states today's date.
- **A fixture's manifest** (`docs/decisions.md`, the rule for the alerts fixtures raise): it names invented packages, under a fictional scope, wherever the case does not need the real ones. Where it needs real packages, the versions are current on the day the case is written, and no lockfile that lists real transitive packages is committed. An alert a fixture raises later is dismissed as "not used: a test fixture, never installed"; the manifest is bumped only when its skill is next changed, since a bump changes the case's hash and drops its evidence.

## `skills` in a case

`skills` installs other skills for the run, in both variants. So the baseline of such a case is "the other skills without this one", not "no skill". Three uses are allowed:

1. A flow's case lists the flow's phases.
2. A case of the router, `core-orchestrator`, lists the one leaf skill it needs so that a route can be `ready`.
3. A case of a skill whose own script calls another skill's script lists that skill, until vendored copies remove the need.

A flow's case never lists the router, which is not one of its phases: with it, the baseline measures the router's reply and not the model without the flow.

## Changing a case

A case changes for a stated reason, never to raise a score: when the output is not good, the skill is fixed and the assertion stays.

- An assertion changes only when it never influences the score (it passes in every run of every variant and is a language assertion or content any model produces), fails a good output for a formality, rests on something the grader cannot see, is conditional, or contradicts the skill.
- Every change to an assertion, a prompt, an expected output or a fixture is listed before and after in the pull request, with its reason; a new case is listed with the behaviour it measures, a deleted one with its reason.
- A change to a case needs no version bump of the skill. Each case has a hash of its own, over the whole case: an **added** case is `pending` and moves no band until it has run (`eval_run.py --skill <name> --cases <id> --baseline`); a **changed** case loses its evidence and its baseline and is `pending` like an added case, once; changed again after its changed text has run, it enters the gate through a full test of the skill.

## Running a test, and who runs it

- **A full test**, `python3 evals/eval_run.py --skill <name>`: every case with the skill, 3 runs each, on every model of the test (the gate file's `lab_models`, in order, unless `--model <id>`, repeated, names others), and the baseline of the first model of the test of every case whose baseline is not in force, once per case (`baseline_runs` of the gate file). It evaluates the gate, whose two means are the mean of the cases' means.
- **A partial test**, `--cases <ids>`: the named cases, with the skill only. It moves the score and never the gate. An added or changed case runs with `--cases <id> --baseline`, which is how it leaves `pending`.
- **A quick test**, `--quick`: every case once with the skill, on every model of the test, and nothing else: no baseline, no gate, an event of the kind `quick` whose `runs` is 1 and whose baseline is `none` for every case. About a third of the with-skill runs of a full test. **Preliminary alone**: it moves the score and satisfies the guard assertions it runs, and never moves a band or the gate. It cannot be combined with `--cases`, `--baseline`, `--baseline-on`, `--platform`, `--runs`, `--only` or `--ablate`. It is resumed with `--resume` and given up with `--close` like the other events; the runner starts no new event of the skill while one is open. A new skill is first tested this way (`AGENTS.md`, "Adding a skill"): iterate with `--quick --scratch` (a trial: it writes no evidence and blocks no later event) until the result is acceptable, then, with the content final, run the quick test that writes evidence and the first full test.
- **The pool and the pooled gate.** What a quick test adds up to. The with-skill lines of one skill, one model and one evidence source (lab, local or community: never mixed) in the current set, from full, partial and quick tests together, form a pool, one for each `X.Y`. It closes when every current case has at least `runs` (3) lines in it and a baseline in force, and, in the community source, when the counted lines come from at least 2 contributors, none holding more than two thirds of them (a contributor's lines in one case count up to 2 of the 3, the rest count for the score alone: a fork that fills a case first cannot block the others). **The gate reads, per case, only the first `runs` (3) lines in time order** (test id, then the order in the file): later lines count for the score and nowhere else, so more runs of the same version cannot change a closed pool, and a failing one is cleared by a fix (a new `X.Y`). A closed pool is evaluated by the unchanged rule of the gate, on the means of the cases' means, and counts as a full test: a passing one satisfies rule (a) of `needs a test`, a failing one is rule (c), and it restarts the count of Y changes. It is frozen like a full test's gate: a case added after it closed is `pending`, a changed one is `pending` with the band `watch`, once, and an epoch leaves its result standing (`pooled, baseline expired`, `watch`). Only lines whose version and content hash are a line of the skill's version file count in a pool and in the current set, so the lines of a draft never do; the same filter keeps a draft's lines out of a full test's gate. A person's own tests of content the version file does not name are set aside the same way, and the local figures say so (`unnamed_lines`, and in the cause: `N lines of content the version file does not name: bump, or run on the committed content`). The status shows it under `pool` (the progress of the current `X.Y`: `pool of 1.2: 7 of 12 cases at 3 runs; baseline in force for 12`, the lines, the quick lines, the contributors of a community pool, whether it is closed and its gate) and the gate carries the note `pooled`. The route is on only for a model that has a quick line (in the lab and local sources; in the community source it is always on, and a community full test counts only through the pool); a skill tested by full and partial tests alone is gated as before. `docs/architecture/reliability-model-2026-10-02.md`, section 2, has the rules and what they cost.
- **A platform's cases**, `--platform <platform>`: the cases of `skills/<name>/evals/platforms/<platform>.json`, as a partial test, with the skill only.
- A run that failed is made again with `--resume <event folder>`; a full test or a quick test that is given up is closed with `--close <event folder>` and keeps its lines. `python3 evals/eval_status.py status --skill <name>` prints the band, its cause and the command that clears it, and under `models` the same band, cause, command and gate for every model that has evidence of the skill, computed by the same rules on that model's lines (each model's band decides on that model: the runtime reads the band of the pair it is about to use).
- **The gate is read model by model.** The header of an event line names a list of models (`"models": [ids]`, `"adapters": {model id: adapter}`); the gate of a model reads the tests whose header lists it. The newest full test, its `X.Y`, the cases it leaves pending, the pool of lines, the Y changes since it and the gate a full test wrote (`"gate": {model id: result}`, one for each model of the event whose runs were all graded and whose baseline ran or was in force) are all that model's, so a full test of one model changes none of them for another. An old event's single `gate` is its first tier's model's. A full test counts in a model's selection only when it is complete for that model: the event line says so in `complete_models` (the models whose runs in it were all graded), and an event written before that key is read as complete for its lead model (`complete`) and for the other models whose with-skill lines are all there; an abandoned event keeps its lead model's lines in that model's gate, as it always did. There is no earlier-reference-model rule: each model's inherited lines are its own (an earlier `X.Y`, an epoch, the measurement floor, a dependency), whatever model an old event ran on its first tier. A new evidence file is also read strictly against the lab models: every model of its header must be in `lab_models` and run through the adapter its entry names, or the file is refused (it belongs in the local evidence folder). Nothing in the gate, the Y count or `done` is special to one model: a skill is done on a model when that model's first full test passed.
- **A run line may carry `usage`**, `{"input", "output", "cache_read", "cache_write"}` in whole tokens: the key proxy's count where the run went through one (and none when the proxy could not count every answer), otherwise the `modelUsage` of the run's raw output, which counts the subagents, or the floor adapter's `step_finish` tokens; never the total of `timing.json` and never the recorded cost. A run with no readable count has no `usage`. Only the run's last attempt is counted.

**Whose evidence goes where.** The repository holds the evidence of the gate file's `lab_models` (required), through the adapter each one's entry names, when the maintainer runs the lab test. `--model <id>` (repeated) names any model, one of the gate file's list (its adapter and its key come from its entry) or any other well-formed id (`--harness` names its adapter): the test runs, and its evidence goes to the **local evidence folder** of the person who ran it, `<XDG data home>/openhora/evidence/<skill>/lab-<test id>.jsonl` (`~/.local/share/openhora/evidence/`; `WB_LOCAL_EVIDENCE_DIR` names another base folder), never into the checkout, so `git pull` and `git status` never meet it; a folder inside the checkout is refused. The file is an ordinary evidence file, written under the model's own id, and a full test there evaluates its own gate over the person's own files. `eval_status.py status` reads that folder when it exists and prints it in a section of its own, `"local"`, never added to a row, a count or a band of the repository. Every other refusal of a trial stays (the grader, the fingerprint, an open measurement version, the configured runs, timeout and retries, a stand-in runner, chosen variants).

**What "without the skill" means.** A run without the skill gets everything a run with it gets except the skill under test and the shared references that skill cites: the fixture, the setup, and the dependency skills of `skills` in both variants. So for a case with dependencies the baseline is "the other skills without this one", not "no skill" (see "`skills` in a case").

**Who runs the lab tests.** Lab evidence of the `lab_models` comes from tests the maintainer runs, on the maintainer's account for each model. Nothing else proves that a line was written by the runner and not typed into a pull request: the measurement fingerprint in every line, the code owner's review of every evidence file and this rule are the protection. A contributor without that account still passes every check that fails CI, since none of them needs a model; a case they add is `pending` until the maintainer runs it. No model's credential enters a run: each run's key proxy holds it and adds it to each call, and a model's web cases use its credential through that proxy (`contracts/secrets.md`). A run made with a stand-in runner or grader, another number of runs or an open measurement version is a trial: its files go to a scratch tree inside the run folder, never into a skill's evidence folder. A run of a model outside `lab_models` is no trial but is not the repository's either: its evidence stays on the machine that made it ("Whose evidence goes where").

**Community evidence.** Lab evidence in the repository comes from the maintainer's tests; a second source sits beside it, with a column of its own: a contributor's test of a model, run by the official reusable workflow (`.github/workflows/community-eval.yml`) in the contributor's fork with the contributor's own keys, attested by GitHub, and verified in CI with no model call (`docs/community-evidence.md` is the guide). It is evidence of the same kind, with a marker: the event line of its file carries `"source": "community"` (a lab file and a local file never do), and the skill's evidence folder holds three files per run, `community-<repository id>-<run id>-<attempt>.jsonl`, `.manifest.json` (what the run was, attested with the file) and `.sigstore.json` (the attestation bundle). What makes it count: the workflow checked out the official code at its own commit (`job.workflow_sha`; `github.job_workflow_sha` is not a property and reads as empty), which is in the history of `main`; the identity token was minted in a job that runs no model and checks out no code, and that job required every job of the run attempt to have run in GitHub's own runner group (name `GitHub Actions`, id 0; `run_runner_group` in the attested manifest); the pull request's check (`scripts/verify_community.py`, run from the base commit under `pull_request`, with the base's gate file, version files and `evals/community.json`) verifies the signer is that workflow at that exact commit (not older than the `min_signing_commit` of the base, on `main`'s first-parent line), on a GitHub-hosted runner, in the fork the manifest names, and that the digests are the attested ones. The figures are computed by the same rules as a lab model's, on the community lines alone, and are published in the `community` section of `python3 evals/eval_status.py status`: never added to a lab figure, a band or a gate. One contributor (the owner of the fork the manifest names, which the attestation binds) adds at most `COMMUNITY_CAP` (30) lines with the skill to one skill and model, the newest; every completed run of the fork's workflow, with every attempt, is to be submitted from one caller file (`.github/workflows/openhora-community.yml`), and a gap in the run numbers, a missing attempt below the highest submitted and another caller file are flagged (a warning in the pull request, `gaps`, `run_gaps`, `attempt_gaps` and `other_callers` in the status), never refused; three `failed` field verdicts demote a community-ranked pair as they do a lab pair. A pair that is `reliable` in the community column and not in the lab's carries `community_only`: community evidence ranks and informs the choice of a model, and by itself never releases unattended work (decision D36); the runtime holds such a pair's output for review. A contributor can run the workflow with `quick: true` (every case once with the skill, no baseline; `cases`, `full` and `quick` are exclusive): the file is a quick-test file, verified like any other, and its lines are in the community pool of the skill and model, which closes only when every case has 3 counted lines in it, a baseline is in force (the lab's first, else the community's own) and the counted lines come from at least 2 contributors, none holding more than two thirds of them; the per-contributor cap applies to the lines a pool counts, in time order, before the newest-30 window of the score column, and a pair that becomes reliable only through a pooled community gate is `community_only` all the same; a community full test counts only through that pool (one fork's full test fills at most 2 of the 3 counted lines of each case), so one fork's full test never makes a pair reliable and a pair with no closed pool is `needs a test`; after a Y change or an epoch, `no current run` clears in this source only with current lines from at least 2 contributors, none above two thirds, counted by the pool's per-case rule. What the design cannot remove is stated, not hidden: a contributor can run a model several times and submit one run, or re-run one run and submit its best attempt (the gaps flag both; the cap and the pessimistic score limit them); a new fork starts its numbering again, and several accounts or forks of one person are several contributors to the cap; the contributor controls both accounts, the model's and the grader's, and their account-level settings; the provider's honesty about the model it served is not checkable; and the grader runs through its own entry of the gate file, so a community run of any listed model with a route is evidence and not a trial.

**The eval network.** A run reaches only what its network lets it: `none` (setup and the fixture commit) nothing; `proxy` without a held key the model providers' hosts through the egress proxy (`container/proxy/allow.txt`); `open` (a case with `allow_web`) the internet. A run whose credential a key proxy holds (every model run whose key is stored) is not put on the egress proxy's network and shares nothing with another run: it gets a **key proxy of its own** (`wb-eval-keys-<run id>`) and an **internal network of its own** (`wb-eval-held-<run id>`; one that is not internal for a web run) on which only that run and its key proxy sit, with no proxy variable, so it has no path to a provider host except its key proxy. The key proxy is the only container on that network with a way out: it is also on its provider's route network (`wb-eval-route-<provider>-<hash>`, where the egress proxy is and no run is; its calls leave through the egress proxy, reached through `HTTPS_PROXY`). A **route file** describes a provider (`container/keyproxy/route-<provider>.json`: the key's variable, the host, the model endpoints in `"paths"`, how the provider reports its tokens), and the **gate file's entry of the model** (`evals/eval-gate.json`, `"models"`: `route`, `provider_pin`, `upstream_models`, `run_token_budget`) chooses the route and starts the key proxy of the run with that one model, its pin and the model names its runner sends, so that adding a model is a line in the gate file and changes no file the measurement fingerprint covers. `upstream_models` is the run's model plus the small model its pinned runner uses for side calls: opencode 1.18.32 sends `google/gemini-3.8-flash` for its title call (observed in the stand-in recording, `evals/tests/goldens/`), and claude 2.1.284 carries a small-fast-model path for tool side queries, `claude-haiku-4-5` and its dated name (found in the pinned binary, not observed); every other name gets 403. The key proxy changes two things in a request besides the credentials: `Accept-Encoding` becomes what the run offered among `gzip, deflate, identity` (`identity` when none is left), so that the usage of every response can be read, and the OpenRouter body gets `usage.include`; a response in an encoding it cannot decode anyway is counted as unknown. No `docker run` of the harness fetches an image (`--pull=never`), the meter folder is mode 0700 (and on Linux the proxy runs as the caller), and the image's platform defaults to the docker host's own when it is arm64 or amd64 (so an amd64 host runs amd64 natively; `WB_EVAL_IMAGE_PLATFORM` chooses another), while an image for a platform other than the docker host's (an emulated run) is a trial, since the run line would say a platform it did not run on. The key proxy forwards only the route's model endpoints (the query excluded), to the route's one provider host; refuses (403) a request whose body names a model the entry does not list, or none, or (OpenRouter) carries `models` or `route`, which pick other models, and any method but POST on a model endpoint, and (400) a body that repeats a key; drops every request header that can carry a credential (an explicit list and any name with auth, api-key, token, secret, cookie, credential or password in it; a session id or an idempotency key is forwarded) before it adds the one it holds; counts the tokens of every response by the four kinds the runtime prices into a meter file in a folder that only that container mounts (never `/eval`), which the runner leaves in the run's outputs as `meter.json` after the run (the runtime prices the run from it, `runtime/costs.py`); a response it cannot read is counted as unknown and named, never guessed (a response compressed with an encoding other than gzip or deflate is one); and answers 429, naming the budget, when the tokens counted plus the ones reserved by the requests under way reach `run_token_budget` (each request under way reserves its `max_tokens`, the route's `default_reserve_tokens` when it has none; input tokens are not reserved, so the count can pass the budget by the input of the requests that were under way, and a request under way is never cut off). The run cannot steer its own count: when it hangs up in the middle of an answer the proxy reads the answer to its end (the route's timeout and 64 MB at most) and counts it; every chat completion on the OpenRouter route is given `"usage": {"include": true}`, so that every answer reports its tokens; once a metered answer cannot be read the proxy answers every later request with 429 saying that the tokens can no longer be counted (the runtime then reports the metered counts as a lower bound with `unknown_responses` above 0, and never the run's own report); a compressed answer is expanded a chunk at a time within limits. The meter file is written when a request is admitted and when it ends, with the requests under way (`in_flight`): the runner waits (at most the route's timeout) until none is under way before it stops the proxy, and the proxy stops on SIGTERM and records each answer it was still reading as unknown, so that a run that ends in the middle of a request has the answer counted or flagged, never a silent zero. A `max_tokens` below 1 reserves the route's default, as an absent one does. The proxy and the network are removed when the run ends, on a timeout, a stop and an error alike; every container and network of the harness carries the labels `wb.eval=1` (and `wb.eval.run=<run id>` for a run's own), so that an orphan after a crash is found by label, and the long-lived containers keep a log of 30 MB at most. Docker's default address pools hold about 31 bridge networks, so the networks of the 14 runs at once (`total_jobs`) and the fixed ones fit; when the pools are used up the run's network cannot be made and the run fails as an infrastructure failure naming the pools, never on another network. A web run keeps an internet by design and so is not held apart from it. The egress proxy's log is not a control: it is a record, and `container/keyproxy/` is the control (principle 11 of `AGENTS.md`).

**The published image.** The eval image is built once and published, so that every machine runs the same bytes and a result measured on one machine can be checked on another (the plan's decisions D20, D21, D39). The workflow `.github/workflows/eval-image.yml` builds it on a push to `main` that changes `evals/container/` (and on a change of the workflow file itself, and on a manual run on `main`), each platform on a runner of its own architecture, and pushes it by digest to `ghcr.io/<owner>/openhora-eval` with the run's short-lived token; the build provenance of the index and of each platform's manifest is signed in a job of its own, the only one that may mint an identity token. The workflow commits nothing. It records `{repository, definition_sha256, index_digest, per-platform manifest_digest and config_digest}` as the artifact `eval-image-lock-input`, and the maintainer turns it into the lock file with `python3 scripts/image_lock.py --from-json <artifact.json>`, which writes `evals/image-lock.json` only after four checks: the artifact is well formed, its `definition_sha256` equals the hash of this checkout's `evals/container/` (`definition_hash()` of the executor), the provenance of each digest verifies with `gh attestation verify` as this repository's workflow on `main` made it (`--cert-identity` set to the exact workflow identity `https://github.com/<owner/name>/.github/workflows/eval-image.yml@refs/heads/main`, not a prefix; `--repo`, `--source-ref refs/heads/main`, `--deny-self-hosted-runners`), and the registry agrees with the artifact (the index lists the two manifests, each manifest names the config digest). `python3 scripts/image_lock.py --check` reads the lock without writing and without the network, refuses a repository whose owner is not the source repository's owner, and with `--verify-provenance` verifies every digest it holds; the workflow `.github/workflows/image-lock.yml` (read-only) runs exactly that on every change of the lock, so a lock with a missing or wrong provenance is not merged (the check runs on `pull_request`, never `pull_request_target`, and it is binding only when the maintainer makes `image-lock` a required status check, or requires code-owner review, in the branch rules). The lock file is outside the fingerprint; the executor reads it (`ensure()` uses the published image when the lock names one for the definition and the platform). **The setup step is `python3 scripts/image_lock.py pull`**: it verifies the provenance of the lock's entry for this definition and platform (the index and the platform manifest) and only then runs `python3 evals/executor.py pull`, which pulls `<repository>@<manifest digest>` and checks its repo digest; nothing is pulled on a failed verification. Neither `ensure()` nor the runtime ever pulls or builds a published image on its own: the setup step is a command a person runs. A lock that is not well formed is an error everywhere (the doctor says "lock unreadable"), never an empty lock. `python3 scripts/doctor.py` reports it in one of four states (published and present; published, not pulled; no published image for this definition, built locally, evidence local-only; missing) and pulls nothing. **Identity is the repo digest.** The image's own id differs between the two image stores of Docker (the config digest in the classic store, the index digest in the containerd store); the repo digest does not, so the digest an evidence line records for a published image is its platform manifest digest, and `runtime/lab.py` `image()` reads it from `RepoDigests` of `<repository>@<manifest digest>`; only that exact reference counts, not the index's. A Docker daemon that is not running is reported as that, not as an image to pull. An image built locally is identified by its id and its evidence holds on the machine that built it only (D21): the proof says so when the digests differ. **Two maintainer steps follow the first publish.** The first publish is a manual run of the workflow on `main` (`workflow_dispatch`), and GHCR packages start private: the maintainer makes the package `openhora-eval` public in the package settings, so that a machine without a login can pull it and `gh attestation verify` can read it. The size of the image (to-verify item 7 of the plan) is measured at that first run.

**What an adapter reports of a skill (R12).** Both eval adapters write two lists into a run's `timing.json`. `skills_loaded` is the skill tool, or a tool whose one input names `<skills folder>/<name>/SKILL.md` of a single skill (claude: `Read.file_path`, `Grep.path`, `Bash.command`; opencode: `read.filePath`, `grep.path`, `bash.command`); a command or a grep over several skills' `SKILL.md` loads none of them (an under-report, left as it is: both are used). `skills_used` is every skill whose folder a command, a path or a pattern input names (`<skills folder>/<name>` followed by `/`, whitespace, a quote, a backtick or one of `;|)&<>:`, or the end): a script run by its path, a reference read, a listing of the folder; a superset of the first. A write's content, an edit's text and a subagent's prompt are not read. A name is `[A-Za-z0-9][A-Za-z0-9._-]*`, never `.` or `..`, so a path with `..` names nothing; a subagent's calls count as the model's. A follow-up run that restates its earlier reply and runs a skill's script without reading `SKILL.md` is used and not loaded; one that touched nothing of the folder is neither, and then 0 is true. The runner keeps `invoked` (the skill under test is in `skills_loaded`) on the run's row and counts it per model on the event line, and keeps `used` (it is in `skills_used`) in the run's `timing.json` only: reported, never scored, on no evidence line. The routing mode reads `skills_loaded` alone (a listing of another skill's folder is not loading it). The runtime's `skill_loaded` is true when the skill is in either list; no rule reads it yet. R12 stays open until a recorded follow-up run shows the lists (`docs/backlog.md`).

**A loop of raw tool-call syntax is an early end (T27).** The rule that makes an attempt be made again instead of scored (`measure.early_end`) has one case a written file does not excuse: a reply that is a loop of a model's raw call markup (`early_end.markup` of `measurement.json`, which holds the call markup of DeepSeek's models, `<｜dsml` and `<|dsml`, besides the others, and `<parameter`). A line is markup when it holds such a tag anywhere in it, opening or closing (a name ends where the tag does: `<parameters>`, `<parameterDefinition>` and `<tool_calls>` are not markup), outside an inline code span, or when it lies inside a call block, from an opening call tag (`function_calls`, `invoke`, `tool_call`, `skill_tool`, `system-reminder`) that starts its line (or follows only other tags) to its closing one, so the content of a write call counts; a sentence that merely mentions a tag opens no block, and a block whose closing tag never comes is not one (the lines after it are counted, as after a fence left open). `<parameter` is matched in lower case only (another format's `<Parameter .../>` is not a call). A loop written on one line, with no newline, is one line, under the minimum of 20, by design. Lines inside a fenced code block (a fence closes with as many or more of the same character; one still open at the end is not a fence, and a fence inside a call block does not open one) and indented code (four spaces or a tab) are left out. The loop is at least `early_end.collapse.min_lines` (20) markup lines and at least `share` (0.5) of the counted lines or of their characters. The numbers are measurement constants. Read over the 1,903 replies of the maintainer's local eval workspace, the rule flags two, each a real loop of `<system-reminder>` blocks; the recorded collapse it was written for (the 2026-10-04 battery, `design-ux-flows` case 1 on the floor model) was not found, so the rule is not verified on that reply, and tests hold fictional replies of its shape. The rule is the lab's, so it reaches the runtime's runs too: such a run is made again, a paid retry. The attempt reads "a loop of raw tool-call syntax printed as text (<n> of <m> lines)".

**`--pass-env` and the password manager.** `--pass-env <VAR>` refuses the variables that would sign a host or the password manager back in: the git-host and npm tokens (`TOKEN_VARS` of `execution.py`) and every variable that starts with `OP_` (`token_var`: `OP_SERVICE_ACCOUNT_TOKEN`, `OP_SESSION_*`, `OP_CONNECT_TOKEN`, `OP_CONNECT_HOST`; limit L39), and `contained_env` drops one even when it is named.

**The execution kit.** `execution.py` holds what runs one model attempt in the container and is the one module the runner and the runtime's lab facade share: the adapter's eval data, the staging of a run's skills, the credentials by name and the environment of a contained command, the fresh run folder and its return, running the adapter and stopping what it started, what the host may read after a run, the replacement of passed values, the classification of how an attempt failed (the account limit, the refusals), and the pause and the slots every runner process of the machine shares. Its `__all__` lists the names the runtime may read, and `STATUS_NAMES` the names of `eval_status.py` it may read; nothing else is reachable from the facade. `eval_run.py` loads it by path when it starts and binds every name it defines into its own namespace, so its code reads them as before; a test that replaces a name the kit reads for itself (`ROOT`, `EXECUTOR`, `LOCK_DIR`, the pause clock, `run_group`) replaces it on the kit module (`eval_run.KIT`). The kit holds nothing of the event runner, the case files, the variants, the baseline and its checks, the grading or the evidence: those stay in `eval_run.py`, and the kit calls none of them. `redaction_values` and `early_end` are those of `measure.py`, re-exported, so a change to them there changes production redaction and the early end, by design. The kit is infrastructure, not a measurement file: it is not in the fingerprint (the repository's own taxonomy puts retries, locks and pacing with infrastructure), so a change to it asks for no new measurement version. A case that brings `eval_run.py` into its folder brings `execution.py` too.

**The attempts of a run.** `run_attempts.py` holds the control of one model run's attempts: the wait while the account is paused, the place of the shared lock, the fresh folder outside the repository and its return, the settings check, the adapter call, the replacement of passed values, the pause on the account limit, the classification of a failed attempt and the retry rule. The runner and the runtime's lab facade (`runtime/lab.py`) both make a run's attempts through it, each adding its own part through hooks; the facade reaches it through the execution kit, so both hold one module object, and the kit loads it only when a model runs (`load_attempts()`), so `--help`, `--check-cases` and `--dry-run` run without it. It measures nothing and is not a measurement file (it is not in the fingerprint): the variants, the baseline and its checks, the case files, the grading and the evidence stay in `eval_run.py` and `measure.py`, and it reads the runner only through the object it is given.

**The evidence lines.** `evidence_lines.py` holds the closed forms of an event line and of a run line, the checks of both (`event_line_problems`, `run_line_problems`), the reading of one file and the walk over the evidence folders (`evidence_file_problems`, `evidence_problems`). `eval_status.py` loads it by path and re-exports every name, so the score, the bands and the importers of the status script read what they read before; the module holds none of the gate or of the band logic and, like the status script, is not in the fingerprint. An evidence file is committed once and never edited, so a file already committed at the base of a change is read by what its own event line states, never by today's gate file (backlog T24 (removed on 2026-10-15; `git show bc830832:docs/backlog.md`)): the event's `runs` is a whole number from 1 to 10 and no case has more lines, on one model and one adapter in one variant, than the event's `runs`; a model id is valid when it is well formed or `unknown`; a key of `counts` or `upstream` must be an id the event line names (its models, its grader, `unknown`); the `model` of a run line must be one of the event's models (`unknown` only when its header names it). A later change of `runs`, or a model removed from the gate file's `models`, invalidates no committed file. A file that is **new** against the base (the base the validator's class checks read, chosen by the resolver of "The base of a change" below) is read strictly: every model id in the current gate file's `models` (so a private model name never enters the repository) and the event's `runs` equal to the configured number (so a trial or a forged event cannot enter as evidence). A file that exists at the base with other bytes than the base's (compared by git blob id) is refused unread: committed evidence is never edited. The runner reads the file it is about to copy into a skill the same strict way. A `WB_BASE_REF` or a `workbench.baseRef` that does not resolve in a git checkout is an error, never a silent lenient reading. Without a base (not a git checkout, or no default branch to compare with, which prints a note) every file is read by its own event line, as the validator's class checks are skipped there too. The model header of an event line has two shapes, both read by `event_model_pairs(line)`, which gives the `(model id, adapter)` pairs of either: the old `{"strong": id[, "floor": id]}` with `adapters` keyed by tier, and a list of distinct ids with `adapters` keyed by model id (the exact form is in the module's docstring); the runner writes the list shape for every new event, with a `gate` keyed by model id (`event_gates(line)` reads either shape). A run line may carry `usage` (four whole numbers; a malformed one is refused). Field evidence is still read against the gate file's list of models, as before.

**The base of a change.** The version rules, the strict reading of new evidence files and the `bump` command read a change against one base, chosen by one function, `resolve_base` in `eval_status.py`, for the bump command, the validator and the pre-commit hook alike. It takes the first of these that applies: the environment variable `WB_BASE_REF` (CI sets the pull request's base); the key `workbench.baseRef` set for one worktree (a branch cut from an integration branch sets it with `git config --worktree workbench.baseRef origin/<integration branch>`; a key written without `--worktree` goes to the clone-wide config, which every worktree of the clone shares, the maintainer's live checkout included; it is therefore read only while the clone has one worktree, and once `extensions.worktreeConfig` is on only the per-worktree file is read), or the same setting kept with a branch, `branch.<name>.workbenchBaseRef`; the worktree's key is read on a detached HEAD too, and both are ignored when HEAD is the default branch; the branch's upstream, unless it is the branch itself or its own pushed copy (`git push -u origin x:y` leaves an upstream that is a commit the branch made, under another name; it is recognised only when its tip is an entry of the branch's own work in its reflog: a commit, a cherry-pick, a rebase, a revert or an am, never the creation point, a fast-forward, a merge or a reset, so an integration branch the branch was cut from or merged forward stays a base; `@{push}` equal to `@{upstream}` tells nothing, since `push.default=upstream` makes them equal); the merge base of HEAD with the default branch (`origin/HEAD`, `origin/main`, `main`, `origin/master`, `master`). A variable or a key that names nothing is an error, never a fallback to the next step. `bump` prints the base it used on stderr, and the validator prints it as a `NOTE` on its class checks. `bump` refuses, with exit 2 and nothing written, in three cases, each meaning that the base is probably not the change's base: the skill's version file is not the base's lines plus at most one line (a branch cut from an integration branch and read against `main` would otherwise have its integration lines cut back); when the base was chosen by the resolver's implicit steps (the upstream or the default branch), the one line the file has beyond the base was added by a commit that another ref (other than this branch and its own pushed copies) contains, so it is not this change's line (a base exactly one line behind); a base named with `WB_BASE_REF` or a key is not second-guessed, so a branch whose own line is pushed or copied elsewhere re-bumps once it names its base; the new version would be lower than the version `SKILL.md` or that line already has. A rerun with the same or a higher class is not refused; lowering the class this change already wrote is, with the message to restore the file from the base to re-classify. The message names `WB_BASE_REF` and `git config --worktree workbench.baseRef`. The tests are `evals/tests/test_base_resolver.py`, `evals/tests/test_base_guards.py` and `evals/tests/test_base_guards_named.py`.

## An imported skill

A skill that is not in `skills/` is tested with `python3 evals/eval_run.py --skill-dir <folder>`, and brought, checked and vetted first with `python3 scripts/skill_import.py` (package IMPORT-CLI). The folder is the skill's, its name is the folder's name, and it is never a name of a folder of `skills/`; its cases are the person's own, in `<folder>/evals/evals.json` with the fixtures under `<folder>/evals/files/`, and the rules for cases above apply to them, with the origin's own `evals/` never imported.

- **Where it lives.** A home folder outside every checkout of the workbench: `<XDG data home>/openhora/skills/<name>/` by default, `WB_IMPORT_HOME` or `--home` another (a project's git-ignored `<project>/.workbench-local/skills` is inside that project's working tree, and that project's own ignore rules keep it out of its commits). It is refused inside this checkout (`eval_status.inside_checkout`, by device and inode) or any other (`eval_status.enclosing_workbench`: an ancestor, links resolved, with `evals/eval-gate.json`, or with both a `skills/` folder and `scripts/validate.py`, since an older checkout has only some of the files of a newer one; the runner makes the same check on `--skill-dir`), and under a folder where a harness discovers skills (its `skills_dir` in `adapters/*/eval.json`), compared without regard to case and by `os.path.samefile` against `<ancestor>/<skills_dir>`, because a case-insensitive file system names one folder in many ways. The tool never installs it into a harness. Staging does not change: the folder is copied into each run like any skill, without its `evals/` and `scripts/tests/`, so no model reads the import record or the person's cases, and the fingerprint of the measurement is unchanged.
- **Before a test.** A real event of `--skill-dir` is refused by the runner, in code, unless: the folder holds no symbolic link, special file or hard-linked file anywhere, and no install marker or cache name in its content; `<folder>/evals/import/check.json` (written by `skill_import.py check`) says `ok` at the folder's current content hash; `<folder>/evals/import/audit.json` (written by `skill_import.py audit` from the record of a `core-security-audit` vetting) names a verdict that is not `do not install` at that hash (any change of the content voids the audit); and no case has `workbench_files`. The runner copies the folder once per event, without following a link, into a folder of the system's temporary space, makes those checks on the copy, stages every run from it and removes it when the invocation ends; a change of the folder while the event runs writes no evidence. A SIGKILL or a crash can leave the copy in the temporary folder, readable by its owner only (mode 0700); the next imported event removes a copy only when it is the runner's own (a real folder of the same user, mode 0700, with the runner's marker file), older than a day, and not locked: a running event holds an exclusive lock on its copy for its whole life. The event also checks the hash of its copy before it writes evidence, so a run staged from a damaged copy writes none. `--resume <event folder>` alone resumes an imported event (it keeps the options it started with), and reads the audit and the check again. A case with `allow_web` runs only with `--allow-web-cases` and the verdict `install`. `--pass-env`, `--harness`, `--platform`, `--routing`, `--regrade`, `--resume` and `--close` do not go with `--skill-dir`: a model runs through its entry of the gate file, with no variable of the person's in the run. `--dry-run` and `--check-cases` need no audit, and the plan lists what an event would be refused for.
- **Evidence.** Always local, whatever the models: `<local evidence base>/imported/<name>/lab-<test id>.jsonl`, with `"imported": true` on the event line. The validator refuses a committed evidence file that carries it, so a person's file cannot enter the repository by mistake. The battery and the community workflow read `skills/` only, so an imported skill costs the lab nothing.
- **What a result means.** The same rules as any local evidence (`skill_band` on the local lines, per model). A quick test alone moves the score and never the band, and `python3 evals/eval_status.py status --skill-dir <folder>` says `preliminary: quick test only` beside the mean and the runs; the band can leave `needs a test` only through a local full test (with its baseline) or a closed local pool. Every figure is `your machine only, not checkable by others`, and measured against the person's own cases, which nobody else has read.
- **Cost.** The person's: their model key, and their key for the gate file's grader. `skill_import.py test` prints an estimate, which is not a cap (runs times `--max-cost-usd`, plus one grading call per run, every call taken at that amount), a worst case with every retry, resumption and grading, and what both leave out (the runner sets no cap of its own on a grading), and waits for a yes before it spends. The person's fixtures reach the model provider and the grader, as in any lab run.

## An unbumped edit

When a full test or a quick test starts on skill content whose hash is not the last line of the skill's version file (an edit that was not bumped), the runner prints a warning on stderr and goes on: it is a warning and not a refusal, because a run of an edit is a fair trial of it. What it costs is said in the warning: since the pooled gate (package P11) `gate_of` sets aside the lines whose version and content hash the version file does not name, so the lines of that test carry no weight in a gate, and a second lab model would get no stored gate. The command that fixes it is `python3 evals/eval_status.py bump --skill <name>` (for a skill from outside, `python3 scripts/skill_import.py bump --name <name>`), followed by the test again. A partial test, a platform test and a resumed event print no such warning, and a skill with no version file is left to the validator.

## Testing a local model

A model on your own machine is tested in the same container as any other, to see how far it gets and whether it can run a skill (backlog N14). Skill tests are development work, so a slow CPU model is acceptable. The model is served by a container of its own that the run reaches and nothing else; the weights stay on your disk, mounted read-only into it. No hosted run changes: `evals/tests/test_executor_local_golden.py` proves, against the commit before the package, that a hosted run's docker arguments, call sequence and runner behaviour are the same.

**1. The server image, once.** `python3 evals/executor.py pull-local-server` pulls the llama.cpp server image that `evals/local-model-server.json` pins by digest (`--accelerator cuda` for the CUDA one) and checks that docker lists that digest. A test never pulls.

**2. The weights, in a folder of your choice outside the checkout.** One GGUF file (a model split into parts is refused). Download it from the model's own publisher and keep its checksum.

**3. The configuration, outside the repository.** `$XDG_CONFIG_HOME/openhora/local-models.json`, else `~/.config/openhora/local-models.json` (`WB_LOCAL_MODELS_FILE` names another file):

```json
{"models": {"example-coder": {"weights": "/home/you/models/example-coder-q4_k_m.gguf", "context": 32768, "memory_gb": 24,
                              "accelerator": "cpu", "cpus": 8, "parallel": 1, "timeout_seconds": 1800, "load_timeout_seconds": 900}}}
```

`weights` (an absolute path to a regular file ending in `.gguf`, not a link and not inside the checkout), `context` and `memory_gb` are required, because they are about your machine and are never guessed. `memory_gb` is the memory the server may use: the size of the file, plus the cache of the context (it grows with `context`), plus up to 8 GiB the server keeps for prompt caching, plus room. The context may not exceed the context the model was trained on. `accelerator` is `cpu` (the default) or `cuda`; `cpus` defaults to the docker host's count; `parallel` is how many runs of one event may be served at once (default 1: `--jobs` is lowered to it, with a note); `timeout_seconds` is the limit of one run (default: the gate file's) and counts as the configured value for the event; `load_timeout_seconds` is how long a server has to load (default 900, at most 1500). An unknown key or a bad value is refused with its reason.

**4. Check it.** `python3 evals/local_models.py check example-coder` hashes the file and prints the id (`local/example-coder@<12 hex of the sha256>`), the file type, the trained context and the size. No server is started.

**5. Run it.** `python3 evals/eval_run.py --skill <name> --model local/example-coder --runs 1 --cases <ids>` (a full test is `--skill <name>` alone). The runner hashes the file once per event and again on `--resume`, runs the model under its full id through the `agents-dir` adapter (any other `--harness` is refused), and tests it alone (a mix with a hosted model is refused). A case with `allow_web` is refused with a message naming the cases: the run's network reaches its model server and nothing else; pick the others with `--cases`. **The grader is still the gate file's hosted grader**, through its own key proxy: a local test makes paid grading calls on the grader's account.

**What an event writes and where.** A local model is never a lab model: its evidence stays on your machine, in the local evidence folder (`WB_LOCAL_EVIDENCE_DIR`, else `~/.local/share/openhora/evidence/<skill>/`), shown by `eval_status.py status` as local, and the runtime never runs it (`auto` ranks only models with a price; naming one is refused with "a local model is for lab tests only; the runtime does not run one"). The event line carries `local_model`: the sha256 of the weights, their file type, the context the server ran with, the accelerator, the server image's manifest digest and version line, and the hash of the server's arguments; no free text. The weights' (device, inode, size, modification time) is checked before every server starts and at the end of the event: a change fails the run as infrastructure and makes the event a trial.

**Local evidence pools by model id.** The id `local/<name>@<12 hex of the weights' hash>` is the model: lines made with another context, another `cpus`, another accelerator or another server build all count under it, as one model's lines. That is why the event line records, besides the weights' hash, the context, the accelerator, the server image's manifest digest and version line, and `server_args_sha256` (a hash of the server's arguments, which carry the context, memory, CPUs, threads and load limit): a reader can tell which events ran with which server, and `--resume` refuses to go on with a different weights file, server image or arguments than the event began with.

**Usage is the model's own report.** There is no key proxy and no meter: a run's `usage` comes from the token counts OpenCode reports from the server's replies. Nothing is billed, so a forged count moves no money; the bound on a run is its timeout and the context limit.

**One load per run.** Each run gets a server of its own (a shared one would let a baseline run read or be sped up by the prompt cache of a run that held the skill), so a model is loaded for every run. The weights are memory-mapped, so a second load reads the operating system's page cache. How long a load takes is not promised here: read it from the event's report: each run prints `MODEL SERVER <alias> ready after <n> s` when its server is ready, and `benchmark.json` has each run's `duration_ms`. On a 1.2 MB test model a server on an arm64 Mac was healthy 2.2 s after it started the first time and 2.2 s the second (and 5.3 s and 5.3 s in a later run, under load); no larger model was measured. The sha256 of a 2 GiB file was hashed at about 2.2 GiB/s on that machine (the file had just been written, so it came from memory; a cold disk is slower).

**Speed and hardware.** On macOS, Docker Desktop runs the model on the CPU inside its virtual machine, whose memory setting must hold `memory_gb`; the Apple GPU is not reachable from a container (Docker's own model runner is, but through a host route this design forbids; it is a later decision). On Linux with an NVIDIA GPU and its container toolkit, set `"accelerator": "cuda"`. The first results on a person's machine, before the container existed (2026-10-01, one skill, with the skill): gpt-oss 20B 0.26, Qwen3-Coder 30B 0.43, Devstral Small 2 24B unusable through the runner.

## The interpreter's evidence

The natural-language interpreter is measured apart from the skills. Its lines are `evals/interpreter/evidence/ix-<test id>.jsonl` (the forms are in `evidence_lines.py`; `python3 evals/eval_status.py evidence` validates them with the other evidence), and its standing is `python3 evals/eval_status.py interpreter [--json] [--go]` or `python3 evals/interpreter_status.py`. The rules are section 5 of the reliability model, "Interpreter bands"; in short:

- **Written by the harness only, never edited.** A test event writes one file; a committed file that differs from the one at the base of a change is refused. A new file is read strictly (the configured runs of `evals/interpreter/thresholds.json`, a model and a route that are a row of `runtime/interpreter_routes.json`).
- **No free text.** An event line, an item line and an aggregate line have closed keys, and every value is a closed word, a pattern, a hash, an id, a number or a bool. The held-out test split appears by item id and hash, never by content.
- **Bands per model, route and language** (`needs a run`, `below the gate`, `reliable`), by the Wilson upper bound at z = 1.96 and the numbers of `thresholds.json`; the worst category of an item's runs counts. A change of the route, protocol, prompt, taxonomy, thresholds, served catalog (`evals/interpreter/epochs.json`) or test split leaves no current evidence.
- **A Claude model is measured on the maintainer's account, never over a metered key.** An event has `billing` `metered` (a key of an HTTP route, a cost on every call), `subscription` (an account route: nothing is paid per call) or `none` (the current pipeline). The validator refuses an event whose billing is `metered` and whose model contains `claude` or `anthropic`, and an item line with a cost under any event that is not `metered`.
- **An account route is judged on accuracy only** (decision D3'-a). Its band has the conditions of any route but the p95 latency, and a sequential event is not required of it; the p95 (when one ran) and the list-price equivalent of a call (from the lines' usage and `runtime/prices.json`, with its source and date) are printed beside the band, labelled "not a condition on an account route" and "proxy, not paid, not a go input", with the settings it measured with. An account route is for tests only: it is never priced and never the daily route.
- **Local counts** (split `local`, aggregates only) can demote a band and never promote one.
- **`--go`** prints the go computation (exit 0 when go): the languages where the reference route is reliable, and the cheapest HTTP route that is reliable in at least one of them, is within the cost bound there, holds a sequential sample of at least 100 calls within the latency bound and beats a complete run of the current pipeline. The languages that route does not serve are `off_languages`: tier 1, clarify-by-code and route, with the interpreter off. The runs must cover the whole held-out split (`evals/interpreter/test-split.json` states its items and its count per language), and an item line states the outcome word of its gold.
- **It moves no skill's band.** The skills' evidence, gate, versions and fingerprint are untouched: the files above are not in the measurement fingerprint.

## What checks these rules

The preflight (`eval_run.py --skill <name> --check-cases`, which the validator runs for every skill) checks that each `files` and `grader_files` entry exists, that each `skills` entry is a skill, that each `platforms` entry has its reference, that every path a prompt cites is in the case folder, is an output or is listed in `absent_on_purpose`, and that every assertion is a text or an object with its text and at least one tag of the closed list, a `guard:<effect>` naming an effect of the skill's `side_effects`, with a case `tags` key, when there is one, that lists exactly the tags of its assertions. The validator reports a declared effect with no `guard:<effect>` assertion (a warning until the sweep that closes phase C, an error from it), and, as warnings that stay warnings, a skill with the external-content line or a stop or a gate and no guard assertion, and a guard assertion that passes in every run of the baseline in force. `evals/tests/test_case_rules.py` checks the form of every assertion and its tags. The checks of the three uses of `skills` and of a folder a prompt names are warnings of the preflight until the rows of phase C fix the cases that break them.
