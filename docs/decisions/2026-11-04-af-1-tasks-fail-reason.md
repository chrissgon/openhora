## 2026-11-04: a Google Tasks refusal says its cause, and every refused read or approval leaves one closed line (AF-1 TASKS-FAIL of SPEC-ACEITE-FIX-CODE; no model call, no provider call, no lab run, fingerprint unchanged)

**The decision.** In the acceptance run of 2026-11-04 a Google Tasks write and read both failed and the phone said only that the write "was not done" and that the list was "unavailable". Google's error body names the cause: `error.details[].reason` is `SERVICE_DISABLED` for an API that is off in the OAuth client's project and `ACCESS_TOKEN_SCOPE_INSUFFICIENT` for a scope, and the older `error.errors[0].reason` is `accessNotConfigured` / `insufficientPermissions`. Both Google tasks providers now read those reasons on a 403: `api_disabled: ...` (exit 1) and `scope_missing: ...` (exit 3, the authorize command named); any other 403 is unchanged. The runtime keeps the word: the reader's `ReaderError("api_disabled")`, the effect's `provider` error that starts `api_disabled:`, the phone sentences `TODO_API_OFF`, `TODO_NOT_CONNECTED` (code `not_configured`) and `FAIL_TASKS_API_OFF`, and the sentence `FAIL_EVENT_GONE` for the closed code `event_gone` of a preparation (it was in the plain `FAIL_NOT_DONE` path before; it is in this package only because the package owns the file). `messaging_failure.from_error` checks `api_disabled:` before every other rule, so a text of code 3 that holds it still says the API is off.

**What is logged.** One stderr line per failed read, `tasks: read of <account> failed (<code>)`, and one per refused approval, `effect: decision <id> not written (<word>, <kind>[, <closed prefix>])`. The prefix is one of a closed list (`api_disabled`, `scope_missing`, `changed`, `ambiguous`, `not_configured`); no title, no list name, no address and no provider sentence is printed. A write whose outcome is unknown prints no such line: it may have landed.

**What did not change.** No approval check, no card hash, no effect document: the same decision stays open after a refusal and approving it again with the same hash tries again (OPEN-3 of the spec, kept as recommended, so approval 32 of the run stays `pending-execution`). The cause of rows 25 and 26 is likely, not verified, the Tasks API being off in the Cloud project of the OAuth client (OPEN-1: the maintainer runs `providers/tasks/google.py --check` himself); this package is built either way, so the next person is told. The reason strings are Google's documented ones and have not been checked against a live 403 (the providers' READMEs list it under "To verify").

**Golden.** The entry replay (`runtime/tests/test_entry_replay.py`) keeps its rows: no prestate fails a tasks read with a code. The phrase snapshot (`runtime/tests/snapshots/phrases.*.txt`) is regenerated by the keeper, not by this package; four keys are added in `runtime/phrases_parts/aceite-fix-1.{en,pt-BR}.json`.

**Not done here.** `Bridge.failed` takes the account from `payload["account"]`, while a step effect keeps it in `payload["effect"]["account"]`, so a tasks or calendar failure still says "Sua conta" in general words; left for after both aceite-fix specs land.
