## 2026-11-28: Files by e-mail (AT2; #893)

The e-mail messenger provider (`providers/messenger/email-imap.py`) now emits `attachments` and declares them, with the same shape as the other channels' and no change to the bridge, the operations, the store or the phrase table (ATT-1, ATT-1b and ATT-3 already take a file by reference from a provider that declares `attachments`; limits L47 and L48 hold unchanged). A PDF in a message from a listed, DMARC-passing sender is held and carded like one from a phone, with typed `Send /add <n>` and `Send /discard <n>` lines, since an e-mail has no buttons.

**Decided on the spec's recommendation, open to the maintainer.** Three questions were put to the maintainer and not yet answered; the package proceeds on the recommended answer of each, and a different answer is a later package.

- **D1, the size of a file.** One mebibyte in all, the channel's own limit (L45), declared as `max_attachment_bytes` 1048576, so the bridge's cap for e-mail is 1 MiB. Rejected for now: raising the read bound to the host's 25 MiB, because the whole message is read before the bridge's policy is known, so a larger bound would let any sender whose domain passes DMARC make the provider read 25 MiB before the policy says no; the right way to a larger file is `BODYSTRUCTURE` and a fetch of one part by section after the policy, a new parser of server output and a new fetch form, which is its own package.
- **D2, a message over 1 MiB.** Kept as today: dropped as `size` with a log line and no answer, so the channel creates no backscatter and the existing guarantee that its body is never fetched holds. Rejected for now: reading its header and answering `ATT_TOO_LARGE` to a listed sender, which needs a reply path from the provider that the channel does not have.
- **D3, a forward by subject with a file.** No file: the FWD rule that the body of a forward by subject is never read holds, so no part is listed and no child is started. An attached message (`message/rfc822`) is not descended into either: its files are not the sender's, and the update is marked forwarded. Rejected for now: listing the files of a forward with `forwarded: true`, which would always open a card for what the sender did not write.

**What is built.**

- A file is a part of the message that is not multipart, is not under an attached message, is not the part taken as the text, and has the disposition `attachment`, or a name and no `Content-ID` (an inline PDF with a name is one; a signature logo referenced by `cid:` is not). At most 10 files, from at most 200 parts visited by a recursion over `iter_parts()` (never `walk()`, which descends into an attached message). The work is done in the budgeted child that already makes the text, whose one answer is now a JSON line.
- The ref is `<uidvalidity>:<uid>:<file number>`: an IMAP uid under one UIDVALIDITY names one immutable message, so the same ref names the same bytes, and the same function numbers the files in the update and in the fetch.
- The listen request `fetch` reads the message again on a connection of its own (never the mailbox thread's), admits it again with every check of the update and requires the ref to be among its files, so a message that no longer passes gives no file; the file is read in the child and written only as `<out>/content` (new, `O_EXCL` and `O_NOFOLLOW`, mode 0600, removed when the write does not finish), and a file over `max_bytes` writes nothing. The ref is checked against a closed full-match pattern before any connection. No IMAP command is new. The fetch runs on a thread of its own, so a send is answered while a fetch waits. The answer kind `gone` (the mailbox no longer holds the message) is new for this provider and is one the bridge already knows.
- `/add` and `/discard` join the commands that are the first line alone, so a phone's signature after them is not read as part of them. On e-mail they are not bound to a reply to the card, as on a phone: an attachment card is not a decision, the act makes a held file a source and never an effect, and the card's hash binds it; limit L45's reply binding covers approve, reject, release and answer only.

**Alternatives rejected.** Fetching a single MIME part with `BODYSTRUCTURE` and `BODY.PEEK[<section>]` now (see D1). Trusting the ref in the fetch without reading the message again: a ref is only a name, and the policy of a message that changed since the update (a flipped authentication result, a replaced message under a recycled uid) must be asked again at the moment bytes are taken. Reading every part of an attached message to list its files: they are not the sender's words and the walk into one is what the hostile-MIME bound avoids.

**Not verified.** The live check against a real mail host is the maintainer's, as for the other channels: a PDF and a Word document from a listed address, `/add`, a photo offered for saving only, and a 2 MB PDF that gets no answer. Known gap, not changed here: `contracts/runtime.md` cites a limit L66 (the FA-1 paragraph and L49) that has no entry of its own; the guards that apply to a held file are L47 and L48.
