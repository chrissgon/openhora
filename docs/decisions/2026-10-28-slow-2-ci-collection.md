## 2026-10-28: CI collects without assertion rewriting and steals work; the oracle parses once; no tree scan at import (SLOW-2; the maintainer's go, 2026-10-28, OPEN-SL-1 accepted)

The shards of `checks.yml` spent 60 to 85 s between "Installed" and the first progress line collecting 22,552 items in every worker, 72 % of it in pytest's assertion rewriting; `scripts/tests/test_select_tests_oracle.py` parsed the whole tree five times and was one shard's tail (120 s); `scripts/tests/test_layer_map.py` scanned the tree at import in every worker. Measured on the base (`SPEC-SLOW-TESTS`, run 40631516525): shards 12.8 / 12.1 / 9.7 min, python39 11.6 / 8.9 / 11.9 min.

- **CI flags.** The three run steps of `checks.yml` (the whole suite and the selection of `tests-shard`, and `python39`) and the two of `nightly.yml` run pytest with `--assert=plain --dist worksteal`. The hook and a run by hand keep assertion rewriting and the default schedule. Nothing reads assertion-introspection text (no `pytester`, no `match=` on an assert message), and an `assert` raises in both modes. The nightly keeps its `--reruns 3 -rfER`.
- **The failure re-run.** Each of the three jobs has a step `The failures again, with assertion detail` that runs `pytest -q --lf --lfnf=none` on the same targets, in the default mode, with no launcher and no workers (the cache of that runner holds only that shard's failures; `--lfnf=none` runs nothing when no test is recorded as failed, so a crash or a collection error reruns nothing). Its condition is `failure() && steps.<id>.outcome == 'failure'` (the run steps have the ids `whole`, `selected` and `py39`), so it runs only after its own run step failed. It is `continue-on-error: true` with `timeout-minutes: 10`. It cannot turn a job green: a job whose earlier step failed ends red whatever a later step does, `continue-on-error` keeps the re-run's own failure from adding anything, no run step is `continue-on-error`, and `tests` still reads `needs.tests-shard.result`. `scripts/tests/test_checks_wiring.py` holds those conditions in a function with planted workflows (`always()`, an `||`, no `continue-on-error`, a run step that continues, a re-run through the launcher or without `--lfnf=none`, the wrong step id, a missing step), each caught.
- **The oracle.** `real_import_oracle` is split into `importers_of(root)`, the parse (unchanged), cached per process by `str(root)`, and the walk. The five changed files of the test share one reading of the real tree; a fictional tree has its own entry. The same selected sets as before: 40 cases (10 start files, depths 1 to 4, the real tree, the old and the new function side by side) gave 40 identical sets; the old function took 171 s for them, the new one 4 s. New cases: a fictional tree whose depth bound is exact, a graph per root, the cache serving a parser made to raise, and a vacuity case that shows the same patched parser fails when the cache is cleared.
- **`test_layer_map.py`.** `EDGES = edge_set()` at import is `real_edges()`, a `functools.lru_cache` function called by the tests. A test loads the file's own text as a fresh module with the tree walk made to raise; a planted `EDGES = edge_set()` at import is caught (a vacuity case), and with the old line in place the test fails with "the tree was scanned while the module was imported".
- **Measured here (cold, Python 3.12, one process, all 22,577 items, shard 1 of 3).** Collection 27.5 s without `--assert=plain`, 7.1 s with it. CI per-shard walls are in the pull request, from its own run.
- **Not done.** The durations-aware or by-file split of the shards (SPEC-SLOW-TESTS 4.5): rejected, the slowest shard was 11 % above the mean. The observed corpus replay is SLOW-1.
- **Principle 13.** Saved: about 20 s of collection per process, on every worker of the six test shards of a run (spec estimate 40 to 55 s per shard on the 4-vCPU runner), the oracle's 120 s tail, about 3 s of tree scan per worker, and the queueing of consecutive long items behind one worker. Safety given up: a CI failure's first report shows the assert's own message without pytest's introspection; the failure re-run prints the detail for the failed tests in the same job, and a person running a failing test by hand has it at once. Hard limits are unaffected (principle 11): no production code and no measurement-fingerprint file changed.
