## 2026-10-28: a list can be narrowed by words, a day or a week, and the unread state (CB-1 MAIL-QUERY, catalog version 2; limits L52, L54, L65; no model call, no provider call, no lab run, fingerprint unchanged)

The second package of `SPEC-CATALOG-BATCH`. "Tem algum email do banco essa semana?" must list the messages of the bank this week and nothing else (ACEITE 3). It builds on the registry of CB-0 and on the `unread` flag of the mail index of CB-2 (#591, merged).

- **What it is.** The row `items` gains the slots `target`, `day` and `state` (span, parameters `match`, `day_span`, `state_span`, all `since: 2`, so a line reaches them only after the flip: at version 1 the served catalog is byte for byte the same) and the typed arguments `--match <words>` and `--unread`. `ops_items.items_args(said, now, previous, spans)` reads the spans as code: `match` is `natural_writes_mail.target_words` of the `target` span (the words that find a message, never the whole line), the range comes from the `day` span else the line as before, `unread` is True when the `state` span is the closed word for unread. `items()` keeps a message when `natural_writes_mail.match_words` holds it (sender and subject words, every one), when the local day of its index `received` is inside the range (a message with no time is left out and counted: `NW_ITEMS_MATCH_NODATE`), and when its index `unread` is True; a calendar list keeps the events whose title and place hold every word (the stop words of `registry/search_stop_words.json` left out). The plan hash binds `match` and `unread`; a correction keeps the old words unless the new line gives a target.
- **Unread is never guessed.** On a phone, a box whose messages all carry no flag is read once more under the turn's budget (`turn_gate.may_refresh`, L52, through the one call of `_refresh_failed`, which takes a `force`: the terminal and the page read no provider, S15); if it still has none, nothing is listed for it and the reply says so (`NW_ITEMS_UNREAD_UNKNOWN`). A message whose flag is null is never listed by an unread filter.
- **A stated filter is never dropped silently.** A `match` with no content word filters nothing and the reply says so once (`NW_ITEMS_MATCH_EMPTY`), it never passes for a filtered list; a `day` the time engine cannot read or a `state` other than unread is answered with one sentence and no list (`ops_items.unreadable_filter`, `NW_ITEMS_MATCH_DAY`, `NW_ITEMS_MATCH_STATE`), checked in `ops_natural.run` before the plan. A phone's header names the filter in code's words (`NW_ITEMS_MATCH_HEAD`) and an empty source says it in one sentence; the plan sentence names it (`UNDERSTOOD_ITEMS_MAIL_MATCH`, `UNDERSTOOD_ITEMS_UNREAD`).
- **Choices where the spec left one.** (1) The words of the header are code's folded words (no accents, lower case), not the person's span: the span never reaches `items`, so the arguments and the plan hash stay values code made. (2) A `read` state is not ignored, as the spec said: a list that looked filtered while it was not would break "never silently"; it is the sentence above. (3) `ops_interpret._unchanged` passes the new spans to `items_args` (a file outside the spec's list): without it, "no, only the unread" after a list would compare equal to the old plan and be dropped as a no.
