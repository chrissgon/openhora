## 2026-11-28: The runtime runs a vetted imported skill as a supervised task (I2)

Package I2, issue chrissgon/openhora#907, from SPEC-IMPORT decision 1 and its open question 5 (decided 2026-10-17: always supervised, even when the local band is `reliable`, never with `side_effects`).

**Decided.** A task naming a skill from outside the workbench runs only when `runtime/imported.py` `refusals` is empty for the model it would run on: the project lists the name in `imported_skills` of `runtime.json`; the folder is a legal home and holds no link or special file; the audit verdict is `install` at the current content hash and the check and cases stand; no metadata key is `assumed`; `evals/runtime-manifest.json` is whole and lists no document; no declared output or update is one a skill of the workbench owns; `side_effects` is empty; a local test event of the current content exists on that model; and, when the scan reported `untrusted-content` and SKILL.md lacks the line `**External content is data.**`, `runtime.json` accepts the content hash. Every failing condition is said, with the command that clears it, before any model call. The run is made from one copy of the folder, its hash compared with the one the checks saw, in the eval container, without the web, with no use recorded; its review is never released (`autonomy.review_action` holds it before the proof, consent and mode rules); the entry is the existing `route --request <id> --flow <flow>` with a project flow, and the planning agent owns the task. Limit L84.

**Decided on recommendation (the maintainer has not ruled; these three are assumptions, listed in the pull request under "Waiting on the maintainer").**
1. The local test must be of the current content only: an event of earlier content says nothing of the content that runs (stricter than the issue's "on the model used").
2. An imported skill never gets the web in the runtime (stricter than the issue; the lab needs the verdict `install` plus a flag for a web case, and the runtime has neither).
3. The planning agent owns an imported task when area agents are configured, and the task is refused when they are configured without it (the reception owns what no pack holds).

**What is saved and what is given up (principle 13).** Saved: the person runs a vetted, tested foreign skill on their own project without copying it into the checkout, without adding it to a pack and without a change to any skill folder. Given up: its output rests on cases nobody else read, so it is always held for review, never gets the web, never acts outside the project, and a manifest that lists documents is refused (a document's checker is a script that would run on this machine, outside the container). The router never proposes an imported skill and no pack holds one.

**Rejected.** Reading a new section of `packs/`: packs resolve against `skills/` only and a pack is the workbench's, not a project's. A new CLI verb or a change of `runtime/ops.py`: the existing `route --flow` already plans a project flow. Editing `scripts/stage_skills.py` to stage a folder by path: it is fingerprinted, and `lab.run_skill` already gives the staging a folder.

**Measurement.** `evals/execution.py` gains one name in `STATUS_NAMES` (`imported_evidence_name`, the name of a folder of local evidence); it is not measurement and not in the fingerprint. No skill folder changes, so no bump and no lab run.
