## 2026-11-01: A store connection is closed after its last reference goes, and a stop signal is not lost in the drop of a connection made on the main thread (CONN-LEAK)

**What the earlier decision left open.** `docs/decisions/2026-11-01-fd-limit.md` (FD-LIMIT) moved the egress proxy's first-line read off `select.select` and said the leak behind the descriptors "is a separate package and the maintainer's call". The maintainer decided to build it.

**The defect, one level lower than FD-LIMIT said.** `runtime/ops_core.py` `context()` opens two connections, not one: `store.init_db` (through `providers/store/sqlite.py` `_init`, which never closes its own) and then `store.open_db`. Nothing in `providers/store/sqlite.py` closed anything, and no connection `context()` opens was closed anywhere; the only two closes in the runtime (`runtime/ops_reads.py` `version`, `runtime/run_stop.py` `loop`) each close their own local connection. `sqlite3.connect` is called in one place in production code (`connect`). From Python 3.11 a `sqlite3.Connection` refers to itself through its statement cache, so one dropped without `close()` stays open, with its file and its `-wal` descriptor, until the cyclic collector reaches it; on 3.9 and 3.10 reference counting closes it at once. Measured at the base (`e1`: 100 `init_db` + `open_db` + a read with the collector off): 399 descriptors left on 3.12.14, 0 on 3.9.6.

**Decision.** `connect` returns a small `Connection` object that owns the real `sqlite3` connection. The object is outside the cycle, so reference counting sees its last drop on every version; what happens at the drop depends on the thread. 0 callers change; the approval and execution path (`_approve_effect`, `_execute_effect`, `execute_under_policy`, `approve`, the gate, limits L15, L16 and L55) is untouched: each holds its `ctx` in a frame for the whole call, so the connection cannot be dropped during it, and every write there commits inside `store.write` before any drop.

- **A connection made on the main thread has no `__del__` and no Python runs in its drop.** A close releases the lock of the interpreter, and a stop signal's handler that runs then raises inside whatever frame is running, which in a destructor can only be printed and dropped, so the stop is lost (`runtime/messaging.py`, `runtime/mcp.py`, `runtime/ops_steps.py` and the default SIGINT raise from their handlers). The first build of this design closed in `__del__` and lost 83 of 1,492 stops on `ops.pending` and 9 of 251 on `Bridge.tick` in the reviewer's probe, where the base loses none; a second build that only moved the close out of `__del__` (the destructor appended the real connection to a list) still lost 2 of 1,496 and 1 of 3,000, because a handler can run at any bytecode check inside the destructor's own frame. The final shape: a weak reference (`_Dropped`, a `weakref.ref` carrying the real connection) whose callback is `list.append`, a call in C, so the drop runs no Python. The next `connect` of the main thread (or `close_dropped()` by name) takes each entry out of the list and out of the table that keeps the references alive (a reference that dies before its referent never calls back) BEFORE it closes it, in an ordinary frame, where a handler's exception is a normal raise out of `connect`; nothing is retried and the next call carries on with the rest. The order is: read the last entry, take it out of the table of references, take it out of the list (`remove` of the entry that was read, not `pop()`, which would take a newer entry that another thread's callback appended in between), then close, so that a stop at any line leaves the entry for the next drain or leaves only a local, and the connection goes to the collector, never pinned by the table. Only `sqlite3.Error` is swallowed there (a connection another thread made refuses its close and is left to the collector).
- **A connection made on any other thread (`_ThreadConnection`) closes in its own `__del__`**, and swallows a refusal: those threads run no signal handler, and a request thread ends with no later `connect` to close for it. A main-thread connection dropped on another thread lands in the same list and the main thread closes it; a thread connection dropped on the main thread is refused, in silence, and left to the collector. `_ThreadConnection.__del__` runs on whichever thread drops it, so a thread connection handed to the main thread and dropped there runs Python in the drop and can lose a stop (9 of 181 in a tight probe on 3.9); no production path hands one over (an AST and grep pass found none), and the claim of this decision is exactly: never in the drop of a connection made on the main thread.
- Four pieces make a drop safe: a real `execute` (a method reached only through `__getattr__` on a temporary would close first), a cursor class that holds its `Connection` (built from the class `sqlite3` hands out, not named, because the validator's `harness-name` check reads `\bCursor\b` as an editor's name), `__enter__` and `__exit__` (an implicit lookup does not go through `__getattr__`), and a guard in `__getattr__` for an unset slot.

**What the cost is, on the main thread.** The last connections stay open until the next `connect` of that thread: at most what was dropped since the last one, 2 for an operation's `context()`; a main thread that connects no more leaves them open until the process ends, as a collector with nothing to do would. A connection dropped with a transaction open would hold it, and the write lock of the file, until then, for every writer in any process (they wait 10 s and fail; the bridge's `end_runs` waits up to 120 s). `store.write` used to run `BEGIN IMMEDIATE` before its `try`, so a stop that landed right after `BEGIN` returned left the transaction open (at the base too: 7 of 2,351 and 1 of 665 stops on 3.12 left the lock held in the review's probe, 0 on 3.9). The `try` now opens before `BEGIN` and the exit rolls back only when `conn.in_transaction`: a `BEGIN` that fails (`database is locked`) opened nothing, so nothing is rolled back and its own error is raised; commit, rollback on `BaseException` and what is re-raised are as before. What remains: a second stop that lands during that `ROLLBACK`, or between the end of the body and `COMMIT`, leaves the lock held until the next `connect` of the main thread (the only other `BEGIN` is `cmd_export`, a CLI process). Measured after the change: the lock held after a stop, 0 of 2,880 and 0 of 680 on 3.12, 0 of 2,936 and 0 of 682 on 3.9. In the service the main thread serves requests on other threads and runs the loops on threads, so its own connects are few; the connections that matter there are thread connections, closed at the drop. A harness that makes one connection on its main thread and then only watches the file sees that connection stay open (the first `e3b` run did: no WAL was ever removed, until the parent called `close_dropped()`).

**What a drop keeps alive, and what it does not.** A cursor from `execute` holds its `Connection` (its `held`), so `open_db(db).execute(...).fetchone()` on a temporary works. Nothing else holds it: a cursor from `conn.cursor()` kept after the holder is gone, a saved `conn.commit`, and `executemany`, `executescript`, `iterdump` and `cursor` called on a temporary reach the real connection through `__getattr__`. On a thread they meet `Cannot operate on a closed database`, and they worked at the base; on the main thread they work until the next `connect`. No production line does any of these (an AST scan over `runtime/ providers/ scripts/ evals/`, tests included, finds no attribute access on a call of `context`, `open_db`, `open_ready`, `init_db` or `connect`; `grep` for the methods above finds one unrelated `self.cursor(...)` in `providers/messenger/email-imap.py`), and the tests pin the behaviour. So "the failure mode is the safe one" holds for what the collector did (a connection that is missed behaves as before), and not for these calls, which the design makes fail on threads.

**Alternatives, one line each.** A context manager at the 124 `context()` sites: the largest diff, on the riskiest path, and the next caller can forget. Closing at one boundary with `context()` registering what it opened: a missed boundary leaks silently and every test that calls `ops.<name>` directly keeps leaking. A connection reused per project and thread: `ThreadingHTTPServer` makes a thread per request, `check_same_thread` is on, and a nested `store.write` would raise on one connection where a second waits today. A `ctx` that closes itself when dropped: `ops_core.context(path)["store"].tasks_list(ops_core.context(path)["conn"])` and `conn = ops_core.context(w.path)["conn"]` show that the owner of the close has to be the connection. `gc.collect()` on each tick: treats the symptom and leaves the bridge's line paths and the suite as they are. Closing in `__del__` on every thread: loses stop signals (above).

**The WAL hazard, with its measure.** Closing per operation changes SQLite's WAL life: the last connection of a file to close checkpoints and may remove `-wal` and `-shm` (some builds keep them: Apple's does), and SQLite documents that an open racing that cleanup "might get an SQLITE_BUSY error" (sqlite.org/wal.html, section 9). The store's busy handler waits 10 s. Measured on macOS, 3.12.14, SQLite 3.53.1, a uv-built interpreter (it removes the WAL), `e3b` loops of `init_db`, `open_db`, a read and, every fourth turn, a write, 30 s each, random jitter:

| Variant | Processes | Operations | Refusals | Worst op | Operations that found the WAL gone |
|---|---|---|---|---|---|
| main thread, explicit close, parent drained | 2 / 3 | 19,824 / 30,918 | 0 / 0 | 10 / 15 ms | 11,781 / 11,174 |
| a thread in each process, left to the drop | 2 / 3 | 19,227 / 27,571 | 0 / 0 | 30 / 46 ms | 12,873 / 10,141 |
| main thread, left to the next `connect` | 2 / 3 | 19,456 / 33,069 | 0 / 0 | 28 / 13 ms | 0 / 0 |

The last row is the cost above: the WAL is never removed while each process keeps its last connections open. Cost of a tick: about +0.65 to +0.8 ms per `context()` (medians of 300 calls, 3 alternating runs of each tree, collector on, 3.12.14: `route_queued` 2.00 to 2.69, `dispatch` 3.28 to 4.05, `poll` 2.34 to 3.07, `pending` 2.02 to 2.69), most of it, it looks, the last close removing `-wal` and `-shm` between `_init` and `open_db`. `version`'s `changed_at` (the later of the store file's and the `-wal`'s modification time) can therefore move, and go back, with no write; it is documented as only close to the time, the number decides, and the `-wal` stat no longer races with its removal (`ops_reads.version`). **Linux was not measured.** A refusal on Linux is a stop.

**The bar, with the signal probes.** The probes are throwaway scripts that are not committed (`test_probe_signal.py`, `p_signal.py`, `test_probe_lock.py`, `e3b.py` and the tick-cost script), so a reader cannot rerun them from the repository; the committed proof is the deterministic tests below. A raising `SIGALRM` handler during the real operations on the main thread, 3.12.14 (`test_probe_signal.py`) and a `SIGTERM` to a child looping `init_db` + `open_db` + a read (`p_signal.py`), fired / arrived / lost:

"Reported as ignored in a destructor" is 0 on every final run. The final shape is true by construction, not by a low rate: the drop runs no Python, so the handler runs in the frame of whoever dropped the object.

**What stays with the collector.** A connection whose holder sits in a reference cycle: `runtime/ops_runs.py` `failure = e` (two lines) keeps a frame, and so a `ctx`, when a run cannot start; left as it is (the path of a run's start, normally a short process). A close refused on another thread. Test lines that call `sqlite3.connect(db)` directly (`providers/store/tests/test_sqlite.py` and `test_sqlite_reminders.py`) bypass `connect` and wait for the collector.

**Not decided here.** `context()` opens a connection only for `init_db` and takes the write lock briefly on every operation, reads included (`ops_reads.py` `version` works around it); that changes when a store is created and migrated, which is behaviour, and is a backlog question. No new limit (L) row: the bar is a descriptor count and a signal that must not be lost, engineering invariants held by tests and by a one-door guard, and when they break the result is the collector's old behaviour. No line in `contracts/runtime.md` about the connection; its sentence about `changed_at` is corrected.

**Whole suite.** The local run, on the earlier shape of this change (head `7755b467`, `__del__` closing, before the review rounds), over every folder of `scripts/test_dirs.py` with `-n 4`: 24,639 passed, 0 failed, 410 skipped, 1262 s, a descriptor peak of 389 per worker. The continuous-integration run with the label `full-suite` ran the whole list on Linux at head `f5d5132b` (the weak-reference shape, before the final round) and was green: the status of its checks was read, not its logs.

**The tests.** `runtime/tests/test_store_connections_close.py` counts the connections the real operations open, the ones left open at once (at most `DROP_BOUND` = 2, what the last operation dropped) and after the named drain (0), and the descriptors (bound 3 after the drain), with a `Counted` `sqlite3.Connection` subclass (holds on every interpreter) and `/dev/fd` (bites from 3.11); a path on another thread shows 0 left at once. `providers/store/tests/test_sqlite_connection.py` pins the object, the thread rule, a planted `BaseException` from a close that reaches the next `connect` while a `__del__` that closes loses the same exception to `sys.unraisablehook`, what a drop keeps alive, the modes of the side files a reopen makes, and the one-door guard. Against the base the runtime file fails 13 tests on 3.12 and on 3.9, the same 13; mutants of the final code (a refused close kept forever, a drain that catches `BaseException`, references not kept, no drain in `connect`, a `__del__` on the main-thread class, no held cursor, one class for every thread, the close before the pop, a `pop()` in place of `remove`, the table emptied after the list, a Python function as the callback, `BEGIN` before the `try`, an unconditional `ROLLBACK`, an `__exit__` that swallows) are each caught; the callback test reads `__callback__` of a real connection's reference and wants a builtin method of `_DROPPED`.

**Not verified.** A running service, and several projects in one service; 3.11 and 3.13 on the real paths (3.12.14 and 3.9.6 only); Linux, for the WAL race, for the modes of the side files and for the cost of the close (CI's Linux job runs the test suite on this branch, and nothing there measures the race); a signal other than `SIGALRM` and `SIGTERM` on the real handlers of `messaging.py`, `mcp.py` and `ops_steps.py` (the probes use handlers of the same shape); the explanations of the descriptors SQLite keeps after a close, which are the author's reading of the counts.
