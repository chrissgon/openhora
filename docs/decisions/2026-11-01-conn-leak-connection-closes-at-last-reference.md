## 2026-11-01: A store connection closes when its last reference goes (CONN-LEAK)

**What the earlier decision left open.** `docs/decisions/2026-11-01-fd-limit.md` (FD-LIMIT) moved the egress proxy's first-line read off `select.select` and said the leak behind the descriptors "is a separate package and the maintainer's call". The maintainer decided to build it.

**The defect, one level lower than FD-LIMIT said.** `runtime/ops_core.py` `context()` opens two connections, not one: `store.init_db` (through `providers/store/sqlite.py` `_init`, which never closes its own) and then `store.open_db`. Nothing in `providers/store/sqlite.py` closes anything, and no connection `context()` opens is closed anywhere; the only two closes in the runtime (`runtime/ops_reads.py` `version`, `runtime/run_stop.py` `loop`) each close their own local connection. `sqlite3.connect` is called in one place in production code (`connect`). From Python 3.11 a `sqlite3.Connection` refers to itself through its statement cache, so one dropped without `close()` stays open, with its file and its `-wal` descriptor, until the cyclic collector reaches it; on 3.9 and 3.10 reference counting closes it at once. Measured at the base (`e1`: 100 `init_db` + `open_db` + a read with the collector off): 399 descriptors left on 3.12.14, 0 on 3.9.6.

**Decision.** `connect` returns a small `Connection` object that owns the real `sqlite3` connection and closes it in `__del__`, when the last reference to the object goes. The object is outside the cycle, so reference counting ends it at the last drop on every version. 0 callers change; 0 production lines change under `runtime/`; the approval and execution path (`_approve_effect`, `_execute_effect`, `execute_under_policy`, `approve`, the gate, limits L15, L16 and L55) is untouched: each holds its `ctx` in a frame for the whole call, so the connection cannot close during it, and every write there commits inside `store.write` before any drop. Four pieces make a drop safe: a real `execute` (a method reached only through `__getattr__` on a temporary would close first), a cursor class that holds its `Connection`, `__enter__` and `__exit__` (an implicit lookup does not go through `__getattr__`), and a `__del__` that swallows what another thread's close raises (sqlite3 refuses any use on another thread: that connection goes to the collector, as before). The cursor class is built from the class `sqlite3` hands out, not named, because the validator's `harness-name` check reads `\bCursor\b` as an editor's name.

**Alternatives, one line each.** A context manager at the 124 `context()` sites: the largest diff, on the riskiest path, and the next caller can forget. Closing at one boundary with `context()` registering what it opened: a missed boundary leaks silently and every test that calls `ops.<name>` directly keeps leaking. A connection reused per project and thread: `ThreadingHTTPServer` makes a thread per request, `check_same_thread` is on, and a nested `store.write` would raise on one connection where a second waits today. A `ctx` that closes itself when dropped: `ops_core.context(path)["store"].tasks_list(ops_core.context(path)["conn"])` and `conn = ops_core.context(w.path)["conn"]` show that the owner of the close has to be the connection. `gc.collect()` on each tick: treats the symptom and leaves the bridge's line paths and the suite as they are.

**Why this one.** Its failure mode is the safe one: what it misses behaves exactly as today (the collector closes it). The other designs fail with `Cannot operate on a closed database` on a path nobody enumerated, or leak silently at a boundary someone forgot. It also gives 3.11 and later what 3.9 and 3.10 already do with the same code, so the consequences of closing per operation were already live on the 3.9 job.

**The WAL hazard, with its measure.** Closing per operation changes SQLite's WAL life: the last connection of a file to close checkpoints and removes `-wal` and `-shm`, and SQLite documents that an open racing that cleanup "might get an SQLITE_BUSY error" (sqlite.org/wal.html, section 9). The store's busy handler waits 10 s. Measured on macOS, 3.12.14, SQLite 3.53.1, with a uv-built interpreter (it removes the WAL): `e3b` (explicit close, 30 s, random jitter) 2 processes 19,715 operations and 3 processes 30,750, 0 refusals, worst 21 and 47 ms; the same with the connections left to `__del__` (no close call) 19,086 and 27,408 operations, 0 refusals, worst 16 and 29 ms; 11,687, 10,917, 12,569 and 10,044 of those operations found the WAL gone. Cost: about +0.7 ms per `context()` (medians of 300 calls, 3 alternating runs of each tree, collector on, 3.12.14: `route_queued` 2.01 to 2.66, `dispatch` 3.31 to 4.05, `poll` 2.36 to 3.05, `pending` 2.04 to 2.70), most of it, it looks, the last close removing `-wal` and `-shm` between `_init` and `open_db`. **Linux was not measured.** A refusal on Linux is a stop.

**What stays with the collector.** A connection whose holder sits in a reference cycle: `runtime/ops_runs.py` `failure = e` (two lines) keeps a frame, and so a `ctx`, when a run cannot start; left as it is (the path of a run's start, normally a short process). A close refused on another thread. Test lines that call `sqlite3.connect(db)` directly (`providers/store/tests/test_sqlite.py` and `test_sqlite_reminders.py`) bypass `connect` and wait for the collector.

**Not decided here.** `context()` opens a connection only for `init_db` and takes the write lock briefly on every operation, reads included (`ops_reads.py` `version` works around it); that changes when a store is created and migrated, which is behaviour, and is a backlog question. No new limit (L) row: the bar is a descriptor count, an engineering invariant held by a test and by a one-door guard, and when it breaks the result is the collector's old behaviour. No line in `contracts/runtime.md`.

**The bar.** `runtime/tests/test_store_connections_close.py` counts the connections the real operations open, the ones left open and the descriptors, with a `Counted` `sqlite3.Connection` subclass (holds on every interpreter) and `/dev/fd` (bites from 3.11); against the base it fails the same 10 tests on 3.12 and on 3.9, and passes the 5 that must pass there. `providers/store/tests/test_sqlite_connection.py` pins the object and the one-door guard (an AST walk finds `sqlite3.connect` called only in `connect`).
