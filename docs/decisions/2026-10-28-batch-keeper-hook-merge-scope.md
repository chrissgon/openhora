## 2026-10-28: on a merge commit the hook's fast set reads the branch's own changes, not every file the base brought in (BATCH-KEEPER hook-merge-scope; no model call, no lab run, fingerprint unchanged)

When a base is merged into a package branch with `git merge`, `.githooks/pre-commit` listed the staged files with `git diff --cached` against HEAD, so every file the base brought in counted as changed. L64H's merge commit ran 4,113 tests in 626 s where its own change needed a few hundred.

- **Change.** `staged()` in the hook compares the index with `MERGE_HEAD`, the incoming side, when `MERGE_HEAD` exists (`git rev-parse -q --verify MERGE_HEAD`, which is also right in a worktree). What differs from the base is the branch's own changes plus the files of a conflict resolution, which is what this commit adds to the base. Without `MERGE_HEAD` the command is the one it was. The 14 guards run either way; `scripts/select_tests.py --direct` is unchanged.
- **Tests** (`scripts/tests/test_hook_merge_scope.py`, a real `git merge` in a temporary repository with fictional names): the base brings 50 tests, the branch changes two and resolves one conflict; the hook lists those three and the fast set is those three and the guards. A vacuity case with the old command lists the 50 again; a case without `MERGE_HEAD` keeps the old list.
- **Principle 13.** Saved: the tests of files the branch never touched, minutes per merge commit. Given up: a merge whose result is wrong in a file that only the base changed, with the branch's other files compiling against it, is not tested by the hook. That is the case CI's selection covers on the pull request (the selection reads the whole branch against its base), and the hook was never the gate (TEST-SPEED).
- **Principle 8.** The names in the tests are invented.
