## 2026-10-30: an open e-mail card changes its recipient when the person types the address (mail-card-recipient; written with stand-ins only: the model calls of the one paid proof were made by the maintainer and are reported below; no lab run, fingerprint unchanged)

### The maintainer's decisions of 2026-10-30

Given in chat in Portuguese and translated here from Portuguese.

1. A line on an open e-mail card that asks to change who receives it opens a new card for his approval, when the person typed the address literally in the line. A name stays refused: something would have to guess the address.
2. His rule, which replaces the closed code form first briefed: "Tudo que for um pedido do humano vamos sempre preferir o modelo responder, para poder funcionar em qualquer situacao. Regras de codigo apenas onde termos total previsibilidade do input." (Portuguese; in English: whatever is a request of the human, the model should answer, so that it works in any situation; rules of code only where the input is fully predictable.) validate: allow english-only -- the maintainer's own words, quoted

### The rule

The model reads whether the line asks to replace the recipient: its answer is `{"recipient": "<address>"}`. Code checks the answer and alone decides what the new card holds. An answer opens a new card only when ALL hold:

1. the card has exactly one recipient;
2. the line, with its quoted texts and its text block removed, tokenizes without a bad `@` (`natural_writes_mail.tokenize`);
3. the distinct addresses of that line, leaving out the card's current recipient, are exactly one, and it equals the model's answer ignoring case.

The address written on the card is the token of the line (`mail_revise.typed_recipient`), never the model's string, never an address of the card, of a mail body, of an attachment or of a forwarded message. The sender, the subject and the body are copied from the old card and checked equal (`ops_card_revise._recipient`, with the origins `line-span` for the recipient and `card-copy` for the rest); the new card is a new document with its own hash and is approved on its own, so the old hash is refused for good. A name, several addresses, an add, a remove, a copy, a second change in the same line, an address that is not whole, an address only inside quotation marks (double, curved, angle or single; a mark left open leaves the address undecided and it is refused), a card with two recipients: one sentence (`RV_RECIPIENTS`), the old card stays open. The same sentence is said when the line types a whole new address outside quotes that the card does not hold and the model answers only a change of the text (`troca para x@y.example e muda o assunto para Sexta`): a text answer can never apply a new recipient, so nothing is changed instead of applying the subject alone and dropping the request for the recipient in silence. The same address as the current one: `RV_ALREADY`. A reply card, a reply draft, a card with a Cc, a Bcc or a file, an outbox card: `RV_NOT_REVISABLE`, no model, as before.

### Limit L63, old and new

Old: "the recipients and the account of the new card are copied from the old card by code and checked equal, so a revision can never change who receives an e-mail (an instruction that asks for it gets one sentence and no model call)."

New: see `contracts/runtime.md`, limit L63, the paragraph "A waiting card changed by words": the account is copied and checked equal, the recipients too unless the model answers `{"recipient": "<address>"}` and code takes that answer only for the one new address the line types whole outside its quoted texts; any other answer about the recipients, a name included, gets `RV_RECIPIENTS`. **The price the maintainer should know:** such a line is now one model call like any change of a card, so the card's subject and body reach the model provider for it (L63 loses "no model call" on these lines). The same paragraph's "Where code cannot enforce it" now says what code does not protect (below). Limits L60, L61, L55, L42, L16, L62 and L64 need no text change; they were checked one by one in the spec.

### Second review of the reworked change (2026-10-30)

- **The proof's judge of group C looks at the text `accept` leaves**, row by row (`CHECKS`), and the report keeps every group C answer with that text: the closing lost to the line that asks for a name after a closing (a replacement is accepted by `accept`, known, in the backlog) and a valid text that is not the card (`banana`) are misses, so a run can be read again without paying again.
- **`_replaces` matches whole words**: `troca "15" por "16"` answered with `R$ 150` turned into `R$ 160` is refused, as in the base.
- **The gate**: on the card of an e-mail, a line that holds a whole address outside quotation marks reaches the model (`mail_revise.types_address`), whatever its words: the short spoken forms of "to" that the list of phrases did not hold. A list of phrases is the wrong direction under the maintainer's rule that a person's request is read by the model and a rule of code stands only where the input is fully predictable. A line with no address and no word that asks for a change still never reaches the model. The price, stated in L63: a new request in free words that holds an address, typed while a card waits, is now read by the model against the card; it answers with the recipients sentence or "I could not make that change" and the card stays, where before the line went on to its own path. `troca 15h por 16h` stops at the gate by design: the code guard `turn_gate.new_request` reads a time in it, so it is the event family's line, as `muda para as 10h` is.
- **Backlog, not in this PR**: a closing the person asks for without quotation marks (put a thanks line at the end) gives `same`, so `RV_FAILED`; and when the model answers a replacement the closing vanishes while the bot says "with your change".

### What code does not protect

Hard, in code: the recipient of a new card is an address the person typed; a name can never become a recipient; nothing is sent without the approval of the new hash. Measured, not enforced (group D of the proof measures the first): the model may take an address the person typed for another purpose as the new recipient; may answer only the address on "change the recipient to X and change the subject" (the subject change is then lost, and the card shows it); or may reword the text on "change to Ana" (To unchanged, `RV_DONE_MAIL`, the card shows it). Under the maintainer's rule these are the model's reading; the card and its approval are the protection, and OPEN-1 measures how often.

### Open points and their answers

- **OPEN-1, how the new prompt is proved.** No harness measures this prompt (`interpreter_measure.py` reads only the interpreter's). The stand-in tests prove code's side only. Recommended and built: one throwaway paid run on the daily route, `runtime/tests/mail_card_recipient_proof.py`, 37 fictional lines three times each (111 calls; every line is one the product sends to the model, checked by a test).
