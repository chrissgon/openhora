## 2026-11-07: the HyperFrames engine's container image (V3a-image; no measurement change, no skill changed, no lab run)

The image the HyperFrames engine of `renderer:video` draws in, `providers/renderer/hyperframes-image/`, built from the pins the S2 spike measured on 2026-11-07 and from the conditions carried from it that concern an image: determinism and limits are the provider's (package V3a); closed fonts (condition 6) and the supply chain (condition 7) are here. The plan is the short-video plan v3; the review findings cited are F11, F13, G4, G9 and G14.

- **D1. One image per engine, scoped by a manifest (F11).** `manifest.json` lists the files of the definition, and the tag is `openhora-hyperframes:<the first 12 characters of the sha256 of those files>`. A change to the ffmpeg engine, to a block or to any file outside the list never changes this image; a change to a listed file always does. The build context is the same list less what docker reads itself, and a test keeps the manifest, `.dockerignore` and the folder in step. Rejected: hashing the folder by glob, as the ffmpeg engine's definition on `feature/short-video` did (an added engine or block rebuilt the image); one image for both engines (a HyperFrames-only change would rebuild the image that verifies every render).
- **D2. `providers/_container.py` is not changed.** It owns no image: each provider's own module hashes and builds its image (the converter's `DEFINITION_FILES`), so a per-image manifest needs nothing of it, and its `old_definition_images` already keeps images apart by repository. The run limits package V3a needs (`--cpuset-cpus`, `--shm-size`, the disk-backed scratch) stay V3a's, as the plan's file ownership says.
- **D3. The image keeps its own copies of the browser pin, of `_fetch_browser.py` and of the three fonts.** Package V1a brings the ffmpeg engine's copies, and this package does not depend on V1a. A build context that reached into the ffmpeg engine's files would make this image hash files it does not list. A test compares each copy with the ffmpeg engine's when both are in the checkout. The cost: a change to the browser pin or to the fonts is made in two places, and that test fails until both agree.
- **D4. The fonts are in the image, at `/opt/fonts`, checked by sha256.** The last layer purges the font package apt pulls in and fails the build when any other font file is left outside HyperFrames' own `node_modules`. The font files inside `node_modules` are listed (`/opt/hf-build/node-modules-font-files.txt`), not removed: no render without them was measured. The code guard of condition 5 of S2 (`check_fonts`, package V3a) is what keeps a page from using them.
- **D5. The amd64 sha256 of the headless shell is recorded here, from one download.** Chrome for Testing publishes a size and an md5 and no sha256 (G4). The archive of 155.0.8059.39 for linux64 (124,203,329 bytes) was downloaded once with the maintainer's word, its size and md5 matched the published values, and its sha256 is in `pins.json`. Package V1a records the same value in the ffmpeg engine's pin. The amd64 sha256 of the static ffmpeg is the value HyperFrames 0.9.19 pins in its own render image; it was not downloaded, and the first amd64 build checks it.
- **D6. `scripts/doctor.py` is not changed here.** Its image families are `providers/<name>/container.py`, and the renderer will hold two images in one folder. `hf_image.py` exposes `IMAGE_REPOSITORY`, `definition_hash()` and `image_tag()` so that the family is one entry when package V3a adds it.
- **D7. The HyperFrames registry files are not in this image.** They come with package V3b and its allowlist, at the place the Dockerfile marks (`# Hook for V3b`); adding them rebuilds this image only.
- **Principle 1.** HyperFrames is an open-source renderer, not an AI tool, so `providers/` may name it. In this package its maker's name appears once: the copyright line of `NOTICE.md`, which the licence requires.
- **Principle 13.** The saving: the image hashes only its own files, so the ffmpeg engine and the blocks change without rebuilding it. The loss: two copies of three things (D3), held together by a test rather than by one file.
- **Not verified:** the image was built on arm64 only; no amd64 build was run, so the amd64 ffmpeg sha256 and the amd64 Debian and npm packages are unchecked. GSAP's licence text was not read. Whether a render works with the font files of `node_modules` removed was not measured.
