## 2026-10-27: a timed Outlook event is written in the zone the card names (OUTLOOK-TZ, scenario 16, no model call, no provider call, no lab run, fingerprint unchanged)

`SPEC-OUTLOOK-TZ`, lane A (A1). The maintainer decided on 2026-10-21 ("S3 dropped") that the 18:00-for-14:00 event of the live test was the account's display zone and that the instant had been saved right, so nothing here claims to fix what Outlook web shows when its display zone is wrong. What this buys: the event carries its own named zone (its details, other clients and a later edit by hand say "Brasilia", not "UTC"), and RECUR (daily and weekly, decided 2026-10-26) needs it, because Graph expands a recurrence in the zone of the event's `start`, so a weekly 07:00 series written in UTC would move by an hour across a clock change in any zone that has one. OPEN-1 (build now, fold into RECUR, or drop): build now, the supervisor's decision, so that RECUR's card and writer change carry only the recurrence. OPEN-2 (stop if Microsoft's page does not list IANA names): it does, so the package proceeds; no IANA-to-Windows table is hand-written (principle 14).

- **What it is.** `providers/writer/outlook-calendar.py`: `event-create` and `event-patch` take an optional `--time-zone <IANA name>` (a flag, not a spec key: `providers/_writer_calendar.py` and the Google writer are untouched). Without a name that is `Area/Place` or `Area/Region/Place` and that `zoneinfo` loads: exit 2, nothing sent. With it, a timed event's `start` and `end` are the same instants as wall times in the zone, with `"timeZone": "<name>"`; a moment whose wall time is ambiguous in the zone (the repeated hour of a clock change) or does not read back as the same instant is sent in UTC, as before. An all-day event, a run without the flag and every read are unchanged (reads still ask `Prefer: outlook.timezone="UTC"`; Graph converts). `ALLOWED` is unchanged.
- **The runtime.** `calendar_document.outlook_zone_args`, appended by `provider_args`: for an Outlook timed create, or a change that carries times, when `doc["zone"]` is an IANA name of the writer's own form, `--time-zone <doc["zone"]>`; never for Google, a removal, an all-day event or an offset zone (`UTC-03:00`). The name comes only from the document's zone (the host's), never from the person's line or a model. The flag is in the dry run, so `dry_run_sha256` covers it; the document's keys do not change.
- **Source.** Microsoft's own page for the type, https://learn.microsoft.com/en-us/graph/api/resources/datetimetimezone (read 2026-10-27): `timeZone` "can be set to any of the time zones currently supported by Windows, as well as the other time zones supported by the calendar API", with a list of IANA names under "Additional time zones" (`America/Sao_Paulo` is on it), and "create or update might not support all". **The list is shorter than the IANA database** (`Europe/Lisbon`, used in tests, is not on it): a host zone that Graph does not accept makes the create or patch fail at Graph (exit 1, nothing written). The fix, if a person's zone is off the list, is a follow-up that adopts CLDR's `windowsZones.xml` as a pinned data file, not a table written by hand. Not checked against the live service (no call was made): the maintainer's check is scenario 16 on a throw-away event.
- **Cost of the upgrade.** An Outlook card drawn before the upgrade and approved after it fails closed (`effect_calendar.py`: the real dry run no longer hashes to the document's `dry_run_sha256`); the person asks again. No new card, no new approval path, no credential touched. The host's zone name now goes to Microsoft with each timed event (Microsoft already holds the mailbox's own zone).
- **Tests.** `providers/writer/tests/test_writer_outlook_calendar.py` (the zone on create and patch, Lisbon in July and January, the repeated hour, bad names with no request, the dry-run hash with and without the flag, all-day, the flag refused by `event-delete` and `event-get`, read-back by the same instant, and a vacuity case); `fake_graph_calendar_write.py` now converts an event written in an IANA zone to UTC when asked `outlook.timezone="UTC"`, as Graph does; `runtime/tests/test_calendar_write.py` (the flag for a timed create and a change of times, not for Google, a removal, an all-day event or an offset zone).
