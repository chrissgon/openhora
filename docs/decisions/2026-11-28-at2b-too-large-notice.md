## 2026-11-28: Tell the person when an e-mail was too large to read (AT2b)

The maintainer asked whether an e-mail with an attachment over 1 MiB is dropped without telling him, and said: "It must tell me; otherwise I will think the e-mail went through when it did not." This supersedes D2 of `docs/decisions/2026-11-28-at2-files-by-email.md` ("a message over 1 MiB ... dropped as `size` with a log line and no answer"), which is not edited. Raising the limit itself is a separate backlog item, AT4 (chrissgon/openhora#1025), and is not part of this entry.

**What is built.** When the e-mail provider (`providers/messenger/email-imap.py`) finds that a whole message is over `MAX_SIZE` (1 MiB), it keeps the log line `dropped a message: size` and also writes one error event of a new kind, `too-large`, with a fixed reason that names nothing of the message (no size, uid, address or subject). The listen session (`runtime/messaging_provider.py`) counts these events apart from `skipped` (`take_too_large`); a `too-large` event never ends or pauses the session. `Bridge.notify_unread` (`runtime/messaging_bridge.py`) now loops over the two kinds: each has its own count, its own sentence (`TOO_LARGE_ONE`, `TOO_LARGE_MANY`, in English and Brazilian Portuguese, `runtime/phrases_parts/at2b.*.json`) and its own hour per chat, so a chat may get one line of each kind in the same hour. The rules of the skipped kind are unchanged: the hearers are read first, a chat that no longer hears loses what it was owed, a deferred reply is tried at the next tick, a failed one an hour later.

**To whom.** To the listed senders who hear the "N more waiting" count, as for a skipped message. Never addressed to the writer as such: the size is checked before any header is read, so nothing about who sent it is known, and no reply goes to the address that wrote (no backscatter); the writer gets the line only as a listed sender who hears the count (the owner sending a 2 MB PDF is told). Anyone who can send mail to the address can cause the line, because no authentication, sender check or per-sender rate comes before the size check: spam or a newsletter over 1 MiB gives every hearer the line, bounded to one line per hour per chat, and the line carries nothing of the sender. The sentence says the message was too large (over 1 MB with its attachments), that nothing was done with it, and asks the sender to send files of about 700 KB in all at most, because the 1 MiB counts the encoded message and base64 makes a file about a third larger (a test ties the sentence to the declared `max_attachment_bytes`).

**What stays silent.** The other `size` drops of the provider (`HEADER_VALUE_MAX`, `ADDRESS_HEADER_MAX`) come from crafted or abnormal messages, not from a person attaching a big file. A message of unknown size stays `unreadable`, with no event.

**What a restart does.** The provider saves the last uid handled after each message (`cursor.json`), so an oversize message is not handled again at the next poll, after a reconnect of the IMAP connection or after a restart of the process: one event per message. A crash or a failed cursor write between the event and the save can repeat one. The bridge's count of what a chat has not yet been told is in memory, so a restart of the bridge forgets a line held back for the hour (the same as for skipped messages); no persistent state was built for it.

**Not verified.** The live check against a real mail host is the maintainer's: a 2 MB PDF from a listed address should give the too-large line once.
