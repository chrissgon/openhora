## 2026-10-28: the real table is checked in the mode of the run, not always strict (BATCH-KEEPER snapshot-real-table-mode; corrects `2026-10-28-keeper-snapshot-batch-strict.md`; no model call, no lab run, fingerprint unchanged)

**What was wrong.** #643 made `test_the_snapshot_is_the_table` follow `WB_GENERATED_BLOCKS` (strict on a batch, main, a push and the nightly; lenient otherwise), but `test_the_real_table_is_lenient_clean_and_strict_clean_on_this_tree` also checked the real table in strict mode whatever the mode, so a package that added a phrase key still had to regenerate the snapshot files (S41-11 2a had to). That kept the hot spot #643 was meant to remove.

**Change (tests only).** The test is now `test_the_real_table_is_clean_in_the_mode_of_the_run`: `snap.problems(os.environ.get("WB_GENERATED_BLOCKS", "lenient"))` against the real files, so strict only where the variable says so. A separate test, `test_the_real_table_is_lenient_clean_whatever_the_snapshot_says_about_wording`, keeps the lenient check on the real table in every run (a renderable table). Two tests on a planted tree: the strict comparison is clean on a freshly written tree and names a stale one (a reworded sentence and an added key) while lenient passes it; and a vacuity case where a strict check whose comparison is replaced by an empty result passes the same stale tree, so the planted case does exercise the comparison.

**Principle 13.** As in the entry it corrects: a package no longer regenerates the snapshot; the batch does, and its strict run (and the nightly's) checks the files byte for byte.
