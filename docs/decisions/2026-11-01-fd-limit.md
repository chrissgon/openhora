## 2026-11-01: The egress proxy's first line is read with a selector, not select.select (FD-LIMIT)

**What happened.** A local whole-suite run at 09d0ca54 (14 xdist workers, every folder of `scripts/test_dirs.py`) gave 3 failed, 24,606 passed. All three were in `providers/script/tests/test_script_host.py` and failed with `ValueError: filedescriptor out of range in select()` at `providers/script/container.py` (`Egress._first_line`). The file alone passes.

**Cause (measured).** `select.select` refuses any descriptor numbered 1,024 or more (FD_SETSIZE). The worker held more than that open: a throwaway plugin that counted `/dev/fd` after every test showed that, across 14 workers, 8 reached 1,024 or more descriptors at the start of some test, the highest peak was 2,882, and the open descriptors were almost all regular files, SQLite connections to `store/tasks.sqlite` and its `-wal` file. On CPython 3.11 and later a `sqlite3.Connection` holds a reference cycle through its statement cache, so reference counting never closes it: it stays open until the cyclic collector runs. A loop of 300 `store.open_db` calls with no `close()` left 0 descriptors on 3.10, 48 on 3.11.6 and 62 on 3.12.14. The connections are opened by `runtime/ops_core.py:178` (`context()`, through `providers/store/sqlite.py:951`) and are not closed by its callers.

**Why it did not always fail.** The same suite, run again with the logging plugin, gave 24,609 passed, 0 failed, 410 skipped. Whether a container test lands on a worker above 1,023 descriptors depends on how xdist schedules the tests, so the failure depends on scheduling.

**Decision.** `Egress._first_line` waits on the proxy's standard output with `selectors.DefaultSelector` (epoll on Linux, kqueue on macOS), which has no descriptor ceiling, in place of `select.select`. A test with its own literals puts the pipe on descriptor 1,100 (raising the soft limit inside the test and restoring it; it skips only when the limit cannot be raised) and checks that the first line is read whole, joined across two writes, and empty on a closed pipe; a vacuity case shows that `select.select` raises on that same descriptor. Nothing else in the provider changes.

**What this does not do.** It removes the crash in `_first_line`. It does NOT fix the leak: the SQLite connection that `runtime/ops_core.py:178` opens for every operation is still left to the cyclic collector on Python 3.11 and later, and any other `select.select` on a descriptor above 1,023 would fail the same way. Nothing was measured in the service itself, only in the test suite and in a micro-measurement of `open_db`. Whether the leak is worked on is a separate package and the maintainer's call.

**Left as it is.** `providers/script/egress_proxy.py:166` (`tunnel`) also calls `select.select`. It waits on two sockets, not on a child's pipe, and it runs inside the proxy's own container, whose process holds only the sockets of its connections, and it is capped at 16 concurrent connections (`MAX_CONNECTIONS`, line 50), so it cannot reach descriptor 1,024. It is not changed here.
