## 2026-10-28: readers and writers for Google Tasks and Microsoft To Do, and the scope transition (CB-4; no model call, no real provider call, no lab run, fingerprint unchanged)

SPEC-CATALOG-BATCH package CB-4 (the secretary's tasks, decided 2026-10-26: "Sim, as duas"; no due dates in v1, the maintainer's "Sem vencimento na v1", 2026-10-27; OPEN-CB-7, OPEN-CB-12). The runtime half (operations, cards, policies) is CB-5.

- **What exists.** `providers/tasks/google.py` and `microsoft.py` (class `integration:tasks`: `--check`, `lists`, `open --list <default|id> [--max n]`, GET only on two paths each) and `providers/writer/google-tasks.py` and `microsoft-todo.py` (class `writer:tasks`: `--check`, `task-get`, `task-insert`, `task-complete`, GET, POST and PATCH on the list and task paths only: no DELETE, no move, no clear; limit L57), with `providers/_writer_tasks.py` (the spec reader, the id patterns, the lookup after a lost answer; the ledger is the calendar writers' own). Every write verb takes `--account` and compares it with the token record's account.
- **Scopes and the transition rule (OPEN-CB-7).** Google gains `https://www.googleapis.com/auth/tasks`, Microsoft `Tasks.ReadWrite`. `PREVIOUS_SCOPES` (the four, the five) are kept: every provider but the tasks ones accepts EXACTLY the new set or EXACTLY the previous one, the tasks providers need the new one and refuse the previous with exit 3 and the authorize command named, the authorization always asks the new set. For Microsoft a refresh names only the permissions the provider reads (the five) unless the record holds the six, then it names the six; a record's stored scope is judged by the same two sets (`parse_account_record`; `check` of `microsoft_auth.py` prints `tasks` and exits 3 for a record of the five). The six `--check` prints that said `PLATFORM_SCOPES` now say `PREVIOUS_SCOPES` (the set those providers need). CB-4b, a dated one-line follow-up, removes `PREVIOUS_SCOPES` once both accounts carry the new set.
- **Facts the spec assumed that the vendors' pages (read 2026-10-27) do not settle, or that differ.** (1) Google Tasks' service endpoint is `https://tasks.googleapis.com`, not `www.googleapis.com`. (2) No page of the Tasks reference mentions `@default`; Google's Ads Scripts example uses it as the list id in the calls that list, insert and update tasks, so `--list default` sends it and `lists` prints `default: null` for Google (the reference marks no list). (3) No page documents `If-Match` for tasks.patch or Update todoTask, so none is sent; the writers read the task again before the PATCH and compare (the dry run's hash covers the approved etag as `requires`). (4) The Graph pages for listing lists and tasks say "some of the OData query parameters" and name none, so no OData parameter is sent; the open tasks are chosen in the provider. (5) Graph states no title length; Google allows 1,024; both providers use 200. (6) Google lists return at most 100 tasks a page; Microsoft's page size is not stated. None of the facts stops the package: each is listed under "To verify" in `providers/tasks/README.md` and `providers/writer/README.md`.
- **Due dates.** The reader outputs of the spec listed `due`; the maintainer's decision (no due dates in v1) is applied to the readers as well: no due date is asked of either service (the `fields` list of the Google reader names none) or printed.
- **After the independent review (merge, no blocker; five small fixes).** The registry text that `resolver.py --list` shows (and the same cells of `contracts/secrets.md`, which a test holds equal) now says five Google scopes and six Microsoft permissions with `tasks` and `Tasks.ReadWrite`, says plainly that these can change and delete tasks at the service although the writers never delete, and lists the four task scripts as readers; the window between the writers' fresh read and the PATCH is named honestly (one network round trip, about 100 to 500 ms; the worst case is completing a task whose title was edited in it; a task deleted in it answers 404, reported as `changed:`); `task-get` carries `external_content: true`; every id has one cap of 300 characters in the readers and the writers; and a comment and a test pin the PATCH body to the code literal `{"status": "completed"}` (Google documents the removal flag of a task as writable).
