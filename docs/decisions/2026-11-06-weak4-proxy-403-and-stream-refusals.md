## 2026-11-06: A refusal is read in the stream's system and error events, and the key proxy's own 403 is not a refused key (weak4; infrastructure)

**Decision.** In `evals/execution.py`: (a) `provider_refusal` also reads the `system` and `error` event lines of `stream.jsonl` (never the model's text or a tool's output), so a fallback after a policy stop that the last message does not mention (`Cyber safeguards flagged this message.`) is a `refused` attempt, a capped kind; (b) `auth_refusal` skips a 403 whose surrounding text names `the key proxy`: the proxy's 403s are its model and path policy (`evals/container/keyproxy/keyproxy.py`), never the provider refusing the credential. Such a failure falls through to `adapter`, which is retried and capped, so a side call to another model can no longer stop a whole event.

**Why.** An event on `core-security-audit` stopped on a 403 from the key proxy that the runner read as a refused key (kind `auth`, never retried, event stopped). A real credential refusal stays `auth`: it says nothing about the model, so scoring it 0 would put an infrastructure failure into a mean.

**Kind and cost.** Infrastructure (retries and classification). `execution.py` is not in the measurement fingerprint, which is unchanged, so no measurement command is run, no measurement version, epoch or skill bump follows, and no line, baseline or band changes. A run already capped writes the same line (`outcome: timeout`, score 0) whatever the kind; only the `benchmark.json` counts move from `adapter_failures` to `refusals`. This is consistent with the decision of 2026-10-01 that a refused baseline scores zero (a capped refusal is a score of zero), which the fixture of `core-security-audit` case 1 keeps.
