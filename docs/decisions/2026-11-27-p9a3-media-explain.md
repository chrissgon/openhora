## 2026-11-27: The text a scan found in a video's pictures is explained by a model only when the person presses a button (P9-a3; plan video quality v6, R3-12; spec `SPEC-video-P9a-scan-before-approval-2026-11-26.md`, section 5; answers P9-3)

**Status.** Built after the maintainer's answer to P9-3. It completes P9-a (`docs/decisions/2026-11-26-p9a-scan-before-approval.md`, which recorded P9-3 as not asked yet and is not edited). The skill has no lab evidence: its first full test is in the batched lab event, so every run is supervised until then.

**Context.** P9-a1 and P9-a2 read the text and QR codes in the pictures and clips of a media set on this computer and show them as warnings; nothing leaves the computer and limit L82 forbids the text to enter a model's prompt. The plan also has a skill that explains what the text found means (a stock agency's mark, a phone number, a link anyone can open, a sentence in another language). That needs the text to go to the model that runs it and to that model's company, so the question was whether it may, and how.

**The maintainer's answer to P9-3**, verbatim: "Sim, só ao apertar o botão (Recomendado)" (validate: allow english-only -- the maintainer's own words, quoted). Gloss: yes, only when he presses the button, which is option (a) of the question: for one media set at a time, with no consent word, the text read from public pictures only.

**Decision.**
- D1. A new skill, `mkt-video-media-explain` (marketing area, capability, no requirement and no side effect). It reads only the lines it is handed, writes one file (`.workbench-local/video/scan-explained.json` in its own run folder) and decides nothing: a finding is a quote, one of nine concern words (`licence_mark`, `contact`, `link`, `brand`, `claim`, `language`, `sensitive`, `none`, `unclear`) and an explanation of at most 240 characters. Its stop rules: nothing to explain (no file, one line), and asked to act (it says it only explains). It carries the external-content line: an instruction planted in a scanned line is quoted to the person and never followed.
- D2. A new operation, `video-media-scan-explain` (`runtime/ops_media_scan_explain.py`), class G, terminal and page only, refused on the `--lan` socket, messaging and the MCP mode. The page's button "Explain the text found" calls it without `confirm`: nothing is sent, and the page shows the exact text that would go, the model that would receive it and that model's company; a second press ("Send this text and explain it") runs it with `confirm`. There is no consent word and `media.consent` is unchanged.
- D3. What code decides, in order, before anything runs: the video waits at the caption review; the set is fetched; the scan holds text or a QR item to explain; the source of each file has a stock or web licence tier (`library`, `per-item`, `unverified`), and a file whose source has none is left out with its slot named, whatever it holds, so a future upload source of the person's own files never reaches a model; the skill is a folder of this checkout that requires nothing and has no side effect; the routed model.
- D4. The prompt is rendered by code from the slot ids, the text lines and the QR items (a link's host, a scheme word, a QR code's text) alone, each checked again. Never a picture, a frame, the slot's search words, the description of a slot or anything of the recording. The run has no tool, no web and no file of the project (the artifacts the skill declares are emptied for the copy), and is supervised until the skill has lab evidence; the page says so.
- D5. The answer is one file, read without following a link, at most 64 KiB, checked by the skill's script (run isolated, with the lines that were sent as the grounding: every quote must be one of them) and again in code; either failing refuses the file whole. The findings are kept in the stock folder as `scan-explained.json` beside `scan.json`, keyed by each file's sha256, cleaned on read, never served, never a name a step may read, never in the set document or its hash, and the page shows them as "Explained by <model>, not checked:", as text.
- D6. Limit L83 (`contracts/runtime.md`) states this as the one route by which scanned text leaves the computer, and L82 now says so. A run row holds a neutral line; the text and the explanation are in no phrase, task state, decision body, run row, log, messaging card or MCP answer.
- D7. The pack of the content area (`packs/content.txt`) lists the skill, so the content area agent may run it.

**Choices of the builder, each small.** The two presses (preview, then send) are the spec's "without confirm, what would be sent; with it, the run", drawn as two buttons so that what leaves is shown first. The skill's own script takes the grounding lines through an optional `--task-file` that the runtime writes; the skill's own run has no such file, so there it checks the shape and the closed words, and the grounding is checked in code on the host. The run's bounds, 300 seconds and 0.60 dollars, are validity bounds (a run must end), the figures of a web search's defaults. The explanation of a finding is cleaned (printable characters, whitespace collapsed) and a quote is kept exact; a quote that is not one of the lines that were sent refuses the file whole.

**What it saves and what it loses (principle 13).** Saves: the person can ask what a watermark, a phone number or a QR link in a stock picture means before a post goes out, in plain words. Loses: when he presses the button, text read from public stock and web pictures goes to the model and its company, which is why the preview shows it first and the files of a source with no licence tier are left out; and the explanation is a model's reading of a computer's reading, shown as "not checked".

**Verified and not verified.** Verified by offline tests with stand-ins for the run and the engine: that nothing runs without `confirm`; that the prompt holds only the slot ids, lines and QR items and none of the slot's words, a description, a file name or the recording's id, in the form of the skill's first eval case; that no file of the project enters the run; that a file from a source with no licence tier is left out and its text never reaches the prompt; that each refusal of the order leaves nothing run; that every bad answer (an invented quote, a quote of another slot, a concern outside the list, a web address, an over-long or missing field, a missing, extra or unknown slot, a link, a huge or non-JSON file) is refused whole and keeps nothing, with either check refusing alone; that the findings are kept as the spec says and cleaned on read; that no text of a picture is in the store; that the operation is refused on the local network's socket and messaging; and that the page draws the preview, the findings and a planted `<img>` line as text. Not verified: the skill on a real model (the supervisor's quick trials, then the batched lab event), a real run through the real lab, and the page in a browser.
