## 2026-11-08: tier A: the wrapper, the admission run and the allowlist (V3b-3, steps 7.1 to 7.7; no measurement change, no skill changed, no lab run)

**What.** A component of the HyperFrames registry can become an `hf:` tier-A overlay only through code that fails closed. `hyperframes-image/hf_wrap.py`
holds the admission lint (the closed codes of section 7.1 of the spec) and the wrapper (a scope, a guarded `window` and `document`, nested timeline).
`hyperframes-image/hf_compat.py` runs, inside the HyperFrames image with no network, 51 planted escapes (at least one per lint class, plus the runtime
cases of the spec) and a clean control before it gives any component a verdict; one admitted escape fails the run (`planted_escape_admitted`) and no
report is written, and there is no option that skips this. `hyperframes.py compat` mounts a survey folder read-only and copies the report back.
The composer writes a placeholder and a row of `instances.json` for a tier-A beat; `hf_render.py` reads the files from the image's registry folder, checks
each sha256, lints again, wraps, and refuses `tier_a_file_missing`, `tier_a_hash`, `block_lint` and `block_escaped`. `registry.sha256`,
`fetch_registry.py` and the two Dockerfile hook lines bake the registry's LICENSE (and, later, the admitted files) into the image at the pinned commit.

**Why.** Plan V3b row, section 7 of `SPEC-video-V3b`, decisions VD3, VD9, VD12 and D7 of V3a-image (registry files come with V3b). Settled by the
supervisor on the spec's recommendation (not the maintainer's word): OPEN-6 (the `notice` of an `hf:` block is a pointer in our words), OPEN-7 (tier A
admits overlays only; a caption is `caption_tier_b_only`), OPEN-8 (`preset: null` blocks are listed, not drawable in M1), OPEN-14 (the survey is
`registry/components/*` text files at the pin), OPEN-15 (two image builds). The survey was approved by the maintainer ("Sim", STOP B-survey) and run by the
supervisor; it holds 238 components, 855 files, 5,225,571 bytes (83 rows not fetched).

**Measured.** Offline only, by the executor, on the synthetic and fictional inputs of the tests: 51 planted escapes, 51 refused by the lint; the clean
control admitted; each of the 14 escapes that act at run time stopped by the guard when the lint is bypassed (run in `node` against stubs of `window` and
`document`, `tests/test_hf_wrap.py`). Read-only reading of the survey with the new code (executor, no execution of any component): the licence assumed
known, 23 of 238 components pass the static check, the rest are refused (variables_untyped 85, escapes_scope 41, caption_tier_b_only 17,
writes_window 13, bundled_media 12, fonts 12, dynamic_code 10, media 6, timers 5, frames 5, nondeterministic 5, network 4). 358 of the declared variables are of
type `enum`, which the spec maps to nothing (`variables_untyped`); mapping `enum` to a `choice` parameter is the one change that would admit many more
and is the maintainer's to ask for. These counts are not the compatibility run's: the run (and its report) waits for the HyperFrames image, built by the
supervisor. Determinism: the wrapper's output is a function of its inputs (two calls, same bytes; tested). No render was run, so no repeatability figure exists.

**Principle 11.** The admission lint, the planted-escape refusal, the sha256 check of every registry file and the lint again at draw time are code; the
wrapper's guard (strict mode, a frozen `window` Proxy whose writes throw, shadowed network, timers, clock and storage, the instance's own `document`) is
code and its throw also marks the log, so a component that catches the error still fails the render. What code cannot see, such as a visual that hides
text, is the C10 contact sheet: a maintainer's judgement. The lint is text-level and refuses a token in a comment too: a pattern that strips comments is
the way a lint is walked around.

**Not verified.** That `hyperframes render` puts the page's console output in `hf.log` (the second `block_escaped` signal depends on it; the first, the
render failing, does not); that the guard behaves in Chrome headless shell 155 as in `node`; that `chrome-headless-shell --dump-dom` runs the guard page

`registry-item.json` fields beyond `type` and `tags` mean what the report assumes (read from the survey: `type` is `hyperframes:component` for every item); the

two builds).

**Saving and loss.** (1) Only the two files a block needs (`<name>.html`, `registry-item.json`) are pinned and baked, not every file of a component: it
saves bytes in the image and in the review, and loses nothing the wrapper reads (a component that needs another file is refused, since a relative `src`
or `link` is a lint refusal). (2) `enum` variables are refused as the spec says: it loses most of the registry's components for now and keeps the
parameter model of the allowlist (`text`, `color`, `number`) unchanged. (3) `window.__timelines = window.__timelines || {}`, the registry's own idiom, is
allowed beside `window.__timelines[id] = tl` and the guard accepts exactly that write of the same object: it admits the idiom every component uses and
nothing else written to `window`. (4) A component that declares no variable but reads `getVariables` is refused `variables_untyped`: fail closed over a guess
about its inputs.
