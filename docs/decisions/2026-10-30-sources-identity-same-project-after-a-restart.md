## 2026-10-30: the same project after a restart, and the reason on the phone (sources-identity)

**The rule.** A marker of the sources folder (`.openhora-sources`) names this project when its `dev:ino` is this folder's (today's rule, untouched). It also names it when only the device differs, the inode is this folder's, and the marker's `project_path`, stat'ed now, is this very folder (`os.path.samestat`, never a string compare: `realpath` keeps the case a person typed). Anything else stays refused with code `foreign`. A read writes nothing and logs one stderr line per process and project. The marker is renewed only by a writer, in `take_lease` under the sources lock and this host's lease, and keeps the old id in `renewed_from`. `--adopt-sources` on such a marker takes nothing over: it is already this project's. Limit L21's text changed (`contracts/runtime.md`), approved by the maintainer word for word.

**Why.** Two live symptoms read `Não consegui ler Gmail agora.` (validate: allow english-only -- the Portuguese sentence the phone showed) on the phone: the marker was refused after a restart (the device number of the project folder changed; the inode and the path did not), and after adopting the marker the same read failed with `not-configured` (Google's seven-day expiry of an unverified app's grant). Neither can be cured from a phone, and the plain sentence said a retry might.

**Measured (macOS 27.0.1, APFS, Python 3.9.6).** Two disk images, each with one `mkdir` at the same mount path, gave `A dev=16777239 ino=16` and `B dev=16777239 ino=16`: fresh volumes collide on inode, and today's rule already treats them as one project when the device number is reused too. With another image attached first, A came back as `dev=16777243 ino=16`: the same folder under a new device, the shape of the live bug. A `cp -a` to a new path gave a new inode (1089155034 to 1089155077); a case spelling and a link pass `samestat`; APFS gave a new inode at every delete and recreate (root 4 of 4, image 3 of 3); `f_fsid` equals `st_dev` on a data volume, so it is no way out. Not run: a real restart, Linux inode reuse, NFS, SMB, exFAT, block-clone restores, two hosts on one synced folder.

**Options.** (a) inode plus path, device ignored when both match (chosen); (b) volume UUID (a subprocess of 127 ms on a path `check_folder` runs before every use, none on overlay, tmpfs or NFS, and still needs (a) for every old marker); (c) a random id kept in the project (a copy keeps the id: breaks the hard requirement that a copy is refused).

**Saving and loss (principle 13).** Saved: no terminal step after any restart or remount, on every project, and no reply refused for a reason that does not exist. Lost: one wrong match, wider than "the same mount path". A project folder B that has the same inode as the marker's and a device number that was not reused, and whose recorded path still leads to it, passes. That holds at the same mount path, and also when volume B is mounted elsewhere and a symlink is left at A's old mount path (the recorded path then leads, through the link, to B's folder). It needs `sources_dir` outside both volumes and the person to have named one folder for both and accepted it. Then B's store lists no row of A (reads go by the store's catalog and fail the hash check), and what B can do is write, in two ways. An import of the same source id and version finds A's folder as a leftover with no record and moves it aside, and the sweep removes it after 24 hours. And the version sweep (`runtime/upkeep.py` `sweep_versions`, line 316 takes the lease) removes the old version folders that B's own rows name, in A's folder, with no import at all. For a mail or calendar source that is a re-read; for an imported file it is the loss of that version. The marker's `renewed_from` is the trace. The limit is still enforced by code. OPEN-1 (also compare the folder's birth time, macOS only) was decided: not now.

**The reasons.** A closed word for a refusal only the computer solves: `folder` (codes `foreign`, `folder`, `path`) and `authorization` (a mail or calendar read whose provider answered `not-configured`, carried as `provider_kind`, never as text). Each has its own sentence on a phone (`NW_ITEMS_REFUSED_FOLDER`, `NW_ITEMS_REFUSED_AUTH`, no command, no path, no id: L62); two sources with one reason are one sentence. Every other failure keeps the plain sentence, because a retry may work. `not-configured` also covers a rejected client or a wrong scope; the sentence fits those too. Not decided here: `FAIL_NOT_AUTHORIZED` still promises the page (OPEN-2), a calendar line by name still answers "not found" with an expired authorization (OPEN-3), `ops_ask` still puts the English refusal in a question over sources (OPEN-4), and `evals/local_models.py` keeps `st_dev` in a stat it compares across a restart (backlog).

**Known limits of the reasons (review of #673).** (1) A provider exits 3 (`not-configured`) also when the OS secret store is locked or unavailable, the credentials folder is unsafe or the password manager is locked (`providers/_google.py` `find_account_record`, `providers/_msgraph.py`). That is not an expired authorization: unlocking cures it. `sources_mail._closed_kind` therefore asks `secret_state.unreadable_sentence` (fresh, no secret read) and, when it answers, drops the word, so the phone gets the plain sentence. A 401 on the API call (`providers/_google.py` `get_json`, `providers/mailbox/gmail.py`: "rejected the access token") and a refused refresh also exit 3. They cannot be told from an expired authorization without reading the provider's text, which the runtime never does, so they stay `authorization` (a re-authorization is the cure for a revoked or expired token; a transient 401 would be said to need the computer, a known limit). A class that does not resolve or a provider that cannot start is `not-configured` too and also stays. A store that cannot be asked at all is not guessed at: the plain sentence. (2) A person who re-authorizes inside the 120 s cooling time of a mail lookup still hears "authorize again" until the cooling ends (`mail_refresh.last_reason`); not changed. (3) A calendar line by name with a refused folder now gets the folder sentence (a small change in `event_lookup._found`), no longer "no such event"; an expired authorization on a calendar line by name, and a snapshot older than 26 hours whose folder is also refused (the age is looked at before the folder is opened), are still "not found" (OPEN-3). (4) The phone sentences are given to a phone only: the terminal, the conversation and the page keep their words.
