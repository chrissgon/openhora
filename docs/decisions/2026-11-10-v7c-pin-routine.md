## 2026-11-10: The pin routine of the reference fetcher: a check that tells, and two commands the person types (V7c; decision 15, V7 section 6.4)

**Decision.** The reference fetcher's tool (yt-dlp, pinned in `providers/fetcher/tool-pin.json`) is raised only by the person, with a typed yes each time. A routine only tells.

- `ytdlp.py pin-latest`: one https GET of the releases API's `latest` page. That host only, global addresses only (checked on every address the name resolves to, the connection made to the checked address with the host name as the TLS name), a redirect is refused and not followed, at most 1 MiB, 30 seconds, no token. It prints the current and the latest version, whether the latest is newer, its date, size and sha256. It downloads nothing and writes nothing.
- `ytdlp.py pin-raise --version V --confirmed`: reads the release of `V` and writes `<state>/fetcher/pin.json` (0600), only when `V` is newer than the committed pin, the release has exactly one asset with the committed asset's name, its address is the committed address with the version replaced, and it carries a sha256 digest. `tool` and `redirect_hosts` come from the committed pin, so a raise never widens where a download may redirect. Without `--confirmed` it refuses before any call.
- The effective pin (`_fetcher_image.effective_pin`) is the local raise when it is valid (a regular file of this user, closed to others, 8 KiB at most, passing the same checks as `pin-raise`), else the committed pin. A raise that is not valid is ignored, never trusted. The definition hash already covers the effective pin, so a raise gives the image a new tag and the next `build --confirmed` is the download (a maintainer's yes, STOP 2 of V7). The committed `tool-pin.json` is never written by a verb.
- The routine: the step kind `tool-check` (`runtime/step_tool_check.py`) and the flow `flows/fetch-tool-check.json` (one task, no parameters), made a routine by the person with `routine-create` (weekly recommended). The step asks the `tool_check` service (`runtime/ops_step_seams.py`) for `pin-latest`. When a newer release exists it opens one question card that names both versions and the two commands to type, and offers to run nothing. It never downloads, writes a pin or builds.

**The service is narrow by structure.** A step kind may not import a module that calls a provider (limit L30, `test_steps_gate.py`), so the check reaches the provider through a service. `ToolCheck.latest()` takes no argument and starts the literal verb `pin-latest` of the class `fetcher:video` with the minimum environment of the class; it has no verb parameter, so no caller can reach `pin-raise`, `build`, `fetch` or `measure`. A test reads its code and its signature. The step module's row in `ALLOWED` of `test_steps_gate.py` is `{"steps"}`.

**`networked` is set on the kind.** The flag governs two things (`runtime/ops_waits.py` `networked_steps`, `runtime/ops_routines.py` `local_reason`): a plan holding such a step is approved from the terminal or the page by default (limit L36), and a routine whose flow holds one is made and changed only from the terminal or the page (limit L33). `pin-latest` makes a network call from the host, so the flag is set: nobody can create or change this routine from a messaging app, whatever the project grants. Not setting it would let a routine that reaches the network be made from a chat. The kind is also `unattended`, so the routine's runs start without the person, which is the point of a check; the only thing a run can produce is a question.

**A coupling to the engine, stated.** When the pin is current there is nothing to tell, and the engine has no way to skip a stop. The `check` step writes `state["steps"]["review"] = {"status": "done", "result": {"skipped": true}}` itself, and the engine's loop then passes the step (`steps.run` skips a step whose recorded status is `done`). The stop is named `review` because the engine allows no other word (`steps.STOPS`). This relies on the engine's state shape and that loop, and no engine file is edited (principle 13: a `skips` hook in `steps.py` would be a larger change to a file other kinds depend on, for one kind). A test runs the real engine over the kind with the pin current and asserts the task ends `done` with no question card, so a change to the state shape breaks that test and not production.

**Why a typed yes each time (OPEN-5, recommended and taken).** yt-dlp is a large third-party program that runs with network and parses hostile pages. An unattended raise would trust a release nobody looked at, and the build downloads it. Alternative rejected: a standing policy that raises unattended after a 7-day cooldown (an unattended download; principle 13 says no until a stale tool is shown to hurt). Cost accepted: a stale yt-dlp fails fetches until the person raises it, and the `fetch_failed` sentence says the tool may be out of date.

**Files outside the V7c row, approved by the supervisor.** `runtime/ops_step_seams.py` (the `tool_check` service and its docstring), `runtime/tests/test_steps_gate.py` (one row of `ALLOWED`, no assertion changed). One more edit was unavoidable: `providers/fetcher/tests/test_fetcher_image.py` pins the exact `VERBS` tuple, so its expected literal gains the two new verbs (a V7a test; the assertion is extended, not weakened).

**Verified offline.** Every case of V7's section 8 for V7c, with a fake opener and a fake service: no network, no docker, no download, no yt-dlp run. **Not verified:** the real `pin-latest` against the live API (the response's field names are those the V7 spec recorded at STOP 1: `tag_name`, `published_at`, `assets[].name`, `size`, `digest`, `browser_download_url`); that a routine fires the kind end to end on a real project (the engine and the flow are tested, the routine's scheduling is the existing one's); the generated blocks (verbs of the provider, runtime modules) are regenerated by the supervisor.
