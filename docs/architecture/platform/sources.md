# The sources of a project

What a person gives a project to read, how it becomes clean text a task can use, and the guardrails that keep it from becoming a way in. It crosses three layers of the platform map and belongs to none alone: the runtime owns the registry and the folder (`runtime/sources.py`, `runtime/ops_sources.py`), a provider converts (`providers/converter/`), another reads a Notion page (`providers/documents/notion.py`), and the store keeps the rows. Package P4 of the delegation plan; decisions D9, D10, D11, D13, D16, D29 and D30 of `docs/architecture/delegation-platform-plan-2026-10-14.md`.

## Purpose

A project declares **sources**: an uploaded file (a PDF, a Word document, a spreadsheet, a presentation, a CSV, an HTML page, a text file) or a Notion page chosen by its address, and, since RT-1, a window of the person's mailbox or of one calendar read as a snapshot (rule 18). Each import is an **immutable version** kept in the project's **sources folder** (`sources_dir`), as the original, the converted text and a manifest. A **catalog**, built by code from the converted text alone, tells the planning run what each source holds, so that the **plan** can name, for each task, the sources it needs; the person approves that plan by its hash, and a task **receives copies** of the newest version of each source at the moment it starts. The sources folder itself never enters a run.

The idea behind each piece, in one line each:

- the folder is the person's, it is dedicated and private, and the runtime treats it as hostile ground: it writes only inside it, through an open descriptor, and reads nothing from it that it did not first check against a hash;
- a file is never read on this machine: bytes go through the generic intake (the length bounded first, the type read from the bytes), a container with no network converts them with adopted open tools, and only the converted text is scanned, catalogued and handed to a run;
- the planner is given data, not instructions: the catalog is text other people wrote, and it is named in the external-content line of `core-orchestrator`;
- a task sees only the sources chosen for it, and the plan shows them before anyone approves it.

## Artifacts it owns

| Artifact | Where | Notes |
|---|---|---|
| The sources folder | `sources_dir` of `runtime.json` (mandatory, no default; accepted only in the terminal) | `.openhora-sources` (the marker; it names the project folder's device and inode, so a folder serves one project), `.incoming/` (the assembly area; it also takes a leftover numbered folder aside), `<source id>/<version>/original.<ext>`, `converted.md` or `converted.csv`, `manifest.json`. Files are mode 0400; a version is moved into place with one rename and never written again |
| The registry | table `sources` of the store (migration 11; migration 14 added the type `drive`, migration 19 the type `onedrive`, migration 21 the types `mail` and `calendar`) | id, type (`file`, `notion`, `drive`, `onedrive`, `mail` or `calendar`), origin (a file's name, a Notion page's address, a Drive file's id, a OneDrive file's `<drive id>/<item id>`, or the closed line of a mail or calendar window; never a credential), the person's description. Never deleted; only the description changes |
| The versions | table `source_versions` | one row per version: label (`import`, `refresh`, `changed-by-person`), who made it (`runtime` or `person`), the sniffed kind, the hashes and sizes of the original and the converted text, the converter and its tools, `hidden_text` (1 found, 0 none found, null not examined: P8), warnings, the catalog entry, the origin's own version (a Notion page's `last_edited_time`), the date from the clock. Never changed, never deleted |
| What a task received | table `task_sources` | for each run: the source id, the version and the sha256 of the converted text copied; plus `tasks.sources`, the ids the approved plan chose |
| The copies in a run | `.workbench-local/sources/<source id>/converted.<ext>` in the run's copy | made when the task starts; staged like the file drop, so never brought back |

## Dependencies

- `runtime/intake.py` (P0): the length bounded before a byte is read, the type read from the bytes with the sniffers `sources.py` adds (PDF, Office Open XML, text), the hash while it streams, one upload at a time.
- `providers/_container.py` (P0): the lifecycle and every limit of the container (no network, a read-only root, every capability dropped, memory-backed `/tmp` and `/scratch` with no exec, an image never pulled at run time); `run(stdout_cap=)` was added for the converter's stream.
- `runtime/workcopy.py`: `scan` for the credential scan of the converted text, `entering` for what a run sees.
- `providers/resolve.py`: the class `converter:document` (a role, not listed in `contracts/environment.md`: no skill may require it) and the call to the documents provider.
- `runtime/lab.py`: `local_evidence_base()`, the folder the sources folder must be disjoint from.
- The store: migration 11, and `plan_approve` / `request_add` carry `sources` on the tasks.

## Business rules

The numbered limits L21 to L27 of `contracts/runtime.md`, each with a test named after it (`runtime/tests/test_sources_limits.py`):

1. **L21** dedicated, private, marked for this project, mode 0700 (at acceptance and before every use).
2. **L22** disjoint from `data_dir`, `store_db`, the checkout and the local evidence folder, by device and inode.
3. **L23** the runtime writes only inside it and never follows a link out (the import staging folder in `data_dir` included); a pipe where a file is expected is refused before it is opened; the home folder, the root, a folder that contains the project and a folder at or under the project's `docs/` or `.workbench-local/` are refused.
4. **L24** what a container writes comes back only as regular files, with closed names, under a byte cap.
5. **L25** a file changed outside the runtime is found by its hash, checked again, labelled as the person's, and never used unattended.
6. **L26** the work copy excludes the folder, even inside a tracked tree, and nothing a run leaves is written into it (a returned path inside it is kept; a change set that touches it is refused).
7. **L27** the catalog is built only from converted output.

Beside them:

8. **A converted text is scanned for credentials after the conversion**, because text compressed inside a PDF is invisible to a scan of its bytes; a text that fails is not kept, and nothing is left in the folder or the store.
9. **A source has a size cap, with a warning.** An original is at most 25 MiB (the intake's route limit). The converted text is at most 1 MiB: a task reads all of it, 1 MiB is beyond what a model's context takes, and indexing or retrieval waits for a real case. From 256 KiB (about 65,000 tokens at four bytes a token) the import succeeds and says it is large, and the catalog entry carries the warning.
10. **The planner chooses, code checks.** The router's reply may carry a `Sources:` line (`runtime/router.py`); an id the project does not hold, or a skill that is not in the plan, makes no plan (the person is asked). An `@mention` is added by code to every task of the delivery. The ids are part of each task, so they are in the plan hash; a new version of a source changes none of them.
11. **A task receives the newest version at the moment it starts** (D29): copied from the folder after its files are hashed against the record; recorded as id, version and sha256, only for the copies the run received (a copy that fails the credential scan again stops the task with the reason). A version made by the person (`changed-by-person`) goes only to a task the person starts with `run-next`; the dispatcher's starts and `run-task` are unattended and refuse it (the page cannot start a task). A source refreshed after the plan and before the start reaches the task as the newer version; one refreshed after the start does not reach that run. A later run of the same task takes the newest version at its own start.
12. **A Notion page is read with its own read-only secret** (`NOTION_SOURCES_TOKEN`, store username `notion-sources`), by `read --as-source`; `NOTION_TOKEN`, which writes, is never used for sources. The page's id is extracted from the address (every URL shape the provider knows: a bare id, `Title-<id>`, a workspace path, a `p=` query, a `notion.site` host); anything else is refused.
13. **The channels.** The four writes (`source-add`, `source-import`, `source-refresh`, `source-describe`) are for the terminal and the page (`source-add` registers a OneDrive, a mail or a calendar source from the terminal alone; `source-mail` and `source-calendar` of rule 18 are the terminal's); the catalog read (`sources`) is also for the MCP mode and the messaging channel, and sits in the group `sources`, which a project's policy turns on (it is not in the default policy of messaging: the catalog shows samples of the person's data). The files a listed sender sends through a messaging app are another road to a version (rule 16).

14. **A Google Drive file is a source by its id, with one scope and no folder** (P7). The person picks one or more FILES in Google's Picker (`source-drive`); each file id is registered as a source of type `drive` and imported like any other. The registry's type column admits `drive` since migration 14 (P7 stored a Drive source as a `file` row whose origin was `drive:<file id>`; the migration rewrote those rows to the type `drive` with the bare file id as the origin, and `sources.public_row` is the identity for them). The provider is `providers/documents/gdrive.py` (the documents class, read only, `SOURCES_ONLY`), with the scope `drive.file` and the secret `GDRIVE_SOURCES_TOKEN`. **`drive.file` is not read-only**: it lets the app read and write every file the person picked. The provider sends GET requests only and the runtime calls only its read verbs; the token is as private as those files. **A folder is not a source**: under `drive.file`, a picked folder gives the app nothing inside it (the spike of 2026-10-15: `files.get` on the folder answered, `files.list` of its children returned none while it held files), so the Picker lets the person open folders and not pick them. A Google Doc is read as Markdown (its text, no converter), a Sheet as a workbook, Slides as a PDF, any other file as it is; the bytes go through the same intake, converter, credential scan and rows as a file of the person's, and the manifest and the catalog name the file. **A refresh asks Drive for the file's version first** (`stat`: Drive's `version` and `modifiedTime`, recorded as the version's `origin_version`) and reads nothing when it matches; bytes already held make no version either. The files of a version are still checked against their hashes when Drive did not change (limit L25).
15. **The Picker never runs in the runtime's page.** Its script and frames come from Google's hosts, which the page's policy (`default-src 'self'`) and the interface's rule (nothing from another host) forbid. It runs on a one-shot server on 127.0.0.1 (`providers/documents/gdrive_picker.py`, started by `providers/documents/gdrive_auth.py`): a random port; every request must carry that exact `Host` (no DNS rebinding); the way in is the printed start URL `/start?k=<key>` (a random key, served once: without it nothing is revealed, neither the consent URL nor the nonce); the OAuth callback is served once, only when shaped like one, and its state compared in constant time; the page, the token and the picks need a nonce that /start gives only to the key's holder; a post must carry the server's own `Origin`; it stops after the picks, a cancel, a failure or ten minutes. The authorization asks for `drive.file` and nothing else (PKCE S256, a state, offline access); the refresh token, the client and the Picker's API key are one record in the OS secret store, and the access token is made in memory for each call. The provider's process has the minimum environment and that one secret; a run receives converted text only, and its environment is an allow-list that holds no Drive secret.
16. **A file a messaging app brought is held, then added by a person.** (ATT-1) A listed sender's file is fetched only when the channel's policy lists the group `add-sources` for that sender (the default policy of messaging does not: nothing is downloaded), after the platform's declared type and size, the day's count (20 files and 100 MiB for the project) and the held ceiling (10) were checked; it waits in `<data_dir>/attachments/held/<id>/` (never in a run, a prompt or the sources folder), recorded in the table `attachments` with the sender's id, and becomes a version of a source only when a person adds it (a card, the page, the terminal) or when the sender's profile holds the grant `add-sources-direct`. The type is read from the bytes; a declared type of the converter's list that the bytes contradict is refused. The version is made by `ops_sources.import_bytes` (the same container, credential scan, hidden-text flag and size warning as any import) with a **provenance** `{channel, platform, profile, attachment}` kept in the manifest, in `source_versions.provenance` and in the catalog line (`sent on telegram, profile staff`): the sender's id is in the store alone. A caption is read only when it is exactly `@<source id>` on one file (a `file` source: a new version labelled `refresh`; a free id: a new source; a `notion` or `drive` source: refused). On a messaging app a sender sees and decides only the files they sent (the terminal and the page see all). The grant makes new sources and never a new version of one that exists. Every fetch counts against the day, also one that ended with no file. The held file is deleted when it is added, refused, discarded or after 7 days (`upkeep`). A version from an attachment is usable by a task that starts on its own, like a page upload. Limit L48.
17. **A OneDrive file is a source by its drive and item ids, chosen in the terminal, read with one scope that reads more than it is asked for** (O2). There is no picker: `source-onedrive --search <text>` (or `--folder <path>`) lists up to 25 candidates from the person's own OneDrive (name, folder, size, date, and the `<drive id>/<item id>` to give back; they are another person's text in principle and are cleaned to one line, never run or used as a path) and registers nothing; `source-onedrive --item <drive id>/<item id>` (repeatable) registers each chosen FILE as a source of type `onedrive` (the type column admits it since migration 19, which rebuilds `sources` as migration 14 did and rewrites no row) and imports it through the same intake, converter, credential scan and rows as any file (DOCX, XLSX, PPTX, PDF, CSV, HTML and text; a legacy `.doc`, `.xls` or `.ppt` is refused with "save it as .docx, .xlsx or .pptx"). A folder, a OneNote notebook, an item shared from another drive, an item OneDrive flagged as malware and a deleted item are refused with the provider's reason. The provider is `providers/documents/onedrive.py` (the documents class, read only, `SOURCES_ONLY`), with the delegated Microsoft Graph scope `Files.Read` (and `offline_access`) and the secret `ONEDRIVE_SOURCES_TOKEN`; the provider's process gets the minimum environment plus that one secret, and no run, manifest, catalog or message ever holds a token or a download address. **`Files.Read` reads every file of the person's own OneDrive and writes none**: Microsoft has no scope granted per chosen file, so the narrowing to the chosen files is the runtime's (only a registered item id is read; `search` and `children` serve the terminal and register nothing). The refresh asks the item's cTag (it moves with the content and not with a share or a rename) and reads the file only when it differs from the one recorded with the newest version; the eTag is kept in the manifest. SharePoint sites, Teams libraries and files shared with the person need `Files.Read.All` (an administrator's consent) and are not built. Authorization is `uv run providers/documents/onedrive_auth.py authorize`, once ([`providers/documents/README.md`](../../../providers/documents/README.md), "OneDrive"). Registering a OneDrive source is for the terminal alone: `source-onedrive` is terminal only and `source-add --type onedrive` is refused from the page or any other channel (the operation takes the channel), so a page token cannot register and read an item of the person's OneDrive; `source-refresh` of an already registered one stays on the page, since it reads only what the terminal chose. One file is one source: `register` refuses a second source for the same origin (a OneDrive id compared without case, a Drive id as it is). Code: `runtime/sources_onedrive.py`, `ops_sources.source_onedrive`.

18. **A window of the person's mailbox or of one calendar is a source, read as a dated snapshot and never live** (RT-1). `source-mail` and `source-calendar` (the terminal alone, as `source-onedrive` is: they are refused on the page, the MCP mode, a messaging app and the conversation, and sit in no group) register a source of type `mail` or `calendar` (the type column admits them since migration 21) from a closed origin line and read its first snapshot; a registered source is read again by the same command with no origin, by `source-refresh` (also from the page) and by the `ingest` step of a routine. **`/ask` leaves a snapshot out of its automatic selection** (the sources that fit, and the ranking) and reads it only when the question names it with `@<id>`, from the terminal, the conversation's own shell or the page; from a messaging app such a question is refused with a fixed sentence and nothing runs (decision of 2026-10-18). The origin is `gmail:box=<inbox|important|starred|unread>;days=<1-31>;max=<1-100>` or `outlook:box=<inbox|unread>;days=<1-31>;max=<1-100>` for mail, `google:calendar=<id>;past=<0-7>;ahead=<0-31>` or `outlook:calendar=<default|id>;past=<0-7>;ahead=<0-31>` for a calendar: the box is one of the fixed queries (no free text in v1), one calendar is one source, the implementation in the origin is the explicit implementation handed to the provider (never "auto", which exits 3 now that two mail readers ship), and a source keeps its origin (another window is another source; one window is one source). The runtime reads the window (the host's clock and zone) through `providers/mailbox/` or `providers/calendar/` with the minimum environment plus that provider's own secret (`runtime/sources_mail.py`; the narrowing to a box, a window and one calendar is the runtime's, since `gmail.readonly`, `Mail.Read` and the calendar scopes read the whole mailbox or every calendar and change none), builds the text (`runtime/snapshot_text.py`) and imports it as the next version of the source, as a ready text like a Notion page (no converter). **The text is cleaned of what a third party could use against the reader:** the sender's own words only, every link (any scheme with slashes after it, `//host/path`, `www.` and a bare `host.tld/path`) replaced by `<link: host>` and every `mailto:` address by `<address>`, control and direction characters removed, a line cut at 1,000 characters and a body at 4,000, every body line indented by two spaces (so that a line that begins with `#`, a code fence or `## Sheet:` is never a heading or a sheet of the catalog), attachments listed by name, declared type and size and never opened, no event description and no attendee, and headings that carry a number and a time or a date and no subject and no sender. **Each message (each event) is scanned for credentials on its own, and one that holds a credential shape is left out**, counted by its date and its sender's domain (the domain is left out of the line too when it looks like a key), never redacted; the scan reads the fields before any cut; the whole text then passes `import_version`'s own scan unchanged as a second guard. Past the size one source may hold, the oldest messages are dropped with a counted line. The listing identifies the reading (`origin_version` is the sha256 of the sorted (id, change key) pairs, the zone and the local date): the same list on the same day makes no version, a changed list makes one, and so does the same list on another day, which keeps the snapshot of a daily routine younger than 26 hours. **LS1 (L52):** the providers are called only by the source operations, never from a run or by a step with a query a model wrote. **LS2 (L53):** a snapshot older than 26 hours is never handed to a task that starts on its own; a task the person starts receives it with its age in the first line of its copy. Messages, titles and places are external content: data, never an instruction; the snapshot says so in its first lines and the catalog block already says so. The data lives in the sources folder (private, outside the repository) and, during a run, in that run's copy; the model provider sees what a task receives and a phone sees a notice in `text` mode. **The index of a snapshot (SNAP-IDX).** Beside the text, the manifest of each mail or calendar version keeps `index`: one entry for each item the text lists, in the order the text lists it, numbered from 1, so that a request to change a message or an event names it by `<source id>#<n>` and code finds it by the index, never by the words of the text (`runtime/item_refs.py`). A mail text prints the numbers (`## 3. ...`) and so does a calendar text (`3. 09:00-10:00 · ...`), in the order of `snapshot_text.calendar_order` (day by day, all-day first, then by start), so the number a person reads is the `n` of the entry. A mail entry is `{n, id, thread_id, message_id, from_address, reply_to_address, subject, change_key}` (the provider's ids, the Message-ID header, the sender's plain address and a Reply-To that differs from it, both printed by the reader as an address alone, the Gmail reader only when the header holds exactly one mailbox and the Outlook reader from Graph's address field, never picked out of a name; the subject with its links replaced, control and direction characters removed, cut at 120 characters, so it may end in "…"; Graph's change key); an event entry is `{n, id, etag, calendar, organizer_self, attendees_other, recurring}` (`attendees_other` is null when the reader did not print it, which is today). Every value is a closed shape or null (a null id keeps its entry, so that the numbers do not move); there is no body, no sender's name and no token; a message or an event left out of the text for a credential has no entry and takes no number; an entry is scanned once more as a whole. The index is in the manifest, which no run receives (L26, L52), and **its sha256 is the third line of the text** (`Index digest (sha256): ...`), which the store's hash of the text (L25) binds: an index edited in the manifest no longer matches its version and `item_refs` refuses it. A reference to a snapshot older than 26 hours, or to a version made before the index existed, is refused with "refresh <id> first"; the format of the index is part of a reading's signature, so the first refresh after the index existed always makes a version that has one.

    **References (`runtime/item_refs.py`).** `resolve(ctx, "<source id>#<n>", channel=, sender=)` returns `{kind: "item", source, type, implementation, calendar (a calendar source) or box (a mail source), version, read_at, age, n, count, entry}`: `implementation`, `calendar` and `box` come from the SOURCE ROW's origin (`sources_mail.origin_of`), never from the manifest, and the manifest's `origin` and every calendar entry must agree with them. `created:<number>` returns `{kind: "created", pending, type: "calendar", entry}` through a function the calendar write path gives. **Who may use a reference:** the terminal, the conversation, the page and a call with no channel; a messaging sender only when its profile lists `ask-mail`; the MCP mode never; the check is `item_refs.may_read`, in `read_index`, before anything is looked up. Every refusal is an `ItemRefError` with a `code` and an English sentence; **the packages that write (W1 to W3) map each code to a phrase key**: `malformed`, `zero`, `not_readable` (the caller may not read the snapshot), `no_source`, `not_snapshot`, `wrong_kind` (the caller needs the other type), `no_version`, `stale` (older than 26 hours: refresh the source first), `no_index` (a version made before the index: refresh), `integrity` (the version's files, its index or its manifest do not agree with the store's record: refresh), `past_end`, `created_unavailable`, `created_unknown`.

16. **A question is answered from the content, not from the catalog** (AQ-1). `ask` (`runtime/ops_ask.py`) gives the converted text of the sources that code selected (`runtime/ask_select.py`: `@` mentions, else all that fit 256 KiB and five files, else a ranking by plain word rules over the catalog; never a model's choice, because the catalog is third-party text) to one contained run of the answer skill, with no plan to approve, and checks the reply by code (`runtime/ask_reply.py`: each quote must be in its source's copy; `not-found` replaces the model's prose with a fixed sentence; the sources and versions read are appended, and a line says when the skill is not proven on the model). The copies are a task's (rule 11), the run is the contained run's (one attempt, no web, nothing back; limit L49), and the answer leaves only to the shell or chat that asked (limit L50). A source over 256 KiB is answered only by a task: chunking and retrieval wait for a real case (rule 9). The question is a request made with its run, titled "Question <n>", and never mirrored to the task board (`board.asked`); the conversation shows the answer only to the channel that asked. The skill that answers (`asst-answer`) is planned: until it is written `/ask` replies that no skill answers yet. `contracts/runtime.md`, "The answer from sources", is the contract.

## Known limits and improvements

- There is no screen for the sources yet; the page's routes exist and the plan card shows each task's sources (and highlights a web task that receives them). An ingest is a task since P5: the step kind `ingest` (`runtime/step_ingest.py`) wraps the same operations on the step engine, with the arguments a plan shows and its hash covers; the terminal's `source-import` stays the synchronous way.
- A Drive folder as a source is not built (`drive.file` does not reach a picked folder's files; it would need `drive.readonly`, a wider scope, and the maintainer's decision). Drive write-back is not built (the Drive provider is sources-only); the hidden-text flag of a converted HTML or PDF is built (P8: `outputs.md`, "Hidden text").
- A mail source selects one of the fixed boxes (Gmail `inbox`, `important`, `starred`, `unread`; Outlook `inbox`, `unread`) with a number of days and a most; a free Gmail query, user labels and Outlook folders by name wait for the pilot to show which are needed. A calendar source reads one calendar; several calendars are several sources. Event descriptions and attendee lists are left out (fewer third-party words in front of a model; Microsoft's `Calendars.ReadBasic` has none). A link in a message is replaced, so a task that needs one asks the person. An attachment is listed and never opened (turning one into a file source is a later package). The first version is read only: writing to a calendar or answering a mail is a later package with its own effect word. The window, the zone and the clock are the host's. Nothing of Google or Microsoft was run by the package: the Graph body format, the calendar id shape, `GET /me/calendars` under `Calendars.ReadBasic`, the attachment `$select`, that a calendar token cannot get a Gmail scope and the scope strings returned are the maintainer's live steps (`providers/mailbox/README.md`, `providers/calendar/README.md`). A Google app left in Testing expires its refresh tokens after seven days, and then L53 refuses the stale snapshot to an unattended task until the person authorizes again.
- A OneDrive folder as a source is not built (files only), nor are SharePoint sites, Teams libraries and files shared with the person (`Files.Read.All`, an administrator's consent; package O3 on the maintainer's word); OneDrive write-back is not built (the provider is sources-only). Nothing of OneDrive was run against Microsoft by the package: the download host suffixes, the `scope` string returned, the loopback redirect in the person's browser and a work tenant's consent are the maintainer's live step (`providers/documents/README.md`, "OneDrive"). The terminal lists candidates; a OneDrive search box on a sources screen waits for that screen.
- The Markdown export of a Google Doc, Google's 10 MB export limit and the Picker's behaviour with the page's headers are not verified against the live service (`providers/documents/README.md`, "Google Drive").
- A PDF of scanned pages has no text layer; no OCR is made, and the manifest notes it.
- A Word document, a spreadsheet or a presentation with macros (a VBA project part, a macro sheet or a macro-enabled content type, judged by the package's content and not its name) is refused for every source before any tool reads it (package ATT-5, `providers/converter/_inner.py` `refuse_macros`); the refusal is the converter's failure sentence and is recorded as a refused import like its other refusals. A macro-enabled file embedded in a plain package is not opened, and the old binary formats are not a type the intake takes. It needs the converter image rebuilt (`providers/converter/README.md`).
- A table in a PDF comes out as the lines of its cells (`pdftotext`), not as a Markdown table; the MarkItDown measured recovers the table but drops the page marks and writes `(cid:n)` for a bullet, so `pdftotext` was kept (the comparison in `docs/decisions.md`).
- Text a Word document marks as hidden still comes out (pandoc keeps it); like the text hidden by CSS in HTML it waits for the hidden-text flag of P8.
- A formula cell with no stored value in a workbook comes out empty (the converter reads stored values, it calculates nothing).
- A source over the converted cap is refused, not indexed: indexing and retrieval wait for a real case. A question reads at most 256 KiB of converted text and five sources (`ask`): a larger source is answered only by a task of a plan, or after a package of chunking that waits for a real case (`docs/backlog.md`).
- A folder synced between machines is written by one host at a time: every writer takes the folder's lease (`.openhora-lease`, limit L28), and a live lease of another host refuses the write and names that host; the sources lock stays a file under `data_dir`, never inside the folder. Old versions are pruned beyond `source_versions_kept` ([unattended.md](unattended.md)).
- The converter image is built from a pinned definition by a step the person starts (`providers/converter/container.py build --confirmed`); the base image is pinned by digest, the Debian packages by a dated snapshot of the Debian archive and the Python packages by a lock of exact versions and sha256 hashes (`providers/converter/requirements.lock`, installed with `--require-hashes`). The tools it holds are poppler's `pdftotext` and `pandoc` (the Debian versions of that snapshot), `openpyxl`, and `python-pptx` 1.0.2 for presentations; which tool converts which format was chosen by a measured comparison in which Microsoft's MarkItDown was measured and not adopted (`providers/converter/README.md`, `docs/decisions.md` 2026-10-15).
