## Ranked findings (impact on the Lego goal, security first)

Each finding gives its evidence, the fix, the cost (S: hours, M: a day, L: more) and what the fix buys.

### 1. A standing policy's bounds (limit L15) are enforced inside a handler, not by the runtime. `autonomy.covers` has no caller.
- **Evidence:** `runtime/autonomy.py:220` `covers(...)` checks every bound: effect kind, target, file globs, items per run, per day. No module of `runtime/` calls it. Only `runtime/tests/test_autonomy.py` and `test_standing_approval.py` do.
  - `ops.standing` (`runtime/ops.py:1343`) checks the approval's existence, its file hash, its expiry and the mode, but not the bounds.
  - The one effect executed under a policy is the handler's. `runtime/handlers/published_posts.py:342` `broken_bound` and `:327` `_inside` (its own glob reading) re-implement the bounds. Then `:425-426` runs `commit-files --confirmed` itself.
  - The architecture README's cross-cutting table names `autonomy.py (covers)` as the enforcement of L15.
- **Why it matters:** a hard limit lives in the layer most likely to be replaced or multiplied (handlers are the extension point). A second handler that forgets the bound check executes effects outside the approved policy. Nothing in code or structure stops it, which goes against principle 11.
- **Fix:** add one operation, for example `ops.execute_under_policy(project, policy, effect)` with a verb `cli.py execute-standing --policy --effect-file`. It calls `autonomy.covers`, runs the provider verb, and records `action_add` inside the run lock. A handler prepares the effect document and asks. It never passes `--confirmed` itself. Remove `broken_bound` and `_inside` from the handler, and add a test that no file under `runtime/handlers/` contains `--confirmed`.
- **Cost:** M.
- **Buys:** the policy limit is enforced once, in code, whatever handler is added. It also deletes the fourth glob reading (see 11).

### 2. The runtime's sandbox is reached through about 40 private names of the measurement runner. The retry rule that decides which attempt is scored sits outside the fingerprint.
- **Evidence:** `runtime/lab.py:56-84` `ALLOWED` lists names that are all defined inside the 3,444-line `evals/eval_run.py`. Examples: `contained_env` (`:1514`), `run_group` (`:1646`), `Slots` (`:2380`), `redact_folder` (`:1833`), `stage_run` (`:559`), `harness_settings` (`:530`), `run_failure` (`:1701`). The lab side has no marker saying these names are load-bearing; the allow list lives on the consumer.
  - `lab.load_status` returns the whole status module, with no allow list. The facade calls `load_gate`, `event_config`, `skill_version`, `content_hash`, `fingerprint_problem`, `GATE_REL`, `all_status` and `skill_evidence` (`runtime/lab.py:155, 185, 223, 249-254`).
  - `evals/run_attempts.py:143-245` decides which attempts are made again and never scored: early end, adapter failure, refusal. It is not in `FINGERPRINT_FILES` (`evals/eval_status.py:555`).
- **Why it matters:**
  - The lab layer does two jobs: measuring, and the execution kit the runtime uses for production runs (container, staging, settings refusal, redaction, attempts).
  - Replacing the measurement tool would break the runtime. Limits L1, L4, L6 and L14 travel with the measurement runner.
  - A refactor inside `eval_run.py` can break the runtime silently, until `test_lab_facade.py` runs.
  - A change to the retry rule changes what is measured without being a measurement change.
- **Fix:**
  - Extract an execution module (for example `evals/execution.py`, or `sandbox/`) holding the `ALLOWED` names and `run_attempts.run`. Put it in the fingerprint.
  - `eval_run.py` and `runtime/lab.py` both import it. `ALLOWED` and `FORBIDDEN` disappear, and the parity test becomes trivial.
  - Give the facade a narrow status port (for example `standing()` and `identity()` in `eval_status.py`) instead of the whole module.
- **Cost:** L.
- **Buys:** the lab's measurement and the runtime's execution become two pieces with one shared kit. The runtime depends on the kit, not on the runner, and the fingerprint covers everything that decides a score.

### 3. The project configuration fails open: an unknown top-level key is ignored, so a misspelled security key turns its protection off without a word.
- **Evidence:** `runtime/project_config.py` docstring, lines 14-16: "ignores every key it does not know". It also says `protected_paths` absent "means none". A file with `"protected_path": [...]` or `"protectedPaths"` loads with no protected path, and limit L20 for change sets falls away. The accepted-hash rule does not catch it: the person accepts what they wrote.
- **Fix:** close the top-level key list: the task runtime's keys plus the first runtime's known keys (`agent`, `harness`, `model`, `mailbox`, `publisher`, `vote`, ...). Refuse an unknown key with exit 3 and the nearest known name. Drop the first runtime's keys at stage 7.
- **Cost:** S.
- **Buys:** a hard limit that rests on a configuration key cannot be lost to a typo.

### 4. Shells map operations by hand, and the operations layer holds shell syntax. A new shell re-decides what every operation is, and the channel rule (A7) has nowhere to live.
- **Evidence:**
  - `runtime/cli.py:152` `VERBS`, plus a 58-line `if a.verb == ...` chain (`:220-278`) with one shared flag set.
  - The conversation's parser is in the domain: `runtime/ops.py:2268` `SAY_COMMANDS`, `:2270` `SAY_HELP`, `:2352` `_say_command`.
  - `ops.context` (`:241-245`) names `python3 runtime/cli.py accept-config`; this is A6.
  - The planned service and MCP mode would be the third and fourth hand mapping of the same operations.
- **Fix:** one declarative table of operations (`runtime/operations.py` or a constant in `ops`). Per row:
  - the name and the function;
  - the arguments, with types and whether each is required;
  - whether it calls a model;
  - which channels may call it: terminal, page, chat. This is where A7's rule becomes a column that code enforces.

  `cli.py`, `chat.py` and the planned service derive their verbs, commands and routes from that table. Move `_say_command` parsing into `chat.py`, and keep `say` as one operation that takes an already parsed turn. Have refusal messages name the operation (`accept_config`), never a shell's command line.
- **Cost:** M.
- **Buys:** adding a shell adds a file; adding an operation adds one row. The channel rule becomes code, not a convention each shell repeats.

## Layer by layer

### Layer 1: skills and flows (outside the hexagon)

**What is already right:** a skill is self-contained text with its own scripts. Its substitutability is the proof per model and adapter pair, computed by rules, and it reaches providers by class.

- **Ports:**
  - The frontmatter: a file contract (`AGENTS.md`, "Frontmatter contract"), read by `runtime/skill_meta.py` and `scripts/validate.py`.

  - The reply text the runtime classifies: an implicit convention, bound by `runtime/tests/test_skill_text_binding.py`.
  - A skill's scripts called by the runtime: an in-process import (`ops._task_script`) or a subprocess with the host interpreter (`documents.check_edit`).
- **Replaceability:** a skill rewritten from scratch must keep its `outputs` paths and template structure (its readers depend on them) and pass its cases. For a skill the runtime uses, it must also keep the exact reply phrases in `runtime/endings.py:53-79`, its `asking_openings`, and, for `eng-implement`, the function names `load`, `find_tasks` and `status_of` of `scripts/task.py` (`runtime/plan.py:36`).
- **Extensibility:**
  - A new skill outside the runtime adds a folder; validator rules and the routing table warn (`[routing-table]`).
  - A new skill in a runtime pack also adds its manifest, and may need an edit to `runtime/endings.py` (finding 5).
  - A new class row edits the router (finding 11).
- **Substitutability:** the lab's gate and bands, per model; this is a black-box conformance test. No conformance test exists for agents (`agents/*.md`): they have no lab test.
- **I/S:** the router carries copies of two contract tables (`requirement-classes.md`, `owners.md`) it may use only partly; the cost is that every contract change bumps it (finding 11).
- **D:** sound for skills. The reverse edges are the problem: the runtime reads skill internals (findings 5 and 9).
- **Security at the boundary:** gates and stop rules are measured by guard assertions, not enforced in code. That is acceptable only because the runtime executes no effect a skill did not stop before (limit L16) and the providers refuse without `--confirmed`. A16 (evidence files editable) stays a review-only guard.
- **Simplicity:** two flow notions (finding 16).

**Verdict:** a Lego piece, with conditions. It holds on its own and is proven per pair; it stops being files-only once the runtime uses it (findings 5, 11).

### Layer 4: the lab (an outbound adapter for proof and for execution)

**What is already right:**

- **Extensibility:** a new model tier edits `runtime/lab.py:101` `TIERS`, `evals/executor.py:73` `ROUTE_FILES`, the container's route files and `allow.txt` (finding 12). A new adapter edits `evals/tests/test_executor_docker.py:88, 331` (finding 13).

- **D:** the runtime depends on the lab's implementation names, not on a port the lab owns (finding 2). `evals/measure.py`'s `redaction_values` and `early_end` reach production runs through `ALLOWED`, so a measurement-side change also changes production redaction.
