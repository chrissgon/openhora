# The outputs of a task

How a task's result leaves the project: as a file made by code, or as a write to the platform that holds the project's documents; and how the text a source holds is checked for what a person cannot see before a model reads it. It crosses the layers like the sources do: the step engine (`runtime/steps.py`) runs the kinds that make a file and the kind that prepares a write, an effect kind (`runtime/effect_write.py`) carries the write, the operations layer approves and executes it (`runtime/ops_step_effects.py`), a provider renders (`providers/exporter/container.py`) and another writes (`providers/documents/`). Package P8 of the delegation plan; decision D17 and finding S9 of `docs/architecture/delegation-platform-plan-2026-10-14.md`.

## Purpose

Four things, one idea: **nothing leaves the project, and nothing reaches a model, in a form the person has not been able to see.**

- **A file made by code.** A task's result, a Markdown or a CSV file, becomes a CSV file, a workbook, a Word document or a PDF, by adopted open tools in a container with no network and no model. The file is written into `docs/outputs/` of the project.
- **A write-back.** The text of a project document replaces, whole, a document on the platform (a Notion page today). It is an **external effect**: the person is shown the exact content, approves its hash once, code writes it once, and the approval and the result are recorded. If the document was edited after the task read it, nothing is written and the person is asked again.
- **Something new on the platform.** The same effect word and the same approval make a new page under a parent page, a new table (a Notion database with its columns) filled from a CSV file or a workbook, or add rows to a table the task read. The weekly report that ends as a table the team already uses is the case. The hash covers the operation, the parent or table, the title and every column, type and cell. Package NOTION-OUT; the section "A new page, a new table, rows added" below.
- **An e-mail is sent after the person approves it.** A step task prepares an e-mail from the project's outbox (a dedicated account); the person is shown the sender, every recipient (the Bcc too), the subject, the text whole and each attachment by name and hash, approves the hash once, and code sends it once, to exactly those recipients. It is the same effect path as the write-back with another word, `send`. Package EMAIL-SEND; the section "Sending an e-mail" below.
- **A post is published after the person approves it.** A step task prepares one drafted post (the content file the marketing skills write) for a platform; the person is shown the platform, that it goes out now and not at its slot, the post and its first comment whole, the image by name and hash and the provider's dry run, approves the hash once, and code publishes it once, under the key the publishing skill uses, so a post that either path published is not published again by the other. It is the same effect path as the write-back with a word that already had a module, `publish`, which keeps its other job (the reply to a comment under a standing approval). Package PUBLISH-EFFECT; the section "Publishing a post" below.
- **Hidden text is flagged.** An HTML page or a PDF can hold text a person cannot see (white on white, a one-pixel font, `display: none`, the invisible render mode of a PDF) that a model reads. The converter counts it, names the kinds and gives location hints, never the text, and the version's manifest and the catalog say so.

## Why these tools (principle 14)

| Format | Tool | Why |
|---|---|---|
| CSV | the standard library's `csv` | a table is rows of text; nothing to adopt |
| XLSX | `openpyxl` (Debian package, already in the converter's image) | writes a cell as a typed string and sets the quote-prefix style; no model of a spreadsheet to build |
| DOCX | `pandoc` (Debian package) | reads GitHub-flavoured Markdown and writes Word |
| PDF | `pandoc` to HTML, then `WeasyPrint` (installed from `requirements.lock`, wheels only, by hash) | HTML and CSS printed on pages, with the DejaVu fonts, in Python with no JavaScript engine. The Debian package of the same name depends on `python3-cffi`, which pulls a compiler, the Python headers and a numerical stack and makes the image about three times as large (measured: 1.27 GB against 506 MB). The short-video renderer's headless browser is an image built for video frames and lives on another branch; a document needs no browser |

Why a second image and not the converter's: the converter reads a person's hostile file into text; the renderer writes a file from a task's text. They share no tool but pandoc and openpyxl, the renderer needs WeasyPrint and its fonts, and another package's change to the converter's definition (the PPTX path of P4b) must not rebuild or break the renderer. Both are built from the same Debian snapshot and base image.

## Where an output goes

`docs/outputs/` of the project, through `write_file`, which refuses the sources folder. The sources folder holds what people gave the project as immutable versions made by the import; an output written there would be read by a later task as something a person provided (limits L23 and L26). A person who wants an output as a source imports it. A task never replaces a file that is already there unless its arguments say `"replace": true` (the plan shows its arguments, so a plan that replaces a file says so); the project's version control is the history.

## The formula guard (finding S9)

A spreadsheet runs a cell as a formula when its text starts with `=`, `+`, `-` or `@`; a tab and a carriage return are on the usual lists (OWASP's guidance), and so is a line feed here; the four fullwidth forms of `=`, `+`, `-` and `@` (U+FF1D, U+FF0B, U+FF0D, U+FF20) are guarded because some spreadsheets read them as their ASCII twins. The guard looks past leading spaces, no-break spaces, ideographic spaces (U+3000), zero-width characters and byte order marks. A guarded cell is written:

- in a CSV file: with a single quote in front of it, as the guidance says (the file has no cell types, so the quote is part of the text), and in front of every segment of the cell that follows a `;`, a bar or a tab inside it, because a spreadsheet in a locale that separates cells with `;` (pt-BR, de, fr) splits there: `x;=1+1` is written `x;'=1+1`. Every cell is quoted and a row ends with CR LF, so a lone CR or LF is inside the quotes;
- in a workbook: as a text cell (never a formula) with the quote-prefix style, its text unchanged.

A cell that starts with none of them is written as it is, except that in a workbook a plain unsigned number (digits, one decimal point, no leading zero, at most 15 digits) is stored as a number. **A signed number such as `-5` is text on purpose**: the guard does not tell it from `-5+cmd`, and a table of negative amounts is read as text in the workbook and with a quote in the CSV. The cost is real; the person converts the column. Tests: one for each guarded character, in a CSV file and in a workbook (`providers/exporter/tests/test_exporter_inner.py`), and the real workbook read back in the container (`test_exporter_docker.py`).

A Markdown document is cleaned before a writer reads it: a picture becomes its text, a raw HTML or other raw fragment is dropped, a metadata block is text and sets nothing, and a link keeps its address only when it is `http`, `https`, `mailto` or a fragment (a `file:`, `smb:` or `javascript:` address in a document is how a file or a login leaks).

## The write-back

```
step task "write-back"                 person                           code
  prepare: read docs/<file>.md (no credential, <= 256 KiB)
           read the target (documents provider `read`)
           record sha256 of the text it holds
           write effect.json (target id + path + base + content)
  write  : the gate opens an `effect`   ->  sees the content whole, the hash,
           decision, hash = sha256(effect.json)    the target's id and what it replaces
                                             approve --sha256 <hash>  (terminal or page)
                                                                      read effect.json by that hash
                                                                      record the approval (scope action)
                                                                      read the target again: same text?
                                                                      provider `write --confirmed`, once
                                                                      effect_done: decision approved, task done
```

**The hash.** It is the sha256 of the canonical text of the effect document, which holds the target's identifier, the path, the content whole, the content's hash and the base. The target's id is inside it (finding S9): a document aimed at another target has another hash, and the approval of the first covers nothing of the second (`test_a_different_target_is_a_different_hash_and_the_first_approval_covers_nothing_of_it`). The effect file is read only if its bytes have the approved hash, so an edit after the preview stops at the read.

**Refused by structure.** Nothing in the engine or in the kind writes to the platform: the gate has no executor and `prepare` only reads. The one function that writes is `effect_write.execute`, reached from the operation `approve` and nowhere else, and it refuses unless it is given the approval of this document: scope `action`, status `pending-execution`, and a `payload_sha256` equal to the hash of the document it is about to write. `approve` itself refuses an effect from any channel but the terminal and the page (`EFFECT_CHANNELS`), and a word typed into a conversation is no approval. A messaging channel or the MCP mode cannot approve a write.

**Edited since it was read.** The platform's version is rounded and may not move for a small edit, so the guard is the text: just before the write the target is read again, and its text must have the sha256 the task recorded. A different text is `stale` and nothing is written, with two exceptions that the same read tells apart. If the text is exactly what this write would leave (the provider's dry run prints the sha256 of its own round trip of the content), an earlier attempt of this approval landed and its answer was lost: nothing is written again, and the write is recorded as `replayed`. And if the write call itself fails, nobody knows whether the page was replaced (a lost answer; a replace that appended the new blocks and failed before deleting the old ones): the effect says the outcome is unknown and to read the page, stays open, and approving the same hash again reads the page first. A `stale` effect is answered with the reason ("nothing was written by this attempt; the document is not the one the task read: it was edited, or an earlier attempt did not finish"), the approval of that attempt is revoked, the task is ready again and, started, starts over from `prepare`, which reads the page as it is now and opens a new effect with a new hash. A page left half written by a failed replace matches neither text and comes back this way. The person's edit is never overwritten. A text that was changed and put back is not stale. Between the second read and the write is the platform's own gap, the width of a call; the write replaces the whole document and merges nothing (the documents contract), so this is said, not hidden. With `source` the task also compares the page with the converted text of that source's newest version, the version it read, and stops at `prepare` if they differ.

**Once.** After `effect_done` the decision is resolved `approved`, the approval `executed` and the task `done`; a second approval of the same hash is refused (`not open`). The provider's write passes an idempotency key built from the store and the decision, but a write to an existing document ignores it (the key serves creation), so what makes a retry safe is the page read described above: a page that already holds this content is recorded as `replayed`, not written again.

**Any platform.** The effect names the class `integration:documents`, not an implementation: `read` and `write` are two verbs of its contract. A provider that cannot write answers exit 2 and the effect fails with nothing written; the Google Drive provider is sources-only today, so a Drive write-back is a second target added with its own work and tests, and edits none of the modules above.

**The configuration bounds apply.** The documents object's `expires` (the bounds of writing to a platform) is checked when the task prepares and again at the approval.

## A new page, a new table, rows added

Package NOTION-OUT. The weekly report ends as a table the team already uses: a task makes a CSV file (or a workbook) in `docs/outputs/`, and a step task of the kind `output-table` puts it on the platform after the person approves it. The effect word stays `write`; the document says which of four **operations** it is, and the hash covers the operation.

| Operation | Step kind and arguments | Makes | Read again just before the write |
|---|---|---|---|
| `update_page` | `write-back` (above) | replaces a page's text | the page's text |
| `create_page` | `output-page`: `parent`, `title`, `content` (a Markdown file) | a page under the parent | the parent: it exists and is not in the trash |
| `create_table` | `output-table`: `parent`, `title`, `rows` (a CSV file or a workbook), optional `columns` | a database with one data source under the parent, its columns, and the rows | the parent |
| `append_rows` | `output-table`: `table` (a data source id), `rows`, optional `columns` | the rows, added to the table's end | the table's columns (hashed), its row count and the time of its newest edit |

**Why two new kinds and not `write-back`.** A write-back replaces text, and its arguments, checks and preview are about that. A page made, a table made and rows added each have arguments of their own; a kind per shape keeps each closed. The names carry no product (`output-page`, `output-table`); Notion is the provider behind them.

**The hash.** The effect document has exactly these keys (`runtime/output_document.py`): `effect` (`write`), `operation`, `task`, `store` (the first 12 hex characters of the sha256 of the project's store path: task numbers start again in every project and the provider's ledger is one file for the person), `cycle` (the task's cycle: it advances when a decision was answered because the table had changed), `provider`, `target` (`{id, path}`: the parent page or the table's data source, and the project file the content came from), `target_name` (the name the platform gave the parent or the table when it was read), `title` (null for rows added), `base` (`{schema_sha256, row_count, version, rows_done}`: the table's columns hashed, its row count, the time of its newest edit, and how many of these rows an earlier approval of the same task already wrote; four nulls for a new page or table), `content` (the Markdown, or `{columns: [{name, type}], rows: [[...]]}`), `content_sha256`, `bytes`, `idempotency_key`, `notes` (how each column's type was settled) and `remarks` (what is true of the table as a whole). The hash is the sha256 of the canonical text of that document. A different operation, parent or table, name, title, file, column name, column type, cell, base, note, remark, cycle or key is another hash, and the approval of the first covers nothing of it (`test_a_changed_parent_title_column_type_cell_or_operation_is_another_hash_and_the_old_approval_covers_nothing`). The P8 write-back document gained the `operation` key (`update_page`), so its hash covers it too.

**The preview.** A page is shown whole. A table is shown as the parent or the table with the name the platform gave it next to its id, the title, the file, the hash and the command that approves; the columns with their types and how each was settled (`given`, `inferred: ...`, `text, ambiguous: ...`, `the table's`); the row count; the first 20 rows and, for a longer table, the last 3 (a cell longer than 60 characters is cut in the preview and written whole); and, under "Read before approving", the remarks: the sheet of a workbook that was read and the hidden sheets before it, the number of cells that hold a formula with no stored value (they are empty here), and the select options the platform will ADD to the person's table (a value that is none of the options the table has). The hash covers every row. For rows added, it also shows the base the table had when it was read (row count, hash of the columns, newest edit), says that the columns of the rows must be columns of the table, and, when an earlier approval of the same task wrote some of these rows, says "N of these M rows are ALREADY in the table" and that approving sends only the others.

**The column rule** (`runtime/table_data.py`; nothing is guessed silently, an ambiguous column is text and the preview says so):

- *title*: the column `columns` names as a title; with none named, the first column. Exactly one column is the title; every row needs a title.
- *checkbox*: every cell is `true` or `false` (any case) and none is empty. A column with a gap is not inferred as a checkbox (an empty cell would become `false`, which is a guess); naming the type in `columns` makes the gap unchecked, and the note says so.
- *number*: every non-empty cell is a plain number: an optional minus sign, digits with no leading zero, an optional decimal part, at most 15 digits. `007`, `1,200`, `1e3`, `50%`, a phone number or a zip code is text.
- *date*: every non-empty cell is an ISO 8601 date, or a date-time **with its Z or offset**, and a real calendar day. A date-time with no zone is not a date (the platform would read it in a zone of its own): the column is text and the note says so, and a column named as a date stops the step (`cell_not_type`). A workbook's date-and-time cells have no zone, so they land here too; add the offset in the sheet or in the CSV file.
- *url*: every non-empty cell starts with `http://` or `https://` and has no space.
- *rich_text*: everything else, and a column with no cell. "Ambiguous" in the note means some cells fit a type above and others do not.
- *select*: never inferred; only `columns` makes one. Its options are the values that occur (at most 100, each at most 100 characters, no comma).

A type given in `columns` is checked against every cell; a cell that does not fit stops the step (`cell_not_type`), it is never turned into something else. For rows added, the table's own types decide: a column of the file must be a column of the table, in one of these seven types, and the table's title column must be among them (`column_not_in_table`, `column_type_differs`, `column_type_unsupported`, `title_missing`). Cells are stripped of the space around them; an empty cell is nothing. A cell that starts with `=` is text for the platform, which never evaluates it (the formula guard is about files a spreadsheet opens).

**Reading a workbook.** The first sheet that is not hidden, with the standard library (`zipfile`, `ElementTree`): shared and inline strings, numbers, booleans, dates by their cell format (the 1900 and 1904 systems), the cached value of a formula (a formula with no cached value is empty and counted in a remark); a row that stops short has empty cells after it. Refused: a part with an entity declaration or a DOCTYPE, found in the bytes, and a part with a NUL byte, which is how a UTF-16 part would hide one (`xlsx_unsafe`); more than 200 parts, a part over 16 MiB, a ratio of expansion over 200 (`xlsx_unsafe`); a file that is not a workbook, a damaged or encrypted part, a compression `zipfile` does not read, a bad string index, an error cell, no visible sheet (`xlsx_unreadable`); a cell with a value beyond column 30 (`too_many_columns`). A cell with a value and no reference (`r`) is refused, and a cell with no value says how far to the right it is and is ignored, and no list is built from a column index that is not below 30. Verified against workbooks built by hand and against one made by `openpyxl`; not against a workbook an office program saved.

**The caps, and why.** At most **500 rows** and **30 columns** a table operation (one call a row at 2.8 calls a second takes about three minutes, which the 900 s limit of the long verbs covers with room for rate-limit waits); **2,000 UTF-16 code units** a cell (the service's limit for one text object is "2,000 characters" in its reference, which does not say in which unit; code units are the larger count, so what fits is safe; nothing is split); **100** characters a column name; **1 MiB** for the table as the effect document holds it, **1 MiB** for a CSV file and **2 MiB** for a workbook; a table of more than **2,000 rows** takes no rows added (the guard counts rows by listing them: 21 calls at most). A longer file is split by the person into files of 500 rows; each is approved on its own. The provider checks the same numbers again (`providers/documents/notion_tables.py`), and a test holds both sets equal. A page's Markdown is converted by the documents provider's block writer, unchanged by this package. Closed reasons: `too_many_rows`, `too_many_columns`, `cell_too_long`, `table_too_large`, `table_empty`, `table_ragged`, `columns_bad`, `title_empty`, `title_count`, `column_unknown`, `cell_not_type`, `too_many_options`, `table_not_text`, `rows_missing`, `rows_too_large`, `xlsx_unreadable`, `xlsx_unsafe`, `content_refused` (a credential in the content).

**Idempotency.** The key is the document's own, derived from the task, the cycle, the operation, the target, the title, the content's hash and the base, so the same document is written once however many decisions reach it. The provider's ledger records it before the call and marks it done after it:

- a page or a database: one entry under its parent. Done: the next run finds it and writes nothing. A page made but not finished (the body failed halfway) is finished on the same page. An entry whose outcome is unknown (a lost answer, a 5xx) is looked for among the parent's children (exactly one with the title, made since the attempt began and claimed by no entry): found, it is adopted; not found, the key stays pending until the person runs `resolve`, because a listing can lag behind a write and a second database is worse than a question. A page or a database that the person put in the trash since is not the one the key made, and it is made again (it is not called replayed).
- a row: one entry under the data source, `<key>/row-<n>`, with the hash of its values and the task's scope (`task-<id>`). A row done is skipped. A row whose outcome is unknown is looked for in the table: a row made since the attempt began that holds exactly its values (dates compared as dates, date-times as moments: the service writes `Z` back as `+00:00` and adds milliseconds) and that NO entry of the ledger claims, under any key; found, it is adopted, else written. **Residual risk, stated:** if the platform's listing lags and the row is there but not yet listed, it is written a second time. The row key lives in the ledger on the machine, not in a property of the table, because a column added to a person's table would be an unapproved change.
- **The scope is what makes a task that starts over safe.** When the table changed after some rows were written, the task starts over with a new cycle and so a new key. The provider finds, by the scope and the hash of each row's values, the rows the earlier key wrote, moves their entries under the new key and does not send them again; `prepare` counts them (`rows-state`, a read of the ledger) and the preview says how many. A row of the new file that matches none of them is written.
- **The ledger is trusted only as far as the table bears it out.** A row counts as done, in the preview, in the stale answer and in what is skipped, only if the page it made is among the rows the table lists now (`rows-state`, `table-read`: at most 2,000 rows; a table with more rows than the listing reads is refused, not guessed at). A row a person trashed is a row to write again.
- **The scope and the key carry the project.** `s<store>-task-<id>`: two projects have a task 1 each and one ledger file, and neither finds the other's rows.
- A done entry of these verbs older than **90 days** is dropped when the ledger is next saved, unless its key still has an entry of unknown outcome (pending): then none of that key's entries is dropped, so a row done is not written again because its neighbour is still in doubt. The runtime refuses to approve an output decision older than 90 days (it says so and asks to reject it and start the task again): the ledger could have forgotten its key. A pending entry, a page made by `write` and an entry recorded by `resolve` are kept.
- **The task (or the key) is locked while it is written.** The provider takes an exclusive lock for the life of a write: on the scope of the task when the call gives one (`scope/<scope>`), else on the key under its target (a file next to the ledger, removed with the lock). A provider that outlives a killed runtime therefore cannot run beside the next run of the same task, even under a new key (the task started over after the table changed); the second is refused after 2 seconds. Another task is not held back.

**A lost answer and a failure after some rows: what the check compares, exactly.** A call that fails after the first write call is `unknown` for all three operations: the decision stays open, and approving the same hash again reads what is there and writes only what is missing, recording `replayed` when nothing new was written. For rows added `rows-state` (with the key and the scope) says how many rows of this document the ledger holds as done AND the table still lists (`rows_done`, those of an earlier approval included) and how many are of unknown outcome (`rows_pending`); `base.rows_done` is how many the task counted when it read. Then:

1. every row done: nothing is compared and nothing is written; the result says `replayed`;
2. the table's columns (hashed) must be the ones the task read, else `stale`; and `rows_done` must not be fewer than `base.rows_done` (rows the task counted are no longer in the table, or the ledger lost them), else `stale` and nothing is sent;
3. `written` = `rows_done` now minus `base.rows_done`: the rows this document's own attempts wrote. With `written` and `rows_pending` both zero, the row count and the time of the newest edit must be exactly the ones the task read, else `stale`;
4. otherwise the row count must be `base.row_count + written`, up to `rows_pending` more (a row of unknown outcome may or may not have landed), else `stale`. The time of the newest edit is not compared (this document's own rows move it). **The gap, stated:** while a row of unknown outcome is pending, one row a person adds in the same window is not told from it, so the count is allowed to be one higher.

A row the platform refuses (a 4xx) is released and named in the message; it fails again until the file is corrected, and the person rejects the decision and starts over.

**Stale.** A table whose columns, row count or newest edit are not what the task read (a row added, removed or edited, a column added) answers the decision with the reason, writes nothing more, revokes the approval of that attempt and sends the task back to `prepare`, which reads the table as it is and opens a new decision with a new hash. If an earlier attempt of the same task had already written rows, the answer says so ("this attempt wrote nothing more, but an earlier attempt already wrote N row(s) into the table and they stay there") and never "nothing was written"; the new preview counts them.

**The write lock.** A write of one page takes a call, and a write-back still holds the project's write lock for it. An output can take minutes, so it is not made holding that lock, which a sync of the documents and the return of a run wait for (`runtime/ops_step_effects.py`). The write lock is taken ONLY for the record at the end (the stale answer, or the resolution of the decision); the reads, the approval row and the remote write take none. What keeps a second writer out is the lock of the decision (`output-<pending id>.lock`, taken first and removed with the lock: a second approval of the same decision is refused, not queued, and so is a reject or an answer of it, with "being written; wait for the write to finish"), the effect lock of the request that `approve` already holds, the provider's lock of the key, and the provider's ledger.

**Cancelling the request during a write.** Cancel is a brake and stays available. `runtime/ops_cancel.py` `request_cancel` is the one function the four ways of cancelling a request call (`ops.cancel`, `board._take_state`, the direct reply in `ops_say._say_route`, `ops_routines._close_stops`). It takes, without waiting, the lock of every open effect decision of the request; a decision whose lock is held is one being written, and it is passed to `store.request_cancel(keep=...)`, which cancels everything else and leaves that decision and its task alone. The locks it took are kept until the cancel is done, so an approval cannot begin between the look and the cancel. An approval that meets one of those locks, or the lock of a write, is refused with "is being cancelled with its request or written by another approval; wait for that to end, then approve it again if it is still open". When the write ends it records (`effect_done`) as usual: the decision is `approved`, the task `done`, the state row written, and the request, cancelled meanwhile, stays cancelled. If the write fails with an unknown outcome the decision stays open and can be approved again or rejected.

**The record of a write that landed** waits for the project's files for as long as it takes (`wait=None`) instead of the usual 60 seconds, so that a busy writer cannot leave the decision open after the table was made.

**The rate and the retry.** The provider keeps to 2.8 calls a second (a pause of 0.35 s between two calls), under the 3 a second of a workspace that is not on a Business or Enterprise plan, and retries a 429 and a 529 up to four times, waiting the `Retry-After` the service names (at most 60 s). A 429 is a request the service did not carry out; after the retries it fails and the row is of unknown outcome, found by the rule above on the next run.

**Which token.** The write token is `NOTION_TOKEN`, the documents mirror's. `NOTION_SOURCES_TOKEN` (the read-only integration of sources) is never used by these verbs (`test_the_token_that_writes_is_notion_token_and_the_sources_token_is_never_used`).

**Limits.** L30 and L31 hold unchanged for the new operations: `runtime/step_output.py` imports only `output_document`, `steps`, `table_data` and `write_document`, holds no write verb, and reaches the platform only through `ctx.services`, where `documents` gained four reads (`stat` with a name, `table-read`, `rows-state`); the one function that writes is still `effect_write.execute`; the approval comes from the terminal or the page only; L31's row lists the new tests. No new limit was needed.

## Sending an e-mail

```
step task "send-email"                 person                           code
  prepare: check To/Cc/Bcc (plain addresses, at most 20 in all, none twice),
           the subject (one line, <= 200), the text (<= 100 KB, no credential)
           read each attachment (a file under docs/, no link, not the sources folder, <= 18 MB together)
           the sender is the `from` of the project's `outbox`
           the provider's dry run (no connection, no credential): what it would send
           write effect.json (sender, recipients, text, attachments by hash, key, Message-ID, dry-run hash)
  send (gate): opens an `effect` decision      ->  reads sender, every recipient, subject, text
               the hash covers all of it            approve --sha256 <hash>  (terminal or page)
                                                                         ->  execute: read each attachment again, compare its
                                                                             sha256 (changed: stale, nothing sent, start over),
                                                                             dry run must hash to the document's, then
                                                                             `send --confirmed` once; record
```

**The document** (`runtime/send_document.py`): `effect`, `task`, `provider`, `from`, `to`, `cc`, `bcc`, `subject`, `body`, `body_sha256`, `in_reply_to`, `attachments` (path, name, media type, size, sha256), `message_id`, `idempotency_key`, `dry_run_sha256`. The key is `send-` and 32 hex digits of the sha256 of the task, the sender, the recipients, the subject, the text, the reply and the attachments (name and hash); the Message-ID `<oh.<32 hex>@domain>` derives from it. So the recipients are inside the hash: an approval of one e-mail covers no other recipient, and an e-mail is sent once however many decisions reach it. The date and the MIME boundaries are not content: the provider makes them.

**What the person sees** (`body(doc, digest)`): the sender, To, Cc and Bcc first (so that a long text cannot hide a recipient), the subject, the reply, the number of recipients, the text exactly, one line per attachment (name, size, sha256, path), the hash and the command that approves it. The Bcc is shown to the approver and hidden from the others.

**The configuration.** `outbox` in `docs/workbench/runtime.json`: `{"provider": "auto" | "<implementation>", "from": "<address>"}`, accepted with `accept-config`. There is no list of allowed recipients (the person approves the exact recipients of each e-mail by its hash) and a cap of 20 recipients in all is code. One outbox account per machine: the provider holds the account (`setup`), and another `from` is refused. At the approval `preflight` checks that the outbox still names the document's sender and resolves to the document's provider.

**What the message says is what was approved.** A mail library decodes some texts into more than they say (an RFC 2047 encoded word in a subject or an address), so `=?` is refused in the subject, every address and the reply id, a lone `\r` in the text is written `\n` when the task is planned (the hash and the message then agree), a non-ASCII domain must be given as `xn--`, and the provider builds the message and reads it back before the dry run and before the send: the headers, the text and the attachments must be exactly the document's, else nothing is sent. The dry run's hash covers that reading.

**Refused by structure.** The gate has no executor and `prepare` only asks for a dry run: `ctx.services.outbox` has `enabled`, `sender`, `provider` and `dry_run` and no way to send (`runtime/ops_step_seams.py`; a test holds the names and that the file holds no `--confirmed`). The one function that sends is `effect_send.execute`, reached only from the operation `approve`, under the lock of the decision (every send is `is_long`): a reject or an answer of the decision is refused while it runs, and the project's write lock is not held while the e-mail is sent. `POLICY` is false and the word is a STEP kind, so no standing approval can name it (`ops._bounds_words`). Limit L42.

**Results.** `sent`; `replayed` (the key was done already, or the provider found the message in the Sent folder after an earlier attempt lost its answer: nothing was sent again); `unknown` (the provider's exit 4 or a timeout: the e-mail may or may not have been sent; the decision stays open, and approving it again meets the provider's ledger, which looks in the Sent folder first); a refusal with nothing sent (exit 1 of the provider guarantees it; one refused recipient is all-or-nothing); `stale` (an attachment is not the file the task read: the decision is answered, the approval revoked, the task starts over from `prepare`).

**Where it can be approved.** In the terminal and on the page (`operations.EFFECT_CHANNELS`). A messaging app may approve it only when the project's accepted policy grants the group `approve-effect-send` (decision POL-1, limit L44; the name is `effect_send.APPROVAL_GROUP`), from a card that carried the whole text, and an e-mail with an attachment is never whole on a messaging card: `effect_send.on_cards(doc)` is false, because the card cannot carry the file the hash covers.

**What code cannot enforce, and the live checks.** What a server does with a message once it said 250 (the host's); whether the host files a copy in the Sent folder, which `lookup` depends on; the size the host accepts (the cap is 18 MB of attachments, about 24 MB after encoding). To verify on first use: [providers/mailer/README.md](../../../providers/mailer/README.md).

## Publishing a post

```
step task "publish-post"                   person                           code
  prepare: read the content file (docs/marketing/content/<name>.md; no link, not the sources folder);
           refuse a post whose Status line says blocked
           the publisher's check: ready, a token not past its expiry
           skills/mkt-publish/scripts/payload.py build (unedited, isolated, no --publisher): the text, the
             first comment, the one image, the key (the file's name), the platform's limits
           the provider's dry run of those files (no token read, no request): what it would send, and what its
             ledger holds under the key: published or pending is refused here
           write effect.json (platform, slot, text, comment, image by hash, the ledger, the dry run, the key)
  publish (gate): opens an `effect` decision   ->  reads the platform, "published NOW, not at <slot>", the
                the hash covers all of it            post and the first comment whole, the image by hash,
                                                     the dry run;  approve --sha256 <hash>  (terminal or page)
                                                                         ->  execute: build the post again, in a private
                                                                             folder; another text, comment, image, slot or
                                                                             key is stale (nothing published, start over);
                                                                             the dry run (and the ledger) must equal the document's;
                                                                             `publish --confirmed` once; record
```

**Why the skill's script and not a second reader.** `payload.py` decides what a post is and what a platform takes, and it is the script the publishing skill's own scheduled job is built from. `runtime/publish_payload.py` runs it as the reply runs `mkt-engage`'s gate (`runtime/isolated.py`: the interpreter's isolated mode, an environment of five names, the project as the working folder) with no `--publisher`, so no job is written and nothing is scheduled. The files the publisher is given are the files the script wrote, so the publisher's ledger sees the bytes the skill would have given it. The fields of `payload.py` that the runtime reads are pinned by a test (`test_the_fields_of_payload_py_that_the_runtime_reads_are_where_it_expects_them`): a later change to the script that moves one fails there and not in a live publication. The image must be a plain relative path of the project whose file, opened with no link on the way, has the hash of the copy the script made; a path outside the project, a link or a file changed meanwhile is refused.

**The key, and how a post is never published twice.** The key is the content file's name without `.md`, the skill's own. The publisher's ledger holds a key for one content and publishes it once: the same key with the same files is a `replayed` answer, the same key with other content is refused, a key left `pending` by an unknown outcome blocks every attempt. So whichever path runs first wins and the other cannot publish: a post the skill's job already published is refused at the preview (`already_published`, read from the dry run's `existing_status`) and replayed at the approval if it went out in between; a job that is scheduled and has not run has written nothing to the ledger, so it cannot be seen, and a post published here first is replayed when that job runs. A post published here is replayed when the skill's job runs. The ledger is the provider's, in its data folder; the runtime starts the provider with the minimum environment plus `XDG_DATA_HOME` (`runtime/publish_payload.py` `PASSES`), so a person whose data folder is not under their home has one ledger for the terminal and for this path. The ledger's path, as the dry run prints it, is in the document (so in the hash and on the card), and a ledger that could differ is refused at the preview and again at the approval: the dry run must print the document's ledger; the same dry run made with the person's own variables named `PUBLISHER_<PLATFORM>_LEDGER` must print the same file; and no scheduled job for the key (the scheduler's `list`, read with the `SCHEDULER_HOME` of the person's environment for the key and a `--ledger`, as the vote job pins one from the tick's environment) may be pinned to another file. A scheduler that is not configured has no jobs; one that fails, times out or answers something else than a list is a refusal, because a pinned job could be in it.

**Immediate only.** The call carries no `--at` and no `--ledger`. The slot the content file names is shown ("published NOW, when you approve, and not at its slot") and is part of the hash; scheduling stays the publishing skill's. One post per decision, which is the skill's `action` scope.

**What the person sees** (`body(doc, digest)`): the platform and that the post goes out now, the content file and the key, the token's expiry, the content file's own check line (the drafting step's words, decided on by nobody), the post exactly, the first comment exactly, the image by name, size, hash and source, the ledger's path, the provider's dry run as it is hashed, the hash and the command that approves it. A post whose `- Status:` line says blocked opens no effect.

**Where it can be approved.** In the terminal and on the page (`operations.EFFECT_CHANNELS`). A messaging app may approve it only when the project's accepted policy grants the group `approve-effect-publish` (decision POL-1, limit L44; the name is `effect_publish.APPROVAL_GROUP`), from a card that carried the whole text, and a post with an image is never whole on a messaging card: `effect_publish.on_cards(doc)` is false, because the card cannot carry the file the hash covers.

**One word, two paths.** `effects.KINDS["publish"]` is the facade `runtime/effect_publish.py`. It re-exports the names of `runtime/effect_reply.py` as they are (`POLICY`, `PROVIDER_CLASS`, `policy_platform`, `policy_effect`, `policy_argv`, `resolve_targets`, `policy_judgement`), so a reply under a standing approval is checked and executed as before, and adds the step path's names; `describe` answers for both documents (a post's has the key `operation`). A word that is both a STEP kind and a POLICY kind stays in the words a standing approval's bounds may name (`effects.step_only_words`): a bound can cover the reply to a comment on a post the project published, and no bound can name a post, which is approved by its own hash each time. `GATE` stays false: a skill that declares `publish` still opens a review at its gate, as before.

**Results.** `published`; `replayed` (the ledger held this key with this content already: nothing was published again); `unknown` (a timeout, or a failure after which the ledger holds the key `pending` or cannot be read: the decision stays open; approving again meets the ledger, and a pending key stays blocked for this path and for the skill's job until the person looks at the profile and settles it with the provider's `resolve`); a failure after which the ledger holds the key as `published` (the post is out and its first comment failed: approving again replays the post and retries only the comment; or the key holds another post: nothing was published by this attempt); a refusal with nothing published (the ledger holds nothing afterwards; the decision stays open); `stale` (the post is not the one the task read: the decision is answered, the approval revoked, the task starts over from `prepare`).

**Refused by structure.** The gate has no executor and `prepare` only asks for a dry run: `ctx.services.publisher` has `provider`, `check` and `preview` and no way to publish (`runtime/ops_step_seams.py`; a test holds the names and that the file holds no `--confirmed`). The step module imports only `publish_document` and `steps`, and holds none of the flags that publish. The one function that publishes is `effect_publish.execute`, reached only from the operation `approve`, under the lock of the decision (every publication is `is_long`). Limit L43.

**What code cannot enforce, and the live checks.** What the platform does with a post once it answered; that the skill's scheduled job and this path see one ledger (a scheduler that runs the job with another data folder has another one); how the platform renders what the dry run printed. To verify on first use: [providers/publisher/README.md](../../../providers/publisher/README.md).

**The document** (`runtime/calendar_document.py`): `effect`, `task`, `account` (`google` or `microsoft`), `implementation` (`google-calendar` or `outlook-calendar`), `address`, `calendar` (the project's name) and `calendar_id`, `operation` (`create`, `change`, `cancel`), `event_id` and `base_etag` (the version read: Google's etag, Graph's changeKey), `read_at`, `zone`, `send_updates` (always `none`), `event` (as it will be), `before` (as it was read), `changed`, `idempotency_key` (`cal-` and 32 hex digits of the whole content) and `dry_run_sha256`. An event is title, all-day or not, wall times in the zone, the instants the request carries, place, reminder in minutes and notes. Nobody is invited and no recurrence is made; a meeting or a series is not changed.

**The request.** A create is one POST; a change is one PATCH of the changed parts, with `If-Match: <etag>` on Google and, on Outlook, a read of the event and a comparison of its changeKey right before the PATCH (Graph documents no If-Match); a removal is one DELETE with `If-Match` on Google, which sends the event to the calendar's trash for 30 days. Every write sends `sendUpdates=none`. The Outlook writer has no removal (Microsoft does not say where a removed event goes; it stays off until a live check). The title, the place and the notes travel to the writer in a private file (0600, removed at once), never on a command line, and are not in the state file's approval row (`describe`).

**Refused by structure.** The gate has no executor and `prepare` reaches the calendar only through `ctx.services.calendar_read`, which has `event_get` (the one read, with the account's token), `dry_run` (a write verb with `--dry-run` and no credential) and no way to write (`runtime/ops_step_seams.py`; limit L58). The one function that writes is `effect_calendar.execute`, reached only from the operation `approve` under the lock of the decision (`is_long`). `POLICY` is false and the word is a STEP kind, so no standing approval can name it (`ops._bounds_words`). `preflight` re-reads `accounts` at the approval: a calendar taken out of the file, or renamed to another id, writes nothing (limit L55). Limit L56 is the version: the event is read again at the approval and another version is `stale` (the decision is answered, the approval revoked, the task starts over from `prepare`).

**Results.** `done`; `replayed` (the writer's ledger held the key, or the writer found the event in the calendar after an earlier attempt lost its answer: nothing was written again); `unknown` (the writer's exit 4 or a timeout: the change may or may not have landed; the decision stays open, and approving it again looks in the calendar first); a refusal with nothing written (exit 1 guarantees it); `stale`.

**Where it can be approved.** In the terminal and on the page. A messaging app may approve it only when the project's accepted policy grants the group `approve-effect-calendar` (`effect_calendar.APPROVAL_GROUP`), from a card that carried the whole event (`on_cards` is always true: the card is the whole change), and a sender may ask for one only with the group `calendar-write`; both are in no default policy and need `accept-config --widen`. The card is said line by line in the project's language (the keys `CARD_CAL_*`); the hash is the same in every language.

**What code cannot enforce, and the live checks.** What the service does after it answered; the gap between the writer's read and its PATCH on Outlook; whether Graph keeps the extended property the lookup after a lost answer depends on. To verify on first use: [providers/writer/README.md](../../../providers/writer/README.md).

## The rule that a review is harmless to pass

A stop of a step task passes on the word `continue` from any channel, including a messaging app. So no step performs an external effect itself, before a stop or after one, and every external effect goes through a gate, whose approval is the hash of the exact content from the terminal or the page. What is **code**, and what is a **test**:

- Code: `steps.register` refuses a kind that declares an `effectful` step, whatever its place and whether or not the kind starts on its own. A step kind is handed its services through `ctx.services` (`runtime/ops_step_seams.py`): `documents` has `read` and `stat` and no way to write (its two verbs are literals), `effect_files` writes and reads the effect document and does not execute it, `render` makes a file from a text. The document of a write-back and its preview are in `runtime/write_document.py`, which holds no function that calls a provider; the one function that writes to a platform is `effect_write.execute`, which only the operation `approve` reaches, and which refuses unless given the approval of exactly the document it writes. So a step kind has no function in reach that could write.
- Test, not code: Python cannot stop a module from importing another. A static test over `runtime/step_*.py` (`runtime/tests/test_steps_gate.py`) holds each step module to a row of the modules it may import (none that calls a provider: not `documents`, `board`, `effects`, the operations layer or `project_config`), and fails on `--confirmed`, `--dry-run`, `.execute`, a network module of the standard library. It is a tripwire; a new kind is reviewed for what it imports, and adding one to the table is a visible change. `step_ingest` is the one kind with a wider row (it imports a source through the operations of the sources).

A standing approval cannot name the word `write`, the word `send` or the word `calendar` either (`ops._bounds_words`): each write-back, each e-mail and each change to a calendar is approved by its own hash. The word `publish` is a STEP kind and a POLICY kind at once, so its bounds stay: they cover the reply to a comment, never a post, which is approved by its own hash each time.

| `display_none`, `visibility_hidden`, `hidden_attribute` | HTML | the element and what is under it are not shown. Text in a `<title>` outside the head, and the rest of a page after a `<title>` that is never closed (a browser reads it all as the title), is `display_none` too: a browser never shows a title, and a converter reads the tags |
| `zero_size`, `tiny_text` | HTML, PDF | a font of 0, or under 2px in HTML and 2pt or less in a PDF; a box of 1px or less with overflow hidden or a clip |
| `off_page` | HTML | a position or a text-indent 500px or more off the page |
| `transparent` | HTML | opacity 0 or a transparent text colour |
| `white_on_white`, `color_matched` | HTML, PDF | a text colour with a contrast ratio under 1.1 against its background (the page's default white when none is set) |
| `invisible_text` | PDF | text in the invisible render mode: it appears only when poppler's `pdftohtml` is told to show hidden text |

The record is `{"examined": true, "count": n, "kinds": {kind: n}, "hints": ["display_none in div element 11", "white_on_white on page 1 count 1"]}`; a hint names a kind and a place (an element's number in the document, a page), never the text. The host keeps only words of the closed list, bounded numbers and hints of lower-case letters, digits and a few signs, so a container cannot use the flag to carry text (`runtime/sources.py` `hidden_text_record`). `null` means not examined (a Word document, a spreadsheet, a CSV, plain text, a Notion page, a Markdown export); `{"examined": false}` means the check could not be made, and the catalog says so; an HTML page or a PDF whose converter gave no record the host can read is `{"examined": false}` too, never "none found". The count stops at 2000 hidden elements and the record then carries `capped: true` (the catalog says "at least"). A hint is at most 80 characters (its tag name is cut at 20 and reduced to letters, digits and hyphens) and the whole `info.json` is kept whole JSON under its cap, dropping the hints first.

**What it does not find**, because the person should not read "none found" as "none there": text under a picture or a drawn shape (a PDF's gray text on a gray rectangle is not seen); a colour match against a background that a style sheet outside the page, a selector with a combinator, a pseudo-class or an attribute, or a rule inside `@media` sets; text drawn as paths or as an image; the alt or title text of a hidden element; text a script moves or writes; hidden text of a Word document (`w:vanish`), a spreadsheet or a presentation; and, in a PDF, off-page text, which `pdftotext` does not extract and so no model reads. **A false positive on purpose:** a scanned PDF with a recognised-text layer is flagged `invisible_text`, because the person sees the picture and the model reads the layer.

## Known limits and improvements

- A calendar change (W1) has no attendee, no recurrence, no conferencing link, no attachment and no clearing of a reminder; a meeting, a series and an event someone else organizes are refused; removing an Outlook event is off. Nothing was run against a real Google or Microsoft calendar: the writers are tested against stand-ins on loopback, and the live checks are listed in `providers/writer/README.md`.
- Drive write-back is not built (P7's provider is sources-only). D17's real cases, one for each direction, are chosen with the maintainer: everything here is tested on fictional fixtures and the Notion provider's stand-in service, and nothing was run against a real workspace. That includes the outputs of this page: the endpoints for a database, a data source, a page under a data source and the child listing were read in the public reference (`providers/documents/README.md`, "Calls the outputs make") and not measured live.
- A table is one data source: a database with several data sources, a relation, a rollup, a formula, a status, a people or a multi-select property are not made or filled (rows added to a table that has such a column leave it empty; a file column that maps to one is refused). A row's cells carry no rich formatting.
- The kinds are started with `run-step`, or by a flow that holds them as tasks with `step` and `args`.
- A signed number in a table is text (above). A Markdown table cannot be the input of a workbook: the task writes a CSV.
- The renderer's PDF uses fonts of the image (DejaVu); a script they do not cover (for example Chinese) comes out as boxes.
- The renderer's image is about 500 MB and is built once by a step the person starts; the lock of WeasyPrint's wheels is refreshed by hand.
- An e-mail is sent from the plain text the task prepared: no HTML, no inline image, no threading beyond `in_reply_to`, no read of the replies (that is the e-mail channel's, a later package). A recipient is a plain address. Starting an e-mail from a phone needs the router to route it (a later package, EMAIL-ROUTE); today it is started in the terminal or on the page.
- A post is published from the one file the publishing skill's script builds: no scheduling (the skill's), no second post in a decision, no edit of the text in the approval (change the content file and start again), no read of how the post did. The first comment is the provider's: it may fail after the post is out, and approving again retries only the comment. Starting a post from a phone needs the router to route it (a later package); today it is started in the terminal or on the page.
- A write-back replaces the whole document; there is no merge and no diff against the page beyond the hash. A person who wants to see what changes compares the preview with the page.
