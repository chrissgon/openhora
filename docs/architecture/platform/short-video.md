# A feature across layers: the short video

Part of [the platform map](README.md). This page has the eight sections of a layer page, in the same order, and it is not a layer: it follows one feature (a recording and a script become a vertical video) through the providers, the shared presets and the checks. The layer that holds the code is [providers.md](providers.md).

## Purpose

Two classes make a short video, and both are used by the task runtime alone: no skill requires them (decision VD2 of [the V0 decision](../../decisions/2026-11-07-v0-short-video-hyperframes.md)), so [contracts/environment.md](../../../contracts/environment.md) does not list them. `providers/resolve.py` knows both as roles (`ROLES`).

- **`transcriber:speech`** (`providers/transcriber/whispercpp.py`). Takes an audio or video file, a pinned model name and a language, and writes a transcript, word by word with times (`transcript.schema.json`). It runs whisper.cpp in a container on the person's machine; the audio never leaves it and no model of any provider sees it. It returns counts on stdout, never words.
- **`renderer:video`** (`providers/renderer/ffmpeg.py`, the default engine, and `providers/renderer/hyperframes.py`, the second). Takes a recording, a transcript, a post with a script block and a platform file, and returns a 1080x1920 H.264 + AAC video, a cover frame or a still frame of a recording. No model is involved: the edit list is built by code from the transcript, the beats come from the post's script block, a pinned headless browser draws the overlays frame by frame, and ffmpeg cuts and composes. A second engine, HyperFrames (`providers/renderer/hyperframes.py`, V3a), sits behind the same class (VD1); since V4 `CLASS_DEFAULTS` makes it the default engine, and a project names `ffmpeg` with `media.renderer` in `docs/workbench/runtime.json`. V3a renders the cuts and the zoom (`render --base-only`); V3b-1 adds the composition of captions and beats (`render` without it), which draws only the blocks of `blocks/engines/hyperframes.json` and, until V3b-2's gates exist, only from a test blocks folder.

Everything that reads a recording, a transcript or a post runs inside a container (VD4), through `providers/_container.py`: no network, a read-only root, every capability dropped, no host environment, an image run by the id the build recorded.

## Abstractions

**The common part and the drawing part.** The renderer's modules fall in four kinds, and the kind says what a module may import.

| Kind | Modules |
|---|---|
| Common (no browser, used by every engine) | `_align`, `_edl`, `_media`, `_redact`, `_text`, `_timeline`, `_vocab`, `_layout`, `_assets`, `_output`, `_blocks`, `_hf_page`, `_hf_compose`, `_gsap_lint`, `_payload` |
| Drawing (the ffmpeg engine's own: the browser, the frames, the storyboard) | `_cdp`, `_frames`, `_lint`, `_render`, `_preview`; the host's `_browser` |
| Host (not in the image) | `_docker`, `_image`, `_host`, `ffmpeg.py`, `hyperframes.py` |
| Inner (the container's entry point) | `_inner.py`: imports only common modules at the top; `render`, `storyboard` and `selfcheck` import the drawing modules inside their own functions |

What the three newest common modules hold: `_layout` is the arithmetic of where a thing may be drawn (`zones`, `face_hit`, `caption_hit`); `_assets` is what is served to a page (`font_allowlist`, `load_fonts`, `load_assets`, `read_regular`); `_output` is how a result is stored (`read_platform`, `make_cover`, `make_still`, `png_size`, `write_once`). An old module imports each moved name back, so a caller and a test still find it where it was. A second engine imports the common modules and `_host.add_common_parsers` and never `_frames`, `_cdp`, `_render` or `_preview`. `_blocks` is the catalogue: the blocks, the engine that may draw each, and the check of a block's parameters.

**The host and the inner side.** The host (`_host.py`, with `_docker.py`) checks the flags, stages the inputs into a private job folder (`Job`), builds the `docker run` command, runs it and reads the result as untrusted, rebuilt from a closed schema. The inner side (`_inner.py`) runs inside the container on `/job` and `/in` (read-only), `/out` (the one writable mount) and `/scratch` (memory-backed). `_host.COMMON_VERBS` names the verbs that need no browser and that every engine serves the same way: `analyse`, `base`, `align`, `check`, `cover`, `still` and `verify`.

**The HyperFrames engine and its two-stage encode.** `hyperframes.py` draws the picture in the HyperFrames image and leaves every other stage to the common image, so that the two engines' outputs pass the same checks. A render runs five containers, each with no network: `hf-page` writes `index.html` and `vars.json` (numbers only, no font family, no word of the edit list) into the run folder's `project/`; `proxy` makes a pinned 1080x1920 H.264 proxy (x264 on four slice threads) of the recording at the edit list's fps into `project/media/`; the HyperFrames container (`hyperframes-image/hf_render.py`) checks the project and the page's fonts and runs `hyperframes render` once into a ProRes HQ intermediate, with four workers and no frame cache; `encode` makes the final H.264 from the intermediate with the same output options as the ffmpeg engine and every count fixed (the decoder and the filter graph on one thread, x264 on four slice threads: x264 follows the cores a container sees, and with frame threads one encode in eight differed on amd64, so slice threads, which share no state between frames in flight, are what gives one sha256 whatever the cores: check C2; slice threads cost some compression at the same CRF); and a fresh common container verifies the candidate (`_host.finish_render`, shared with `ffmpeg.py`). A render that draws also measures and gates what it drew (V3b-2): after `hyperframes render`, `hf_measure.mjs` writes the boxes the page reports at every frame into `boxes.json`; the `encode` container (`_hf_gate.py`) refuses a box on the face or a caption below 1560 with the ffmpeg engine's own rules, and, after the encode, a face region that differs from the undrawn base (`psnr` per kept range, under 30 dB: `face_pixels_changed`). No flag turns either off. The proxy, the frames and the intermediate live in a disk work folder, `<work>/hf-<id>/` (`--work-dir`, or the renderer's own work folder), checked for free space before the first container and removed when the render ends. The limits are constants of `hyperframes.py`: memory 6144 MB by default and at least 4096 for the drawing container, 1024 processes, 4 workers, `/scratch` 256 MB, `/tmp` 512 MB, no `--shm-size`; `--cpuset` pins the cores. The free-space need and the cap on the intermediate assume 28 MiB of ProRes per second of output (Apple's nominal HQ rate, not measured here).

**The image of each provider and its manifest.** The transcriber image is built from `providers/transcriber/Dockerfile` (the base by digest, whisper.cpp by tag and commit), and holds no model. The ffmpeg engine's image is built only from the files `image-manifest.json` lists; the tag is the sha256 of exactly those files (`_image.py`), so an edit to a host-only file (`ffmpeg.py`, `hyperframes.py`, `_docker.py`, `_browser.py`, `_host.py`, `_image.py`) never changes it. The HyperFrames engine's image has its own definition (`providers/renderer/hyperframes-image/manifest.json`, driven by `hf_image.py`) and its own family in `scripts/doctor.py`; `hyperframes.py build --confirmed` writes its build record, which `--check` and `render` read. `scripts/doctor.py` names each family's definition module and finds the images of earlier definitions to remove.

## Dependencies

- `providers/_container.py`: the one container lifecycle (the docker client, the local-daemon check, the run command, the stderr cap, the reaping) behind both providers' function names. This page's providers never call docker another way.
- `providers/resolve.py`: `ROLES` (`transcriber`, `renderer`) and `CLASS_DEFAULTS` (`renderer:video` is `ffmpeg`).
- `shared/references/video-presets.json`: the vocabulary of presets and their typed parameters, read by flag (`--vocabulary`).
- `skills/mkt-social-copy/scripts/check_script.py`: the post-writing skill's own checker, which `align` and `storyboard` run isolated inside the container and whose refusal is final.
- The shared redaction copy: `providers/renderer/_redact.py`, a generated copy of `shared/scripts/redact.py` (the credential formats `check` scans with), kept identical by `scripts/sync_copies.py`.
- `shared/references/platforms/<platform>.json`: the platform file a render is checked against (`--platform-file`).

## Entry points

Each verb prints one JSON object on stdout and diagnostics on stderr; a refusal is `refused: <closed code> <field>` on the first line, and the text of an input is never echoed. The full flags are in `python3 providers/transcriber/whispercpp.py --help` and `python3 providers/renderer/ffmpeg.py --help`.

| Provider | Verbs |
|---|---|
| `providers/transcriber/whispercpp.py` | `--check [--model <name>]`, `models`, `build (--confirmed \| --dry-run)`, `reap`, `transcribe --in <file> --model <name> --language <code\|auto> --out <transcript.json> [--timestamps word\|ml1\|dtw] [--timeout <s>] [--threads <n>] [--max-seconds <s>] [--memory-mb <n>] [--dry-run]` |

`verify --in <mp4> --platform-file <f> [--sha256 <hex>] [--edl <f>]` checks a stored render in a fresh container: the sha256 (given, or the file's own), ffprobe's facts against the platform's spec, the bt709 tags and, with an edit list, the length. Every renderer verb also takes `--memory-mb`, `--cpus`, `--scratch-mb` and `--timeout`. Exit codes: 0 ok, 1 refused or failed, 2 usage error, 3 not configured.

## The new-video flow and the delivery

The flow `new-video` (`flows/new-video.json`) starts one step task of the kind `media` (`runtime/step_media.py`, `KIND`) with the recording's id and the post.

1. `take`: reads the post (`_take`), takes the platform from its `- Network:` line, needs a video entry in the platform's data file and a script, and binds the recording to the task (`MediaStore.bind`, `runtime/ops_step_seams.py`).
2. `transcribe`, 3. `analyse`, 4. `still` (a side step, `_still_due`), 5. `retakes` (`base --retakes propose`: the rule's proposals, each with a default, `cut` or `keep`, and a closed reason; the review shows a `cut` one as cut by the rule and "Keep it" brings it back, V3e), 6. `align-proposal`: each calls one verb of the transcriber or the renderer through `MediaEngine.call`, whose list of verbs is closed (`MediaEngine.CLASSES`).
7. `review`: the stop "Check the captions" (`_review_decision`).
8. `remap`, 9. `base`, 10. `align`, 11. `check`: the edited transcript, the edit list with the project's theme (`theme.theme_from_text`), the beats with the person's anchors and added animations, and the renderer's check.
12. `render`, 13. `cover`, 14. `verify`: the file `render-<sha12>.mp4`, its cover (`MediaStore.settle_cover` names it by its own hash) and the renderer's verify; 15. `preview` (a side step, `_preview_due`): the renderer's `preview`, only for a render larger than 15 MiB; `render.json` carries the blocks the renderer drew and their hash.
16. `document`: the delivery document (`deliver_document.build`), written through `EffectFiles.write`. 17. `deliver`: the gate (`steps.Gate`, redo `remap`).

The gate and its hash: the decision's hash is the hash of the document, which names the render's sha256 (limit L67). Approving it marks that exact file downloadable (`runtime/effect_deliver.py` `execute`, `media.mark_delivered`); nothing is published.

The way back: while the video waits at the delivery approval, `ops_media_edit.edit` writes the review and answers the open delivery by code under the decision's lock (`ops_step_effects.resolution_guard`). The next start finds the answered decision, prepares `remap` again (`steps.prepare_again`; `step_media.CLEANUP` keeps `transcript.edited.json` and `review.json`) and renders again: a new hash and a new approval. An edit that changes nothing is refused before anything is answered. The command and the route that call `edit` are V1b2's.

From the terminal (V1b2-1): `media-in --path <file>` takes the recording and prints its id; `video-new --media <id> --post docs/marketing/content/<name>.md` makes one request with one step task and runs it to the caption review; `captions-read --task <id>` shows the captions and their revision; `captions-edit --task <id> --revision <n> --edits-file <path>` edits them (at the review, or at the delivery approval, where the delivery is answered by code); `answer --id <id> --text continue` closes the review; `video-run --task <id>` runs the video on to the delivery approval; `approve --id <id> --sha256 <hash>` approves the exact render; `video-download --task <id> --out <file>` saves it to a new file outside the project (the render is hashed again as it is copied); `video-still --task <id> --out <file>` saves the face-box still. The settings of a new video are the key `media` of `runtime.json` (`language`, `transcriber_model`; the defaults are `pt` and `small`). The page reaches the same operations from V1b2-2.

From the page (V1b2-2): the eight operations are routes of the local service, in the policy group `media` (no grant list holds it, so no messaging app or connected client can use it): `GET` and `POST /api/v1/projects/<id>/media` (the list; the upload, the file as the body with `Content-Type: video/mp4` or `video/quicktime`, read as a stream, at most 1 GiB), `POST .../videos` (`media_id`, `post`: a job), `POST .../videos/<task>/run` (a job), `GET` and `POST .../videos/<task>/captions` (the review; an edit `{revision, edits}` with the edits as JSON text), `GET .../videos/<task>/still` and `.../download` (the face-box still; the delivered video as an attachment `video-<12 hex>.mp4`). The upload, the still and the download are answered `409` on the `--lan` socket before a byte is read (limit L68); the approval of the delivery uses the existing `POST .../pending/<id>/approve`, which the `--lan` socket also refuses (L67).

On the page (V1c-1): the Building's panel has a section "Videos" (`interface/js/views/lobby-videos.js`). Its form uploads one recording (MP4 or MOV, at most 1 GiB, checked before sending) and starts the video with a post chosen from `docs/marketing/content/`; the list shows the recordings newest first with one of twelve states (`lobby-video-model.js`: not started, ready, working, waiting for the review, waiting for the delivery, delivered, failed and the rest) and the action each state offers (Start, Run, a link to the decision it waits on, Download of a delivered video). A deliver decision is drawn as its own card (`floor/cards.js`): the lines of the delivery document, one per line, then its hash, and the line "Nothing is marked downloadable before you approve this exact content." On a page that is not on loopback (`js/cards/deliver.js`, which fails closed) the upload, the download and the approval of a delivery are not drawn and the page says to use this computer's own page (127.0.0.1); Reject stays. That is a courtesy: the service refuses all of them on the local network (L67, L68). The demo shows one fictional delivered video and refuses every video write. The caption review (V1c-2, `js/views/lobby-captions.js`) is a dialog the Videos section opens: it reads `captions-read`, draws the words by caption chunk, the retakes, the beats and the animations, sends exactly one closed edit at a time with the revision it read (a stale revision is read again and said), offers "Add an animation" from the catalogue (the blocks as text, with `use_when` and a sample; no drawn preview), and at the review its Continue answers the review decision and runs the video; the face box, the cover, the theme and a slot stay in the terminal. At the delivery approval, on this computer's own page, "Watch the video" plays the render the open decision names (`video-watch`, limit L71: the bytes hashed again, at most the preview bound, nothing marked; the policy gains `media-src 'self' blob:`); a render over the bound is watched through the renderer's preview copy (`deliver_document.preview_name`), and one with no preview is downloaded after the approval.

Add an animation (V1b3): `captions-edit` has the edit kind `animation` (VD15): `{"op": "animation", "block", "params", "word_from", "word_to"}` adds a review-only beat, `{"op": "animation", "id", "remove": true}` removes one. The catalogue is read as data from `providers/renderer/blocks/catalogue.json` (`media_animation.read_catalogue`), and refused when its `blocks_sha256` is not the sha256 of `blocks/pins.json`. The parameters are checked by the renderer's own checker: `media_animation.checker` calls the host verb `block-params` through `MediaEngine`, which keeps only that verb's closed refusal line (a code and a parameter's name, never a value). The animation is stored in `review.json` (`animations`, an origin word range like an anchor) and never written into the post file; `align` appends it to `beats.json` as an overlay `a<n>` with `beat` 1000 + n and score 1, and an animation whose words were all cut stops the step (`animation_lost`). Added animations plus the script's beats that are not dropped are at most 12 (`limits.beats_max`). Only overlays with a preset, no asset slot and a block of the project's engine can be added in M1. The route `GET /api/v1/projects/<id>/video-catalogue` (operation `video-catalogue`) lists the blocks with `addable` and `why`, and crosses the LAN socket (VD18).

Retention (decision 12): the recording and the transcript 7 days after delivery, the render 30 days after it, an undelivered recording 30 days untouched (`media.purge`, `runtime/upkeep.py`).

Removing a recording (media-remove): `media-remove --media <id>` shows what would go (bytes, files, the tasks that named it) and removes nothing; with `--confirm` the whole folder goes, the delivered video included. It is refused while a task that is not `done`, `cancelled` or `failed` names the recording, or while its task lock is held. The route is `POST /api/v1/projects/<id>/media/remove`, which crosses the LAN socket (only an id crosses). The quota refusal tells the person to remove a recording they no longer need, with no command (the same sentence reaches a phone). The page's button comes with a later page package.

The side step `preview` (V3d) stands between `verify` and `document` (`step_media.ORDER`): for a render larger than `deliver_document.PREVIEW_MAX_BYTES` (15 MiB) it asks the renderer for a copy that fits, and `_document` records it as the delivery document's `preview` (`deliver_document.preview_name` names its file), which makes `deliver_document.on_cards` true; `preview` is in `MediaEngine.CLASSES`. The messaging package then sends the recording in through `media.receive` and a caption correction through `ops_media_edit.edit`.

From a messaging app (V1d-1, limit L69): a listed sender whose profile holds the group `media-phone` sends a video. The bridge checks its declared size against the least of the media store's 1 GiB, the quota left and the provider's file limit before fetching anything (Telegram's bot download is 20 MB, so most recordings of a minute or more get the over-cap sentence, and the Drive link or the page is the way in for them). `video-phone-in` keeps it, the caption (the post's name) or a numbered list chooses the post, `video-phone-start` runs the video to the caption review, and the words go to the sender's chat. A reply to the caption card, one line per correction `wrong -> right`, is mapped by `runtime/media_phone_words.py` to the closed edits and applied by `ops_media_edit.edit`; `continue` answers the review and runs the video. A correction in a reply to the delivery card renders again and asks again. A Google Drive link sent instead of the file (V1d-3, limit L70) is fetched with the project's Google account when one is connected, otherwise from the shared link over https from a closed host list, global addresses only, at most three checked redirects and the size known first; it becomes a recording and goes on from the post choice.

## The storyboard of a post

What a script's beats will look like, before a recording exists (V5-1, VD14). The operation `video-storyboard` (`runtime/ops_media_storyboard.py`) is asked for one post by the Videos section of the page ("Draw the storyboard", under the post choice) or by the terminal (`python3 runtime/cli.py video-storyboard --project <dir> --post docs/marketing/content/<name>.md`, which also prints the sheet's absolute path). It is advisory, and the page says so in one fixed sentence.

- **The engine.** The renderer's `storyboard` verb exists on the ffmpeg engine only, and the ffmpeg image is the one every HyperFrames project already builds, so the call is `MediaEngine(root, "ffmpeg")` whatever `media.renderer` says. It mounts no recording and no transcript (the verb takes the post, the post-writing skill's own checker and the vocabulary).
- **What it returns.** For each beat with a preset: the still, the block that drew it (`drawn_block`, the ffmpeg engine's block for the preset) and the block the project's own engine will use (`video_block`, from the generated catalogue, `null` when that engine draws none: HyperFrames has no `cutaway` or `pip`). The page names both for a beat where they differ.
- **The folder and the replay.** `<data_dir>/media/storyboards/<key>/`, `<key>` being the first 16 hex of the sha256 of the post's bytes, the theme's flags and `blocks/pins.json`. The same key is returned from the folder with no call (the verb gives the same bytes for the same inputs). A folder holds the stills of the script's own on-screen text and no recording, and is removed 30 days after its last use (`upkeep.sweep_storyboards`). `media.purge` never touches it: its name is not a recording's id.
- **The route.** `POST .../video-storyboard` with `{"post"}` is a job; one picture is `GET .../video-storyboard/<key>/<file>` with a name `beat-<n>.png` or `sheet.png`. Neither is in `operations.LAN_REFUSED_OPS`.

## Reference videos

Package V7b (decision 15; the provider `fetcher:video` is V7a's): a person gives public links of short videos to learn from; the platform measures them and keeps numbers, never the video. **A reference is looked at and measured, never used.**

- **Switch.** `media.references` is `"on"` or `"off"` (absent is off). Turning it on is a widening: `accept-config` stops, prints the terms (public links only, no account and no cookie, reference only, the whole video deleted as soon as it is measured, subtitles, details and facts kept on this computer for 30 days, a copy you make yourself is yours to answer for, the platform's own terms are yours to respect) and needs `--widen <hash>`. It is an item of the same record as the accounts (`policy_widening.reference_items`). Turning it off needs no ceremony.
- **Terminal only** (L72). `reference-add --link <url>` finds the platform whose fetch file lists the link's host exactly, fetches the subtitles and the details (`fetch --stage meta`), measures them (`measure`, no network) and prints the id, platform, duration, subtitles, words and beats. `reference-video --reference <id>` prints the duration and the size bound and fetches nothing; with `--confirm` it fetches the whole video (at most 300 seconds and 200 MiB), measures it and deletes it. `reference-list` (id, platform, added, duration, subtitles, frames measured, days left), `reference-read` (the facts, then the third-party text last under "External text (data, from the platform, not checked)", every line quoted with `> `) and `reference-remove` (a preview, then `--confirm`).
- **The store** (`runtime/references.py`): `<data_dir>/references/<id>/` outside the project, the marker `.openhora-reference`, the link in `record.json` only, 50 references and 2 GiB. The provider's answer and `facts.json` are checked against closed shapes; the host never parses a title, a description or a subtitle (they sit in `facts.json` under `external_text`, and no model reads them in V7).
- **Reference only** (L73). The video is deleted in a `finally` right after `measure`, success or failure; the media store (`receive_file`) and the renderer refuse a path inside a reference store; no operation serves or copies a reference's bytes. What is not caught: a copy or a hard link the person makes outside the store during the minutes the video exists.
- **Retention** (L74). Subtitles, details and facts 30 days after the reference was added, by the upkeep part `references`; a stray `video.*` or `.fetch-*` after an hour; a folder with no record after a day.
- **Not built here.** The fetch and the measure themselves (V7a), the pin routine (V7c), messaging and the page (V7d). The runtime is tested against a fake of the provider's verb contract; nothing was fetched.

## Known limits and improvements

- The storyboard is asked for, never automatic (V5-1): no flow draws it by itself, and it is drawn by the ffmpeg engine for every project (see "The storyboard of a post"). The page's storyboard needs a PNG to show, so the demo copy of the interface says it has no engine; the live leg is one docker-gated test of `runtime/tests/test_media_storyboard.py` (`WB_RENDERER_DOCKER_TESTS=1`), written and not run by V5-1.
- The ffmpeg image installs the DejaVu system font (`fonts-dejavu-core`) and has no last layer that fails on a font outside the allow-list, which condition 6 of the V0 decision asks for; the HyperFrames image has that layer (OPEN-3). A purge layer for this image is left to a later package.
- The HyperFrames engine renders the cuts and the zoom (V3a) and, without `--base-only`, the captions and the beats (V3b-1: one root composition, `gsap` pages inlined and `renderat` pages in iframes; whether a `renderat` page draws the same frames on both engines is the one-file measurement of the V3b spec, section 5.9). Its face-box and 1560 gates and the pixel check are V3b-2's (`_hf_gate.py`, which reuses `_layout.face_hit` and `_layout.caption_hit`), tier A (the wrapper, the admission run and the allowlist, which admits nothing) is V3b-3's, the five tier-B ports of registry components and the engine's default blocks are V3b-4's, and V3c the shared tests of both engines, the HyperFrames image in CI and amd64 determinism.
- Not verified for the HyperFrames engine (V3a-2 did not run these; each waits on the maintainer's word for a local build or for a recording): that the final sha256 is equal at 4 and at 8 cores on a real recording (S2 measured it on synthetic content at 4 and 8 cores with `-threads 1`; the encode here uses 1 thread, measured at 2 and 4 cpus on synthetic content in CI); the real ProRes rate (28 MiB/s is the format's nominal figure; S2's synthetic content gave 13.9 MB/s); the flag spellings of `hyperframes render` 0.9.19; that `TMPDIR` on the disk work folder serves HyperFrames' frames as `/scratch` did; that HyperFrames' ProRes file carries audio the encode accepts; that the common image's ffmpeg has `prores_ks` (V3a-1's CI leg checks it); that `/sys/fs/cgroup/memory.peak` exists on every daemon; and determinism on amd64.
- `selfcheck` is the one inner verb that is not a drawing verb and still imports the drawing part (`_cdp`), because it reports the container mode.
- The `hf:` allowlist is empty (V3b-3 admitted no registry component) and the committed `blocks/engines/hyperframes.json` runs `gsap` and `renderat`, with the five tier-B ports of V3b-4 (`blocks/hf/<name>/`) as its defaults for `caption`, `keyword`, `number` and `quote` and `oh:list` for `list`; a block whose parameters differ from its preset's cannot be named by a beat yet (OPEN-6 of the V3b0 spec).
- The synthetic renders in CI prove the container path of both engines on a generated recording (the `renderer` job for the ffmpeg engine, the `hyperframes` job for both, V3c-2: on amd64 the HyperFrames job's first run is the first amd64 build of its image); a render of a real recording on the maintainer's machine is a separate, manual step.
- Picking the block of a script beat's preset (G14) and a preview of an added animation are later (V1b3 OPEN-5, OPEN-10).
- A missing HyperFrames setup is found at the render, after the caption review, not at the start: the render is refused `not_configured` (the review is kept), never replaced by the other engine. Every default video now uses the HyperFrames caption block, which carries the highlight transition flaw left for later, and renders about 2.6 times slower at real size (963 s against 364 s at 4 cpus, `providers/renderer/reports/engine-contract-2026-11-10-arm64.json`).

On a messaging app the delivery is approved from a card (decision 14): the render is its own preview when it is at most 15 MiB, and a larger render gets a copy that fits from the renderer's `preview` verb (V3d), the bridge sends it as a video before the deliver card, and the card offers its approval only after the provider confirmed it. When that copy cannot be made, the delivery is approved in the terminal or on the page. The body of the card is said in the project's language (`CARD_VIDEO_*` lines), and the title is the fixed `Deliver the video`.
- Effects (V9a-3): the face check no longer proves the face is unchanged on the frames of a grade (flash, dip, mono, tint), only that both engines drew the same picture there and that no overlay covers it (the maintainer's answer to OPEN-8, 2026-11-10); mono goes through two bt709 conversions around the CSS matrix on the ffmpeg engine (every frame of a range that has a mono row, one or two grey levels off a pure conversion), so the live leg L3 measures whether 30 dB holds, and the first remedy if not is the drawing method, never the threshold. A drop of the script's punch at review (`p<beat>`) is checked against the range 1 to 12 only, because the edit operation does not pass the set of the script's punch beats yet (`ops_media_edit.py` is outside the package); the align step ignores a drop that names no punch. The interface has no control for effects yet (`captions-edit` only).
