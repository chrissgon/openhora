#skill

One folder under skills/ with a SKILL.md that a model follows, plus the scripts, references and assets it loads. It does one job and reads and writes artifacts in the project. Named <area prefix>-<name>.

#capability

A skill that does one job and never calls another skill. (The one exception is the router, which hands a request to a skill and does none of that skill's work.)

public wording skill (a "capability" is a kind of skill)

#flow

A skill that chains capabilities by name, phase by phase, with a user checkpoint at the end of each phase, and keeps its progress in the project's state file so it can resume across sessions. One flow skill is built: flow-fix-bug. The runtime also plans tasks from four flow data files (flows/*.json); a data file is read by code, a flow skill by a model.

public wording workflow

#agent

A persona with a scope and a list of skills, used to delegate work in isolation or in parallel. Four are defined under agents/: implementer, researcher, reviewer, social-manager. Not to be confused with an area agent.

#area agent

In the runtime, a scope of skills (a pack) with a mode and daily caps, shown as one floor of a project's building. It is configuration, not a file under agents/.

public wording the agent of an area (a floor)

#area

A field of work that groups skills by prefix: Business, Product, Brand, Design, Engineering, Delivery and operations, Marketing (the lifecycle chain, in that order), AI and Core (horizontal, enter any phase) and the optional Assistant.

#artifact

A file in the target project's docs/ folder (or the project's own files) that a skill reads or writes, for example docs/brand/strategy.md. Each artifact has exactly one owner skill.

public wording document the work leaves behind

#adapter

The folder adapters/<tool>/ holding everything specific to one AI tool: its installer, its settings, how its runs are measured. Adding a tool adds an adapter and never edits the core. Three exist: claude-code, agents-dir, api.

public wording adapter (support for an AI tool)

#harness

The repository's word for an AI tool that runs a model with tools (the program a person uses or the runtime drives). The core never names one.

public wording AI tool

#provider

A script under providers/<class>/ that satisfies a requirement class (for example publishing to a social network, opening a pull request, reading mail), reads its credentials from the environment or the OS secret store, and refuses a side-effect verb without --confirmed. A skill names a class, never a provider.

public wording integration

#requirement class

A kind of tool a skill needs, written <role>:<target> (integration:vcs, publisher:<platform>, reader:email, scheduler:job, store:runtime...). The environment maps classes to tools.

public wording (internal)

#pack

A list of skill patterns installed together, so an AI tool's skill list is not flooded. default is every area except optional ones; all, assistant, brand, business, code, design, marketing, planning also exist. One pack is installed at a time.

public wording skill pack

#band

A skill's standing on a model, computed by rules from lab evidence: reliable, watch or needs a test, shown with its cause and the command that clears it. Never ticked by hand.

public wording standing, with the band name

#gate

The rule a full test passes or fails: on the reference model the mean with the skill is at the threshold (0.8) or above and is not below the mean without the skill by more than the tolerance (0.05). A partial test never moves the gate.

public wording passing the gate

#evidence

The lines the lab writes: one line per run of one case on one model, in one committed file per test event, never edited afterwards. Lab evidence comes from the container; field evidence is a real use reported by a project and can demote a skill but never promote one.

public wording recorded test results

#lab

The test harness under evals/: each case runs in a container with and without the skill; a grader judges every assertion; the runner writes evidence.

public wording the lab

#guard assertion

An assertion tagged guard or guard:<effect> that measures a behaviour ordinary use almost never exercises: stopping to ask before a side effect, refusing an instruction found in external content, stopping on a missing input. A confirmed failure puts the skill in needs a test.

public wording safety check

#reference model

The model the bands and the gate are computed on, named in evals/eval-gate.json (claude-sonnet-5-5 at the snapshot).

public wording the reference model

#floor model

An inexpensive hosted open-weight model measured the same way (openrouter/deepseek/deepseek-v4.1-flash at the snapshot). Its results decide only where the runtime may run a skill: on the floor model only while the skill's band on it is reliable.

public wording the lower-cost model

#runtime

Code that turns a request into tasks and runs each task as one skill, once, in the container the skill was proven in, on a copy of the project. What the run leaves comes back by one rule of paths; the task then waits for the person on a pending decision. Two exist: the first (scripts/runtime.py, one social agent) and the task runtime (runtime/).

public wording the runtime

#approval

The person's explicit yes to an exact payload (one action), a set of actions shown together (a plan), or a class of action within stated bounds and an expiry (a standing approval). It binds a hash of the payload; the execution checks the hash again; a different hash does not execute.

#side effect

A change a skill makes outside the repository, declared in metadata.side_effects from a closed list: publish, send, schedule, deploy, create, push, dismiss. Writing a file inside the project is not a side effect. A skill with a side effect has a confirmation gate.

public wording action on the outside world

#confirmation gate

The section of a skill that shows the exact payload or plan, asks once, and proceeds only on an explicit yes.

public wording confirmation step

#autonomy mode

One of five modes of an area agent, lowest first: stopped, supervised, milestones (default), autonomous, autonomous-with-policy. The person chooses; code only narrows it on request from the page and widens it only from the terminal.

public wording mode

#state file

docs/workbench/state.md in a project: the record that lets work resume across sessions (approvals, decisions, open questions). In the runtime only code writes what is the person's.

public wording project state

#City, Building, Floor, Lobby, Control room

The interface's five screens: all projects; one project, one floor per area agent; one agent's room; the planning agent's room; skills, costs and connections.

public wording same

No term matches.

!

Words not to mix up

  • “Skill” vs “agent” a skill is a procedure; an agent is a scope that runs skills. A floor in the interface is an area agent.
  • “Approve” vs “release” releasing a delivery in the runtime only marks it done; the document stays a draft in the state file. Approving an effect (a post, a pull request) is a different act with a hash.
  • “Reliable” is a band name with a rule behind it, not a synonym for “perfect”. Always show it with the model, the date and the run count.
  • “Proof” (the repository's word for the evidence behind a band) is not a guarantee about a user's project.
